# @between-pages/api

The Fastify process: registers the routes defined in `@between-pages/contracts`, validates and serializes them with Zod, and publishes the OpenAPI document generated from them. It owns sessions, the personal diary routes, the collaboration WebSocket and the PG commit chain of the [diary collaboration kernel](../../docs/adr/2026-10-26-diary-collaboration-kernel.md) (phase 2: personal diaries; phase 4, sharing, in progress: ranges and bindings open and freeze shares, and the partner reads and writes through the authorized-state reader), and the day list with its unread marks ([unread-and-day-page](../../docs/adr/2026-10-28-unread-and-day-page.md)). Beyond the diary it keeps the two-clocks settings, the shared rules of space records ([space-records](../../docs/adr/2026-10-29-space-records.md)) and wishes and gifts on them ([wishes-and-gifts](../../docs/adr/2026-10-29-wishes-and-gifts.md)).

| `POST /api/diaries` | `{ timezone, date? }` → `{ created, diary }`: the caller's diary for `date`, or for today in `timezone` from the server's UTC clock; created with its first generation when missing, and opened to the partner in the same transaction when the range the caller confirmed for their open binding covers the date (kernel D5). A future date or a zone that is not an IANA name is `400 VALIDATION_FAILED`. |
| `GET /api/diaries/:diaryId` | `{ diary }`: the current generation's committed state (base64 Yjs update), `generationId`, `seq`, clientID bindings. |
| `GET /api/diaries/:diaryId/receipt?batchId=… \| ?operationId=…` | `{ receipt }` of the caller's committed batch, or `{ receipt: null }`. The same shape as the ACK; answerable forever, also to a partner after the share froze. |
| `GET /api/diaries/:diaryId/history[?cursor=…]` | History points newest first, 50 per page, computed at read time (kernel D6); the cursor is opaque. `nextPointInMs` is how long until the group being written becomes a point, or `null` when none is open. The owner sees every commit; the partner only each epoch's commits up to where it froze, filtered before grouping, so no private commit shows in points, counts or pages. Groups never span a generation or an epoch boundary. |
| `GET /api/diaries/:diaryId/history/:publicId` | One committed version the caller may see, as server-rendered author runs; `500 VERSION_UNREADABLE` when its stored parts fail their sha256. |
| `GET` / `POST /api/diaries/:diaryId/read` | The caller's own read coverage of a diary they own or that was ever shared with them: `{ ranges: [{ clientId, from, to }] }` clock ranges; `POST { ranges }` (1–1000) adds to it and answers the union. Merged across devices by character identity and kept across reopening (kernel D15); returned to no one else. `404` for anyone else. |
| `GET /api/spaces/:spaceId/shared-diaries[?before=YYYY-MM-DD]` | The partner's diaries shared with the caller, newest date first, 30 per page: `{ diaries: [{ diaryId, diaryDate, ownerId, epochId, share: 'live' \| 'frozen', excerpt, updatedAt }], nextBefore }`, each by its live share or else its last frozen one. `404` outside the space. |
| `GET /api/days[?before=YYYY-MM-DD \| ?after=YYYY-MM-DD]` | The dates with the caller's own diary or one the partner shared with them, merged on the server, newest first, 20 dates per page: `{ days: [{ diaryDate, mine, partner }], nextBefore, nextAfter }` ([unread-and-day-page](../../docs/adr/2026-10-28-unread-and-day-page.md) D3). `before` pages older dates (`nextBefore` set); `after` takes the 20 dates nearest after the anchor (`nextAfter` set), so a jump to a date asks `before` the next day and `after` the date ([book-frontend-workspace](../../docs/adr/2026-11-01-book-frontend-workspace.md) D4); both at once is a 400. `mine` is `{ diaryId, excerpt, updatedAt, hasText, unread, sharedWithPartner, writing }` (in a live share now), `partner` `{ diaryId, epochId, share, excerpt, updatedAt, hasText, unread, writing }` by its live share or else its last frozen one; either is `null`. `writing`: someone's text commit is newer than the newest history point of the caller's view, so the list folds that diary (book-frontend-workspace D8); a share that only opened, or a frozen one, is not being written. `excerpt` and `updatedAt` as on the lists below; `hasText` is some non-blank text, false when unreadable. `unread` (D2): a character the other author wrote, visible in the caller's view (own current text, or the epoch's authorized text), not in the caller's read coverage and inserted no later than the newest history point of the caller's view (kernel D6, with the history idle time); a frozen share counts all of its text. An unreadable text keeps its card with `excerpt: null`, `unread: false`. A diary never shared with the caller leaves no card or field. `Cache-Control: no-store`. |
| `GET /api/days/next-unread[?before= \| ?after=]` | `{ date }`: the nearest date older than `before`, newer than `after`, or from the newest, whose own diary or partner's share has list `unread` as on `GET /api/days`; `null` when that direction has none (book-frontend-workspace D5). Own diaries without another writer's editor instance are skipped unread. `Cache-Control: no-store`. |
| `GET /api/days/:date` | `{ day, google }`: that date as on the list; `mine` and `partner` both `null` when the caller can see no diary on it, the same for a date with none and one the partner did not share. `google` is the caller's own Drive only: `connected`, the day Doc's `docUrl` once written, for `mine` and `partner` the commit time of the version the Doc holds, and `problem` when newer text is not in it yet (`reconnect`, `storage_full`, `unreachable`, `failed`) (server-backup-and-google-docs D9, invariant 14). `Cache-Control: no-store`. |
| `GET /api/space/unread` | `{ features: { wishes, anniversaries } }`: how many records of each space feature hold something the caller has not seen (space-records D8), deletion notes included; `404 NOT_FOUND` for an account never bound. `no-store`. |
| `POST /api/space/seen` | `{ records: [{ type, id, mark }] }` (1–200) → `{ recorded: true }`: raises the caller's own marks to what was on screen, each `mark` being the one the record came with (the count of the partner's changes and actions on it visible to the caller); records the caller cannot see are ignored, a lower mark changes nothing. Allowed after unbinding. |
| `GET /api/wishes` | `{ me, partner, readOnly, mine, theirs, preparing, wall, notes }` (wishes-and-gifts): both wish lists (still wanted, by hearts then newest), the caller's own gifts in preparation, every revealed gift newest first, and deletion notes for records the caller had acted on (`acted: prepared \| acted`). Each record carries `unread` (`new`, `edited`, `acted` or `null`) and its `mark`. `preparingGiftId` on a partner's wish is the caller's own preparation; a wish never says whether anyone else prepares. `readOnly` once unbound. `404` for an account never bound. `no-store`. |
| `POST /api/wishes`, `PUT /api/wishes/:wishId`, `POST /api/wishes/:wishId/delete` | Create (`{ requestId, name, link, note, want }` → `{ wish }`), edit (`{ expectedRevision, … }`; an older revision is `409 RECORD_STALE`, a new link clears its preview) and delete (`{ requestId }` → `{ deleted: true }`) the caller's own wish. A wish of the partner, or one already received, is `404 NOT_FOUND`. Deleting a wish someone prepares for turns that gift into a surprise and answers the same. |
| `POST /api/wishes/:wishId/received` | `{ requestId }` → `{ giftId }` ("收到了" on the caller's own wish): reveals the partner's gift in preparation with its card, or puts a gift from the partner on the wall; the wish leaves the list. The answer is the same in both cases. |
| `POST /api/gifts`, `PUT /api/gifts/:giftId`, `POST /api/gifts/:giftId/delete` | Prepare (`{ requestId, wishId }` for a wish of the partner, `{ requestId, wishId: null, name, link? }` for a surprise → `{ gift }`, private to the caller; preparing a wish again returns its gift), edit the name and link of a gift the caller created, and delete it (for one in preparation, stop preparing). |
| `POST /api/gifts/:giftId/reveal`, `PUT /api/gifts/:giftId/card`, `PUT /api/gifts/:giftId/date`, `PUT /api/gifts/:giftId/occasion` | The giver reveals (`{ requestId }` → `{ gift }`; once revealed, again answers the gift as it is), writes or changes the card (`{ expectedRevision: null \| n, text }`), and either person sets a revealed gift's wall date (`{ requestId, date }`) or occasion (`{ requestId, occasion: holiday \| meeting \| no_reason \| null, anniversaryId: uuid \| null }`, at most one set; an anniversary not alive in the space is `404`). A gift carries `anniversary: { id, name } \| null`, the name copied when it was set and kept after the anniversary is deleted. A gift revealed by either path is dated in the receiver's local date, else the revealer's, else UTC (partner-local-dates D4). |
| `GET /api/anniversaries?timezone=` | `{ me, partner, readOnly, anniversaries, home, notes }` ([anniversaries](../../docs/adr/2026-10-29-anniversaries.md), [partner-local-dates](../../docs/adr/2026-10-30-partner-local-dates.md)): every anniversary soonest first. Each carries its `basis` (`own` for the caller's own birthday, counted in `timezone`; `partner`, counted in the partner's last reported zone while bound; `unknown`, counted in `timezone` while that zone is unknown or after unbinding), `next` (`date`, `startsAt` and `endsAt` of that date in the basis zone, `type` yearly or count, `years`, `count`, `daysLeft`), `dayCount`, the caller's own `reminder` (default 7, 0 for one's own birthday) and `due`; `home` is the one due anniversary for the home strip (today first, birthdays first on one day, else the soonest; null after unbinding). No answer carries the partner's zone. `no-store`. |
| `GET /api/anniversaries/:anniversaryId?timezone=` | `{ me, partner, readOnly, anniversary, years }`: every year from the anniversary's year (or the year it was recorded) to this year in its basis zone, newest first, each with its date and the wall's gifts given for it that year. |
| `POST /api/anniversaries`, `PUT /api/anniversaries/:anniversaryId`, `POST …/delete` (all `?timezone=` but delete) | Create (`{ requestId, kind, birthdayOf, name, note, year, month, day }` → `{ anniversary }`; a birthday names one of the two, `other` has a name 1–30, only a birthday may omit the year, the day must exist; a second together day is `409 RECORD_EXISTS`), edit by the author (`{ expectedRevision, kind, birthdayOf, name, note }`) and delete by the author (`{ requestId }`). |
| `PUT /api/anniversaries/:anniversaryId/date`, `…/count`, `…/reminder` (all `?timezone=`) | Either person corrects the date (`{ requestId, year, month, day }`) or turns the day count on or off (`{ requestId, showCount }`, needs a year), each an action; the caller sets their own reminder (`{ days: 0 \| 1 \| 3 \| 7 \| 14 \| 30 \| null }`), no history and allowed after unbinding. Each → `{ anniversary }`. |
| Space-record writes | Every write needs an open binding: after unbinding `409 SPACE_READ_ONLY`. The author and actor are the session's user; bodies are strict. A `requestId` already committed by the caller answers like its first commit; the same ID with another body is `400 VALIDATION_FAILED`. Someone outside the space, and a gift in preparation for anyone but its giver, is `404 NOT_FOUND`. |
| `GET /api/backup` | `{ backup: { google, progress, attention, events } }`, the caller's own only (server-backup-and-google-docs invariant 14). `google.state` is one of: `unavailable` (no Google client or `GOOGLE_TOKEN_KEY` on this server), `disconnected`, `connected`, `reconnect` (the grant failed, the token key changed, or a Testing grant is past seven days), `disconnecting` (waiting for the worker to revoke). `email` is the Drive account's. `expiresAt` is set only with `GOOGLE_DRIVE_TESTING=true`. While disconnecting, `google.retrying` says that telling Google has failed so far. While a connection exists, `progress` gives the days still waiting, the days whose last attempt failed with why (`unreachable`: Google could not be reached, answered 5xx or 429; `failed`: anything else), the newest version any Doc holds (`backedUpTo`) and the `Between Pages` folder's URL. `attention` is why the home page shows a banner: `reconnect`, `storage_full`, `failing` (writes have been failing for a day) or `expiring` (a Testing grant within two days of its end). `events` lists the newest 20 problems. Always `no-store`. |
| `POST /api/backup/google/start` | `{ url }`: Google's consent page for `drive.file` only, `access_type=offline`, `prompt=consent`, a fresh `state` and an S256 PKCE challenge. Its verifier is kept for ten minutes under the state's sha256, one per user. `GOOGLE_UNAVAILABLE` without Google; `GOOGLE_DISCONNECTING` while the old grant is still being revoked, because revoking a Google grant also ends any newer token of it. |
| `POST /api/backup/google/finish` | `{ code, state }` from the web app's `/backup/google/callback` page → `{ backup }`. The state must be one this user started within ten minutes, and it is used up either way (`GOOGLE_STATE_INVALID`). The code is exchanged with the verifier; a grant without a refresh token or without `drive.file` is `GOOGLE_EXCHANGE_FAILED`. The account is the one Drive's `about` names for the new token. The refresh token is sealed (AES-256-GCM, `GOOGLE_TOKEN_KEY`) before it is stored, and no token, code or state is ever returned or logged. |
| `POST /api/backup/google/disconnect` | `{ backup }` with `disconnecting`: backups stop at once. The worker revokes the grant at Google, then deletes the ciphertext; Drive files stay. Waiting days stay queued and continue after reconnecting. |
| `POST /api/backup/run` | `{ backup }`: "现在备份". Queues the caller's registered backup tasks and makes every waiting day due now, written at its newest commit instead of its newest history point. |
| `GET /api/diaries/:diaryId/shares/:epochId` | `{ diary }`: the shared diary as that epoch authorizes it, `share` `live` (current generation, every commit of the epoch) or `frozen` (the version it froze at), with `seq` counting only the epoch's commits and bindings only of clientIDs in that text. |
| `GET /api/diaries/:diaryId/characters/:clientId/:clock[?epochId=…]` | `{ author, writtenAt, clockAdjusted }` of a character visible in the owner's current text (no `epochId`) or the caller's epoch; `writtenAt` falls back to the server's receipt time when the writer's clock was more than a minute ahead (kernel D15). |
| `GET /api/sync` (WebSocket) | The collaboration socket, messages per `@between-pages/contracts` `ClientMessage` / `ServerMessage`. Handshake: `Origin` and session, else `403` / `401` before upgrading. `subscribe` → `synced` (commits after `knownSeq`; for the owner also `shared`, whether the diary has a live epoch in the same snapshot, with any later `context` held until after it) then live `commit`s: without `epochId` the owner's personal entry, every commit of the generation; with `epochId` the partner's entry, only commits stamped with that live epoch (a frozen epoch or another generation is `STALE_CONTEXT`). `context` messages tell the owner of every opening and stop, and the partner of the ones that concern them. `submit` → `ack` after PG COMMIT, then a `commit` broadcast, or `error` with the D10 code; a partner writes only with the live epoch's `epochId` and generation, anything else (including after a stop) is `STALE_CONTEXT`. `cursor` (from a caught-up subscription of that generation, and from a partner only while their share is live) is relayed at once as `cursor` with the sender's user to the other person reading the same generation, never to its sender, never stored or answered; a closing connection clears its caret. A session that ends closes the socket with `4401`. |
| `GET /api/binding` | `{ binding, invitation }`: the caller's current binding (space summary and `periodId`) or `null`, and their latest open invitation (`pending`, or `expired` once seven days have passed) or `null`. |
| `GET /api/spaces`, `GET /api/spaces/:spaceId` | The spaces the caller takes part in, current (`active`) or archived; one space with its periods oldest first. Participants in slot order (slot 1 is the ID that sorts first). Never a sharing range. |
| `POST /api/binding/invitations` | `{ requestId, sharingSelection }` → `{ invitation, token }`: a 32-byte base64url token, valid seven days, closing the caller's previous invitation; the same `requestId` again returns the stored invitation with `token: null`, with another selection `VALIDATION_FAILED`. A bound caller gets `ALREADY_BOUND`. |
| `POST /api/binding/invitations/:inviteId/revoke` | Revokes the caller's own invitation; again is a no-op; a used one is `INVITE_USED`, anyone else's `NOT_FOUND`. |
| `POST /api/binding/invitations/preview` | `{ token }` → `{ inviter, expiresAt, mode: 'new' \| 'restore' }`; binds and reserves nothing. Refusals as for accepting. |
| `POST /api/binding/invitations/accept` | `{ token, sharingSelection }` → `{ binding, restored }`. Each confirmed range (the inviter's from the invitation, the caller's from the body) opens its owner's covered diaries in the binding transaction. Refusals, invitation first: `INVITE_INVALID` (404), `INVITE_USED`, `INVITE_REVOKED`, `INVITE_EXPIRED` (also for a link closed by rotation after it expired), `SELF_INVITE`, then `ALREADY_BOUND`, `PARTNER_FIXED` (409), then `SHARE_OPEN_FAILED` (409, nothing bound). A restore reuses the pair's space. |
| `POST /api/spaces/:spaceId/unbind` | `{ expectedPeriodId }` → `{ spaceId, closedPeriodId }`: ends that period for both, closes both people's open invitations and freezes every live share of the space; a period that already ended returns the same answer and nothing else changes. |
| `GET` / `PUT /api/spaces/:spaceId/my-sharing` | The caller's own range: `{ selection, revision, confirmedPeriodId }` (empty, `0`, `null` before any confirmation), readable in archived spaces. `PUT { requestId, expectedPeriodId, expectedRevision, selection }` → `{ revision, changeId }` stores the canonical selection for the open period: another period `PERIOD_CLOSED`, another revision `POLICY_CONFLICT`, a repeated `requestId` its original answer, or `VALIDATION_FAILED` with another body. Covered diaries without a live share open, live ones no longer covered freeze, in the same transaction (kernel D5); a diary whose clean baseline cannot be built refuses the save as `409 SHARE_OPEN_FAILED` with `error.dates`, storing nothing. |

## Invariants

- Every route is registered from a `routes` entry in `@between-pages/contracts`; no path or response shape is written inline.
- Responses are serialized through their Zod schema, so a handler cannot return a field the contract does not declare.
- `openapi.json` equals `renderOpenApi()` output (`verify-openapi-current`).
- `access: 'user'` routes run the login guard and answer 401 without a session (invariant 13).
- Only `src/auth/` and `src/db/` touch Better Auth or the `auth_*` tables; everything else gets the caller from `request.user` (invariant 10, `verify-auth-boundary`).
- Better Auth's origin and CSRF checks are pinned on: it disables them by default when `NODE_ENV=test`, so tests would otherwise pass against weaker settings than production runs.
- A first sign-in writes `auth_user` and `auth_account` in one transaction (the Drizzle adapter's `transaction: true`; its default is off), so a failure leaves no orphan user (tested).
- Every non-GET/HEAD/OPTIONS `/api/*` request outside `/api/auth/*` must carry `Origin` equal to `publicOrigin`, else 403 `FORBIDDEN_ORIGIN`, including unknown routes (invariant 7, HTTP part).
- `drizzle/` holds a migration for every change in `schema.ts` (`verify-migrations-current`).
- Rules spanning the relationship tables — one permanent space per account, policy owners are participants, both bindings of a period commit together — are not constraints: every relationship write runs in `withUsersLocked`, which locks the users rows of everyone it touches in UUID order before any space or period row, and re-reads what it decides on under that lock (spaces-and-invitations D9, D10; tested with 20 concurrent acceptances, crossed and mutual invitations, and a failure injected after the first binding row).
- The caller of every relationship route comes from the session; request bodies are strict, so an actor, owner or member list in them is a 400.
- An invitation token is never stored, logged or returned again: the database keeps its SHA-256, a retry of the same request gets `token: null` (invariant 10, tested).
- Opening runs in two phases (kernel D5): phase 1 builds and self-checks every clean baseline in one read snapshot without locks and writes nothing; phase 2 is the range, binding or creation transaction itself, locking users → space → policy → diary rows by ID, rechecking each diary's version and generation and rebuilding a changed one inside the lock. Either every covered diary opens with the new revision or binding, or nothing changes (kernel invariant 17; tested with an injected corrupt diary and a commit landing between the phases).
- An epoch changes only under its diary's row lock, and freezing records the diary's last committed version; unbinding freezes every live share of the space in its transaction (kernel invariants 11, 13; tested).
- A baseline commit is seq 0 of a new generation, has no batch, author or operations, and carries the epoch's ID; the deleted text of the source state is not in it (kernel invariants 12, 18; tested by decoding the stored delta).
- No foreign key from a commit-path or opening row to `users` or `spaces` where a key check would wait on a row a relationship flow locks before diary rows: `share_epochs.recipient_id`, `backup_outbox.space_id` (kernel D9 lock order).
- `users` is written only by this module's code and holds no email, login method or foreign key into `auth_*` tables; no domain table references an `auth_*` table ([authentication-and-sessions](../../docs/adr/2026-10-24-authentication-and-sessions.md) invariant 1, schema tests).
- A batch is acknowledged only after PG COMMIT, and broadcast only after its ACK; a rejected or failed batch writes nothing and is never broadcast (kernel invariants 6, 7, 8; socket and fault tests).
- The receipt lookup by `(diary, batch)` and by operation runs under the diary row lock, so a batch delivered twice, even on two connections at once, commits once; the same batch ID with another payload is `BATCH_CONFLICT`, a committed operation in a new batch `OPERATION_ALREADY_COMMITTED` (invariant 10, tested).
- A commit locks only the diary row, `FOR UPDATE` with a 5 s `lock_timeout`; diary creation takes the owner's `users` row `FOR KEY SHARE` first. Rows a commit writes carry user IDs without a foreign key to `users`, because the key check would lock that row too (kernel D9 lock order, tested against a held lock).
- The in-memory Yjs state of a diary is used only when its version equals PG's under the lock; otherwise it is rebuilt from PG (tested with two service instances).
- The internal `version` appears in no response or socket message (kernel invariant 15, contract test).
- Every socket `submit` re-checks the session, and every connection re-checks it each 60 s (authentication-and-sessions invariant 8, kernel invariant 24, tested with real Better Auth sign-out). A sign-out or revocation, once Better Auth's transaction commits, publishes a session-ended event that closes every socket holding that session with `4401` and drops its unprocessed messages (tested with real Better Auth and with the stand-in sessions).
- A report of read characters writes only the reporter's own rows, one upsert per clientID, so devices merge without locks; no answer or snapshot carries another person's reading (kernel invariant 26, tested).
- Only `src/store/` writes SQL for the diary tables; transport never imports it.
- Everything a partner receives comes from `reader/` (kernel D17, invariant 14): opening, catch-up, broadcast recipients, history, the shared list and the day list. A partner's reads are bounded by an epoch: its baseline and the commits stamped with it, up to where it froze; live reads and catch-up only in the diary's current generation. A private commit never reaches a partner, whenever the stop notice arrives (tested by decoding every payload of the private-V11 scenario, kernel invariants 12, 15).
- A commit carries the diary's live epoch, stamped under the diary lock, and broadcasting decides recipients from that stamp without reading PG; a partner's write right is checked under the same lock, so a write racing a stop either lands in the frozen version or is refused `STALE_CONTEXT` (kernel invariant 16; tested over 12 rounds landing on both sides).
- A partner's bindings in any answer are limited to clientIDs that appear in what they receive.
- The day list's `unread` is decided per character identity in one read snapshot (text, history points and read coverage together), never by comparing versions or times; it counts only characters whose inserting commit is no later than the newest history point of the caller's view, and only those still visible, so a listed unread is always one the diary page finds and a deletion leaves none (unread-and-day-page invariants 1–5; tested on real PG, including half read, retyped, written then deleted, only deleted and frozen). A deletion after the newest point clears a mark at once, as the visible-text rule requires; new text after it never lights one.
- The day list names no diary the partner did not share, and no partner range: a date with only such a diary has no card, and `GET /api/days/:date` answers it as an empty date (invariants 10, 12; tested). `next-unread` searches the same diaries and never returns a date known only from an unshared one (tested).
- `next-unread` answers with the day list's `unread`. It keeps each (viewer, diary) answer in process memory with its inputs (generation, text version, history-point cutoff, a sha256 of the viewer's coverage rows) and rebuilds the text only when one changed; the memo is a disposable copy, never consulted for anything else (book-frontend-workspace D5; reading or new settled text changes the answer at once, tested).
- A Drive refresh token exists in plaintext only in the API's memory during `finish` and in the worker's while it uses one. It is stored sealed, under a key that lives only in the environment. No response, WebSocket message or log carries it, and only `src/worker/` imports `openToken` (server-backup-and-google-docs invariant 11; tested, including a scan of the source).
- Drive authorization asks for `drive.file` alone. Its state is bound to the user who started it and used once, and PKCE ties the code to that start (invariant 13; tested against a stand-in that checks the challenge).
- A person's Drive holds only what `reader/` lets them see: their own diaries and the partner's at the version a share allows, frozen where it stopped; never an unshared diary or a private commit (server-backup-and-google-docs invariant 5; tested by decoding every Doc of the partner's Drive).
- A day's Doc is written only at a history point it holds (or on "现在备份"), only when its rendered content changed, into the one `current` Doc of that person, account and date, and only while Google still reports the revision this app last wrote; a Doc changed in Google is never written over, also when the change lands between the check and the write; it keeps its content under a new name and a new Doc carries on (invariants 6–8; tested).
- A Doc or folder deleted or put in the bin is made again on the next write or by the daily check, once; the app never deletes or empties anything in Drive (invariant 9; tested, including that no `DELETE` reaches Google).
- Every failure of the copy is shown to its owner: a failed day on the backup page and on that day's pages with its reason, a run of failures as a `copy_failing` entry and, after a day, the home banner; a failed daily check as `check_failed`; a retrying revocation as `retrying`. The reason's detail goes to the worker's log only (tested for each).
- Commits never wait for Google: the copy is written by the worker from the outbox, and Google failures only delay it (invariant 10; tested with Google down).
- Pokes and pets reach only the other member of the caller's current binding, decided in the statement that writes them; nobody else can send or see them, an earlier period's row is never read after a rebind, and no answer tells the sender anything of the partner: whether they saw it, when, or whether they are online (window-mascots invariants 2, 3; tested). Only unseen counts are stored, deleted once shown (invariant 8).
- A partner's time zone and sleep schedule leave the server only while the two have a current binding, decided in the same snapshot that reads them; after unbinding the answer is the same as for no partner, and nobody else ever gets them (two-clocks invariant 1, tested). Only the caller's own zone and schedule are written, from the session.
- Space records are written only through `space-records`, which in one transaction holds the space's open period `FOR SHARE`, checks the record's author or the action's rule, changes the record and appends its history; unbinding updates that period row, so a write commits before an unbinding or is refused after it (space-records invariants 4, 5; tested with each side holding the lock). A record's history is appended only while its row is locked `FOR UPDATE`, so its sequence order is its commit order and a seen mark never skips a later commit.
- Space-record rows carry user and space IDs without a foreign key to `users` or `spaces`: the key check would wait on rows relationship flows lock `FOR UPDATE` while the write holds the period unbinding waits for.
- Every read of a space record, change or action filters `private_to` through `visibleTo`; a gift in preparation, its card and the giver's "我在准备" reach only the giver. The wisher's list, unread summary and the answers to deleting or receiving a wish are the same whether or not anyone prepares (wishes-and-gifts invariant 2; tested byte for byte). Responses carry a per-viewer `mark`, never the global sequence, whose gaps would show private actions.
- Reveals lock the wish before the gift in every flow, so a giver's "揭晓" and the wisher's "收到了" reveal once (tested concurrently).
- Anniversary dates count in the partner's last reported zone, except the caller's own birthday, only while the two are bound, decided in the same snapshot that reads the list; otherwise in the zone the caller's browser sends. The partner's zone never appears in an anniversaries answer (partner-local-dates invariants 1–3). A reminder is read and written only for the caller and never adds history or unread (anniversaries invariant 4).
- The link reader connects only to public addresses, checked on every connection's resolution and after each of at most 3 redirects, within 5 s and 1 MB, with no cookie; it stores text and an https image address, never the image (wishes-and-gifts invariant 7; tested against a local server, a name resolving to private and metadata addresses, and redirects to them).
- Carets pass through memory only: no table, commit, unread mark or backup task (kernel invariant 25); a partner's subscription stops receiving and sending them once its share's stop notice reached it, so no private caret follows a stop (tested).

## Known limitations

- `BINDING_CONFLICT` from the ADR's error list is not produced: competing bindings queue on the users-row locks, and the later one is refused as `ALREADY_BOUND`, `INVITE_USED` or `INVITE_REVOKED`.
- A saved range is stored even when it names the same days as before; it is a new revision, but it opens and freezes nothing then (diaries are compared as day sets).
- Opening a shared diary rebuilds its state and lists its commits each time; the shared list does so for each of its 30 cards. Fine for two people's diaries; keep a per-epoch summary beside the commit if it gets slow.
- Phase 2 of an opening sets no `lock_timeout`: the ADR allows none below 60 s before measurement, and [the K18 measurement](../../docs/validation/diary-kernel-sharing-2026-10-27.md) found far less is needed.
- A session that ends without a deletion (expiry) has no event; its socket closes on its next `submit` or within the 60 s recheck.
- Commit events are in-process: one API instance (kernel D11). Correctness does not depend on it; a missed broadcast is caught up by seq.
- The 1 MB cap applies to the JSON message, so base64 leaves about 750 KB for the updates of one batch. The web editor's paste limit counts the encoded message (`MAX_PASTE_BYTES`, about 780 KB of UTF-8, about 260,000 Chinese characters).
- `GET /api/diaries` has had no web consumer since the home page moved to the day list; it stays until deleting it is agreed (unread-and-day-page, 未解决的问题).
- The day list rebuilds each listed diary's text and timeline and reads its coverage on every request (up to 40 diaries per page): fine at two people's sizes. `next-unread` has the version-keyed memo the ADR named; the day list does not use it, since its excerpts need the text anyway. An unread table still needs asking first.
- The `next-unread` memo holds one small entry per (viewer, diary) for the life of the process and is per process; a second API process would compute its own. A search with nothing unread still reads every candidate's timeline and coverage.
- The diary list rebuilds each listed diary's state to take its excerpt (at most 100 deltas past the latest snapshot each, 30 per page). If that becomes slow, keep the excerpt beside the commit instead; that is a schema change.
- The daily check runs when the worker starts and then every 24 hours of its uptime, not at a fixed time; a worker restarted often checks more often. It reads a Doc's revision only when Drive's modification time is after the app's last write.
- A Doc put back from the bin after the app made a new one leaves two Docs with the same name; the app does not merge or remove either.
- A full Drive is looked at again once a day or on "现在备份"; the banner stays until a write succeeds.
- The Doc is created with Drive's `files.create` (Docs MIME type, in its month folder) rather than Docs `documents.create` and a move: one call, the same file.
- With the Google app in Testing (`GOOGLE_DRIVE_TESTING=true`), Drive grants stop working after seven days, and the backup page asks to reconnect. Publishing the app comes with deployment (server-backup-and-google-docs D9).
- The entry dot's count rebuilds the whole wishes answer; fine for two people's records.
- Anniversaries are not yet in a meeting calendar (anniversaries D6); that joins with meeting plans.
- An anniversary's dates follow the partner's last reported zone: after they travel and before they open the app, the countdown can be off by a day or some hours (partner-local-dates 风险).
- `POST /api/space/seen` checks a record only through the history the caller can see: a record nobody but the caller ever touched has no mark to raise, which is what unread needs.
- Link previews are read only while the worker runs; without it a link shows its site's domain. Big shops often refuse readers, so many previews end with only the domain. `<head>` is read with regular expressions, not an HTML parser.
- `ws` ships no types and `@types/ws` is not a dependency, so the socket object is untyped inside `src/ws/`.
- Session tokens are stored as issued; Better Auth has no option to store only a digest. The cookie carries an HMAC signature, so the database alone cannot forge a session; the database and `BETTER_AUTH_SECRET` together can.
- Rate limiting is Better Auth's built-in, in memory and production only: reliable for one process, to be moved to the database before running several.
- Re-running `npm run auth:generate` drops the two hand edits in `auth-schema.ts`; `verify-migrations-current` then fails, which is the reminder to re-apply them.
- `drizzle-kit` 0.31 pulls an old esbuild loader with 4 moderate `npm audit` findings. It runs only when generating migrations on a developer machine, never in production; re-check when upgrading to Drizzle 1.0.
- `src/server.ts` is excluded from coverage; it only wires `buildApp()` to a port.
