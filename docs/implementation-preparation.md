# 正式实现前：技术栈与开发流程准备方案

日期：2026-10-24。状态：建议稿，等待下一阶段共同决定；本文件不表示已经开始正式实现，也未安装下述所有候选框架。

最新状态：基础性能检查已完成，见 [Web 检查报告](./validation/yjs-web-smoke-2026-10-24.md)。用户明确要求先不进行实现，当前不创建正式骨架或落地工程规范。用户已确认 npm、Node 测试、TypeScript、ESLint、Prettier、GitHub Actions、仓库 Git hooks、新正式模块 80% 行覆盖率、checks/ 及 Web/API/共享契约/原型模块划分；产品文档保留中文，新增工程约定采用英文且不额外维护双语。以上均为待实施约定，尚非已安装或已运行的能力。

补充依据：[技术栈深度调研](./research/tech-stack-2026-10-24.md)。持续维护是生产依赖门槛；协同内核优先验证成熟开源实现，现有自研原型不自动转为正式内核。

Yjs 第一轮验证已完成，见 [ADR-0005](./adr/0005-yjs-authoritative-validation.md)及[验证报告](./validation/yjs-collaboration-2026-10-24.md)：不接受客户端任意二进制更新，服务端校验语义操作后生成权威 Yjs 增量。75 个不同用例、116 项次最终通过；正式 schema、性能与移动端路线仍需验证。

当前范围调整（2026-10-24，用户确认）：先推进桌面 Web；手机实机、Expo/React Native 和 WebView/SQLite 桥接验证暂缓，不阻塞 Web 架构与正式实现。下一轮优先长日记/长历史性能、快照/增量同步，以及升级和旧客户端待发文字恢复。

后续范围收敛：用户希望性能先达到日常写作无明显卡顿，深入优化后置。因此先做基本性能检查，解决明显瓶颈即可，不把完整压力测试、快照/历史压缩优化都作为正式实现前置。协议与本地升级不得静默丢弃待发文字的要求保留。讨论浏览器 SQLite 替代方案后，用户于 2026-10-24 明确确认 Web 本地存储采用 IndexedDB，保存本地副本与未确认操作；服务端主库仍为 PostgreSQL。

## 推荐顺序

1. 阅读[协同验证结论](./validation/collaboration-readiness-2026-10-24.md)，确认已验证的语义和剩余上线门槛。
2. 确定技术栈、部署形态和协同协议的维护范围，写正式 ADR。
3. 根据实际栈落地开发规范、目录契约、CI 和完成标准，运行一轮验证。
4. 将原型中的有效设计与测试迁入正式模块，再开始产品功能实现。

流程原则可现在确定，具体命令、目录和工具规则要跟技术栈一起落地，避免写成不能执行的约定。

## 技术栈建议与证据状态

| 层 | 建议 | 依据 / 尚需决定 |
| --- | --- | --- |
| 语言 | 正式前后端采用 TypeScript strict | 原型使用 ESM JavaScript；正式契约需要约束 actor、稳定 ID、操作批次、保存状态与协议版本 |
| 前端 | React + Vite；TanStack Query + 按需使用 Zustand | 状态管理方向已确认：Query 管普通服务端数据，Zustand 仅在有跨组件客户端状态时引入；正文和待同步操作由协同核心管理，不在多个 store 中复制可写正文 |
| 编辑器 | 直接使用 ProseMirror，加受约束的编辑插件 | 已验证三引擎、作者保护、composition、个人撤销和光标；需决定是否需要 Tiptap 封装，当前纯文本范围倾向直接使用 |
| 同步 | 服务端权威语义操作、稳定标识、原子批次、WebSocket 通知/在线位置 | 已验证；最终序列内核及协议版本须作为正式决策，不把实验实现自动视为定案 |
| 服务端 | Node.js 常驻服务；Fastify 为 API 框架候选，ws 处理连接 | Node/HTTP/ws 已验证；Fastify 尚未集成，选择时确认 cookie/session、限流、payload 和连接生命周期 |
| 主库 | PostgreSQL；正式 schema 与迁移版本化 | 已指定并验证 PG 18.6 行锁、事务、重试和进程崩溃；托管服务商尚未选择 |
| 数据访问 | 倾向 Drizzle + 明确 SQL 事务边界 | 原型使用 pg 和 SQL；ORM 是后续维护性选择，不改变持久化确认原则 |
| 本机数据 | IndexedDB + 原子 readwrite 合并，按账号/空间/日记隔离 | 本轮真实浏览器验证过草稿持久化与标签页合并；正式身份退出/切换和 schema 升级还需实现 |
| 离线 shell | Service Worker，仅缓存静态资源 | 已验证离线刷新；正式更新策略不能用无条件更新打断旧客户端待发编辑 |
| 登录/Google 授权 | 成熟 OIDC/OAuth 库；登录与 Drive 授权分开 | 原型没有真实登录；库、cookie/CSRF/nonce 和刷新令牌存储需独立 ADR，避免自行手写协议 |
| 后台任务 | 先采用 PG outbox + 单独 worker 进程 | 事务登记已验证；Google worker 及幂等更新仍属正式实现 |
| 测试 | Node 测试运行器 + Playwright + 隔离 PG | 本轮已有可运行证据；TS 工具链确认后确定编译/测试命令 |

建议初期用一个仓库、一个常驻后端和 PG，API 与静态前端同源部署。后台 worker 以独立进程运行但共享代码和数据库；暂不引入 Redis/Kafka 或额外微服务。部署提供方仍需根据 PG、长连接、备份、地区与预算选择，本轮不承诺托管兼容性。

### 关于 Yjs 与自定义协议

当前证据支持“服务端理解并验证每条操作”的方案，没有验证将任意 Yjs 二进制更新直接广播的作者权限安全性。选择 Yjs 不自动继承本轮作者保护结论，需要重新验证来源检查、离线标识和个人撤销。

建议把编辑器、作者权限校验和持久化确认边界独立管理。优先验证 ProseMirror + Yjs，Hocuspocus 为服务端基础设施候选；它们及绑定层通过维护审查与同等行为测试后才能正式选定。prosemirror-collab 作为对照候选暂不列为默认生产依赖，其稳定发行较久，且新托管站维护活动本次未完整核验。原型没有经过形式化证明，不直接宣布自研算法生产成熟。具体证据与后续门槛见技术栈调研。

## 建议落地的开发流程

### 范围和契约

- 根 AGENTS.md 保持简短，说明范围、入口、禁止破坏的不变量及检查命令。
- 核心模块单独 README：输入/输出、信任边界、持久化确认、错误与恢复行为。
- 需求变更先更新 spec 或决策记录，验收编号与实现/测试互相可追溯。
- 目录建议按 editor、collaboration、identity、storage、backup 分模块；先明确依赖方向，不把 UI DOM、数据库和同步协议混在一起。

### 变更与评审

- 每个分支围绕一个可评审目标；提交描述实际行为和理由。
- 小型 PR 附问题、行为变化、验证证据和实际限制；协议、身份或数据结构变化附 ADR。
- schema 变更通过 migration；协议及 IndexedDB 变更附版本兼容/升级验证，不直接覆盖旧待同步草稿。
- 不把测试 token、真实日记、OAuth 密钥或数据库凭据写入仓库/日志。

### 完成标准与自动检查

技术栈确定后，把可机械验证的规则配成真实脚本与 CI：format、lint、typecheck、有效单元/性质测试、PG 集成、浏览器关键流程、文档链接及所需文档变更检查。涉及协同/权限/本地持久化的 PR 运行对应浏览器与故障测试；无关的文案改动不强制跑全部数据库和浏览器套件。

“必须做”的规则要有对应检查；纯人工事项在 PR 中明确记录。覆盖率用于发现缺口，不用数字代替作者保护、幂等和故障恢复测试。

### 首个正式里程碑

优先实现 Google 登录与双人空间、PG 迁移、单篇日记及可靠保存状态，再迁入已验证的编辑行为。大段粘贴切分、精确时间元数据、草稿协议版本、会话失效、设备生命周期和真实身份隔离必须从正式设计开始覆盖。

## Web 正式发布前仍需的人工和集成门槛

- macOS Safari、Windows 输入法/原生剪贴板，包含真实帐号切换。
- 真实中美连接，包含高延迟、网络切换和授权失效。
- Google 授权、导出、版本保护、快照完整恢复与实际备份告警。
- 生产环境的协议升级、旧客户端、负载与敏感信息保护。

这些是产品发布门槛，不必在没有正式应用的阶段全部完成；不得把当前验证报告当成上线通过单。

手机支持恢复时再安排实体 iPhone Safari、Android Chrome 的输入法、长按、选区、后台/强制关闭与低内存恢复，以及原生应用编辑器和持久化桥接；这些事项当前后置，不表示已经通过。
