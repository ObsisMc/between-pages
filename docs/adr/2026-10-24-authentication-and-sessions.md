# 用 Better Auth 只做 Google 登录和会话，领域用户与认证层分离

- 状态：已采纳
- 日期：2026-10-24
- 决策者：Ray
- 范围：认证
- 关联：依赖 ADR-0006；依赖 ADR-0004

## 背景与问题

正式实现的第一步是登录和双人空间。[规格 §3](../diary-spec.md) 要求用 Google 登录，同时规定了身份、会话和写入校验的规则；[ADR-0006](./0006-formal-stack.md) 第 25 条把 Better Auth 定为第一候选，要求实现前另行确认。需要决定：用什么库，用户和身份怎么建模，会话怎么保证可撤销，以及哪些部分不交给认证库。

## 决策依据

1. 应用有自己稳定的 userId；登录身份按签发方 + subject 绑定，不以邮箱作为身份（规格 §3）。
2. 登录与"连接 Google 备份"是两个独立流程；拒绝 Drive 权限也能写日记。
3. HTTP、WebSocket 握手和每次写入都校验身份与空间成员资格；会话失效后拒绝新写入，但本地待同步内容保留。
4. 不自己手写 OAuth 和会话协议（规格 §3）。
5. 领域数据不被认证库绑死：换库、增减登录方式不改领域数据；删除身份记录不牵连这个人写过的字。
6. 依赖必须持续维护，安全补丁及时。
7. 两人规模，运维和成本尽量低。

## 备选方案

- **Better Auth**：开源、在 API 进程内运行，满足 1～4，但默认配置会按邮箱合并账号（违背 1），需要显式配置；5 靠下文的两层用户模型满足；6 上发版活跃，但安全公告较多，需要持续跟进。
- **openid-client v6 + 自己实现会话**：经过认证的 OIDC 库，满足 1、2、5、6，完全可控；但会话、CSRF、撤销、限流都要自己写，违背 4。
- **Auth.js（@auth/core）**：2025-09 起由 Better Auth 团队接手，只做安全维护，不满足 6。
- **Lucia**：npm 包已弃用，不满足 6。
- **Supabase Auth**：默认按已验证邮箱自动合并身份（违背 1），还要额外部署或依赖外部服务（违背 7）。
- **Clerk、WorkOS**：托管收费，身份数据在第三方（违背 5、7）；会话不方便和自己的 WebSocket 共用（3）。
- **领域表直接引用认证库的用户表**：少一张表，但领域数据绑在认证库的表结构上，违背 5。
- **完全关闭账号关联**：能禁止按邮箱合并，但也会禁止登录后主动绑定新的登录方式，以后增加登录方式就要改领域数据，违背 5。
- **用认证库的组织插件管理双人空间**："最多两人、一次性邀请"仍要自己约束，还扩大了插件面（6）。

## 决策结果

选择 Better Auth，只用它做 Google 登录和会话；领域用户与认证层分成两层，空间、成员和 Drive 授权都不交给认证库。

- Better Auth 运行在 API 进程内，与 Web 同源；锁定精确版本，且不低于修复 GHSA-965c-763c-88jm（OAuth state 可被用来登录他人账号，严重级）的版本；生产环境不启用任何插件。
- 用户分两层：领域层的 `users` 表只由我们的代码写，存 id、显示名、创建时间、最近活跃时间，以后的时区、作者颜色、停用时间也放这里；认证层是 Better Auth 的表，统一加前缀，存邮箱、头像、登录身份、会话。两层用同一个 UUID 对应，领域行在第一次认证请求时幂等创建。
- 最近活跃时间只供运维和以后的功能使用，写入有节流，不展示给另一位成员：那相当于在线状态回执，与"不默认公开对方已读状态"冲突，要展示须先改规格。
- 首版只接 Google，只申请基本身份范围，不申请 Drive 权限。以后增加登录方式只需增加 provider 配置和身份行。
- 禁止按邮箱自动合并账号；允许已登录的用户主动绑定另一种登录方式。
- 登录不保存任何 Google 令牌；Drive 授权走独立的 OAuth 流程，令牌加密保存在自己的表里（ADR-0004），具体库在实现备份时选定。
- 会话存在数据库中，Cookie 为 HttpOnly、SameSite=Lax，生产环境强制 Secure 及安全前缀；有效期和续期间隔是可调的实施默认值。不使用会推迟撤销生效的 cookie 缓存。
- 双人空间、成员和邀请用自己的表，由 PG 约束和事务保证规格 §3 的规则；退出或切换账号时锁定本机缓存，属于客户端职责。

### 约束

1. 所有领域表只引用 `users.id`，不引用认证层的任何表，`users` 上也没有指向认证层的外键；`users` 不存邮箱和登录方式。
2. 一个登录身份（登录方式 + subject）唯一对应一个用户，由唯一索引保证；同一 subject 换了邮箱仍是同一个用户。
3. 不同 subject 使用已存在的邮箱登录时被拒绝：不建会话、不建用户、不关联到已有用户。
4. 只能在已登录状态下绑定新的登录方式；已属于其他用户的身份不能被绑定过来。
5. 登录流程不保存任何 Google 令牌，也不申请 Drive 权限。
6. 退出或撤销会话后，旧 cookie 在 HTTP 和 WebSocket 握手上立即失效。
7. 所有非 GET 的 API 路由和 WebSocket 握手都校验 `Origin` 属于可信来源；认证库自身的检查只覆盖它自己的端点。
8. WebSocket 连接上的每次写入都重新确认会话有效、用户仍是该空间成员；失效时拒绝写入，不丢弃客户端待同步内容。
9. 最近活跃时间不出现在任何返回给另一位成员的接口中。

### 后果

- 登录协议、会话和认证端点的 CSRF 由成熟的库负责；项目只维护配置、令牌清理、唯一索引、领域 `users` 表、自己路由的 Origin 检查和空间表。
- 多一张 `users` 表和"首次请求创建领域行"的逻辑；换来认证层可以整体替换。
- Better Auth 从 2024-12 到 2026-09 有 37 条安全公告（多数在插件中），需要持续跟进补丁。
- 邮箱冲突需要人工处理；两人规模下可以接受。
- 本决定依据的 spike 用通用 OAuth 插件加模拟 OIDC 服务，没有覆盖真实 Google 端点、同意页面和 HTTPS 下的 cookie 前缀；这些在阶段 1 联调时人工验证一次并记录在验收证据中。

### 确认方式

- 约束 1：迁移后的 schema 测试，检查 `users` 的列和外键，以及领域表的外键只指向 `users`。
- 约束 2、3、4：用模拟 OIDC 服务走完整登录往返的集成测试（同 subject 换邮箱、不同 subject 同邮箱、已登录绑定、绑定他人身份、并发首次登录）。
- 约束 5：集成测试断言身份记录上的令牌列为空、授权请求只含基本身份范围。
- 约束 6：集成测试用退出前复制的 cookie 访问 HTTP 路由和 WebSocket 握手。
- 约束 7：集成测试用不可信 `Origin` 调用写路由和握手。
- 约束 8：协同协议的集成测试（阶段 2）。
- 约束 9：成员相关接口的契约测试。

## 补充信息

- 重新评估条件：Better Auth 核心（非插件）出现严重安全公告且修复缓慢，或项目停止维护时，改用 openid-client + 自己实现会话；需要的认证能力只能通过插件获得时重新评估；规格改为允许展示在线状态时重议约束 9。
- 证据：[Better Auth spike](../../prototypes/auth/README.md)（含落到 `apps/api` 时要用的具体配置）、[spike 测试日志](../validation/artifacts/auth-2026-10-24/better-auth-pg.log)。
- 对应验收：AUTH-01、AUTH-04、AUTH-05 的服务端部分由本决定直接覆盖；AUTH-02、AUTH-03 依赖空间与邀请表；AUTH-06 依赖客户端缓存锁定。
