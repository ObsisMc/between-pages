# 见面计划记下每次见面的日期、地点与两张清单，首页倒数与见面日历都取自它，长期想做的事可以放进某次见面

- 状态：已采纳
- 日期：2026-10-29
- 决策者：Ray
- 范围：领域
- 关联：依赖 space-records；依赖 two-clocks

双人空间里的每一次见面是一条记录：地点和日期（确切的起止日，或"大概 3 月"、"3 月到 4 月之间"，或还没定），两人都能改；每次见面有两张清单，"要准备的"（签证、机票、行李）和"想一起做的"（去哪、吃什么），两人都能加、都能勾，标出谁加的、谁勾的。另有一张不属于任何一次见面的长期清单"以后想一起做的事"，其中一条可以放进某次见面，长期清单上显示放进了哪次，在哪边勾都算完成。做完的事记下完成日期，能点到那天的日期页。首页小条的"下次见面"一行（two-clocks D4）与见面计划页里的按月日历，都从这些记录计算。

本文不负责：纪念日本身（见 anniversaries，它显示在本文的日历里）；提醒与通知（阶段 4）；行程预订、票据与附件；待办的负责人与截止日期（用户 2026-10-29 不要负责人）。共用的归属、作者、动作、解绑、删除、未读规则见 space-records。

## 背景与问题

异地的两个人，见面是最重要的事：没定日期时盼着，定了以后要一起准备签证、机票、住宿，见面前想好去哪、做什么；很多"以后想一起做"的事一直攒着，等某次见面再做。用户于 2026-10-29 确认这个功能要做到四件事：盼头（倒数与见面日历）、一起准备不漏事、一起想见面做什么、长期的"以后想一起做的事"。两地时间的设计（two-clocks）已经决定首页"下次见面"一行和见面日历都用见面计划的数据，不另填日期。

## 决策依据

1. 日期没定时也能有盼头，定了以后有准确的倒数；见面期间也有感觉（用户 2026-10-29 选择大概日期、见面中显示第几天）。
2. 见面是两个人的事：谁订好了机票谁就能更新日期和地点（用户 2026-10-29 选择两人都能改）。
3. 准备和期待分开看；每条标出谁加的、谁勾的，不指定负责人（用户 2026-10-29）。
4. 长期想做的事可以放进某次见面，两处看到的是同一件事，在哪边勾都算完成（用户 2026-10-29）。
5. 能一眼看到过去和将来所有的见面（用户 2026-10-29 要见面日历，不一定放首页）。
6. 做过的事能回到那天的日记（路线图第一批）。
7. 共用规则沿用 space-records；首页的位置由 two-clocks D4 给出。

## 决策

### D1：一次见面是一条记录，日期与地点两人都能改

一次见面的作者是建它的人。字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 地点 | 否 | 最多 50 字，例如"东京"；没填时显示"还没定地点" |
| 日期 | 否 | 见 D2；没填即"还没定日期" |
| 备注 | 否 | 最多 500 字，作者的文字 |

改日期、改地点是动作（space-records D4），两人都能做，记下是谁、什么时候改的；备注只有作者能改；删除这次见面只有作者能做（space-records D6，D7 说明连带的内容）。

原因：依据 2。日期与地点往往由去订票的那个人先知道。

### D2：日期是确切起止日、大概的月份或范围，或者还没定

| 写法 | 例子 | 首页"下次见面" | 日历 |
| --- | --- | --- | --- |
| 确切 | 2027-03-12 到 2027-03-20（可以只有一天） | 见面前"还有 N 天"；见面中"在一起的第 k 天 · 还有 m 天"，最后一天"在一起的最后一天" | 实线 |
| 大概的月份 | 2027 年 3 月 | "大概 3 月" | 那个月的虚线 |
| 大概的范围 | 2027 年 3 月到 4 月 | "大概 3 月到 4 月" | 范围内的虚线 |
| 还没定 | — | 不计入 | 不显示 |

日期只是日历日期（`DATE`），不带时区。天数按查看者当地的今天计算，所以两人可能相差一天，这是两地本来的情况。

**下次见面**：在结束日（大概的取范围最后一天）不早于查看者今天的见面里，取开始日最早的一次；进行中的见面优先。没有就不显示这一行。跨年时显示年份（"大概 2028 年 3 月"）。

原因：依据 1。

### D3：每次见面有"要准备的"和"想一起做的"两张清单

两张清单的条目都是记录：文字归加它的人（space-records D3），勾上与取消勾选是两人都能做的动作，条目旁显示"A 加的 · B 勾了 · 3 月 2 日"。不设负责人与截止日期。

"想一起做的"条目勾上时记下完成日期（D5）；"要准备的"条目不记。

原因：依据 3。准备是任务，想做的事是期待，分开看更清楚。

### D4：长期清单的一条可以放进一次见面，两处是同一条记录

"以后想一起做的事"是不属于任何见面的长期清单，条目同样归加它的人、两人都能勾。

- 一条长期事项同时至多放进一次见面；两人都能把它放进某次见面、改放到另一次、或取出来（动作）。
- 放进去以后，它出现在那次见面的"想一起做的"里，长期清单上显示"放进了：三月东京"；它仍是同一条记录，在哪边勾、取消勾，两边一起变。
- 在见面里新加的"想一起做的"只属于那次见面，不出现在长期清单里。

原因：依据 4。复制一份会让两边的勾选不同步，用户要的是"勾一处、两处都完成"。

### D5：做完的事记完成日期，能点到那天的日期页

"想一起做的"条目与长期事项勾上时，完成日期默认是勾的人当地的今天；两人都能改（动作）。条目上显示完成日期，点开进入那天的日期页（unread-and-day-page 的 `/days/:date`），看两人那天的日记。日记里不会自动写入任何文字；那天两人都没写或没共享时，日期页照常显示（自己可以去写）。

取消勾选时完成日期清空；再次勾上重新取默认值。

原因：依据 6。只链到日期页，不改日记，日记的作者与共享规则不受影响。

### D6：见面日历在见面计划页里，按月看

见面计划页有一个按月的日历：确切的见面在起止日之间画实线，大概的见面在月份或范围内画虚线，点击进入那次见面。过去和将来的见面都显示。日历不放在首页（首页只有"下次见面"一行）。

日历同时显示纪念日的周年日与整数日，样式与见面不同（anniversaries D6）；纪念日的数据由 `meetings` 网页模块经 `api` 读取。

原因：依据 5。

### D7：过去的见面仍可编辑；删除见面时长期事项留下

见面结束后仍可编辑（补勾、改完成日期、补写想做的事）。作者删除一次见面时：

- 放进它的长期事项自动取出，留在长期清单里，完成状态与完成日期不变；
- 它自己的"要准备的"与"想一起做的"条目随之删除；
- 对方按 space-records D6 收到删除提示：对方动过这次见面或其中任何条目时，显示一条，例如"A 删了'三月东京'（含你勾过的 3 项）"。

解绑与重新绑定按 space-records D5：解绑后两人只读；首页小条在解绑后不显示（two-clocks D4），见面计划页里的记录仍可只读查看。

原因：依据 4、7。长期事项不属于某次见面，不应随它消失。

### D8：动作清单

| 动作 | 对象 | 谁能做 |
| --- | --- | --- |
| 改日期 / 改地点 | 见面 | 两人 |
| 勾上 / 取消勾选 | 要准备的、想一起做的、长期事项 | 两人 |
| 改完成日期 | 想一起做的、长期事项 | 两人 |
| 放进见面 / 改放 / 取出 | 长期事项 | 两人 |

见面、条目的新建、修改文字与删除按 space-records D3、D6 由各自作者做。本功能没有私密状态。

## 数据与模块

- **表**（共用列见 space-records）：
  - `meetings`：地点、备注、日期写法（确切、月份、范围、未定）、开始日、结束日；当前状态字段与最后修改人随 D1 的动作更新；
  - `meeting_todos`：所属见面、文字、是否完成及最后修改人与时间；
  - `together_items`：文字、所属见面（可空）、是否长期、是否完成、完成日期及最后修改人与时间。见面里的"想一起做的"是 `meeting_id` 有值且不长期的条目；长期事项是 `long_term` 为真的条目，`meeting_id` 表示放进了哪次见面。
- **服务端**：`apps/api/src/meetings/` 服务，只经 `space-records` 写入；为 two-clocks 的首页小条提供"下次见面"的计算结果（D2）。
- **网页**：`apps/web/src/meetings/`（见面列表与详情、两张清单、长期清单、按月日历），导入 `space-common` 与 `api`；首页小条的"下次见面"一行由 `two-clocks` 通过 `api` 读取，两模块互不导入。
- 迁移与新表在实现 PR 中生成；本 ADR 采纳即视为预先批准。

## 失败与恢复

| 情况 | 结果 | 恢复 |
| --- | --- | --- |
| 两人同时改同一次见面的日期 | 两个动作按提交顺序记录，后提交的成为当前日期，历史里两条都在 | 界面显示最后是谁改的 |
| 删除见面时对方正把长期事项放进它 | 锁住见面行排序：放进先到则删除时一并取出；删除先到则放进被拒为"这次见面已不在" | 对方重新选择见面 |
| 结束日早于开始日、范围颠倒 | 请求被拒 | 改正后再提交 |
| 改日期时刚好解绑 | 写入被拒（space-records D5） | 重新绑定后再改 |

## 不变量

1. 见面的日期与地点两人都能改，每次修改作为动作记录操作人与时间；备注与删除只属于作者。
2. 确切日期的结束日不早于开始日；大概的范围起不晚于止；日期只存日历日期，不随时区换算。
3. "下次见面"按 D2 的规则从见面记录计算：进行中的优先，其次开始日最早且未结束的；没有确切或大概日期的见面不计入。
4. 清单条目的文字只有加它的人能改；勾选由两人都能做并记录操作人。
5. 长期事项同时至多放进一次见面，它在长期清单与那次见面里是同一条记录，完成状态永远一致。
6. 完成日期只在条目完成时存在，取消勾选即清空；链接只指向日期页，不向日记写入任何内容。
7. 删除一次见面时，放进它的长期事项回到长期清单且完成状态不变；它自己的条目随之删除。
8. 见面计划不含私密状态，所有记录与动作两人可见（解绑后只读）。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **见面的日期与地点只有作者能改** | 严格符合"文字归作者" | 订票的那个人不能直接更新（依据 2）；用户选择两人都能改 |
| **只有确切日期与"未定"** | 数据最简单 | 没定日期时首页没有盼头（依据 1） |
| **见面开始后倒数消失** | 简单 | 见面期间也想看到"在一起的第几天"；用户选择显示 |
| **一张清单，每条标类型** | 少一张表 | 准备与期待混在一起；用户选择两张清单（依据 3） |
| **待办可选负责人** | 一眼看到谁还有事没做 | 用户 2026-10-29 不要 |
| **长期事项放进见面时复制一份** | 两处互不影响 | 勾选不同步，违背"勾一处两处都完成"（依据 4） |
| **长期清单与见面清单各管各的** | 最简单 | 用户要求能链接并同步完成 |
| **完成时自动往那天的日记里写一句** | 日记里留下痕迹 | 违背日记只由作者书写、按共享范围开放的规则 |
| **日历放在首页** | 一眼看到 | 首页变挤；用户说不一定放首页，首页只放"下次见面"一行（依据 5） |
| **倒数在两地时间里单独填** | 不建见面也能倒数 | 日期要在两处维护（two-clocks 已否决） |

## 风险与代价

- "下次见面"由两人各自的今天计算，跨日界时两人看到的天数可能差一天；这是事实，不做统一。
- 删除见面会一并删除其中的条目，对方通过删除提示得知；数据仍按 space-records D6 软删除保留在服务器上。
- `together_items` 用 `long_term` 与 `meeting_id` 两列表达三种情况（只属于见面、长期未放进、长期已放进），约束须由检查约束与服务共同保证。

## 验收标准

- 两人分别改见面日期与地点，历史两条动作，当前值为最后一次；对方改备注或删除被拒（API 测试，不变量 1）。
- 结束日早于开始日与范围颠倒被拒（API 测试，不变量 2）。
- "下次见面"：确切的见面前、见面中、最后一天、结束后；大概的月份与范围；多次见面取最早的；全部未定时没有这一行（单元测试，不变量 3）。
- 对方能勾我加的条目但不能改文字（API 测试，不变量 4）。
- 长期事项放进见面后在两处同时显示，在见面里勾上后长期清单也完成；改放到另一次只出现在新的一次（API 测试与浏览器测试，不变量 5）。
- 勾上时有完成日期，取消即清空，点开进入那天的日期页且日记内容不变（组件测试与 API 测试，不变量 6）。
- 删除见面后长期事项回到长期清单、完成状态不变，见面自己的条目消失，对方看到删除提示（API 测试，不变量 7）。
- 验证某条不变量的测试标题带 `[adr:meeting-plans#<编号>]`。

## 补充信息

- 重新评估条件：加入提醒或通知（见面前提醒未完成的待办）；需要负责人或截止日期；日历要显示见面与纪念日以外的第三种内容；需要保存票据或附件。
- 证据：2026-10-29 与用户逐条确认（四个目标、日期与地点两人都能改、确切或大概日期、见面中显示第几天、两张清单、不要负责人、长期事项链接见面并同步完成、完成日期链到日期页、日历在见面计划页、过去的见面可编辑、删除见面时长期事项留下）。
