# 未读按字判定、列表只计已成历史的文字，同一天的两篇日记上下排在一个页面里

- 状态：已采纳
- 日期：2026-10-28
- 决策者：Ray
- 范围：领域
- 关联：依赖 diary-collaboration-kernel；依赖 spaces-and-invitations

首页把本人日记和对方共享来的日记合成一个按日期排列的列表，每天一张卡片，用首字头像标出这天谁写了，有未读时亮一个圆点。打开日记停在开头，有未读时显示"有 N 处新内容 · 跳到第一处"，阅读中随时可以跳到下一处未读，视野外出现新内容时实时提示方向。未读按字的身份判定：日记里实时计算；列表只计入已经成为历史版本的文字，所以对方写了又删、或者正在连续写时，列表不会闪烁，而列表显示有未读的日记，打开后一定能跳到。对方在上方插字、切换过滤或视图时，眼前的文字不被推走。对方共享了某一天时，这一天打开为日期页：两篇上下排列、都能直接写，各自保留 ID、主人和编辑边界。

本文不负责：推送与邮件提醒、搜索、未读统计、"上次读到的位置"、左右并排、离线首页列表、手机端、视觉样式（以后重做）。已读的存储与上报沿用内核 D15，本文只在其上增加判定与展示。

## 背景与问题

用户此前在 Google Docs 里和搭档共写日记，两人在同一个文档里上下各写一段；阶段 2 的阅读需求来自这段经验。正式项目在内核阶段 4 已经具备所需的数据：每个字有不可变的作者和写入时间，每人读过哪些字按字的身份记在服务端，多设备合并、跨重开保留（内核 D15），面向搭档的输出只经获准状态读取入口（内核 D17）。但目前没有任何界面使用这些数据：

- 首页的本人日记和对方共享的日记是两个分开、各自分页的列表，都不知道哪篇有未读；
- 日记里看不出哪些字是新的，也不能跳过去；
- 对方在上方插字时，眼前的内容可能被推走（规格 §6、SYNC-06 没有实现）；
- 同一天的两篇日记只能分别打开，双人拼接页（DATE-03）从内核阶段 4 推迟到这里。

约束：未开放的日期与没有日记必须看起来一样（规格 §3.4）；不提供阅读回执（规格 §8.1）；首版只做桌面 Web，但窄窗口仍要能用。

## 决策依据

1. 列表上能看出哪篇日记有未读；进入日记后可以选择跳到未读，并能逐处跳到下一处（用户 2026-10-28 确认）。
2. 列表显示有未读的日记，打开后一定能找到这处未读，不出现"列表说有、进去找不到"。
3. 对方写了又删、或者正在连续写时，列表标记不应时有时无。
4. 打开日记不自动跳转，由用户选择（用户 2026-10-28 确认；文档类产品的通行做法，见补充信息）。
5. 远端修改不抢走阅读或输入位置（规格 §6、SYNC-06）。
6. 隐私边界不变：对方未共享的日记与不存在的日记不可区分；阅读进度只属于读者本人（规格 §3.4、§8.1，内核 D15、D17）。
7. 同一天的两篇保留各自的 ID、主人和编辑边界；编辑、撤销、未读、光标不跨篇处理（spaces-and-invitations D1，内核 D1）。
8. 首版只做桌面 Web，窄窗口仍可用，以后接手机时不另做一套布局。
9. 性能达到日常写作无明显卡顿即可（用户 2026-10-24 确认）；只有两位用户。
10. 前端样式以后会重做（用户 2026-10-28）：本文规定行为和信息，不规定视觉。

## 决策

### D1：本文的范围

| 做 | 不做（不在本文，不代表以后不做） |
| --- | --- |
| 按日期合并的首页列表、卡片头像与未读圆点 | 系统或浏览器推送、邮件提醒 |
| 日记内的未读提示、"下一处未读"、方向提示 | 搜索 |
| 打开日记的定位与跳转后的位置 | 未读统计页面 |
| 远端修改、过滤与视图切换时的阅读位置锚定 | "上次读到的位置"（理由见备选方案） |
| 同一天两篇日记的日期页 | 左右并排布局 |
| 日期页上两个编辑器之间的作者保护与手动验证 | 离线首页列表（推后，见路线图） |

原因：依据 1、10。范围只覆盖"知道哪里有新内容、去到那里、读的时候不被打断、同一天放在一起读写"。

### D2：未读按字判定，日记里实时，列表只计已成历史的文字

**定义**：对查看者 V 和一篇日记，**候选文字**是 V 在这篇日记里有权读到的当前正文中、由另一位作者写的字：

- V 自己的日记：V 的最新个人正文中搭档写的字；
- 对方共享给 V 的日记：经获准状态读取入口得到的当前轮次正文或冻结正文中对方写的字（内核 D17）。

候选文字中，(clientID, clock) 不在 V 的已读区间里的字就是**未读**（内核 D15）。自己写的字永远不是自己的未读；删除后不在正文里的字不是候选，所以不会留下找不到的未读；对方把旧字删掉再输入是新字，算未读。

**两处判定**：

| | 日记里 | 列表 |
| --- | --- | --- |
| 谁算 | 浏览器，用已加载的正文和 `readRanges` | 服务端，在生成列表时 |
| 计入哪些未读 | 全部 | 只计**已成历史**的：所在提交不晚于这篇日记（在 V 可读的视图中）最近一个历史点所代表的提交 |
| 更新 | 随正文和已读上报实时变化 | 每次取列表时重新计算 |

"历史点"沿用内核 D6 的规则：持续编辑每五分钟一组，连续两分钟没有正文提交补末点，共享的开放、停止、重开各自成点。所以对方停笔约两分钟、或者连续写满一组（最多约五分钟）后，这些字才进入列表判定；在那之前写了又删的字从不让列表亮起来（依据 3）。冻结的共享在停止时已成点，冻结正文中的未读全部计入。

**子集关系**：同一时刻的数据下，列表判定为有未读的日记，日记里判定也至少有一处未读，因为列表计入的字是日记里计入的字的子集（依据 2）。反过来不成立：对方两到五分钟内刚写的字，日记里已经能看到和跳到，列表还不亮，这是冷静期的代价。

为什么列表也精确计算而不从提交时间粗算：粗算（对方最后一次提交晚于 V 最后一次阅读）在对方只删字、或 V 只读了一半时会判断错，违反依据 2。为什么不存一张未读表：要在每次提交和每次已读上报时维护，写入路径变重、多一处必须保持一致的状态；两人规模下现算即可（依据 9）。服务端生成列表摘要时已经为每篇构建正文（`apps/api/src/reader`），未读判定在同一处完成。

### D3：首页是一个按日期合并的列表

首页列出 V 能看到的所有日期，一天一张卡片，日期从新到旧、分批加载。一张卡片包含：

- 日期；
- 这天有日记的人的**头像**：圆圈里放显示名的第一个字（中文取第一个汉字，拉丁字母取首字母大写），颜色用这个人在空间里的作者颜色；有日记但还没有文字时画成空心圆；以后有头像图片时直接替换；
- 两篇里**任意一篇**有列表未读（D2）时显示一个圆点；
- 摘要与最后修改时间，沿用现有卡片的规则。

只有对方有、V 没有的日期也列出；对方未共享或不存在的日记不产生卡片，也不在 V 的卡片上留任何痕迹（依据 6）。没有绑定的用户只看到自己的日记。

**刷新**：进入首页、切回页面、从日记返回时重新获取；首页停留时每 45 秒重新获取一次。不加推送通道：列表本来就有约两到五分钟的冷静期，推送带来的及时性被抵消，却要新增一条按用户的实时通道和它的权限边界。

**接口**：在 `packages/contracts` 新增两个路由，只读，经获准状态读取入口取对方日记：

| 路由 | 用途 |
| --- | --- |
| `GET /api/days?before=<date>` | 一页日期（每页 20 天），`nextBefore` 翻页 |
| `GET /api/days/:date` | 一天的状态，日期页和单篇页的"TA 也写了这天"检查用 |

一天的结构：

```ts
type Day = {
  diaryDate: string; // YYYY-MM-DD
  mine: {
    diaryId: string;
    excerpt: string | null; // 同 DiarySummary
    updatedAt: string;
    hasText: boolean;
    unread: boolean; // 列表判定（D2）
    sharedWithPartner: boolean; // 这篇此刻处在对方可读的当前共享轮次中
  } | null;
  partner: {
    diaryId: string;
    epochId: string;
    share: 'live' | 'frozen';
    excerpt: string | null;
    updatedAt: string; // 最后一次获准提交
    hasText: boolean;
    unread: boolean;
  } | null;
};
```

`sharedWithPartner` 只告诉 V 自己日记的共享状态，不涉及对方；`partner` 不含对方的共享范围或任何未共享日记的信息。按日期合并在服务端完成，因为前端合并两个各自分页的列表容易漏掉或重复日期。首页改用新接口后，`GET /api/diaries` 是否还有使用者在落地时确认，删除公开接口前先问（AGENTS.md）。

### D4：打开日记停在开头，由用户选择跳到未读

- **打开时**停在正文开头，不自动滚动（依据 4）。有未读时在顶部显示"有 N 处新内容 · 跳到第一处"。N 是打开那一刻正文中连续未读字段的段数，之后不随对方打字变化。
- **"下一处未读"**在有未读时始终可用，按正文顺序跳到当前视野之后的下一段未读；日期页上按显示顺序跨篇。
- **方向提示**：视野上方或下方有未读时，实时显示"↑ 上面有新内容"或"↓ 下面有新内容"，只提示方向，不显示数量，避免对方每打一个字数字跳一次。
- **跳到之后**，这段未读停在视野从上往下约三分之一处，短暂高亮后淡出；不留永久标记，也不用作者底色（规格 §8.1）。
- 未读标记、提示与跳转都不改变正文、不产生提交，也不让对方知道（依据 6）。
- "只看我的文字"开启时，对方的字被隐藏：不显示对方的未读提示，也不把被隐藏的字计为已读（PR #30）。

已读仍按内核 D15 记录：前台页面上露在视野中约一秒的对方文字计为已读。

### D5：远端修改、过滤与视图切换时锚定阅读位置

不依赖浏览器的滚动锚定（整篇是一个段落，锚定无法生效，WebKit 的支持也不确定），由页面自己做：在一次远端更新应用前选定**锚点字**，记下它的相对位置（与远端光标相同的 `Y.RelativePosition`）和它在视野中的纵向偏移；更新应用后滚动页面，使它回到原偏移。

| 情况 | 锚点 |
| --- | --- |
| 编辑器有焦点，且光标在视野内 | 光标所在的字 |
| 其他情况 | 视野顶端第一个可见的字 |
| 锚点字被删除 | 相对位置自然落到相邻字 |

同一机制用于切换"只看我的文字"和切换日期页的视图（D6）：切换前锚定视野顶端第一个在切换后仍可见的字。V 停在文末、对方在文末继续写时不自动跟随，只显示方向提示（规格 §6"不强制滚到对方位置"）。适用于本人日记、对方共享的日记和日期页；历史预览是静态的，不需要。

### D6：对方共享了某一天时，这一天打开为日期页

**何时打开日期页**：这一天有对方的可读日记时，点卡片打开日期页（`/days/:date`）；只有 V 的日记时打开现有的单篇页面。

**布局**：两篇上下排列，任何宽度都相同（依据 8）。不做左右并排：两篇长度通常不同，整页滚动时短的一栏下方留空，各自滚动又会出现页中套滚动条，锚定和跳转都更复杂；而在对方文字中插话发生在对方那篇内部，用不到左右对照。每篇上方有标题行：头像、名字，以及状态：

| 状态 | 标签 |
| --- | --- |
| V 的日记不在对方可读的当前共享轮次中（`sharedWithPartner` 为 false） | 仅自己可见 |
| 对方的日记已停止共享 | 已停止共享，内容不再更新（沿用现有说明） |

页面顶部有"跳到 TA 的 / 跳到我的"。

**顺序**：默认按空间位次（与作者颜色同源，spaces-and-invitations D1 的实施默认）。每人可以用"交换顺序"按钮调换，只记在这台设备的浏览器存储里；存储不可用时回到默认顺序。

**两篇都能直接写**：每篇是一个独立的现有单篇会话（编辑器绑定、本机日志、发送、同步连接、已读上报），保存状态、恢复草稿、个人撤销、光标、未读各自独立；撤销只作用于有焦点的那篇。沿用现有协议，每篇一条同步连接，不为日期页改协议。对方那篇按现有规则：当前轮次可写本人文字，停止后只读。

**视图切换**：两篇**都有文字**、且对方那篇共享给了 V 时，页面顶部显示"双人 | 我的 | TA 的"，每次打开都是"双人"。切换只隐藏另一篇，不卸载它，所以待发内容、撤销栈和光标不受影响（与历史预览相同的做法）；被隐藏的那篇不计已读。V 自己那篇有没有共享给对方，不影响能否切换，只决定"仅自己可见"标签。

**V 还没有这一天的日记**：V 那一侧显示"写这天"，点击后用现有的补写过去日期接口创建，并在原页面开始写，不跳转。这一天在 V 的时区还没到时（对方在更早的时区），不显示按钮，改为"你这边还没到这一天"，因为服务端拒绝未来日期。

**打开后不自动改变布局**：V 正在单篇页面写，对方这时共享了同一天，页面不切换成日期页，只在顶部提示"TA 也写了这天 · 切到双人页"，由 V 点击。单篇页在切回页面时和每 45 秒用 `GET /api/days/:date` 检查一次。

**"只看我的文字"**：一个开关同时作用于两篇。

**历史**：每篇从自己的标题行进入各自的历史（内核 D6"双日记页面分别进入对应日记"）。

### D7：作者保护在两个编辑器之间同样成立

单篇编辑器已覆盖打字、删除、回车、剪切、粘贴、输入法、撤销重做、退格和 Delete 跳过、按住连删停在边界、拖入拦截（EDIT-04～09、11）。日期页新增的情况：

| 操作 | 结果 |
| --- | --- |
| 选区从一篇延伸到另一篇后删除、剪切或输入 | 两篇正文都不变 |
| 从一篇拖到另一篇 | 被拦截（现有拖入规则） |
| 撤销、重做 | 只作用于有焦点的那篇 |
| 从对方那篇复制，粘贴到自己那篇 | 成为当前用户写的纯文本（EDIT-08） |

浏览器测试用程序模拟键盘，输入法与剪贴板只在 jsdom 中测过（`apps/web/README.md`）。本文交付前在 Chromium、Firefox、WebKit 中用真实中文输入法和系统剪贴板手动验证一遍，结果写入 `docs/validation/`。手机上的长按连删（EDIT-05 手机部分）随手机支持推后。

## 失败与恢复

| 情况 | 结果 |
| --- | --- |
| 列表请求失败 | 沿用现状：说明暂时无法读取列表；不显示过期的未读圆点 |
| 某篇日记的存储正文校验失败 | `excerpt` 为 null，`unread` 为 false，卡片显示暂时无法读取，其他卡片正常 |
| 已读上报失败 | 这些字保持未读，下次检查重报（现有行为） |
| 锚点字在更新中被删除 | 落到相邻字；偏移最多一行 |
| 日期页上一篇加载或同步失败 | 只有这一篇显示失败与恢复方式，另一篇照常可读可写 |
| 日期页打开时对方停止共享或解绑 | 对方那篇按现有通知转为只读冻结，标"已停止共享"，V 那篇不受影响 |
| "写这天"创建失败 | 按钮保留，显示失败原因；未来日期被拒时改为"你这边还没到这一天" |
| 定时检查失败 | 保持上一次的状态，不提示错误，下一次再试 |
| 浏览器存储不可用 | 交换顺序不被记住，回到默认顺序 |

## 不变量

1. 未读只针对查看者有权读到的当前正文中另一位作者写的字；自己写的字不是自己的未读。
2. 未读按字的身份判定：不在查看者已读区间里的候选字即未读；不以版本号、提交号或时间比较代替。
3. 同一时刻的数据下，列表判定有未读的日记，日记内判定至少有一处未读。
4. 列表只计入所在提交不晚于最近一个历史点的字；最近一个历史点之后的提交不改变列表的未读标记。
5. 删除后不在正文中的字不产生未读，不存在无法跳到的未读。
6. 打开日记不自动滚动到未读；跳转只由用户操作触发。
7. 被"只看我的文字"或视图切换隐藏的文字不计为已读。
8. 远端更新、过滤切换和视图切换前后，锚点字在视野中的纵向偏移不超过一行。
9. 日期页上的两篇是两个独立会话：一次编辑、撤销或粘贴不同时改变两篇。
10. 对方未共享或不存在的日记不产生卡片、头像、占位或任何可区分的信息。
11. 查看者自己的日记不在对方可读的当前共享轮次中时，日期页标出"仅自己可见"。
12. 列表与日期接口只经获准状态读取入口取对方日记，响应不含对方的共享范围。
13. 页面打开后不因对方新增日记自动改变单人或双人布局。
14. 未读标记、提示与跳转不产生正文提交，也不向对方暴露。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **列表按提交时间粗算**：对方最后提交晚于我最后阅读即有未读 | 最便宜，不用构建正文 | 对方只删字或我只读一半时出错，违反依据 2 |
| **维护一张未读表**，提交和已读上报时更新 | 取列表最快 | 写入路径变重，多一处必须保持一致的状态；两人规模不需要（依据 9） |
| **列表实时推送** | 对方一写就亮 | 冷静期（依据 3）已有两到五分钟延迟，推送的及时性被抵消；要新增按用户的实时通道和权限边界 |
| **列表不加冷静期** | 实现更简单，新内容更快出现 | 对方写了又删、或刷新恰好碰到正在写时，圆点时有时无，违反依据 3 |
| **打开即跳到第一处未读**（聊天软件做法） | 少点一次 | 用户要求由自己选择（依据 4）；文档类产品都不自动跳 |
| **记住"上次读到的位置"** | 长文可以续读 | 日记通常短；用户真正要找的是新内容，D4 已覆盖；跨设备需要新表和接口；技术上可行（同 D5 的锚定），以后需要时单独加 |
| **左右并排** | 同一天两篇可以对照 | 两篇高度不同，整页滚动留空、分栏滚动嵌套；窄屏仍需上下；插话发生在对方正文内部，用不到对照（依据 8） |
| **日期页只读**，写时进单篇页 | 一个页面只有一个编辑会话，实现简单 | 用户要求在日期页直接写（2026-10-28），跳页失去意义 |
| **保留两个分开的列表** | 不需要新接口 | 用户要求一个列表；前端合并两个分页列表容易漏或重复日期 |
| **依赖浏览器的滚动锚定** | 不写代码 | 整篇一个段落时无效，WebKit 支持不确定，违反依据 5 |

## 风险与代价

- 每次取列表都要为一页的每篇日记构建正文并比对已读区间。日常长度下预计无感；若列表变慢，先缓存（按日记版本和已读区间版本），仍不够再考虑未读表。
- 冷静期让列表比日记里晚两到五分钟知道新内容。
- 日期页同时运行两个编辑会话和两条同步连接，内存和渲染开销翻倍；十万字级别的日记在 WebKit 上已慢于目标，两篇并排时更明显。
- 交换顺序只记在本设备：换设备回到默认顺序，两人说"上面那篇"时可能指的不是同一篇；作者颜色不变，不会混淆是谁写的。
- 已读只能判断文字是否露在屏幕上，不能判断是否真的被看过：专心打字时，屏幕另一角对方的字也会被计为已读。

## 验收标准

- READ-01：B 在 A 的旧日记中间插字，冷静期后 A 的列表在那天亮圆点，打开后"跳到第一处"到达该处；A 自己的输入不产生未读。
- READ-02、READ-03、READ-06：沿用内核 D15 的已读规则，在新的提示与跳转下重新验收。
- READ-04：多设备合并后列表与日记一致；光标、重复同步不产生未读；删除的字不留下无法跳到的未读。
- READ-05：任何接口和页面都不出现对方的阅读状态。
- SYNC-06：对方在上方连续插入长段落时，锚点字的偏移不超过一行，焦点不被抢走。
- DATE-03 拼接部分：日期页两篇保留各自 ID 与编辑边界，跨篇的操作按 D7 表格。
- EDIT-11、EDIT-08：真实输入法与剪贴板的三浏览器手动记录。
- 不变量 1～5、10、12 由 API 的真实 PG 测试验证；6～9、11、13、14 由 web 测试与端到端测试验证，测试标题带 `[adr:unread-and-day-page#N]`。
