# 列表未读由字的写入、删除与已读记录直接算出，提交时记下删除的字

- 状态：提议
- 日期：2026-11-01
- 决策者：Ray
- 范围：领域
- 关联：依赖 unread-and-day-page；依赖 diary-collaboration-kernel；取代 book-frontend-workspace 的D5 服务端查找

每次正文提交在同一事务里多记一样事实：这批编辑删掉了哪些字的编号。有了它，「对方写的、已成历史、还在获准正文里、我没读过的字」就是三类编号区间相减，PostgreSQL 一条查询就能判定，不用重建正文。下一处未读（`GET /api/days/next-unread`）和日期列表的未读圆点改用这一判定，去掉 API 进程里的判定缓存，所以进程刚启动、对方一次共享几年时也一样快。未读的定义不变，仍按字的身份判定（unread-and-day-page D2）；本文只换算法和它需要的记录。日记里的实时未读仍由浏览器计算，不受影响。

## 背景与问题

[书页工作区 D5](./2026-11-01-book-frontend-workspace.md#d5列表未读与下一处未读保持现有语义) 让服务端查找某方向最近的有未读日期。全部已读时要走完全部候选；现有实现每篇都要重建正文才知道哪些字还在，再与已读区间比。实测三年、2,190 篇、1,643 篇候选时，判定缓存已满 p95 为 209ms，缓存为空约 6.2 秒（[实测](../validation/book-frontend-next-unread-2026-11-01.md)）。缓存在 API 每次启动后都是空的；对方一次共享几年，新出现的那些篇也没有缓存。

聊天和文档产品的未读都不读内容：它们比较写入时就记下的编号或版本（如 Discord 的已读消息 ID、Google Docs 的上次查看版本）。我们不能照搬，因为未读按字算：打开不等于读过，删字不算新内容（unread-and-day-page 不变量 2、5）。但每个字有永不重复的编号，数据库里已经有每次提交插入的字（`diary_character_ranges`）和每人读过的字（`diary_read_ranges`）。只差「哪些字已被删掉」：对方打错又删掉、你从未见过的字，留在「写入 − 已读」里，看起来像未读。真实写作几乎每篇都有这样的字，所以只用现有两张表做粗筛，几乎每篇仍要重建。

## 决策依据

1. 未读按字的身份判定，定义与 unread-and-day-page D2 一致：两种算法对同一数据必须给出同一结果。
2. 查找耗时不能取决于进程里有没有缓存：API 刚启动、一次共享几年之后，按钮出现的时间与平时一样。
3. 对方私人期间的写入、删除及其存在痕迹不能经任何输出泄露（内核依据 3、不变量 3）。
4. 状态在产生它的地方记对：写入的事实在提交事务里记下，读取时只推导，不另维护一份需要同步的结论。
5. 两人规模；改动尽量小，不新增依赖。

## 决策

### D1：每次正文提交记下它删除的字

新表 `diary_deleted_ranges`：

| 列 | 意思 |
| --- | --- |
| `diary_id`、`version` | 哪篇日记、哪次提交（外键到 `diary_commits`） |
| `client_id` | 被删的字是哪个 clientID 写的 |
| `clocks` | 被删的 clock 区间，`int8multirange` |

主键（`diary_id`, `client_id`, `version`）。提交服务在 `insertCommit` 的同一事务里，与 `diary_character_ranges` 一起写入：取本批每个已接受更新的删除集（`Y.decodeUpdate(update).ds`），按 clientID 合并成一个 multirange，一个 clientID 一行。在 `packages/collab` 的 `authorship.ts` 里，与 `insertedRanges` 并列新增纯函数 `deletedRanges(updates)`。

- **删除集里有什么就记什么**：同批插入又删掉的字、非文字项（格式等）的删除也会出现。它们要么从未进入写入记录，要么不是文字，多记不影响 D2 的结果，不必过滤。
- **开放共享的 seq 0 基线提交不写**：基线由当时已提交的状态生成，保留原 ID（内核 D4）。其中被删的字，在更早的提交里已经记过。
- **记录只增不改**：Yjs 的删除不可撤销，「恢复」只能输入新字。所以这张表与 `diary_character_ranges` 一样，是提交时确定、以后不变的事实。

原因：依据 4。它只在提交时写一次；已读上报不碰它，也没有需要和它保持一致的结论，与 unread-and-day-page 否决的未读表不同（见备选方案）。

### D2：列表未读是三类编号区间相减

查看者 V、一篇日记 d 的一份获准正文，由（起点, 边界版本 `bound`）确定，最近一个历史点所在提交为 `cutoff`（`cutoff` ≤ `bound`，unread-and-day-page D2）。按 clientID 分别计算：

```
写入(c) = d 中 clientID c 的插入区间，所在提交 version ≤ cutoff，c 绑定的作者 ≠ V
删除(c) = d 中 clientID c 的删除区间，所在提交 version ≤ bound
已读(c) = V 在 d 上 clientID c 的已读区间
列表未读 ⇔ 存在 c，使 写入(c) − 删除(c) − 已读(c) 不为空
```

没有历史点时（`cutoff` 为空）不计入任何字。为什么与重建正文的判定相等：

- **版本是一条直线**：一篇日记的提交按 version 全序，每批只能提交到当前起点（起点不符即 `STALE_CONTEXT`），新起点的基线取自切换时的已提交状态。所以「版本不晚于 `bound` 的正文」就是全部 version ≤ `bound` 的提交依次作用的结果，包括更早起点里写下的字。
- **获准正文里的字** = 插入版本 ≤ `bound` 的字 − 删除版本 ≤ `bound` 的字。每个可见的字都有插入记录：普通提交为每个新字写记录，基线不产生新字，没有绑定作者的 clientID 会让作者判定直接失败（`authorRuns`）。
- **现有判定**把插入版本晚于 `cutoff` 的字视为已覆盖。剩下的，正好是插入版本 ≤ `cutoff` 的字。

冻结的共享：`bound` 是停止时的版本，之后私人期间的插入和删除都在 `bound` 之后，不参与计算。重开后，私人期间写下、现仍保留的字，插入版本早于新的 `cutoff`，按 D15 表格算未读。查询把一批候选的（日记, `bound`, `cutoff`）作为数组传入，用 `range_agg` 与 multirange 减法在一次查询里判定；`bound` 与 `cutoff` 仍按内核 D6 的规则，从提交时间线算出。

原因：依据 1、2、3。结果只是「这份获准正文有没有未读」，与现在相同；删除记录本身不出服务端。

### D3：日期列表圆点与下一处未读共用这一判定，去掉进程内缓存

`apps/api/src/reader` 只保留一处「列表未读」判定，即 D2 的查询：

- `GET /api/days` 的每篇 `unread` 用它。正文仍要重建，因为摘要和 `hasText` 需要，未读不再从重建的正文里算。
- `GET /api/days/next-unread` 用它，从近到远分批判定候选，遇到第一篇有未读就停。

书页工作区 D5 中「每个（查看者，日记）的判定结果缓存在 API 进程内存中……」一段由本条取代；同一段的其余部分，包括 SQL 先排除不含对方文字的日记、接口形状和前端行为，都不变。

原因：依据 1、2。两处共用一个判定，圆点和跳转不会互相矛盾；不再有缓存，就没有冷启动。

### D4：已有日记一次性补齐删除记录

迁移只建表。补齐由一次性脚本 `apps/api/scripts/backfill-deleted-ranges.ts` 完成：对每个已有正文提交（seq > 0），解出其 `delta` 的删除集，按 D1 写入；已有的行跳过，可重复运行。现在还没有真实日记，只有开发和测试数据库需要跑；写进 `apps/api/README.md` 的部署步骤。

原因：依据 1。没补齐的旧删除会让列表误亮；只影响已有数据，补一次即可。

## 失败与恢复

| 情况 | 结果与恢复 |
| --- | --- |
| 写删除记录失败 | 与提交同一事务，整批不提交，客户端按现有失败重试；不会出现有提交、无删除记录的状态 |
| 旧数据未补齐 | 列表可能误亮或跳到读不到新内容的日期；运行 D4 的脚本即恢复 |
| 正文存储校验失败（`VersionUnreadable`） | 圆点仍按记录计算，可能亮；打开时按现有方式显示无法读取，不伪造正文 |
| 查询失败 | 与现在一样：该方向按钮不出现、列表请求报错，下次刷新重查 |

## 不变量

1. 每个被接受的正文提交，在同一事务里为它删除的每个字记下（日记, 版本, clientID, clock）。
2. 同一数据下，任一查看者与任一获准正文的列表未读，与从获准正文重建判定的结果相同。
3. `GET /api/days/next-unread` 返回的日期，`GET /api/days` 在该日期标有未读。
4. 判定列表未读与查找下一处未读不重建正文，也不依赖进程内状态。
5. 删除记录不出现在任何接口响应、Google 可读副本或日志中；查看者得到的结果只取决于获准正文和本人的已读区间。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **保留缓存，API 启动时预热** | 改动最小，接口不变；缓存已满时已达标 | 对方一次共享几年、缓存因任何原因清空时，仍要逐篇重建数秒（依据 2）；多一份需要判断何时失效的状态（依据 4） |
| **分段查找，带续查游标** | 每次请求耗时有上限 | 总耗时不变，按钮照样晚出现；契约和前端多一个「还在找」的循环（依据 2、5） |
| **只用写入 − 已读粗筛，再重建确认** | 不加表 | 对方打错又删掉、查看者没见过的字会永远留在差集里，真实日记几乎篇篇都要重建，等于没筛（依据 2） |
| **维护未读表或汇总**（如 Matrix 的 `event_push_summary`），提交与已读上报时更新 | 取列表最快 | unread-and-day-page 已否决：写入和已读上报两条路径都要维护，多一处必须一致的结论；本方案只在提交时写不变的事实，结论仍在读取时推导（依据 4） |
| **按版本或时间比较**（文档产品的做法） | 最便宜 | 打开不等于读过，删字不算新内容；违反 unread-and-day-page 不变量 2（依据 1） |
| **把删除写进查看者的已读区间** | 不加表，现有查询即可 | 伪造了阅读，内核 D15 明确不允许；已读区间会同步到浏览器，暴露对方删字的位置（依据 1、3） |

## 风险与代价

- 每次提交多写最多几行；删除集通常很小。三年两人的量级是数十万行以内，按主键前缀（`diary_id`）读取。
- 以后若出现绕过提交服务改正文的路径（运维修复、导入），必须同样写删除与插入记录，否则 D2 的结果会错；不变量 1、2 的测试是护栏。
- 如果以后加入回滚或分支（内核目前明确没有回滚），「版本是一条直线」不再成立，D2 要重新论证。
- 日期列表仍为摘要重建正文，每页约 261ms 不变；本文不处理。

## 落地顺序

1. **记录**：迁移建表（`npm run db:generate -- --name deleted_ranges`），`deletedRanges` 纯函数及其单元测试，提交服务在同一事务写入，补齐脚本。完成条件：新提交带删除记录；脚本在测试库上重复运行结果相同。
2. **判定**：`reader` 里实现 D2 的批量查询，`days` 与 `nextUnread` 改用它，删除判定缓存和覆盖哈希。完成条件：对照测试（随机插入、删除、部分阅读、开放、停止、重开、历史点前后）中，新判定与重建判定逐篇相同；现有 days 与 next-unread 测试全部通过。
3. **实测**：`measure-next-unread.ts` 的数据改得更像真实写作：每篇分多次操作写入，含删字，对方有未读的删字。测进程刚启动的第一次与之后多次，目标 p95 不超过 300ms，结果更新到验证文档。
4. **同步文档**：`apps/api/README.md`（表、部署补齐步骤、不变量、已知限制）、`packages/collab/README.md`（新函数）；书页工作区 ADR 风险一节中「缓存为空」那句改为指向本文。

**自主实现约定**：采纳本 ADR 即批准 D1 的这一张表、一次迁移和补齐脚本，不批准新依赖。实现在一个叠在 PR #54 之上的 PR 里完成。遇到以下情况停下来问：对照测试出现无法用本文解释的不一致；需要改动已读上报或对外接口；实测达不到目标。

## 验收标准

- 提交含删除的批次后，表中出现对应行；提交失败时表中没有（不变量 1，数据库测试）。
- 对照测试：同一数据下，新判定与重建判定对每个查看者、每份获准正文结果相同，包括冻结、重开、私人期间写入后删除（不变量 2、5，数据库测试）。
- 有未读时，`next-unread` 返回的日期在 `days` 中 `unread` 为 true；新建 reader 后的第一次查找不调用正文重建（不变量 3、4，数据库测试）。
- 接口快照与日志中没有删除记录（不变量 5）。
- 实测达到落地顺序 3 的目标并记录在验证文档。
- 测试标题带 `[adr:unread-from-character-records#<编号>]`；运行格式、lint、typecheck、`npm run test:db` 和文档检查。

## 补充信息

- 重新评估条件：加入回滚或版本分支；出现绕过提交服务改正文的路径；删除记录的量使查询超出 300ms 目标。
- 证据：[next-unread 实测](../validation/book-frontend-next-unread-2026-11-01.md)；2026-11-01 与用户讨论业界未读做法（Discord、Telegram、Zulip、Matrix 的聊天未读；Google Docs、Word、Notion、Quip 的文档改动提示）及现有表能否直接判定。
