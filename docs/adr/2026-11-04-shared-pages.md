# 共享页面是两人一起写的纯文字页面，每人只改自己的字，标题与删除两人都能做

- 状态：已采纳
- 日期：2026-11-04
- 决策者：Ray
- 范围：领域
- 关联：依赖 space-records；依赖 diary-collaboration-kernel；依赖 digital-paper-interface；取代 space-records 的D3、D6 的作者限定与D8 的已读规则

共享页面让两个人随时新建一页，一起写计划、清单和随手记。页面属于双人空间，第一版是平铺列表里的纯文字页面，没有目录。正文沿用日记的协同内核：字符级作者不可变，每人只能改自己写的字。标题和删除是页面级操作，两个人都能做，并记下是谁做的。解绑后两人只读，原来的两人重绑后恢复。页面不进 Google 可读副本，未读第一版只做页面级圆点。

本文不负责：可勾选的清单、加粗与标题样式、目录、页面历史、恢复已删除的页面、按字的未读；见面计划的设计（它已采纳，排在本功能之后）。

## 背景与问题

Ray 2026-10-30 提出：见面计划等功能的具体形式还不明确，先在自由页面里实践一段时间再定。2026-11-04 Ray 决定共享页面先于见面计划。

需要回答的问题：

- 两个人写同一页，能不能改对方写的字？
- 页面谁能新建、改标题、删除？删除时对方写的字怎么办？
- 解绑后页面怎么办？要不要进 Google 可读副本？
- 对方写了新内容，我怎么知道？
- 日记的协同内核按"日记主人"和"共享轮次"判断权限，页面没有主人，也没有轮次，内核怎么复用？

已有的约束：规格 §2 的 INV-01（每个人只能改自己的文字）；space-records 的共用规则；内核的服务端校验拒绝删除别人写的字（`FOREIGN_DELETE`），也拒绝格式和嵌入内容；`diaries` 每人每天一行，日记列表、未读与 Google 副本都从这张表出发。

## 决策依据

1. 两个人在页面里和在日记里遵守同一条规矩：各自说过的话由各自负责（规格 INV-01，Ray 2026-11-04 确认）。
2. 页面是两人共有的东西，不是某一个人的：标题和要不要留这一页，两个人都能决定（Ray 2026-11-04 确认）。
3. 一方的删除不能让另一方写的东西无声消失（space-records 依据 4）。
4. 解绑后两人都能看、都不能改，原来的两人重绑后恢复（规格 §3.1，Ray 2026-11-04 确认沿用）。
5. 数据恢复由服务器备份负责；每人 Drive 只放给人读的日记副本（Ray 2026-11-04 确认页面不进 Drive）。
6. 先做能用的最小版本，在实际使用中再决定要不要清单、目录和按字未读（Ray 2026-11-04 确认）。
7. 页面绝不能混进日记列表、日记未读或 Google 副本；这一点靠结构保证，而不是靠每条查询记得过滤。
8. 作者、操作人与"已保存"由服务端在 PG 提交时确定（ADR-0003、ADR-0006）；待发内容不能无声丢失（kernel D7）。
9. 没有消费者的东西不预建（AGENTS.md）。

## 决策

### D1：页面属于双人空间，第一版是平铺列表，没有目录

一页是一条 space-records 记录，类型 `shared_page`，带 `spaceId` 与创建时的 `periodId`。两个人都能新建，不限数量。列表按最后更新时间排列，最近的在前，更新时间取最后一次正文提交或改标题中较晚的一个。第三人一律按不存在处理；从未绑定过的账号看不到入口（space-records D2）。

新建时立刻打开空白页，标题可以留空，显示为"未命名页面"。标题去掉首尾空白后最多 60 字。

不做目录（Ray 2026-11-04 决定）：两个人的页面一开始不多，靠排序和标题就能找到；目录要回答谁能移动、删目录时页面怎么办、解绑后怎么显示。以后要加，给 `shared_pages` 加一个可空的目录字段即可，不需要现在预留。

原因：依据 6、9。

### D2：正文是纯文字，每人只改自己写的字

页面正文就是内核的 `Y.Text('body')`，校验规则不变：每个字的作者不可变，只能删改自己写的字，不接受格式与嵌入内容。界面按作者显示颜色，和日记一致，支持本人撤销与对方光标。

| 想做的事 | 第一版怎么做 |
| --- | --- |
| 列清单 | 手打文字，每行一条 |
| 改对方写的字 | 不能；可以在旁边写，或请对方改 |
| 划掉对方写的一条 | 不能；可勾选的清单留给以后的 ADR |
| 删掉整页 | 能，两人都能（D3） |

原因：依据 1、6。这与 Google Docs 不同，是有意的选择：放开互改要给页面单独放宽校验，还要回答改过的字算谁写的。

### D3：标题与删除两人都能做，并记下是谁做的

这是对 space-records 作者规则的例外，只适用于共享页面。其余规则（作者不可变、绑定中才能写、历史只追加、请求幂等）不变。

- **改标题**是一个动作（space-records D4，动作种类 `renamed`）：页面行保存当前标题、`title_by`、`title_at`，同一事务追加历史。带 `expectedRevision`，两人同时改时后到的得到 `RECORD_STALE`，刷新后再改。
- **删除**是软删除，写法与心愿相同，只是页面服务不调用 `authorOnly`。删除后两人的列表都不再显示，服务端保留全部数据，界面不提供恢复（space-records D6）。
- **删除前确认**：弹窗说明"删除后两人都看不到，也不能恢复"；对方在这一页写过字时，再说明"TA 写的内容也会一起消失"。
- **删除记录**：对方写过字或改过标题的页面，被删除时对方看到一条删除记录，例如"A 删了'旅行清单'（你写过）"，并计入对方未读。

"写过字"由动作种类 `wrote` 表示（D5），所以删除记录直接沿用 space-records 的 `deletionNotes`，不另写判断。

原因：依据 2、3。一页里常有两个人的字，归属创建者会让一方替另一方决定去留；代价是误删风险更高，由确认弹窗和删除记录承担。

### D4：解绑后两人只读，不进 Google 可读副本

沿用 space-records D5、D7：只有存在未结束的绑定期间时才能写正文、改标题、删除或新建；解绑后两人都能读全部页面，界面显示"已解绑，记录只读"，编辑器不可编辑；原来的两人重绑后恢复可写。解绑时没发出去的内容转为可复制的草稿，不在重绑后自动重放。

页面不写入 `backup_outbox`，也就不进 Google 可读副本；数据库的服务器备份照常覆盖。

原因：依据 4、5。

### D5：未读第一版只做页面级圆点，打开页面就算读过

对方新建、改标题、写了正文、删除自己动过的页面时，这一页对你是未读：列表里这一页带圆点，导航的"共享页面"入口也亮圆点。打开这一页，圆点就清除；页面开着时对方继续写的内容，约每 30 秒上报一次看过。不做"下一处未读"，不按字标记。

**这是规格 §8.1 和 space-records D8 "看到才算读过"的例外**，只适用于共享页面。代价是打开了但没读到底，圆点也会消失。接受这一点，因为页面是一起写的工作文档，不是要逐字读的日记（Ray 2026-11-04 确认）；要按字未读时，沿用日记的 `read-tracker` 另写 ADR。

未读沿用 space-records D8 的序号机制（`space_actions`、`space_reads`、`mark`），不新建表。正文提交不是每次都写历史，而是用 `wrote` 动作表示"对方又写了新内容"。一次提交在事务里按下面的规则最多追加一条 `wrote`：

```text
作者在这一页还没有 wrote                      → 追加（"写过字"也由此而来）
对方的 space_reads 已看到作者最新的 wrote     → 追加（下一轮未读）
其余情况（对方还没看到上一条）                → 不追加，圆点本来就亮着
```

`wrote` 的 `request_id` 用这次提交的 `batchId`，`request_digest` 用批次摘要。

原因：依据 6、9。这样写一千个字只产生一条历史，直到对方下一次看过；入口圆点、`mark`、`POST /api/space/seen` 都不用改。

### D6：`documents` 是提交链的父表，日记和页面各指向它

新增 `documents` 表，保存提交链共有的状态；`diaries` 与 `shared_pages` 各自用主键指向它：

```text
documents(id, version, generation_id, created_at)
diaries(id → documents.id, owner_id, diary_date, created_timezone, created_at)
shared_pages(id → documents.id, 共用记录列, title, title_by, title_at)

diary_generations.diary_id、diary_client_bindings.diary_id → documents.id
diary_commits、diary_operations、diary_character_ranges、diary_snapshots：不变
share_epochs、diary_read_ranges → diaries.id：不变
```

日记专有的查询都从 `diaries` 出发，页面不在这张表里，所以不可能出现在日记列表、日记未读、共享轮次或 Google 副本里，不需要在任何查询上加过滤条件。`diary_*` 子表和线上字段 `diaryId` 保留原名，含义扩大为"文档 ID"，这样同步协议、本机日志、发送器都不用改；代价是名字不准，在表注释与 `packages/contracts/src/sync.ts` 里写明。

原因：依据 7、9。见备选方案。

### D7：协同内核只多一条按空间绑定判断的路径

`packages/collab`、`diary_*` 子表、本机日志、发送器、同步客户端和编辑器绑定都不改。`commit`、`ws/sync`、`reader` 里判断权限的地方，从"主人或轮次接收者"变成按文档种类分支：

| 判断 | 日记 | 共享页面 |
| --- | --- | --- |
| 谁能读、订阅 | 主人；对应轮次的接收者 | 空间的两个人，页面未删除 |
| 谁能提交 | 主人；活跃轮次的接收者 | 空间的两个人，页面未删除，有未结束的绑定期间 |
| 不能提交时 | `STALE_CONTEXT` 或 `NOT_FOUND` | 已解绑 `SPACE_READ_ONLY`；已删除或第三人 `NOT_FOUND` |
| 提交的回执 | 提交者随时可查 | 同左，解绑、删除后仍可查 |
| 登记备份 | `registerBackups` | 不登记 |
| 提交后追加 | 无 | 按 D5 追加 `wrote` |

页面只有一个代（generation），基线是空文档，不开轮次，提交的 `epoch_id` 恒为空，不做快照以外的代切换。删除的字和日记一样留在提交记录里。

**锁的顺序只有一种**：先取绑定期间的共享锁，再取文档锁。`withDiaryLock` 改名 `withDocumentLock`；文档是页面时，它先不加锁读出不可变的 `space_id`，以 `FOR SHARE` 锁住未结束的绑定期间（没有就标记只读），再 `FOR UPDATE` 锁文档行。改标题与删除在 `spaceRecords.write` 的事务里再取文档锁，所以删除与提交按文档锁排序：提交要么在删除之前成功，要么得到 `NOT_FOUND`。解绑先写绑定期间再冻结日记，也是这个顺序。

原因：依据 8。反过来取锁时，`FOR SHARE` 会排在等待中的解绑后面，提交、删除与解绑三方可能死锁；`spaceRecords.write` 已经先取绑定期间，所以提交也先取。

## 数据与模块

**数据**（迁移 `0011_documents` 建 `documents` 并改 `diaries`，`0012_shared_pages` 建 `shared_pages` 并登记类型与动作）：

| 表 | 内容 |
| --- | --- |
| `documents` | D6 的父表；用现有 `diaries` 的 `id`、`version`、`generation_id`、`created_at` 回填 |
| `diaries` | 去掉 `version`、`generation_id`，`id` 指向 `documents` |
| `shared_pages` | space-records 的共用列（`private_to` 恒为空），`title`（0～60 字，默认空串）、`title_by`、`title_at` |
| `space_changes`、`space_actions`、`space_reads` | 检查约束登记记录类型 `shared_page` 与动作 `renamed`、`wrote` |

`diaries` 的 `version` 与 `generation_id` 在服务端约 8 处引用，集中在 `store`，都改为读 `documents`。

**接口**（`packages/contracts`，全部 `no-store`）：

| 接口 | 内容 |
| --- | --- |
| `GET /api/shared-pages` | `{ me, partner, readOnly, pages, notes }`：全部页面，最近更新在前，每页带 `id`、`title`、`authorId`、`revision`、`updatedAt`、`unread`、`mark`；`notes` 是删除记录 |
| `POST /api/shared-pages` | `{ requestId, title }` → `{ page }` |
| `GET /api/shared-pages/:pageId` | `{ page, state, generationId, seq, bindings }`，`state` 的形状与 `GET /api/diaries/:diaryId` 相同 |
| `PUT /api/shared-pages/:pageId/title` | `{ requestId, expectedRevision, title }` → `{ page }` |
| `POST /api/shared-pages/:pageId/delete` | `{ requestId }` → `{ deleted: true }` |
| `GET /api/space/unread` | `features` 增加 `sharedPages` |
| `POST /api/space/seen` | `type` 增加 `shared_page`，其余不变 |
| `/api/sync` | 消息不变，`diaryId` 传文档 ID；`SPACE_READ_ONLY` 可作为 `submit` 的错误返回 |
| `GET /api/diaries/:diaryId/receipt` | 增加页面参与者的权限分支 |

**模块**：

- `apps/api/src/shared-pages/`：页面服务，只通过 `space-records` 写入；SQL 在 `apps/api/src/store/shared-pages.ts`。依赖方向与其他功能相同。
- `apps/api/src/commit`、`ws`、`reader`：加 D7 的权限分支。
- `apps/api/src/space-records/`：不改；作者检查 `authorOnly` 本来就由功能服务调用，页面服务改标题与删除时不调用它。
- `apps/web/src/shared-pages/`：列表、页面、标题编辑、删除确认；路由 `/shared-pages`、`/shared-pages/:pageId`；`shell` 的"一起"增加"共享页面"，可见规则与心愿相同。
- `apps/web/src/diary/session.ts`：`createDiarySession` 的取状态与订阅入口改为可传入，日记行为不变，页面传入自己的一组。

## 失败与恢复

| 情况 | 结果 | 恢复 |
| --- | --- | --- |
| 写字时对方解绑 | 提交被拒 `SPACE_READ_ONLY`，页面转只读 | 待发内容转为可复制的草稿；重绑后手动写回 |
| 写字时对方删除页面 | 提交被拒 `NOT_FOUND`，页面显示"这一页已被删除" | 待发内容转为可复制的草稿 |
| 离线写了内容，页面在离线期间被删 | 重新打开时列表里没有这一页 | 列表读本机日志，发现已删除页面的待发内容时显示可复制的草稿 |
| 对方只是开着页面在读，这一页被删或已解绑 | 下一次聚焦或提交时才知道 | 第一版不做实时通知，刷新后显示当前状态 |
| 两人同时改标题 | 后到的 `RECORD_STALE` | 刷新后再改 |
| 响应丢失 | 按 `batchId` 或 `requestId` 查回执或重试 | 与日记、空间记录相同 |
| 提交与解绑并发 | 绑定期间的共享锁排序：提交在解绑之前，或被拒 | 同第一行 |

## 不变量

1. 页面正文的每个字的作者由服务端确定且不可变，只有作者能删除自己写的字；页面不放宽内核校验。
2. 页面属于 `spaceId`；解绑不删除、不移动页面，原来的两人重绑后页面原样可写。
3. 只有存在未结束的绑定期间时，正文、标题、删除与新建才能提交；与解绑并发时，不存在在解绑之后提交的写入。
4. 空间的两个人都能改标题和删除页面，操作人由服务端确定，每次都留下一条只追加的历史。
5. 第三人对页面的任何接口、同步订阅与提交都按不存在处理；已删除的页面对两人的读取都按不存在处理，回执除外。
6. 删除对方写过字或改过标题的页面时，对方得到一条删除记录；删除不物理清除数据。
7. 页面不出现在任何日记列表、日记未读、共享轮次与 Google 可读副本里，也不写入 `backup_outbox`。
8. 一页的 `wrote` 历史每轮最多一条：对方看到上一条之前，继续写不再追加。
9. 对方写了新内容时这一页对你是未读，自己写的不产生自己的未读；打开页面后清除；已读状态不返回给对方。
10. 待发内容在页面解绑或被删除时不无声丢失，都转为本机可复制的草稿。
11. 取锁顺序恒为绑定期间在前、文档在后。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **两人都能改任何字（像 Google Docs）** | 最接近"一起写"，清单能互相划掉 | 违背依据 1；要给页面放宽 `FOREIGN_DELETE`，还要回答改过的字算谁写的 |
| **标题与删除只归创建者** | 完全沿用 space-records D3、D6，不需要例外 | Ray 2026-11-04 否决：页面是两人共有的（依据 2） |
| **第一版就有可勾选的清单** | 清单是主要用途之一 | 内核校验拒绝格式与嵌入，要动协同模型；先用纯文字验证需要（依据 6） |
| **第一版做一层目录** | 页面多时好整理 | 依据 6、9；两个人的页面一开始不多，以后加字段成本低 |
| **页面放进 `diaries`，加种类列** | 不用迁移子表的外键 | 违背依据 7：页面没有日期和主人，每条日记查询都要记得过滤，漏一处就混进列表或 Google 副本 |
| **页面另建一整套 `page_*` 子表** | 与日记完全隔离，名字准确 | 六张表和全部提交链 SQL 要写两份，违背 AGENTS.md 的"一个职责一个归属" |
| **把 `diary_*` 子表和线上字段都改名为 `document_*`** | 名字准确 | 改动面大，协议、本机日志与全部 SQL 都要动，用户没有收益；留到有第三种文档时再说 |
| **按字未读，复用 `read-tracker`** | 符合规格 §8.1，能定位新内容 | 依据 6；列表判定要重建正文（见 PR #55 的讨论），第一版只要知道"这页有新内容" |
| **每次提交都写一条 `edit` 历史** | 不用 `wrote` 的判断 | 两人连续写时历史暴涨，且未读只需要"有没有新内容" |
| **页面进 Google 可读副本** | 用户在 Drive 里也能读 | 依据 5；每种新内容都会增加写入链路的失败情况 |

## 风险与代价

- 两个人都能删除，一方可能误删另一方写的内容；界面不提供恢复，要找回只能由运维从软删除数据里处理。先靠确认弹窗和删除记录，真发生过再做回收站。
- 不能改对方的字，写清单时不如 Google Docs 顺手。这是第一版要验证的点之一。
- 打开就清除未读，可能漏看长页面中间的新内容。
- `diary_*` 表和 `diaryId` 字段名不再准确，读代码的人要知道它们指文档。
- 迁移要动 `diaries` 的列和两个外键，是本功能风险最高的一步，要用真实 PG 测试迁移前后的日记读写。
- 页面删除的字和日记一样留在提交记录里，两人的客户端都可能收到；页面从第一个字起就是共享的，没有私密阶段，所以接受。

## 落地顺序

1. **本 ADR 采纳**：2026-11-04 与 Ray 逐条确认后改为已采纳，`docs/architecture.md` 的 Current decisions 加入本文。
2. **`documents` 拆分**（一个 PR，无用户可见变化）：迁移 `0011_documents`，`store`、`withDocumentLock` 与引用改写；现有日记测试全部通过，加迁移回填的 PG 测试。
3. **服务端**（一个 PR）：迁移 `0012_shared_pages`、契约、页面服务、D7 的权限分支、D5 的 `wrote`、未读汇总，`npm run openapi`，依赖方向规则。
4. **网页**（一个 PR）：`shared-pages` 模块、导航与路由、`createDiarySession` 的入口、草稿恢复；规格 §3、§8.1 与 `docs/acceptance.md` 补上共享页面的条目。
5. 实现后本文转为已实现，路线图与 README 状态行同步。

自主实现约定：本文预先批准 `0011_documents` 与 `0012_shared_pages` 迁移，以及 `checks/modules.json`、依赖方向规则中登记新模块所需的改动；不需要新依赖。第 2 步发现要改协同校验或线上协议时停下来问 Ray。三个 PR 依次叠放，合并前等 Ray 确认。

## 验收标准

- 两人写同一页：各自的字有各自的颜色，互相看到光标，删除对方的字被编辑器和服务端拒绝（API 测试与浏览器测试，不变量 1）。
- 解绑后两人能读不能写，重绑后恢复；并发的提交与解绑没有解绑之后才提交的写入（真实 PG 测试，不变量 2、3、11）。
- 两人分别改标题、删除，历史记下操作人；同时改标题时后到的被拒（API 测试，不变量 4）。
- 第三人的 REST、订阅与提交都得到不存在；已删除页面的读取 404，回执仍可查（API 测试，不变量 5）。
- 删除对方写过字的页面，对方有删除记录与未读；没动过的不提示（API 测试，不变量 6）。
- 页面的 ID 请求日记接口得到不存在；有页面时日记列表、未读与 `backup_outbox` 不变（API 测试，不变量 7）。
- 一人连续提交多次，对方看过之前只有一条 `wrote`，看过后下一次提交再追加一条（真实 PG 测试，不变量 8）。
- 圆点在列表和导航里亮起，打开页面后清除，对方看不到已读状态（API 测试与组件测试，不变量 9）。
- 写字时被解绑或删除、离线后页面已删除，待发内容都能作为草稿复制出来（浏览器测试，不变量 10）。
- 验证某条不变量的测试标题带 `[adr:shared-pages#<编号>]`。
