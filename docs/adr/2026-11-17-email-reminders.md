# 对方的新内容一小时没读、纪念日到了提醒期、备份需要处理时，worker 经 Resend 发一封提醒邮件

- 状态：提议
- 日期：2026-11-17
- 决策者：Ray
- 范围：领域
- 关联：依赖 unread-and-day-page；依赖 server-backup-and-google-docs；依赖 space-records；依赖 two-clocks；依赖 anniversaries；依赖 shared-pages；依赖 authentication-and-sessions；依赖 production-deployment

绑定中的两个人不打开应用也能知道对方写了新东西。后台进程（worker）每 5 分钟检查一次每个人，三种情况发信：

- **有新内容**：对方在日记、共享页面、心愿与礼物里有你一小时没读的新内容，发一封合并的邮件。邮件写明哪些地方有新内容和日记的日期，并附一段约 50 字的日记预览。两封至少隔 4 小时，按你的当地日期每天最多 2 封。
- **纪念日**：纪念日到了你自己设的提醒期，发一封。
- **备份需要处理**：Google 备份需要你处理时，发一封。

三种邮件都不在你的睡觉时段里发。邮件经 Resend 的官方 SDK 发出，正文用 React Email 渲染，发信地址在 `ruihaozhang.com` 的一个子域名上，配好 SPF 与 DKIM。每人在「设置 → 邮件提醒」里分别关掉三类邮件，每封都能一键退订。邮件内容与列表、未读执行同一条隐私边界（SHARE-11）：只写收件人在应用里本来能看到的东西，作者永远不知道对方收没收到、读没读。

本文不负责：轻触"想你了"、时间胶囊与戳团子的通知（各自的 ADR 接到本文的发送机制上）；对方新记或修改纪念日的通知；网页推送与其他渠道；改收件地址；英文邮件。

## 背景与问题

用户于 2026-10-28 决定把邮件通知放在阶段 4：对方写了新内容而你一段时间没读时，发邮件提醒。路线图里"想你了"和时间胶囊都要求对方不打开应用也能知道，因此依赖它。2026-11-07 上线以后，Ray 和搭档每天都在用；对方写了什么，现在只能打开应用才知道。

需要回答的问题：

- 用什么发？发信地址是什么？
- 哪些事件发？
- 多久没读才发？多久最多几封？夜里发不发？
- 邮件里写什么？能不能带正文？
- 在哪里关掉、怎么退订？
- 怎么保证不泄露对方没共享的日记和阅读行为？
- 在哪个进程里跑？崩溃重试时怎么不重复发？

已有的条件：

- **列表未读规则**（unread-and-day-page D2）：只计已成历史的字，按字符身份判定，读取器 `reader` 里已有实现。缓存为空时每人约 6 秒，见[实测](../validation/book-frontend-next-unread-2026-11-01.md)。
- **空间记录的未读序号**（space-records D8，`space_actions` 与 `space_reads`）：心愿、礼物、卡片、纪念日与共享页面都用它；准备中的惊喜因为 `privateTo` 不进对方的未读。
- **两地时间**：每人的时区与作息存在 `users` 上（two-clocks D1、D2）。
- **纪念日**：每人自己的提醒期（anniversaries D3），由服务端算出 `due`。
- **备份**：首页横条的四种原因 `BackupAttention`（server-backup-and-google-docs D9）。
- **worker**：已有后台进程（ADR-0006 第 20 条），取任务用 `FOR UPDATE SKIP LOCKED`，失败时退避重试。
- **邮箱**：领域表不存邮箱，邮箱只在认证层的 `auth_user` 里，是登录用的 Google 邮箱（authentication-and-sessions）。
- **网络**：生产环境的 DNS 与代理都在 Cloudflare 上（production-deployment）。

## 决策依据

1. 对方不打开应用也能知道有新内容；"想你了"与时间胶囊依赖这一点（路线图阶段 4，用户 2026-10-28）。
2. 不打扰：正在用应用时收不到，夜里收不到，一天封数有上限（Ray 2026-11-17 确认一小时、隔 4 小时、每天 2 封、按作息静默）。
3. 邮件与列表、未读执行同一条隐私边界：只写收件人在应用里本来能看到的东西，不透露未共享的日记、共享范围与阅读行为（规格 SHARE-11，Ray 2026-11-17 确认五条规则）。
4. 已读、"已提醒"这类状态由服务端在 PG 里确定（ADR-0003、ADR-0006）。发信是外部副作用：崩溃重试不能让人收到两封，没发出去的也不能记成已提醒。
5. 用户随时能关；退订一键完成，不用登录（RFC 8058，以及 Gmail 与 Yahoo 对发件人的要求）。
6. 用流行、可靠、维护频繁的库，不手写发信协议和 HTML 转义；用的人少的库才要谨慎（Ray 2026-11-17）。
7. 现在只有两个用户：每 5 分钟全量判定一次可以接受，不为它建缓存或实时通道。
8. 没有消费者的东西不预建（AGENTS.md）：推送、更多渠道与更多事件等有了需要再加。

## 决策

### D1：三类邮件

| 类别 | 何时发 | 受「隔 4 小时、每天 2 封」限制 | 需要绑定 |
| --- | --- | --- | --- |
| 有新内容 | 对方的新内容一小时没读（D3、D4） | 是 | 是 |
| 纪念日 | 纪念日进入你的提醒期（D6） | 否 | 是 |
| 备份需要处理 | 首页备份横条出现（D7） | 否 | 否 |

三类都遵守夜间静默（D4）。

**不发的情况：** 对方新记或修改了纪念日（纪念日入口的圆点照旧亮）；对方戳了团子；"想你了"与时间胶囊。最后两个功能各自的 ADR 再决定接不接、怎么接。

原因：依据 1、2、8。三类用同一套设置、退订与发送记录，以后的通知只需要新增一个类别。

### D2：经 Resend 发出，发信地址在独立子域名上

- **SDK：** 用 Resend 的官方 Node SDK `resend`（MIT 协议，每周约 1,800 万次下载，2026-11-13 发布 6.38.1）。它支持幂等键（`idempotencyKey`）和自定义邮件头，自己拼 HTTP 请求的需求因此不存在了。
- **发信地址：** 配置项 `MAIL_FROM`，例如 `Between Pages <remind@mail.ruihaozhang.com>`。用独立子域名，不影响主域名现有的邮件设置。Resend 给出的 SPF、DKIM 记录加到 Cloudflare DNS，另加一条 `p=none` 的 DMARC 记录。
- **回信：** 不设回信地址。邮件页脚写明"这封信由 Between Pages 自动发出"。
- **密钥：** `RESEND_API_KEY` 只放在 worker 的环境里，API 进程不需要它。

原因：依据 6、7。免费额度每天 100 封、每月 3,000 封，两个人远远用不完；域名验证与一键退订头都有现成的支持。各备选方案的比较见下文，其中 Cloudflare 自己的发信服务仍是 beta，而且要 Workers Paid 套餐。

### D3：「有新内容」的来源，以及什么算"新"

只在收件人与对方之间有未结束的绑定期间时判定。来源与"新"的定义：

| 来源 | 对谁算未读 | 什么算"新" |
| --- | --- | --- |
| 日记 | 和首页列表、上下找未读用同一份文字（book-frontend-workspace D5）：本人的日记里对方写的字，以及对方共享给你的日记（当前轮次或冻结的版本）。按列表未读判定：他人写的、已成历史的、不在已读区间里的字 | 列表未读里，不在 **已提醒区间** 里的字。按字符身份判定，不按时间或版本 |
| 共享页面、心愿、礼物、礼物卡片 | space-records D8 的未读（记录类型 `shared_page`、`wish`、`gift`、`gift_card`）；`privateTo` 不是你的历史，本来就不计入，所以准备中的惊喜永远不会出现 | 动作序号同时超过已读序号与 **已提醒序号** |

"已提醒区间"与"已提醒序号"在邮件被服务商受理后写入（D10）。所以同一段内容最多触发一封邮件：你读了它，它不再是未读；你没读，它也不再算"新"。对方之后写的字是新的字符，可以触发下一封。

纪念日记录（`anniversary`）的未读不计入：Ray 2026-11-17 只选了日记、共享页面、心愿与礼物。

原因：依据 3、4。复用已有的两套未读规则，邮件与应用里的圆点不会出现一个说有、一个说没有的分歧。

### D4：一小时没读才发；两封至少隔 4 小时，每天最多 2 封；睡觉时段不发

worker 每 5 分钟对每个开了提醒的人检查一遍：

1. 某个来源第一次出现"新"内容时，记下 **首次发现时间**。"新"内容消失时（读了，或者被删了）清掉这个时间。
2. 只要有任一来源的首次发现时间早于 1 小时前，就准备发一封「有新内容」。这一封列出**当时所有**有"新"内容的来源，包括不到一小时的。
3. 以下任一条成立时不发，等下一次检查再判断：
   - 距上一封「有新内容」不到 4 小时；
   - 按收件人的当地日期，当天已发了 2 封；
   - 当前处在静默时段。

**静默时段**（三类邮件都遵守）：

| 收件人的设置 | 静默时段 |
| --- | --- |
| 有时区，也设了作息 | 作息的睡觉时段，按当前时区解释（two-clocks D2） |
| 有时区，没设作息 | 当地 23:00～8:00 |
| 从未上报时区 | 不静默；"当地日期"按 UTC 算 |

落在静默时段里的邮件会推迟，静默结束后的第一次检查再判断。那时内容已经读过就不发了。

**例子**（收件人作息 0:00～8:00）：

| 时间 | 事件 | 结果 |
| --- | --- | --- |
| 21:00 | 对方写完，字成为历史 | 21:05 检查时记下首次发现时间 |
| 22:05 | 已满一小时，你还没读 | 发第一封 |
| 23:30 | 对方又写了一段 | 23:35 记下首次发现时间 |
| 0:35 | 满一小时，但你在睡 | 推迟 |
| 8:00 | 起床后第一次检查 | 距第一封已超过 4 小时，当天（8:00 已是新的一天）还没发过，发一封 |

实现上，1 小时、4 小时、2 封与 5 分钟都是 `notify` 里的常量，不是配置项。

原因：依据 2、7。一小时让正在用应用的人收不到邮件；冷启动时列表未读每人约 6 秒，每 5 分钟一次对两个人没有压力，所以不用等 PR #55。

### D5：「有新内容」写什么

```text
标题：小红写了新内容

小红写了新内容：
· 11 月 16 日、17 日的日记
· 共享页面
· 心愿与礼物

11 月 17 日的日记里：
「今天下班路上看到一只很胖的橘猫，蹲在便利店门口……」

[ 去看看 ]

这封信由 Between Pages 自动发出。
不再收到这类邮件 · 管理邮件提醒
```

- **名字：** 用对方的显示名（`users.display_name`）。
- **日期：** 列出有"新"内容的日记日期，按日期从早到晚排列。这些日期收件人在首页列表里本来就看得到（依据 3）。
- **区域：** 共享页面与心愿只写区域名。不写页面标题、心愿名称、条数和字数，因为标题和名称是用户写的文字，Ray 只同意带日记预览。
- **预览：** 总是带上（Ray 2026-11-17），只取日记。
  - 取有"新"内容的日记里日期最晚的那一篇，按文档顺序第一段"新"文字，最多 50 个字（按字形簇计，不会截断 emoji），末尾加"……"；
  - 换行和连续空白合并为一个空格；
  - 只用纯文本，经 React Email 转义，不保留任何格式。
- **按钮：** 只有一个区域时直达它：只有一天的日记就打开 `/days/:date`，多天打开 `/days`，共享页面打开 `/shared-pages`，心愿与礼物打开 `/wishes`。有多个区域时打开主页 `/`。链接用 `PUBLIC_ORIGIN` 拼出，不带任何令牌。
- **语言与格式：** 只发中文。HTML 与纯文本两个版本都由 React Email 渲染。

原因：依据 1、3。名字、区域和日期足够让人决定要不要现在打开；预览是 Ray 选的，代价写在"风险与代价"里。

### D6：纪念日到了提醒期发一封

- **何时发：** 纪念日服务对收件人算出 `due`（anniversaries D3：本人对这个纪念日的提醒设置，按本人当地日期）后，提醒期内的第一次非静默检查发一封。同一个纪念日的同一个目标日期（周年日或整数日）只发一封。没设提醒（`days` 为 null）就不发。
- **标题**用首页小条那一行的意思，把"TA"换成对方的名字：
  - "小红的生日还有 5 天"；
  - "在一起 2 周年还有 3 天"；
  - "第 1000 天还有 3 天"；
  - "你的生日还有 1 天"；
  - 当天："今天是在一起 2 周年"。
- **正文**一句话加一个按钮，按钮打开这个纪念日的页面 `/anniversaries/:id`。
- **名称：** 写纪念日的名称（Ray 2026-11-17：不写名称就不知道是哪一个）。

### D7：备份需要处理时发一封

- **何时发：** 收件人的 `BackupAttention` 从"没有"变成某种原因时发一封，原因变了再发一封，回到"没有"后清掉记录。这里的 `BackupAttention` 是首页横条用的同一个函数，四种原因是 `reconnect`、`storage_full`、`failing`、`expiring`。
- **标题**写明原因，例如"Google 备份需要重新连接"或"Google Drive 空间已满，备份已暂停"。按钮打开 `/backup`。
- **其他：** 不需要绑定。不写任何日期以外的日记信息。

原因：这类邮件只涉及本人账号；不打开应用的人也会知道备份停了（Ray 2026-11-17）。

### D8：设置在「设置 → 邮件提醒」，每封都能一键退订

**设置页：** 新页面 `/mail`，和双人空间、搭档、备份并列在"设置"下，页面内容如下：

- 三个开关：有新内容、纪念日、备份需要处理。没有设置记录时三个都是开的。
- 收件地址：登录用的 Google 邮箱，只读，第一版不能改。
- 一句固定的说明："你写的字可能以约 50 字的预览出现在 TA 的提醒邮件里，发出后删改不会同步到邮件"。这句话对每个人都显示，不随对方开没开提醒变化（D9）。

**首页提示：** 上线后每人第一次进主页时看到一条"邮件提醒已开启，可在设置里关闭"，关掉后不再出现。

**退订：**

- 每封邮件带 `List-Unsubscribe: <https://…/api/mail/unsubscribe?token=…>` 与 `List-Unsubscribe-Post: List-Unsubscribe=One-Click`，Gmail 会在发件人旁边显示"退订"。
- 页脚有两个链接："不再收到这类邮件"打开网页 `/unsubscribe?token=…`，"管理邮件提醒"打开 `/mail`。
- 退订只关这一类邮件。
- 令牌是 `HMAC-SHA256(MAIL_TOKEN_KEY, 用户 ID ‖ 类别)`，用 `node:crypto` 计算。不用登录也能用；只能关闭，不能打开；不会过期。
- `/unsubscribe` 页显示"不再收到「有新内容」邮件？"和一个按钮，点了才 POST。GET 请求从不改变状态，邮件服务商预先抓取链接时不会误退订。
- 同一个令牌 POST 第二次，照样返回成功。

原因：依据 5。默认开启是因为两个人都是主动要这个功能的；首页提示保证知情。

### D9：隐私规则

1. **来源边界：** 邮件里的区域、日期与预览，都经获准状态读取入口和列表未读规则生成，也就是收件人在应用里本来就能读到的内容。未共享的日记、共享范围与排除日期不会以任何形式出现，包括数量和存在与否。冻结的共享照常计入。
2. **发送前复查：** 发送前在同一次读取里确认三件事：绑定仍在、内容仍是"新"的、预览里的字仍然存在。解绑后不再发「有新内容」与纪念日邮件，已经排队的也不发。
3. **不透露阅读行为：** 作者不能得知对方是否收到邮件、是否开了提醒、是否读过。没有任何接口返回别人的邮件设置或发送记录，应用里也没有"已提醒 TA"。
4. **固定告知：** D8 的说明对每个人都显示，不随对方的设置变化。
5. **日志：** 只记用户 ID、类别、发送记录 ID 和服务商的错误码，不记邮箱地址、标题、预览或日记文字。

### D10：在 worker 里跑；先写发送记录，服务商受理后才记为已提醒

**模块**（`apps/api/src`），登记进 `checks/verify-dependency-direction.ts`：

| 单元 | 负责 | 不做 |
| --- | --- | --- |
| `mail` | 用 `resend` 发一封信；用 React Email 把三类邮件渲染成 HTML 与纯文本；退订令牌的签名与校验 | 不访问数据库，不判断该不该发 |
| `notify` | 服务层：设置、首次发现时间、已提醒标记、静默时段、频率限制、发送记录与重试 | 不自己判定未读：日记经 `reader`，空间记录经 `space-records` 的 `unseen`，纪念日经纪念日服务的 `due`，备份经备份状态；收件地址经认证层查询 |
| `worker` | 每 5 分钟调用一次 `notify`，之后照常跑备份与链接预览 | — |

`reader` 增加一个入口：按收件人与已提醒区间，列出有"新"文字的日记（日期、文字 ID、未覆盖的区间、第一段"新"文字）。它和列表未读用同一个 `listUnread`，只是把已提醒区间并进已覆盖区间，所以仍然只有一个负责判定的地方。

静默时段在 `notify` 里判断，时区与作息的计算从 `packages/time` 导入（D11），不新增时区库。

**一次发送的流程：**

1. **事务 A：** 在 `mail_sends` 写入一行，状态为"发送中"，记下它要覆盖的来源以及发出后要写入的已提醒标记。同一个人、同一类别在"发送中"的记录最多一条。
2. **发送前复查**（D9 第 2 条），然后渲染邮件，以这一行的 ID 作为 `idempotencyKey` 调用 Resend。复查时发现已经没有可发的内容，就把这一行标为"已取消"。
3. **事务 B：** 记下服务商返回的消息 ID，状态改为"已发送"，在同一个事务里写入已提醒标记，更新"上一封时间"与当天封数。

**失败时：**

- 第 2 步遇到网络错误、429 或 5xx：保持"发送中"，按备份 ADR 的退避方式重试，间隔从 1 分钟翻倍，最多 1 小时，429 按 `Retry-After`。重试时重新复查和渲染，幂等键不变。
- Resend 以"同一幂等键、内容不同"拒绝：说明上一次已经受理，按已发送处理。
- 其他 4xx（例如地址无效）：标为"失败"，记下错误码，不写已提醒标记。
- 发送中满 24 小时：标为"已放弃"，内容仍是"新"的，之后的检查照常判断。

### D11：时区与作息的纯计算放进一个零依赖的包 `packages/time`，网页与服务端共用

**现状：** 同一套时区计算已经写了两份。`apps/api/src/anniversaries/dates.ts` 给纪念日算当地日期，`apps/web/src/two-clocks/time.ts` 给两地时间算当地钟点、重叠时段与"大概在睡"。两份做的是同一件事：把时刻换成当地钟点，把当地钟点换回时刻，跨夏令时与跨午夜时取对，按天加减。静默时段（D4）需要同样的计算，如果在 `notify` 里再写一份，就是第三份。

**为什么会重复：** 两个 app 不能互相引用（architecture.md），而共用的两个包都放不下它：`packages/contracts` 明确不负责行为，`packages/collab` 只管 Yjs 协同模型。

**决定：** 新建 `packages/time`。

- **放什么：** 只放纯函数，只用 Intl，没有外部依赖。包括：
  - 时刻的当地钟点与当地日期；
  - 当地某天某分钟对应的时刻，以及当地一天的起点；
  - 日期加减天数与相差天数；
  - 某时刻是否落在一组作息的睡觉时段里，以及睡觉时段的结束时刻。
- **谁用：** 网页的两地时间、服务端的纪念日日期计算和 `notify` 都从这里导入，原来的两份重复实现删除。
- **规则仍归各自的模块：**
  - 没设作息时按 23:00～8:00 静默，是邮件提醒的规则，留在 `notify`；
  - "大概在睡"的显示、重叠时段的呈现留在网页；
  - 纪念日的 2 月 29 日规则、整数日留在纪念日模块。
- **登记：**
  - architecture.md 的模块表加一行；
  - 依赖方向检查加 `{ dir: 'packages/time', imports: [], externals: [] }`，`apps/api` 与 `apps/web` 可以引用它；
  - vitest 加 `time` 项目；
  - AGENTS.md 的目录表加一行。

原因：AGENTS.md 的"一个职责一个归属"。同一条时区规则只有一份实现，夏令时之类的修复改一处就两边生效。抽出现有代码属于与邮件无关的整理，所以单独一个 PR，排在落地顺序的最前面。

### 技术设计

**表**（一次迁移，本文预先批准）：

| 表 | 内容 |
| --- | --- |
| `mail_settings` | 用户（主键）、有新内容、纪念日、备份三个开关、首页提示关闭时间、更新时间。没有记录等于三个开关都开 |
| `mail_marks` | 用户、来源（`diary`、四种空间记录类型、`anniversary`、`backup`）、来源 ID、首次发现时间、已提醒区间（日记，与已读区间同一形式）、已提醒序号（空间记录）、已提醒键（纪念日的目标日期、备份的原因） |
| `mail_sends` | ID（同时用作幂等键）、用户、类别、收件人当地日期、要覆盖的来源与标记、状态（发送中、已发送、已取消、失败、已放弃）、尝试次数、下次尝试时间、错误码、服务商消息 ID、创建与发送时间 |

**接口**（contracts 与 OpenAPI 随实现）：

- `GET /api/mail`：本人的三个开关、收件地址、首页提示是否已关闭。
- `PUT /api/mail`：改开关，或关闭首页提示。
- `POST /api/mail/unsubscribe?token=…`：不用登录。同时接受 RFC 8058 的一键请求（表单体 `List-Unsubscribe=One-Click`）和退订页的请求；令牌无效时返回 404。

**网页：** 设置页 `/mail`、退订页 `/unsubscribe`、首页一次性提示，都经 `callApi` 调用接口。

**新配置：** `RESEND_API_KEY`、`MAIL_FROM`、`MAIL_TOKEN_KEY`（退订签名，API 与 worker 都需要）。没有 `RESEND_API_KEY` 时 `notify` 不运行，worker 启动日志说明一次；没有 `MAIL_TOKEN_KEY` 时 API 照常启动，退订接口返回 404。测试用 SDK 支持的 `RESEND_BASE_URL` 指向本地的假 Resend 服务。

## 失败与恢复

| 情况 | 结果与恢复 |
| --- | --- |
| Resend 暂时不可用或限流 | 退避重试（D10），内容仍未读时晚一些送到；写日记不受影响 |
| `RESEND_API_KEY` 失效 | 每次发送都失败并记下错误码；Ray 在 worker 日志里看到后换密钥。不写已提醒标记，换好之后照常判断 |
| 发信域名验证失效（DNS 被改） | Resend 拒绝发送，处理同上 |
| 邮件进了垃圾箱 | 用户不知道有提醒；上线时手动检查（验收标准），在 Gmail 里标为"非垃圾邮件" |
| worker 在事务 A 之后、事务 B 之前崩溃 | 重启后这一行仍是"发送中"，用同一个幂等键重试，收件人只收到一封 |
| worker 停了几个小时 | 恢复后照常检查；读过的内容不再提醒，没读的满足条件就发，不补发错过的时段 |
| 两人在排队期间解绑 | 第 2 步复查到没有绑定，标为"已取消" |
| 内容在排队期间被删或被读 | 第 2 步复查后不再列出它；全部没了就标为"已取消" |
| 收件地址无效 | 标为"失败"并记下错误码，不重试 |
| `MAIL_TOKEN_KEY` 更换 | 旧邮件里的退订链接失效（返回 404），设置页照常可用 |

## 不变量

1. 邮件里的日期、区域与预览，只来自收件人当时经获准状态读取入口能读到的内容；未共享的日记、共享范围与排除日期不以任何形式出现。
2. 没有未结束的绑定期间时，不发「有新内容」与纪念日邮件；发送前在同一次读取里复查。
3. 预览只取收件人的列表未读文字，最多 50 字，不取共享页面与心愿的文字。
4. 同一段内容最多触发一封「有新内容」：已提醒的字与序号不再算"新"。
5. 两封「有新内容」间隔不少于 4 小时；同一收件人在同一当地日期最多收到 2 封。
6. 收件人的静默时段内不发任何邮件。
7. 没有任何接口或界面向别人透露某人的邮件设置、发送记录或是否读过。
8. 一条发送记录无论重试几次，收件人最多收到一封；只有服务商受理后才写入已提醒标记。
9. 关掉的类别不再发；退订令牌只能关闭、不能打开；GET 请求不改变设置。
10. 日志与错误信息不含邮箱地址、邮件标题、预览或日记文字。
11. 没有配置 `RESEND_API_KEY` 时不发任何邮件，也不写已提醒标记。
12. 纪念日的同一个目标日期最多一封；备份的同一次需要处理最多一封。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **Cloudflare Email Service** | DNS 与代理本来就在 Cloudflare 上，记录一键配好；不会多一家第三方看到收件人 | 2026-04 起公测，到 2026-11 仍是 beta；发给任意收件人要 Workers Paid（5 美元/月）。Ray 2026-11-17 选了 Resend（依据 6） |
| **Gmail API（`gmail.send`）** | 不用新服务商 | `gmail.send` 是敏感权限，要重新走 Google 审核；发信绑在 Ray 一个人的账号上，搭档收到的信像是 Ray 本人发的 |
| **Gmail SMTP 加应用专用密码** | 配置最简单 | 应用专用密码能登录 Ray 的整个 Gmail，要放在服务器上；同样绑在 Ray 本人账号上 |
| **Amazon SES** | 最便宜，送达率好 | 新账号要先申请离开沙盒，IAM 与配置都比 Resend 繁琐；两个人用不出价格差 |
| **Postmark** | 送达率口碑最好 | 免费额度每月只有 100 封，长期要约 15 美元/月 |
| **自己用 `fetch` 调 Resend** | 少一个依赖 | 依据 6：要自己处理接口格式、错误与幂等；官方 SDK 用的人多、维护频繁 |
| **手写 HTML 模板** | 不加依赖 | 依据 6：名字和预览是用户写的文字，漏一处转义就可能被注入；各家邮箱客户端的兼容问题也要自己处理 |
| **只发纯文本** | 不需要模板库，不存在注入问题 | 没有按钮和样式，链接只是一行网址；Ray 2026-11-17 选了 React Email |
| **不带预览** | 正文不经过发信服务商，也不会留在收件箱里 | Ray 2026-11-17 决定总是带上 |
| **作者同意才带预览** | 每个人的字是否离开应用由作者决定 | Ray 2026-11-17 决定不加这个开关，总是带上 |
| **在 API 的提交事务里触发发信** | 对方一写完就能开始计时 | 一小时的延迟和静默时段本来就要靠定时检查；提交链不应该承担外部副作用（依据 4） |
| **每条新内容发一封** | 最及时 | 违反依据 2；两个人一天能写很多段 |
| **发过一封之后，等你回来才发下一封** | 最安静 | Ray 2026-11-17 选了"隔 4 小时、每天 2 封"；很久不打开应用的人只会收到一封 |
| **在 `notify` 里再写一份时区计算** | 不动已上线的两地时间与纪念日代码 | 违反"一个职责一个归属"：同一条规则变成三份，修一处漏两处（D11） |
| **把时区函数放进 `packages/contracts`** | 不用新建包 | contracts 只放线上格式与路由表，明确不负责行为（architecture.md）；为省一个包打破边界 |
| **网页推送** | 不经邮箱，到达更快 | 依据 8：要新增订阅管理与推送服务；以后可以作为另一个渠道，复用本文的规则 |

## 风险与代价

- **预览离开了应用：** 预览会经过 Resend，留在收件人的邮箱里。作者之后删改不会同步到已发出的邮件。设置页的固定说明告知了这一点，作者没有开关。
- **Resend 能看到的内容：** 收件人邮箱、对方的名字、日记日期与预览。它的后台会保留邮件内容一段时间。
- **只提醒一次：** 一段内容提醒过一次后不再提醒；收件人一直没读，也不会收到第二封。
- **时间粒度：** 每 5 分钟检查一次，实际的延迟是 1 小时到 1 小时 5 分钟；静默结束后最多再晚 5 分钟。
- **多一个包：** `packages/time`（D11）要在架构文档、依赖方向检查与测试配置里各登记一次；抽出时要动两地时间与纪念日两处已上线的代码，靠它们现有的测试保证行为不变。
- **新邮箱的信誉：** 新的发信域名起初可能进垃圾箱。上线时手动检查，必要时在 Gmail 里标为"非垃圾邮件"。
- **依赖：** `apps/api` 新增 `react`、`react-dom` 与 JSX 编译设置，只用来渲染邮件。
