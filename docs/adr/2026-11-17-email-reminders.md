# 对方的新内容一小时没读、纪念日到了提醒期、备份需要处理时，worker 经 Resend 发一封提醒邮件

- 状态：已采纳
- 日期：2026-11-17
- 决策者：Ray
- 范围：领域
- 关联：依赖 unread-and-day-page；依赖 server-backup-and-google-docs；依赖 space-records；依赖 two-clocks；依赖 anniversaries；依赖 partner-local-dates；依赖 shared-pages；依赖 production-deployment；取代 authentication-and-sessions 的不变量 7 与 D7 的来源检查中退订接口的部分

绑定中的两个人不打开应用也能知道对方写了新东西。后台进程（worker）每 5 分钟检查一次每个人，三种情况发信：

- **有新内容**：对方在日记、共享页面、心愿与礼物里有你一小时没读的新内容，发一封合并的邮件。邮件写明哪些地方有新内容和日记的日期，并附一段约 50 字的日记预览。两封至少隔 4 小时，按你的当地日期每天最多 2 封。
- **纪念日**：纪念日到了你自己设的提醒期，发一封。
- **备份**：Google 备份需要你处理，或者连续一天没成功时，发一封。

三种邮件都不在你的睡觉时段里发。邮件经 Resend 的官方 SDK 发出，正文用 React Email 渲染，发信地址在 `ruihaozhang.com` 的一个子域名上，配好 SPF 与 DKIM。每人在「设置 → 邮件提醒」里分别关掉三类邮件，每封都能一键退订。为了让 Gmail 的一键退订能用，退订接口是唯一不检查 `Origin` 的写接口，靠签名令牌认证，而且只能关闭。邮件内容与列表、未读执行同一条隐私边界（SHARE-11）：只写收件人在应用里本来能看到的东西，作者永远不知道对方收没收到、读没读。

本文不负责：轻触"想你了"、时间胶囊与戳团子的通知（各自的 ADR 接到本文的发送机制上）；对方新记或修改纪念日的通知；网页推送与其他渠道；改收件地址；英文邮件。

## 背景与问题

用户于 2026-10-28 决定把邮件通知放在阶段 4：对方写了新内容而你一段时间没读时，发邮件提醒。路线图里"想你了"和时间胶囊都要求对方不打开应用也能知道，因此依赖它。2026-11-07 上线以后，Ray 和搭档每天都在用；对方写了什么，现在只能打开应用才知道。

需要回答的问题：

- 用什么发？发信地址是什么？
- 哪些事件发？
- 多久没读才发？多久最多几封？夜里发不发？
- 邮件里写什么？能不能带正文？
- 在哪里关掉、怎么退订？
- 怎么保证不泄露对方没共享的日记和阅读行为？
- 在哪个进程里跑？崩溃重试时怎么不重复发？

已有的条件：

- **列表未读规则**（unread-and-day-page D2）：只计已成历史的字，按字符身份判定，读取器 `reader` 里的 `listUnread` 已有实现。缓存为空时每人约 6 秒（3 年的数据量），见[实测](../validation/book-frontend-next-unread-2026-11-01.md)。
- **空间记录的未读**（space-records D8）：变更（`space_changes`）与动作（`space_actions`）共用一个序号，`space_reads` 记每人看到哪里。哪些记录、哪些删除记录算未读，由各功能服务决定：`wishes` 的 `unread` 与 `shared-pages` 的 `unread`，导航入口的圆点就是它们给的数。准备中的惊喜因为 `privateTo` 不进对方的未读。
- **共享页面的 `wrote`**（shared-pages D5）：对方看到上一条之前，继续写不再追加新的 `wrote`。
- **两地时间**：每人的时区与作息存在 `users` 上（two-clocks D1、D2）。
- **纪念日**：每人自己的提醒期（anniversaries D3），由服务端算出 `due`；除了自己的生日，日期按对方的当地日期算（partner-local-dates D1）；时区现在由浏览器在请求里带上。
- **备份**：首页横条的四种原因 `BackupAttention`（server-backup-and-google-docs D9）。
- **worker**：已有后台进程（ADR-0006 第 20 条），每 5 秒跑一次各项任务，取任务用 `FOR UPDATE SKIP LOCKED`，失败时退避重试；没配 Drive 时跳过 Drive 的任务。
- **邮箱**：领域表不存邮箱，邮箱只在认证层的 `auth_user` 里，是登录用的 Google 邮箱。只有 `apps/api/src/auth/` 与 `db/` 能碰认证层（authentication-and-sessions 不变量 10，`verify-auth-boundary`）。
- **来源检查**：所有非 GET 的 `/api/*` 请求都要求 `Origin` 等于本站，缺少也拒绝（authentication-and-sessions D7、不变量 7）。邮件服务商代发的一键退订请求不带本站的 `Origin`。
- **运行方式**：API 与 worker 由 Node 直接运行 TypeScript 源码，不经编译（`noEmit`、`erasableSyntaxOnly`），所以加载不了 `.tsx`。生产环境的 api、worker、migrate 三个容器共用一个环境文件（production-deployment）。
- **网络**：生产环境的 DNS 与代理都在 Cloudflare 上。

## 决策依据

1. 对方不打开应用也能知道有新内容；"想你了"与时间胶囊依赖这一点（路线图阶段 4，用户 2026-10-28）。
2. 不打扰：正在用应用时收不到，夜里收不到，一天封数有上限（Ray 2026-11-17 确认一小时、隔 4 小时、每天 2 封、按作息静默）。
3. 邮件与列表、未读执行同一条隐私边界：只写收件人在应用里本来能看到的东西，不透露未共享的日记、共享范围与阅读行为（规格 SHARE-11，Ray 2026-11-17 确认五条规则）。
4. 已读、"已提醒"这类状态由服务端在 PG 里确定（ADR-0003、ADR-0006）。发信是外部副作用：崩溃重试不能让人收到两封，也不能因为不确定有没有发出去而多发。
5. 用户随时能关；退订一键完成，不用登录（RFC 8058，Ray 2026-11-17 选择 Gmail 的一键退订）。
6. 用流行、可靠、维护频繁的库，不手写发信协议和 HTML 转义；用的人少的库才要谨慎（Ray 2026-11-17）。
7. 现在只有两个用户：每 5 分钟全量判定一次可以接受，不为它建实时通道。
8. 没有消费者的东西不预建（AGENTS.md）：推送、更多渠道与更多事件等有了需要再加。
9. 一个职责只有一个归属（AGENTS.md）：未读的判定、时区的计算都不再写第二份。

## 决策

### D1：三类邮件

| 类别 | 何时发 | 受「隔 4 小时、每天 2 封」限制 | 需要绑定 |
| --- | --- | --- | --- |
| 有新内容 | 对方的新内容一小时没读（D3、D4） | 是 | 是 |
| 纪念日 | 纪念日进入你的提醒期（D6） | 否 | 是 |
| 备份 | 首页备份横条出现（D7） | 否 | 否 |

三类都遵守夜间静默（D4）。

**不发的情况：** 对方新记或修改了纪念日（纪念日入口的圆点照旧亮）；对方戳了团子；"想你了"与时间胶囊。最后两个功能各自的 ADR 再决定接不接、怎么接。

原因：依据 1、2、8。三类用同一套设置、退订与发送记录，以后的通知只需要新增一个类别。

### D2：经 Resend 发出，发信地址在独立子域名上

- **SDK：** 用 Resend 的官方 Node SDK `resend`（MIT 协议，每周约 1,800 万次下载，2026-11-13 发布 6.38.1）。它支持幂等键（`idempotencyKey`）、自定义邮件头与 `baseUrl` 选项，返回值带响应头（可以读 `Retry-After`）。
- **发信地址：** 配置项 `MAIL_FROM`，例如 `Between Pages <remind@mail.ruihaozhang.com>`。用独立子域名，不影响主域名现有的邮件设置。Resend 给出的 SPF、DKIM 记录加到 Cloudflare DNS，另加一条 `p=none` 的 DMARC 记录。
- **回信：** 不设回信地址。邮件页脚写明"这封信由 Between Pages 自动发出"。
- **密钥：** `RESEND_API_KEY` 和 `GOOGLE_TOKEN_KEY` 一样放在共用的环境文件里，只有 worker 用它。

原因：依据 6、7。免费额度每天 100 封、每月 3,000 封，两个人远远用不完；域名验证与一键退订头都有现成的支持。各备选方案的比较见下文，其中 Cloudflare 自己的发信服务仍是 beta，而且要 Workers Paid 套餐。

### D3：「有新内容」的来源，以及什么算"新"

只在收件人与对方之间有未结束的绑定期间时判定。来源与"新"的定义：

| 来源 | 对谁算未读 | 什么算"新" |
| --- | --- | --- |
| 日记 | 和首页列表、上下找未读用同一份文字（book-frontend-workspace D5）：本人的日记里对方写的字，以及对方共享给你的日记（当前轮次或最后冻结的版本）。按列表未读判定：他人写的、已成历史的、不在已读区间里的字；冻结的共享全部计入 | 列表未读里，不在 **已提醒区间** 里的字。按字符身份判定，不按时间或版本 |
| 共享页面 | `shared-pages` 的未读：有未读的页面，加上未读的删除记录 | 这一项的序号（space-records D8 的 `mark`）同时超过已读与 **已提醒序号** |
| 心愿与礼物 | `wishes` 的未读：心愿、礼物（准备中与礼物墙）、礼物卡片，加上未读的删除记录；`privateTo` 不是你的历史，本来就不计入 | 同上 |

- **各功能各管各的未读：** `wishes` 与 `shared-pages` 各增加一个入口，列出算进圆点的每一项（引用、当前序号、新建/改过/删除）。原来的 `unread` 改为数这个列表，所以圆点和邮件用的是同一份清单。
- **只提醒一次：** 已提醒区间与已提醒序号在邮件被受理后写入（D10）。除了"结果不明"的极少数情况（D10），同一段内容最多触发一封邮件：你读了它，它不再是未读；你没读，它也不再算"新"。对方之后写的字是新的字符，新的变更与动作是新的序号，可以触发下一封。
- **共享页面的差别：** 按 shared-pages D5，对方看到上一条 `wrote` 之前，继续写不会再产生 `wrote`。所以一页发过提醒以后，只要你还没打开它，对方在这页继续写也不会再提醒。`wrote` 在对方第一次提交时就追加，所以页面的一小时从对方开始写算起，不像日记那样从字成为历史算起。
- **删除记录：** 对方删了你写过字的页面或心愿，也算未读（space-records D6），邮件里写成"有更新"（D5）。
- **纪念日记录**（`anniversary`）的未读不计入：Ray 2026-11-17 只选了日记、共享页面、心愿与礼物。

原因：依据 3、9。复用已有的未读规则和各功能自己的清单，邮件与应用里的圆点不会出现一个说有、一个说没有的分歧。

### D4：一小时没读才发；两封至少隔 4 小时，每天最多 2 封；睡觉时段不发

worker 每 5 分钟对每个开了提醒的人判定一次：

1. 某个来源第一次出现"新"内容时，记下 **首次发现时间**。"新"内容消失时（读了，或者被删了）清掉这个时间。解绑时清掉这个人的全部首次发现时间，重新绑定后从头计时。「有新内容」关着的时候不判定，也清掉它的首次发现时间；重新打开后从头计时，不会一打开就收到一封。
2. 只要有任一来源的首次发现时间不晚于 1 小时前，就准备发一封「有新内容」。这一封列出**当时所有**有"新"内容的来源，包括不到一小时的。
3. 以下任一条成立时不发，等下一次判定：
   - 距上一封「有新内容」不到 4 小时；
   - 按收件人的当地日期，当天已发了 2 封；
   - 当前处在静默时段。

"上一封"和"当天封数"都从发送记录里数，算"已发送"与"结果不明"（D10）两种。"上一封"的时间，已发送的按受理时间，结果不明的按最后一次请求的时间。当地日期在建发送记录时按当时的时区定下。

**静默时段**（三类邮件都遵守）：

| 收件人的设置 | 静默时段 |
| --- | --- |
| 有时区，也设了作息 | 作息的睡觉时段，按当前时区解释（two-clocks D2） |
| 有时区，没设作息 | 当地 23:00～8:00 |
| 从未上报时区 | 不静默；"当地日期"按 UTC 算 |

落在静默时段里的邮件会推迟，静默结束后的判定再决定。那时内容已经读过就不发了。

**例子**（收件人作息 0:00～8:00）：

| 时间 | 事件 | 结果 |
| --- | --- | --- |
| 21:00 | 对方写完，字成为历史 | 21:05 判定时记下首次发现时间 |
| 22:05 | 首次发现时间正好是 1 小时前，你还没读 | 发第一封 |
| 23:30 | 对方又写了一段 | 23:35 记下首次发现时间 |
| 0:35 | 满一小时，但你在睡 | 推迟 |
| 8:00 | 起床后第一次判定 | 距第一封已超过 4 小时，当天（8:00 已是新的一天）还没发过，发一封 |

实现上，1 小时、4 小时、2 封与 5 分钟都是 `notify` 里的常量，不是配置项。

原因：依据 2、7。一小时让正在用应用的人收不到邮件；冷启动时列表未读每人约 6 秒，每 5 分钟一次对两个人没有压力，所以不用等 PR #55。

### D5：「有新内容」写什么

```text
标题：小红写了新内容

小红写了新内容：
· 11 月 16 日、17 日的日记
· 共享页面有更新
· 心愿与礼物有更新

11 月 17 日的日记里：
「今天下班路上看到一只很胖的橘猫，蹲在便利店门口……」

[ 去看看 ]

这封信由 Between Pages 自动发出。
不再收到这类邮件 · 管理邮件提醒
```

- **名字：** 用对方的显示名（`users.display_name`）。标题是"{名字}写了新内容"；只有共享页面或心愿与礼物、没有日记时，是"{名字}更新了共享页面"或"{名字}更新了心愿与礼物"。
- **日期：** 列出有"新"内容的日记日期，按日期从早到晚排列。这些日期收件人在首页列表里本来就看得到（依据 3）。
- **区域：** 共享页面与心愿只写"有更新"。不写页面标题、心愿名称、条数和字数，因为标题和名称是用户写的文字，Ray 只同意带日记预览。
- **预览：** 总是带上（Ray 2026-11-17），只取日记。
  - 取有"新"内容的日记里日期最晚的那一篇，按文档顺序第一段"新"文字，最多 50 个字（用 `Intl.Segmenter` 按字形簇计，不会截断 emoji），截断时末尾加"……"；
  - 换行和连续空白合并为一个空格；
  - 只用纯文本，经 React Email 转义，不保留任何格式。
- **按钮：** 只有一个区域时直达它：只有一天的日记就打开 `/days/:date`，多天打开 `/days`，共享页面打开 `/shared-pages`，心愿与礼物打开 `/wishes`。有多个区域时打开主页 `/`。链接用 `PUBLIC_ORIGIN` 拼出，不带任何令牌。
- **语言与格式：** 只发中文。HTML 与纯文本两个版本都由 React Email 渲染。

原因：依据 1、3。名字、区域和日期足够让人决定要不要现在打开；预览是 Ray 选的，代价写在"风险与代价"里。

### D6：纪念日到了提醒期发一封

- **何时发：** 纪念日服务对收件人算出 `due` 后，提醒期内的第一次非静默判定发一封。同一个纪念日的同一个目标日期（周年日或整数日）只发一封。没设提醒（`days` 为 null）就不发。
- **按谁的日期：** 和首页小条完全一样，由纪念日服务按 partner-local-dates 决定：自己的生日按自己的当地日期，其他按对方的当地日期，对方时区不明时退回自己的。worker 没有浏览器，把收件人存在 `users.timezone` 里的时区传给纪念日服务；没有时按 UTC。
- **标题**用首页小条那一行的意思，把"TA"换成对方的名字：
  - "小红的生日还有 5 天"；
  - "在一起 2 周年还有 3 天"；
  - "第 1000 天还有 3 天"；
  - "你的生日还有 1 天"；
  - 当天："今天是在一起 2 周年"。
- **正文**一句话加一个按钮，按钮打开这个纪念日的页面 `/anniversaries/:id`。
- **名称：** 写纪念日的名称（Ray 2026-11-17：不写名称就不知道是哪一个）。

### D7：备份需要处理或连续失败时发一封

- **何时发：** 收件人的 `BackupAttention` 从"没有"变成某种原因时发一封，原因变了再发一封，回到"没有"后清掉记录。同一种原因 24 小时内最多一封，所以"失败、恢复、又失败"来回跳时不会反复发。这里的 `BackupAttention` 是首页横条用的同一个函数。
- **标题**按原因写：

  | 原因 | 标题 |
  | --- | --- |
  | `reconnect` | Google 备份需要重新连接 |
  | `storage_full` | Google Drive 空间已满，备份已暂停 |
  | `failing` | Google 备份一天没成功，正在自动重试 |
  | `expiring` | Google 备份的授权快到期了，请重新连接 |

  `failing` 不需要用户动手，所以标题只说明情况，不说"需要处理"。`expiring` 只在 Drive 处于测试状态（`GOOGLE_DRIVE_TESTING`）时出现，生产环境的 Google 应用已经发布为正式，不会出现。
- **按钮**打开 `/backup`。不需要绑定。不写任何日记信息。

原因：这类邮件只涉及本人账号；不打开应用的人也会知道备份停了（Ray 2026-11-17）。

### D8：设置在「设置 → 邮件提醒」，每封都能一键退订

**设置页：** 新页面 `/mail`，和双人空间、搭档、备份并列在"设置"下（导航判断"设置"是否选中的规则也加上 `/mail`），页面内容如下：

- 三个开关：有新内容、纪念日、备份。没有设置记录时三个都是开的。
- 收件地址：登录用的 Google 邮箱，只读，第一版不能改。只在本人的设置页显示；`/api/me` 仍然不返回邮箱。
- 一句固定的说明："你写的字可能以约 50 字的预览出现在 TA 的提醒邮件里，发出后删改不会同步到邮件"。这句话对每个人都显示，不随对方开没开提醒变化（D9）。

**首页提示：** 上线后每人第一次进主页时看到一条"邮件提醒已开启，可在设置里关闭"，关掉后不再出现。

**退订：**

- 每封邮件带 `List-Unsubscribe: <https://…/api/mail/unsubscribe?token=…>` 与 `List-Unsubscribe-Post: List-Unsubscribe=One-Click`，Gmail 会在发件人旁边显示"退订"，按一下就生效。
- 页脚有两个链接："不再收到这类邮件"打开网页 `/unsubscribe?token=…`，"管理邮件提醒"打开 `/mail`。
- 退订只关这一类邮件。同一个令牌 POST 第二次，照样返回成功。
- **令牌：** `base64url(用户 ID ‖ 类别 ‖ HMAC-SHA256(MAIL_TOKEN_KEY, 用户 ID ‖ 类别))`，用 `node:crypto` 计算，比较签名用 `timingSafeEqual`。不用登录也能用；只能关闭，不能打开；不会过期。服务端校验签名后才使用其中的用户和类别。
- **退订页** `/unsubscribe` 不需要登录，不在登录保护的路由下面。它先用 `GET /api/mail/unsubscribe/category?token=…` 校验令牌、取到类别，显示"不再收到「有新内容」邮件？"和一个按钮，点了才 POST。GET 请求从不改变状态，邮件服务商预先抓取链接时不会误退订。
- **不支持一键退订的邮件客户端**会在浏览器里打开 `List-Unsubscribe` 的地址。`GET /api/mail/unsubscribe?token=…` 因此重定向（303）到退订页 `/unsubscribe?token=…`，用户看到的是确认页，不是一段 JSON。

**退订接口不检查 `Origin`：** `POST /api/mail/unsubscribe` 是唯一不经来源检查的写接口，路由是 `access: 'public'`。Gmail 的一键退订从 Google 的服务器发出，不带本站的 `Origin`。来源检查防的是"别的网站借用户的 cookie 发请求"，这个接口不看 cookie，认证完全靠令牌，而令牌只在发给本人的邮件里出现；即使被别人拿到，也只能替这个人关掉一类邮件，打不开、读不到任何东西。这一点部分取代了 authentication-and-sessions 的 D7 与不变量 7，其余接口照旧检查。一键退订的表单体（`application/x-www-form-urlencoded`）用 Fastify 自带的 `addContentTypeParser` 只在这条路由上解析，不加 `@fastify/formbody`。

原因：依据 5。默认开启是因为两个人都是主动要这个功能的；首页提示保证知情。

### D9：隐私规则

1. **来源边界：** 邮件里的区域、日期与预览，都经获准状态读取入口、列表未读规则和各功能的未读清单生成，也就是收件人在应用里本来就能读到的内容。未共享的日记、共享范围与排除日期不会以任何形式出现，包括数量和存在与否。冻结的共享照常计入。
2. **每次发送前复查：** 第一次发送和每次重试之前，在同一次读取里确认：
   - 绑定仍在（备份邮件除外）；
   - 这一类邮件仍然开着；
   - 当前不在静默时段；
   - 内容仍是"新"的，预览里的字仍然存在。

   复查不通过就不发（D10 说明之后怎么办）。复查之后、Resend 受理之前的几百毫秒里删掉的字仍会发出，接受这一点。
3. **不透露阅读行为：** 作者不能得知对方是否收到邮件、是否开了提醒、是否读过。邮件相关的接口只返回调用者本人的设置，应用里也没有"已提醒 TA"。
4. **固定告知：** D8 的说明对每个人都显示，不随对方的设置变化。
5. **日志：** 只记用户 ID、类别、发送记录 ID 和服务商的错误码，不记邮箱地址、标题、预览或日记文字。

### D10：在 worker 里跑；第一次请求前才渲染，请求发出后内容不再改变

**模块**（`apps/api/src`），登记进 `checks/verify-dependency-direction.ts`：

| 单元 | 负责 | 不做 | 可以引用 |
| --- | --- | --- | --- |
| `mail` | 用 `resend` 发一封信；把三类邮件渲染成 HTML 与纯文本；退订令牌的签名与校验 | 不访问数据库，不判断该不该发 | 无（只用外部依赖） |
| `notify` | 服务层：设置、首次发现时间、已提醒标记、静默时段、频率限制、发送记录与重试 | 不自己判定未读，也不自己读认证表 | `store`、`reader`、`history`、`wishes`、`shared-pages`、`anniversaries`、`backup`、`auth`（只用下面的邮箱查询）、`mail`、`config`、`errors` |
| `worker` | 每个 tick 处理到期的发送记录；每 5 分钟调用一次 `notify` 的判定 | — | 已有的，加上 `notify` |

- **`reader` 的新入口：** 按收件人与已提醒区间，列出有"新"文字的日记（日期、文字 ID、未覆盖的区间、第一段"新"文字）。`listUnread` 改为返回未覆盖的区间（原来的布尔值由它推出），新入口把已提醒区间并进已覆盖区间。判定仍然只有一处。它沿用 `nextUnread` 的做法缓存每篇的结果，缓存键是原来的输入加上已提醒区间，没变的日记不重建正文。
- **`auth` 的新函数：** `emailOf(userId)` 读 `auth_user.email`。它写在 `apps/api/src/auth/` 里，所以 `verify-auth-boundary` 不用改。
- **时区：** 静默时段在 `notify` 里判断，计算从 `packages/time` 导入（D11）。
- **worker 的节奏：** 判定用自己的 5 分钟计时，像现有的每日 Drive 检查那样。发送记录的重试每个 tick（5 秒）都看到期的，所以退避能从 1 分钟开始。两者都放在"没配 Drive 就返回"那一行之前。

**一次发送的流程：**

1. **判定**（事务）：判定该发时写入一条 `mail_sends`，状态为"发送中"，只记类别与收件人当地日期。同一个人、同一类别"发送中"的记录最多一条，由部分唯一索引保证，所以两个 worker 同时运行（例如部署时新旧交替）也不会建出两条。
2. **发送：** 用 `FOR UPDATE SKIP LOCKED` 取一条到期的记录，先把它的下次尝试时间往后推（租约），再做复查（D9 第 2 条）。
   - **还没发出过请求：** 按当时的状态重新算出内容（来源、日期、预览）和发出后要写入的已提醒标记，渲染好标题、HTML 与纯文本，存进这条记录，再以记录的 ID 作为 `idempotencyKey` 调用 Resend。推迟了几个小时（例如等静默结束）的邮件，因此写的是发出那一刻的内容。
   - **发出过请求：** 不重新算、不重新渲染，发存下的同样内容，用同一个键。
3. **受理后**（事务）：记下服务商返回的消息 ID，状态改为"已发送"，在同一个事务里写入已提醒标记，清掉存下的渲染结果。

**复查不通过时：**

| 原因 | 处理 |
| --- | --- |
| 静默时段、频率上限 | 推迟到允许发的时候再复查 |
| 解绑、这一类关了、内容都不再是"新"的 | 之前没有发出过请求：标为"已取消"。之前有过结果不明的请求：标为"结果不明" |
| 发出过请求之后，部分内容被读了 | 照发存下的内容；读过的那部分不影响，多列一项比破坏幂等好 |
| 发出过请求之后，预览里的字被作者删了 | 停下，标为"结果不明"。不再发送，避免把作者删掉的字送出去 |

**结果不明：** 请求发出了，但没有收到确定的答复，例如网络断开、超时、5xx。这时邮件可能已经到了。大多数情况下重试就能弄清楚：同一个键、同样的内容，Resend 已经受理过时会返回原来的结果，不会再发一封。只有复查不通过而停下，或者满 24 小时放弃时，这条记录才最终标为"结果不明"，并按下面的折中处理（Ray 2026-11-17）：

- **计入频率上限**，和"已发送"一样算进"上一封"与"当天封数"，所以就算它其实已经到了，之后也不会突破 4 小时、每天 2 封的限制；
- **不写已提醒标记**，这段内容如果仍是"新"的，之后还可以再提醒，宁可偶尔重复一封，也不悄悄漏掉一次提醒。

**Resend 的答复：**

| 答复 | 处理 |
| --- | --- |
| 受理 | 第 3 步 |
| 网络错误、超时、5xx | 结果不明，退避重试：间隔从 1 分钟翻倍，最多 1 小时 |
| 429 限流 | 按 `Retry-After` 重试 |
| 429 每日或每月额度用完 | 推迟到下一个 UTC 日或月，worker 日志说明一次 |
| 409 `concurrent_idempotent_requests`（同一个键的请求还在处理） | 稍后重试 |
| 409 `invalid_idempotent_request`（同一个键、内容不同） | 内容固定不变，正常不会出现；出现时按结果不明处理，并记错误日志 |
| 其他 4xx（地址格式不对、密钥无效、发信域名未验证等） | 标为"失败"，记下错误码。同一个人、同一类别 24 小时内不再新建发送记录，免得每 5 分钟重试一次 |
| 发送中满 24 小时（幂等键的有效期） | 没发出过请求：标为"已放弃"。发出过：标为"结果不明" |

地址存在但收不到（例如邮箱已注销）时，Resend 通常先受理、之后才退信；退信不回传给应用，第一版不处理。

### D11：时区与作息的纯计算放进一个零依赖的包 `packages/time`，网页与服务端共用

**现状：** 同一套时区计算已经写了好几份：

- `apps/api/src/anniversaries/dates.ts`：给纪念日算当地日期、当地一天的起点、日期加减；
- `apps/web/src/two-clocks/time.ts`：给两地时间算当地钟点、当地时间对应的时刻、重叠时段与"大概在睡"；
- `apps/api/src/wishes/wishes.ts` 的 `localDate`、`apps/api/src/diaries/diaries.ts` 的 `today`、`apps/web/src/diary/DayEditor.tsx` 的 `todayHere`：都是"某个时区的今天是哪一天"。

它们做的是同一件事：把时刻换成当地钟点，把当地钟点换回时刻，跨夏令时与跨午夜时取对，按天加减。静默时段（D4）需要同样的计算，如果在 `notify` 里再写一份，就又多一份。`HomePage.tsx` 里的 `formatToParts` 只是把日期排成显示用的文字，不算这类计算，不动。

**为什么会重复：** 两个 app 不能互相引用（architecture.md），而共用的两个包都放不下它：`packages/contracts` 明确不负责行为，`packages/collab` 只管 Yjs 协同模型。

**决定：** 新建 `packages/time`。

- **放什么：** 只放纯函数，只用 Intl，没有外部依赖。包括：
  - 时刻的当地钟点、当地日期，以及 `YYYY-MM-DD` 形式的当地日期（没有时区时按 UTC）；
  - 当地某天某分钟对应的时刻，以及当地一天的起点；
  - 日期加减天数与相差天数；
  - 某时刻是否落在一组作息的睡觉时段里。
- **谁用：** 网页的两地时间与日记、服务端的纪念日、心愿、日记和 `notify` 都从这里导入，原来的重复实现删除。
- **规则仍归各自的模块：**
  - 没设作息时按 23:00～8:00 静默，是邮件提醒的规则，留在 `notify`；
  - "大概在睡"的显示、重叠时段的呈现留在网页；
  - 纪念日的 2 月 29 日规则、整数日留在纪念日模块。
- **登记：**
  - architecture.md 的模块表与依赖方向各加一行；
  - 依赖方向检查加 `{ dir: 'packages/time', imports: [], externals: [] }`，`apps/api` 与 `apps/web` 可以引用它；
  - `checks/modules.json` 加上它，包里有 `README.md`，带模块 README 要求的五个小节；
  - vitest 加 `time` 项目；
  - `ops/deploy/Dockerfile` 与 `Dockerfile.web` 在 `npm ci` 之前复制它的 `package.json`；
  - AGENTS.md 的目录表加一行。

原因：依据 9。同一条时区规则只有一份实现，夏令时之类的修复改一处就处处生效。抽出现有代码属于与邮件无关的整理，所以单独一个 PR，排在落地顺序的最前面。

### 技术设计

**表**（一次迁移，本文预先批准）：

| 表 | 内容 |
| --- | --- |
| `mail_settings` | 用户（主键）、有新内容、纪念日、备份三个开关、首页提示关闭时间、更新时间。没有记录等于三个开关都开 |
| `mail_marks` | 每人每个来源一行：用户、来源（`diary`、`shared_page`、`wish`、`gift`、`gift_card`、删除记录、`anniversary`、`backup`）、来源 ID、首次发现时间、已提醒序号（空间记录）、已提醒键（纪念日的目标日期、备份的原因）、已提醒时间（备份 24 小时内同一原因只发一封用它） |
| `mail_notified_ranges` | 日记的已提醒区间：用户、日记、客户端 ID、起、止，与 `diary_read_ranges` 同样的形式和合并方式 |
| `mail_sends` | ID（同时用作幂等键）、用户、类别、收件人当地日期、状态（发送中、已发送、已取消、结果不明、失败、已放弃）、渲染好的标题、HTML 与纯文本（第一次请求前写入，受理或停下后清空）、要写入的已提醒标记、是否发出过请求、最后一次请求时间、尝试次数、下次尝试时间、错误码、服务商消息 ID、创建与发送时间。部分唯一索引：同一用户同一类别最多一条"发送中" |

**接口**（contracts 与 OpenAPI 随实现）：

- `GET /api/mail`（`user`）：本人的三个开关、收件地址、首页提示是否已关闭。
- `PUT /api/mail`（`user`）：改开关，或关闭首页提示。
- `GET /api/mail/unsubscribe?token=…`（`public`）：不改变任何状态，303 重定向到退订页 `/unsubscribe?token=…`。
- `GET /api/mail/unsubscribe/category?token=…`（`public`）：校验令牌，只返回类别；令牌无效时返回 404。
- `POST /api/mail/unsubscribe?token=…`（`public`，不检查 `Origin`）：接受 RFC 8058 的一键请求（表单体 `List-Unsubscribe=One-Click`）和退订页的请求，关闭这一类；令牌无效时返回 404。

**网页：** 设置页 `/mail`、退订页 `/unsubscribe`（不需要登录）、首页一次性提示，都经 `callApi` 调用接口。

**新配置**（由 `parseConfig` 解析，写进 `.env.example` 与 `ops/deploy/` 的环境变量示例）：

| 配置 | 谁用 | 规则 |
| --- | --- | --- |
| `RESEND_API_KEY` | worker | 不配就整个提醒不运行，worker 启动日志说明一次 |
| `MAIL_FROM` | worker | 配了 `RESEND_API_KEY` 就必须配，否则启动失败 |
| `MAIL_TOKEN_KEY` | API 与 worker | 配了 `RESEND_API_KEY` 就必须配，保证每封邮件都带能用的退订链接；API 没有它时退订接口返回 404 |
| `RESEND_BASE_URL` | worker | 可选，只给测试用，指向本地的假 Resend 服务；经配置传给 SDK 的 `baseUrl`，不让 SDK 自己读环境变量 |

**邮件模板：** 写在 `.ts` 文件里，用 `react/jsx-runtime` 的 `jsx()` 组合 React Email 组件，不用 JSX 语法，因为 Node 直接运行源码时加载不了 `.tsx`，这样也不需要构建步骤。

## 失败与恢复

| 情况 | 结果与恢复 |
| --- | --- |
| Resend 暂时不可用或限流 | 退避重试（D10），内容仍未读时晚一些送到；写日记不受影响 |
| Resend 额度用完 | 推迟到下一个 UTC 日或月；两个人正常用不会碰到 |
| `RESEND_API_KEY` 失效、发信域名验证失效（DNS 被改） | Resend 拒绝发送，标为"失败"，24 小时后再试；Ray 在 worker 日志里看到后修好。不写已提醒标记，修好之后照常判定 |
| 邮件进了垃圾箱 | 用户不知道有提醒；上线时手动检查（验收标准），在 Gmail 里标为"非垃圾邮件" |
| 请求发出后没有收到答复 | 用同一个幂等键重发同样的内容；Resend 已经受理过时返回原来的结果，收件人只收到一封。重试停下时仍不明，就计入频率上限、不写已提醒标记（D10） |
| worker 在受理后、第 3 步之前崩溃 | 重启后这条记录仍是"发送中"，用同一个键重发，处理同上 |
| 两个 worker 同时运行 | 部分唯一索引保证只有一条"发送中"，`SKIP LOCKED` 与租约保证同一条只有一个 worker 在发 |
| worker 停了几个小时 | 恢复后照常判定；读过的内容不再提醒，没读的满足条件就发，不补发错过的时段 |
| 排队期间解绑、关掉这一类、内容被读或被删 | 发送前复查不通过，不发（D10） |
| 解绑后又重新绑定 | 解绑时清掉首次发现时间，重新绑定后从头计时；已提醒标记保留，提醒过的内容不再提醒 |
| 关掉「有新内容」一段时间后又打开 | 关着时不判定并清掉首次发现时间，打开后从头计时；关着期间的未读满一小时后照常提醒 |
| 收件人出差换了时区 | 静默时段按新时区；当天封数按建发送记录时的当地日期算，换时区那天 24 小时内最多可能收到 3 封，接受 |
| 收件地址格式不对 | 标为"失败"，24 小时内这一类不再新建发送记录 |
| 邮箱存在但退信 | Resend 受理后退信，应用不知道；第一版不处理 |
| `MAIL_TOKEN_KEY` 更换 | 旧邮件里的退订链接失效（返回 404），设置页照常可用 |

## 不变量

1. 邮件里的日期、区域与预览，只来自收件人当时经获准状态读取入口和各功能的未读清单能读到的内容；未共享的日记、共享范围与排除日期不以任何形式出现。
2. 没有未结束的绑定期间时，不为「有新内容」与纪念日发出请求；每次请求前都在同一次读取里复查。
3. 预览只取收件人的列表未读文字，最多 50 个字形簇，不取共享页面与心愿的文字。
4. 已提醒的字与序号不再算"新"：被受理过的邮件里的内容，不会再触发另一封「有新内容」。
5. 两封「有新内容」间隔不少于 4 小时；同一收件人在同一当地日期最多 2 封。"已发送"与"结果不明"都计入。
6. 收件人的静默时段内不发出任何请求。
7. 邮件相关的接口只返回调用者本人的设置；没有接口返回别人的设置或发送记录。
8. 同一条发送记录的每次请求都用同一个幂等键、同样的内容；收件人最多收到一封。
9. 关掉的类别不再发出请求；退订令牌只对它所属的用户和类别有效，只能关闭、不能打开；GET 请求不改变设置。
10. 日志与错误信息不含邮箱地址、邮件标题、预览或日记文字。
11. 没有配置 `RESEND_API_KEY` 时不发出任何请求，也不写已提醒标记；配了它而缺 `MAIL_FROM` 或 `MAIL_TOKEN_KEY` 时 worker 不启动。
12. 纪念日的同一个目标日期最多一封；备份的同一种原因 24 小时内最多一封。
13. `POST /api/mail/unsubscribe` 是唯一不检查 `Origin` 的写接口；它不读 cookie，只凭有效的令牌关闭一类邮件。
14. 只有服务商受理后才写入已提醒标记；"结果不明"的记录计入频率上限，但不写已提醒标记。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **Cloudflare Email Service** | DNS 与代理本来就在 Cloudflare 上，记录一键配好；不会多一家第三方看到收件人 | 2026-04 起公测，到 2026-11 仍是 beta；发给任意收件人要 Workers Paid（5 美元/月）。Ray 2026-11-17 选了 Resend（依据 6） |
| **Gmail API（`gmail.send`）** | 不用新服务商 | `gmail.send` 是敏感权限，要重新走 Google 审核；发信绑在 Ray 一个人的账号上，搭档收到的信像是 Ray 本人发的 |
| **Gmail SMTP 加应用专用密码** | 配置最简单 | 应用专用密码能登录 Ray 的整个 Gmail，要放在服务器上；同样绑在 Ray 本人账号上 |
| **Amazon SES** | 最便宜，送达率好 | 新账号要先申请离开沙盒，IAM 与配置都比 Resend 繁琐；两个人用不出价格差 |
| **Postmark** | 送达率口碑最好 | 免费额度每月只有 100 封，长期要约 15 美元/月 |
| **自己用 `fetch` 调 Resend** | 少一个依赖 | 依据 6：要自己处理接口格式、错误与幂等；官方 SDK 用的人多、维护频繁 |
| **手写 HTML 模板** | 不加依赖 | 依据 6：名字和预览是用户写的文字，漏一处转义就可能被注入；各家邮箱客户端的兼容问题也要自己处理 |
| **只发纯文本** | 不需要模板库，不存在注入问题 | 没有按钮和样式，链接只是一行网址；Ray 2026-11-17 选了 React Email |
| **用 JSX 写模板并加构建步骤** | 模板写起来更直观 | API 现在不经编译直接运行，为几个模板加构建步骤要改 Dockerfile 与启动方式；`jsx()` 函数一样能用 |
| **不带预览** | 正文不经过发信服务商，也不会留在收件箱里 | Ray 2026-11-17 决定总是带上 |
| **作者同意才带预览** | 每个人的字是否离开应用由作者决定 | Ray 2026-11-17 决定不加这个开关，总是带上 |
| **退订只用确认页，不支持一键** | 不用放开来源检查，认证 ADR 不动 | Ray 2026-11-17 选择一键退订；放开的只是一个只能关闭、靠令牌认证的接口 |
| **请求发出后，重试时重新渲染** | 发出的内容总是最新的 | 内容一变，Resend 就以"同一个键、内容不同"拒绝，幂等失效（依据 4） |
| **判定时就渲染并冻结** | 实现最简单 | 推迟几个小时（静默时段）后发出的是过时的内容，可能列出早已读过的东西、带上已被删掉的预览 |
| **在 API 的提交事务里触发发信** | 对方一写完就能开始计时 | 一小时的延迟和静默时段本来就要靠定时判定；提交链不应该承担外部副作用（依据 4） |
| **直接用 space-records 的 `unseen` 判定空间未读** | 不用改各功能服务 | 哪些记录和删除记录算未读由各功能决定，绕过它们会与导航圆点不一致（依据 9） |
| **在 `notify` 里再写一份时区计算** | 不动已上线的代码 | 违反依据 9：修一处漏几处（D11） |
| **把时区函数放进 `packages/contracts`** | 不用新建包 | contracts 只放线上格式与路由表，明确不负责行为（architecture.md）；为省一个包打破边界 |
| **每条新内容发一封** | 最及时 | 违反依据 2；两个人一天能写很多段 |
| **发过一封之后，等你回来才发下一封** | 最安静 | Ray 2026-11-17 选了"隔 4 小时、每天 2 封"；很久不打开应用的人只会收到一封 |
| **网页推送** | 不经邮箱，到达更快 | 依据 8：要新增订阅管理与推送服务；以后可以作为另一个渠道，复用本文的规则 |

## 风险与代价

- **预览离开了应用：** 预览会经过 Resend，留在收件人的邮箱里。作者之后删改不会同步到已发出的邮件。设置页的固定说明告知了这一点，作者没有开关。
- **Resend 能看到的内容：** 收件人邮箱、对方的名字、日记日期与预览。它的后台会保留邮件内容一段时间。
- **数据库里短暂存着渲染好的邮件：** 从第一次请求到受理或停下，最多 24 小时；之后清空。数据库本来就存着日记全文，备份照常加密。
- **结果不明时可能重复一封：** 极少数情况下（Resend 受理之后、答复之前出故障，并持续到复查不通过或满 24 小时），收件人已经收到的那段预览，之后可能再出现在另一封邮件里。频率上限照常生效，不会刷屏。
- **只提醒一次：** 一段内容提醒过一次后不再提醒；收件人一直没读，也不会收到第二封。共享页面更明显：提醒过以后，你打开它之前，对方在这页写多少都不再提醒。
- **时间粒度：** 每 5 分钟判定一次，从字成为历史到收到邮件最多约 1 小时 10 分钟（首次发现最多晚 5 分钟，判定再最多晚 5 分钟）；静默结束后最多再晚 5 分钟。
- **判定的开销：** 每 5 分钟对每人跑一遍列表未读，缓存命中时只读几次数据库；正文有变化的日记才重建。worker 的各项任务依次运行，判定期间 Drive 副本会晚几秒。
- **放开了一个接口的来源检查：** 退订接口任何网站都能调，但没有令牌什么也做不了，有令牌也只能关闭。
- **多一个包：** `packages/time`（D11）要在好几处登记；抽出时要动两地时间、纪念日、心愿与日记已上线的代码，靠它们现有的测试保证行为不变。
- **新邮箱的信誉：** 新的发信域名起初可能进垃圾箱。上线时手动检查，必要时在 Gmail 里标为"非垃圾邮件"。
- **依赖：** `apps/api` 新增 `react` 与 `react-dom`，只用来渲染邮件。
