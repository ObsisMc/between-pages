# ADR-0003：PG 主存储、持久化确认与事务 outbox

日期：2026-10-24。状态：已采纳；部署服务商和具体运行拓扑待选。

## 背景

用户明确指定 PostgreSQL。早期本地实验采用 Vinext/React + Cloudflare/Sites 脚手架，hosting manifest 使用 D1，并包含平台认证辅助文件。该实验脚手架未纳入本仓库的初次提交；正式应用尚未实现，不能将这些默认配置当成 PG 架构已经完成。

正文保存、并发唯一日记、实时协同及 Google 后台任务需要一致的提交边界，避免界面显示已保存但服务器重启丢失，或数据库提交后遗漏备份。

## 决策

1. PostgreSQL 是正式主存储，保存空间、成员、日记元数据、协同状态/增量、读取进度、任务与备份映射。
2. 文字状态或增量、操作幂等记录、提交版本和 Google outbox 在同一事务内持久化。
3. 数据库事务成功后才确认保存并广播已提交变更。数据库不可用不降级成仅内存“保存成功”。
4. 每篇日记使用单一逻辑提交序列；多实例之间需房间归属/锁、版本检查等一致性协调。具体采用哪一种待验证，不允许两个实例独立覆盖全文。
5. WebSocket 网关与后台备份 worker 可以与应用同服务部署，但生命周期、故障重启和任务续跑要独立可控。MVP 不预设需要 Redis 或 Kafka。
6. 本地缓存用于待同步恢复，不是正式主库；Google 副本是独立恢复资源，不参与正文提交事务，不阻塞写日记。
7. PG 的数据库级备份保留在独立故障域并做恢复演练。协同增量压缩/清理之前必须保证快照完整，不破坏待同步客户端的重连与未读锚点。

## 运行边界

建议逻辑链路：浏览器编辑器与本地队列 → 认证 API/协同网关 → PG 事务 → ACK/广播；PG outbox → 后台 worker → Google。

目前不承诺继续使用原 Sites 托管。实现前需验证所选环境的 PG 连接、长连接、房间一致性、定时/持久任务、Google OIDC 和密钥能力。可迁移为常规 Node 运行时与托管 PG，也可采用能满足要求的其他运行环境；变更托管方案需记录，不擅自把用户要求改回 D1。

不要为了部署方便将平台注入的登录身份直接当作用户要求的 Google 登录已实现；认证 provider 与应用 userId 的映射需要明确。

## 替代方案

- D1 作为正式主存储：与用户指定不符。
- PG 提交后直接内存排队上传 Google：崩溃可能丢任务。
- 同步等待 PG 和 Google 双写完成才保存：Google 故障会阻塞写日记，且没有跨系统原子事务。
- 广播后再写库：另一方看到的内容可能从未被可靠提交。

## 后果与验证

增加事务、幂等和后台任务的实现工作，换来可解释的保存状态与可恢复任务。不提供服务器故障时完整应用仍然可用的高可用承诺。

验收：DATE-03、SAVE-01～08、GOOGLE-05～07、RELEASE-04。
