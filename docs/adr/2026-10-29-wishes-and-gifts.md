# 心愿单让对方不用问就知道想要什么，送礼在揭晓前只有送的人看得到，揭晓后连同卡片进礼物墙

- 状态：提议
- 日期：2026-10-29
- 决策者：Ray
- 范围：领域
- 关联：依赖 space-records；依赖 spaces-and-invitations；依赖 anniversaries

每人在双人空间里记自己的心愿：名称、可选的链接（显示标题和图片的预览）、备注和 1～5 颗心表示有多想要。对方想送时，在这条心愿上标"我在准备"，也可以不依赖心愿单直接准备一份惊喜；准备中可以先写一张卡片。准备中的礼物和卡片只有送的人看得到，许愿的人那边什么都不变，也不产生未读。送的人点"揭晓"，或许愿的人在自己的心愿上点"收到了"，哪个先发生就算揭晓：礼物和卡片出现在收的人面前，进入两人共有的礼物墙。礼物墙按日期排、可按场合与谁送的筛选，日期和场合两人都能改。

本文不负责：收的人回一句感受、链到那天的日记（用户 2026-10-29 未选）；照片（规格不做附件）；代买、付款与物流跟踪；通知（阶段 4）。共用的归属、作者、动作、解绑、删除、未读规则见 space-records，本文只写心愿与送礼自己的部分。

## 背景与问题

异地时送礼最难的是不知道送什么，直接问又没了惊喜；礼物寄到时只是收个快递，事后也没有地方回看这些年互相送过什么。用户于 2026-10-29 确认这个功能要做到四件事：不用问就知道 TA 想要什么、保留惊喜、收礼时有仪式感、攒下一面礼物墙。

"保留惊喜"需要一种只有送的人看得到的状态。space-records 的未读规则（D8）会把对方的动作计为未读，这类状态必须例外，否则圆点本身就泄露了惊喜；这一例外同时补进 space-records。

## 决策依据

1. 对方不用问就能知道我想要什么，具体到款式、颜色和有多想要（用户 2026-10-29）。
2. 准备中的礼物在揭晓前不能以任何方式被收的人察觉：列表、详情、未读圆点、删除提示、错误与计数都不能露馅（用户 2026-10-29 选择只有送的人看得到）。
3. 收礼有一个"揭晓"的时刻，送的人写的卡片在这一刻出现；可以标上场合（用户 2026-10-29）。
4. 礼物墙收录两人互送的所有礼物，不只是心愿单上的（用户 2026-10-29 选择单外的惊喜也能记）。
5. 链接要能看到预览，但服务器不能因此被用来访问内网，也不存图片（规格不做附件；用户 2026-10-29 选择图片直接引用）。
6. 有多想要用图形表示，不用文字（用户 2026-10-29 选择 1～5 颗心）。
7. 共用规则沿用 space-records：文字归作者、动作记操作人、绑定中才能写、解绑后只读、删除时对方有提示、不进 Google、按条目判定未读。

## 决策

### D1：心愿归许愿的人，有名称、链接、备注和 1～5 颗心

一条心愿的作者是许愿的人（space-records D3），只有他能改、能删。字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 名称 | 是 | 最多 100 字 |
| 链接 | 否 | 只接受 `http`/`https`，显示为预览（D7） |
| 备注 | 否 | 尺码、颜色、"哪个牌子都行"，最多 500 字 |
| 想要程度 | 否 | 1～5 的整数，显示为心；心愿单默认按它从高到低、再按新旧排 |

两人都能看到对方的心愿单和自己的心愿单。对方新许的、改过的心愿按 space-records D8 计为未读。

原因：依据 1、6。

### D2：准备中的礼物只属于送的人，收的人看不到它存在

送的人可以：

- 在对方的某条心愿上点"我在准备"，生成一份关联这条心愿的**准备中的礼物**；每条心愿至多一份（只有一位可能的送礼人）；
- 不依赖心愿单，直接建一份准备中的礼物（名称必填，可选链接）。

准备中的礼物、它的卡片和与它相关的所有动作，在揭晓前是**私密**的：只返回给送的人，不进入收的人的任何输出，包括心愿与礼物墙列表、详情、未读与入口圆点、删除提示、计数与错误信息。收的人操作一条有人在准备的心愿（修改、删除、点"收到了"）时，请求的结果与没人准备时完全一样。

送的人可以随时取消准备（删除准备中的礼物），收的人不会知道。

许愿的人修改或删除了送礼人正在准备的心愿时：

- 修改：送的人按 space-records D8 看到这条"改过"；
- 删除：送的人看到删除记录"TA 删了'灰色围巾'，你在准备"（space-records D6），准备中的礼物保留并转为不关联心愿的惊喜，卡片不丢，送的人可以继续送或自己删除。

原因：依据 2、4。这是 space-records 的私密状态例外（space-records D9）：私密的记录与动作只对操作人可见，不计入对方未读，对方的操作不因它的存在而表现不同。

### D3：卡片是送的人写的独立记录，揭晓时出现

送的人可以在准备时写一张卡片（最多 1000 字），作者是送的人，只有他能改。卡片随礼物私密，揭晓时一起出现在收的人面前。揭晓后送的人仍可以补写或修改卡片，按 space-records D8 计为对方的未读。

卡片作为独立记录而不是礼物的一个字段，是因为礼物可能由收的人的"收到了"创建（D4），而卡片的文字始终只属于送的人（space-records D3）。

原因：依据 3。

### D4：揭晓只发生一次：送的人点揭晓，或收的人在自己的心愿上点收到了

| 谁先做 | 结果 |
| --- | --- |
| 送的人对准备中的礼物点"揭晓" | 礼物与卡片出现在收的人面前，进入礼物墙；如果关联心愿，这条心愿离开心愿单 |
| 许愿的人在自己的心愿上点"收到了"，且对方正在准备 | 同上，送的人准备的礼物与卡片一起揭晓 |
| 许愿的人在自己的心愿上点"收到了"，没人在准备 | 生成一份由对方送出的礼物进礼物墙，没有卡片；送的人之后可以补写卡片 |

不关联心愿的惊喜收的人看不到，只能由送的人揭晓。揭晓在锁住这条心愿（或准备中的礼物）的事务里完成，两人同时操作也只揭晓一次。揭晓后不能撤回。

自己买了或不想要了的心愿，许愿的人直接删除，不点"收到了"。还想要同样的东西，重新许一条。

原因：依据 3、4。两种触发都允许，是因为异地寄送时快递常比送的人更早"揭晓"。

### D5：礼物墙收录所有揭晓的礼物，日期与场合两人都能改

礼物墙把两人互送的礼物放在一起，按礼物日期从新到旧排，可以按场合、按谁送的筛选。每份礼物显示：名称（及链接预览）、谁送给谁、日期、场合、卡片。

- **日期**：默认是揭晓当天（按揭晓人的当地日期），两人都能改，例如当面给的、事后才记。
- **场合**：可选，二选一：一个具体的纪念日（如"TA 的生日"，anniversaries D4），或通用场合节日、见面、没什么理由；两人都能设或改。礼物记下纪念日的 ID 与当时的名称，纪念日删除后保留名称、不再链接。礼物墙可以按某个纪念日筛选。

改日期与改场合是动作（space-records D4），记下是谁、什么时候改的。礼物名称来自心愿或送的人建礼物时的名称；从心愿揭晓时复制心愿当时的名称、链接与预览，之后心愿删除不影响礼物墙。礼物的删除按 space-records D6：只有礼物记录的作者（建它的人）能删，对方有提示。

原因：依据 3、4。

### D6：动作清单

| 动作 | 对象 | 谁能做 | 私密 |
| --- | --- | --- | --- |
| 我在准备 / 取消准备 | 对方的心愿 | 对方 | 是 |
| 揭晓 | 准备中的礼物 | 送的人 | 揭晓前的准备是私密的，揭晓本身两人可见 |
| 收到了 | 自己的心愿 | 许愿的人 | 否 |
| 改日期 | 礼物 | 两人 | 否 |
| 改场合 | 礼物 | 两人 | 否 |

心愿、准备中的礼物、卡片的新建、修改、删除按 space-records D3、D6 由各自作者做。

### D7：链接预览由服务端读取一次，只存文字和图片地址

保存或修改带链接的心愿（或礼物）后，后台 worker 读取一次链接，取页面的标题、网站名与预览图片地址（Open Graph 与 `<title>`），存为文字。读取期间和读取失败时显示网站域名。

读取的边界：

- 只访问 `http`/`https`；每次连接前解析域名，拒绝回环、私有、链路本地、组播与云厂商元数据地址；重定向最多 3 次，每一跳重新检查；
- 超时 5 秒，最多读取 1 MB，只解析 `<head>`；不执行脚本、不带 Cookie；
- 读到的标题与网站名按纯文本显示；图片地址只接受 `https`。

图片由浏览器直接从原网站加载，带 `referrerpolicy="no-referrer"`，服务器不下载、不存图片。原网站拦截抓取或图片失效时，退回到只显示网站名。

不为此新增依赖；若实现时确实需要 HTML 解析库，按 AGENTS.md 先询问。

原因：依据 5。读取放在 worker 而不是保存请求里，保存不必等第三方网站。

### D8：解绑与重新绑定

按 space-records D5：解绑后心愿单与礼物墙两人只读，准备、揭晓、改日期等都不能做。解绑时还没揭晓的礼物继续只有送的人看得到（只读）；原来的两人重新绑定后，可以继续准备和揭晓。

## 数据与模块

- **表**（共用列见 space-records）：`wishes`（名称、链接、备注、想要程度、预览标题、预览网站名、预览图片地址、预览读取时间）；`gifts`（送的人、收的人、来源心愿、名称与链接及预览的副本、状态：准备中或已揭晓、揭晓时间、日期、场合：通用场合或纪念日 ID 加名称副本）；`gift_cards`（礼物、正文；作者为送的人）。动作与变更进 space-records 的共用表，私密的那些带 `private_to`（只对该用户可见）。
- **服务端**：`apps/api/src/wishes/` 服务，只经 `space-records` 写入；链接读取在 worker 中，作为 `wishes` 的一个后台任务。
- **网页**：`apps/web/src/wishes/`（心愿单、准备中的礼物、揭晓、礼物墙），导入 `space-common` 与 `api`。
- 迁移与新表在实现 PR 中生成；本 ADR 采纳即视为预先批准。

## 失败与恢复

| 情况 | 结果 | 恢复 |
| --- | --- | --- |
| 两人同时揭晓同一份礼物 | 锁内排序，只揭晓一次，后到的请求返回已揭晓的结果 | 无需处理 |
| 许愿的人删除心愿时对方正点"我在准备" | 锁内排序：准备先到则删除后转为不关联心愿的惊喜并通知送的人；删除先到则准备被拒为"这条心愿已不在" | 送的人可改为直接准备一份惊喜 |
| 链接读取超时、被拒或地址不允许 | 预览为空，显示网站域名 | 修改链接会重新读取 |
| 预览图片加载失败 | 只显示标题与网站名 | 无需处理 |
| 揭晓时刚好解绑 | 写入被拒（space-records D5） | 重新绑定后再揭晓 |

## 不变量

1. 心愿的名称、链接、备注与想要程度只有许愿的人能改；想要程度为空或 1～5 的整数。
2. 揭晓前，准备中的礼物、它的卡片和相关动作只返回给送的人；收的人的任何响应（列表、详情、未读、圆点、删除提示、计数、错误）与没有人在准备时相同。
3. 每条心愿至多关联一份准备中的礼物，每份礼物至多揭晓一次，揭晓不可撤回。
4. 揭晓由送的人的"揭晓"或许愿的人在自己心愿上的"收到了"触发；不关联心愿的惊喜只能由送的人揭晓。
5. 揭晓时卡片对收的人可见；卡片的文字只有送的人能改。
6. 礼物墙的日期与场合两人都能改，每次修改作为动作记录操作人与时间；场合是一个通用场合或一个纪念日。
7. 链接读取只访问公网的 `http`/`https` 地址，受次数、时间与大小限制；只保存文字与图片地址，服务器不保存图片。
8. 预览图片以不带来源信息的方式由浏览器直接加载；读不到时界面仍可用。
9. 解绑后心愿与礼物两人只读，未揭晓的礼物仍只对送的人可见；重新绑定后恢复操作。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **只保留"已收到"，没有准备中的状态** | 没有私密状态，最简单 | 送的人无法提前写卡片，也无法记录单外的惊喜（依据 3、4）；用户选择保留惊喜 |
| **让收的人知道"有一份礼物在路上"** | 增加期待感 | 收的人会去猜，削弱惊喜（依据 2）；用户选择完全隐藏 |
| **只有收的人确认收到才揭晓** | 规则统一 | 单外的惊喜收的人看不到、点不了，只能先提示"有礼物待确认"而提前露馅（依据 2） |
| **礼物墙只收心愿单上的礼物** | 最简单 | 漏掉大量不在单上的礼物（依据 4） |
| **收的人事后补记礼物** | 不需要私密状态 | 送的人无法提前写卡片（依据 3） |
| **卡片作为礼物的一个字段** | 少一张表 | 礼物可能由收的人创建，字段的作者说不清（space-records D3） |
| **日期只有送的人能改** | 符合"文字归作者" | 收的人也常需要补正日期；用户 2026-10-29 决定两人都能改，按动作记录 |
| **缩略图存在自己的服务器** | 显示稳定，原网站看不到访问 | 要存图片、进备份，与规格不做附件冲突（依据 5） |
| **只显示标题和网站名，不要图片** | 最稳妥 | 不像预览；用户选择标题加图片 |
| **想要程度用文字（很想要、有就好）或 0～100 滑条** | 文字更明确；滑条更细 | 用户要图形；滑条难以区分相近的值（依据 6） |

## 风险与代价

- 私密状态是最容易出错的部分：任何一个新接口、通知或统计忘了过滤，都会提前泄露惊喜。实现时集中在 `space-records` 的读取出口过滤，并用"收的人视角的响应在有无准备时逐字节相同"的测试覆盖。
- 服务端去读用户填的网址有 SSRF 风险；D7 的限制必须由测试覆盖，包括 DNS 解析到私有地址与重定向到私有地址。
- 大型购物网站常拦截抓取，预览经常只剩网站名。
- 图片直接从原网站加载，原网站能看到查看者的 IP；接受这一点以避免存图片。

## 未解决的问题

- 揭晓那一刻的呈现（例如打开卡片的动画）由阶段 4 的前端调整决定；本文只规定揭晓前后谁能看到什么。

## 落地顺序

1. **本 ADR 采纳**：与第一批其他功能的设计、space-records 的补充（D9 私密状态）一起评审。
2. **实现**：心愿与送礼是第一个使用双人空间记录的功能，同一 PR 落地 space-records 的共用服务、共用表、`space-common`，以及本功能的迁移、契约、服务、worker 中的链接读取与网页模块；依赖方向规则同时更新。可以拆成多个提交，但在共用部分合并前不合并本功能。
3. 实现后本文与 space-records 转为"已实现"，路线图与 README 状态行同步。

## 验收标准

- 对方不能修改或删除我的心愿；想要程度超出 1～5 被拒（API 测试，不变量 1）。
- 收的人视角：有人准备与没人准备时，心愿单、详情、未读汇总、删除心愿与点"收到了"的响应相同（API 测试，不变量 2）。
- 同一心愿两次"我在准备"只生成一份；两人并发揭晓只揭晓一次（DB 测试，不变量 3）。
- 三种揭晓路径的结果与卡片可见性（API 测试与浏览器测试，不变量 4、5）。
- 两人分别改礼物日期与场合，历史记录两次动作（API 测试，不变量 6）。
- 链接读取拒绝回环、私有、元数据地址，以及经重定向或 DNS 指向这些地址的链接；超时与超大页面被截断（API 测试，不变量 7）。
- 预览图片带 `referrerpolicy="no-referrer"`，图片失效时显示网站名（组件测试，不变量 8）。
- 解绑后两人都不能操作，送的人仍能看到未揭晓的礼物，重新绑定后能揭晓（API 测试，不变量 9）。
- 验证某条不变量的测试标题带 `[adr:wishes-and-gifts#<编号>]`。

## 补充信息

- 重新评估条件：支持多位送礼人或一个账号多个空间；规格允许附件（可以存缩略图）；加入通知（揭晓与准备的提醒必须同样遵守私密规则）；链接预览因网站拦截基本不可用。
- 证据：2026-10-29 与用户逐条确认（四个目标、只有送的人看得到、单外惊喜、两种揭晓方式、卡片与场合、不要感受与日记链接、心愿字段与 1～5 颗心、链接预览方式、礼物墙排序与筛选、日期两人都能改、解绑后未揭晓礼物仍只对送的人可见）；同日纪念日提到第一批后，用户确认场合可以选具体的纪念日。
