# 每人在设置里改自己的名字，两人看到同一个，改后处处现读，Drive 里 Together 下的 Doc 随之重写

- 状态：提议
- 日期：2026-11-18
- 决策者：Ray
- 范围：领域
- 关联：依赖 authentication-and-sessions；依赖 spaces-and-invitations；依赖 google-copy-beyond-diaries；取代 authentication-and-sessions 的D2 中 `users` 只由当前用户入口写入的部分

每人在「设置 → 我的名字」（`/name`）改自己在应用里的名字，两人看到的是同一个。这个名字就是 `users.display_name`，第一次登录时取 Google 名字，没有名字时取邮箱 `@` 之前的部分，这条默认规则不变。名字去掉首尾空白后是 1–20 个字，按用户看到的字计数，不能含换行等控制字符，也不能是看不见的名字；不检查是否与对方重名。接口是 `PATCH /api/me`，改的是谁只从会话里取。所有显示名字的地方本来就是显示或生成时现读这一列，所以保存之后，应用、之后发出的邮件和之后写入的 Google Doc 都是新名字。唯一的例外是礼物场合存下的"X 的生日"。改名时，如果两人正在绑定中，服务端在同一个事务里把这个空间 `Together` 下的所有 Doc 登记为待写，两人各自 Drive 里的汇总和页面 Doc 都会换成新名字；每天一份的日记 Doc 不批量重写，等那一天下次写入时再带上新名字。改名不给对方任何提示，也不保留改名历史。第一次登录不拦，只在设置 → 搭档发邀请时和 `/join` 确认页上，在名字旁边放一个"修改"。

本文部分取代 authentication-and-sessions 的 D2：`users` 表"谁写"一列原来是"只有当前用户入口"，现在加上本文的改名单元，它只写 `display_name`。该 ADR 的其余部分不变，13 条不变量都不受影响。不负责：只有自己看得到的对方昵称（见未解决的问题）；头像；时区、作息与邮件提醒设置（它们各有 ADR）；改登录邮箱或登录方式。

## 背景与问题

名字只存一处，就是 `users.display_name`，由认证 ADR D2 在第一次登录时写入，之后"归领域层所有，Google 资料变化不覆盖它"。但现在没有接口，也没有界面能改它。于是 Google 账号上的全名，或者 Google 没给名字时邮箱 `@` 之前的那一段，会一直出现在对方的页头、作者图例、邀请确认页、邮件和 Drive 里。2026-11-18，Ray 提出让用户改两人空间里显示的名字。他同意写一份只管名字的 ADR，而不是一份通用的"个人资料设置"ADR。

要回答的问题：这个名字是什么（每人一个，还是给对方起私人昵称）；什么样的名字合法；改了之后哪些地方跟着变；已经写进 Drive 和发出去的内容怎么办；要不要告诉对方；第一次登录要不要确认；放在界面哪里、由哪个模块负责。

每个账号只有一个永久的双人空间，首版也不能换搭档（spaces-and-invitations），所以"我在空间里的名字"就是我的显示名字，不需要按空间区分。

## 决策依据

1. 名字是自己的，只有自己能改；两人看到的必须是同一个名字，否则说"我改名了"时两边对不上（Ray，2026-11-18 选 A）。
2. 改名是很少发生的事，不为它新建表、迁移或通知通道；能复用的机制都复用（项目规范：没有当前消费者就不加参数、配置或兼容分支）。
3. 名字在哪里显示，就在哪里现读，不留副本。这样改名不需要追着更新任何地方。
4. Google 里的副本与应用里看到的一致（google-copy-beyond-diaries 依据 1）。汇总 Doc 承诺"按当前状态"，日记和页面 Doc 承诺"到最新历史版本"，两者对名字的处理按各自的承诺来。
5. 模块边界不为一个很少见的场景让步：一个功能不写另一个功能的数据（space-records、architecture 的依赖方向）。
6. 作者和"谁在改"只来自服务端会话，不来自客户端输入（ADR-0003、ADR-0006）。

## 决策

### D1：名字是每人一个，自己改自己的，两人看到同一个

名字就是 `users.display_name`，一个账号一个。只有本人能改，改后对方看到的也是这个名字。不做"给对方起一个只有自己看得到的昵称"。

为什么：依据 1、2。私人昵称要新建一张"谁给谁起的名字"的表，而且每个出口都要按"谁在看"选名字：作者图例、页头、邮件里的"X 写了新内容"、每人 Drive 里的 Doc、纪念日的"X 的生日"、礼物场合的副本。改动面是本文的好几倍，而 Ray 要的是"别再显示 Google 名字或邮箱前缀"，A 已经解决了这个问题。私人昵称留作以后评估，见未解决的问题。

### D2：名字去掉首尾空白后 1–20 个字，不能含控制字符，不查重名

| 规则 | 说明 |
| --- | --- |
| 去掉首尾空白 | 按 Unicode 空白（`String.prototype.trim`）；存的是去掉之后的值 |
| 1–20 个字 | 按 grapheme 计数（`Intl.Segmenter`，`granularity: 'grapheme'`）：`👩‍❤️‍👨` 算 1 个字，`小雨` 算 2 个 |
| 不能含控制字符 | 拒绝任何 `\p{Cc}`（换行、制表符等）与 U+2028、U+2029 |
| 不能是看不见的名字 | 去掉所有空白与 `\p{Cf}`（零宽字符、方向标记）后至少剩一个字符；`\p{Cf}` 夹在中间是允许的，因为 emoji 组合要用零宽连接符 |
| 不查重名 | 可以与对方同名；与原来相同的名字照常保存，返回 200 |

规则写成 `packages/contracts` 里的一个 Zod schema `DisplayName`：接口用它校验请求，网页用它在保存前给出提示，两边是同一条规则。`UserSummary.displayName` 仍是 `z.string()`，所以已有的、超过 20 个字的名字照常读取；只在改名时才要求合规，编辑框里显示原名，要缩短后才能保存。第一次登录时的默认值不经过这条规则（D6）。

为什么不查重名：两人的文字用颜色区分，自己那边显示"我"，所以重名也不会认错作者。要查重就得在两个账号的改名之间加锁：两人同时改名会有竞争，一方先占用某个名字，另一方就用不了。绑定之前没有搭档，规则还会变成有时检查、有时不检查。（Ray，2026-11-18 按推荐定。）

### D3：所有显示名字的地方都现读，保存后就是新名字

下面这些地方都是在显示或生成时从 `users.display_name` 读名字，不需要改：

| 地方 | 服务端或网页的位置 |
| --- | --- |
| 页头账号名、首页问候、首页两扇窗 | `SiteHeader`、`HomePage`（读 `GET /api/me` 与空间参与者） |
| 日记的作者图例、"谁写的"弹层、双页工作区 | `diary/people.tsx`、`DayEditor`、`DaysWorkspace`（读 `bindings` 给出的参与者） |
| 搭档卡片、"与 X 的空间"、空间页参与者、`/join` 的当前账号与邀请者 | `relationship/`、`space/`、`join/`；服务端 `bindings` |
| 站内邀请横幅"X 邀请你一起写日记"（in-app-invitation-by-email，提议中） | 经 `UserSummary` 现读，不存副本 |
| 两地时间里的对方 | `clocks` |
| 心愿与礼物（"X 送给我"、删除提示）、纪念日（"X 的生日"、送礼人）、共享页面的删除提示 | `wishes`、`anniversaries`、`shared-pages` 及其页面 |
| 戳团子与摸团子的气泡 | 网页 `pokes`，名字来自首页的参与者 |
| 邮件标题与正文（"X 写了新内容""X 的生日还有 N 天"） | `notify` 在发信时读，`mail` 渲染 |
| Google Doc 里的"X 的日记""X 的心愿""X 送给 Y"与作者图例 | `backup` 在写入时经 `store/copy.ts` 读 |

- **自己这边**：`PATCH /api/me` 成功后，网页刷新 `me` 和空间相关的查询，页头、首页和正在看的页面马上换成新名字。
- **对方那边**：下次读到数据时（换页、窗口重新聚焦、刷新）看到新名字，不做实时推送，与"服务器推送现在不做"一致。

**唯一的副本：礼物场合。** 选礼物场合时，`gifts.occasion_name` 记下当时纪念日的名字（anniversaries D4），生日就是"X 的生日"。纪念日还在时，界面按 ID 显示它现在的名字，所以会跟着改名变；只有那个生日纪念日被删掉以后，才显示这份副本。因此"先改名、后删生日"时，礼物上留的是旧名字。这份副本保持不变，作为已知限制，原因是依据 5：改名时连它一起改，就要让名字单元去写心愿与礼物的表。纪念日本身改名时也不更新这份副本，两者的处理一致。（Ray，2026-11-18。）

### D4：改名时 `Together` 下的 Doc 重写，日记 Doc 等下次写入

| 已有内容 | 改名后 |
| --- | --- |
| 心愿单、礼物墙、纪念日三份汇总 Doc | 两人正在绑定中时，在改名的同一个事务里调用 google-copy-beyond-diaries 的 `registerSpaceCopy`，`recordType: null`（这个空间所有 `Together` Doc），`privateTo: null`（两人的 Drive 都登记）。之后按该 ADR D5 的 2 分钟规则重写；内容校验值没变的 Doc 不实际写入 |
| 共享页面 Doc | 同上，随同一次登记重写到该页最新的历史版本，作者图例换成新名字 |
| 每天一份的日记 Doc | 不批量重写。那一天下次形成历史版本时，整份按新名字写入；"现在备份"也只处理等待中的日期，不重写它们 |
| 已解绑的空间 | 不登记。`Together` 下的 Doc 写着"（已解绑，内容不再更新）"，名字也不再更新；原来的两人重新绑定时，绑定流程本来就会登记整个空间重写，届时带上新名字 |
| 没有空间 | 不登记 |
| 已发出的邮件 | 保持原样，之后的邮件用新名字 |
| 邀请（链接 `/join` 预览、站内邀请横幅） | 现读，自动是新名字 |
| 名字没变（与原来相同） | 不登记 |

为什么：依据 4。汇总 Doc 承诺"按当前状态整份渲染"（google-copy-beyond-diaries D6），留着旧名字就违背了承诺；页面 Doc 数量少。两类都只要一次登记，复用绑定与解绑已在用的入口，不需要新机制（依据 2）。日记 Doc 是"那一天最新历史版本"的副本，可能有几百份，全部重写既占 Drive 配额，又会在每份 Doc 的 Google 版本历史里多出一版，所以按它自己的规则，下次写入时带上新名字。（Ray，2026-11-18。）

### D5：改名不给对方任何提示

不加未读圆点，不在首页或页头显示"TA 改名为 …"，也不发邮件。不保存改名历史，也不显示"曾用名"。

为什么：依据 2。名字不是对方写的内容。未读、圆点和邮件提醒只针对"对方写了新东西"（unread-and-day-page、space-records、email-reminders），把改名加进去会扩大这三套规则的范围，还要存"改名事件"和"对方是否看过"。两个人之间改名通常已经当面或在聊天里说过。（Ray，2026-11-18。）

### D6：第一次登录不拦，在名字第一次要给对方看到时提供"修改"

第一次登录仍按认证 ADR D2 取默认名字，不加确认步骤，也不加首页提示。在两个地方的名字旁边放一个"修改"，点开就地编辑（与 `/name` 同一个组件），改完留在原页面：

- **设置 → 搭档**（`/partner`），发邀请的表单上方："对方会看到你叫 {名字} · 修改"。链接邀请和站内邀请（in-app-invitation-by-email）都在这一页发出。
- **`/join` 确认页**，现有的"当前账号：{名字}"旁边。

为什么：依据 2。绑定之前名字只有自己看得到；真正要紧的是对方第一次看到它的时候，而这两个页面正好是那一刻。这样不用存"是否确认过"的标记，没有迁移，也不改认证 ADR 的默认规则。大多数人的 Google 名字已经能用，第一次登录就强制填表会让每个人多一步。（Ray，2026-11-18。）

### D7：界面放在设置里，接口是 `PATCH /api/me`，由新单元 `display-name` 负责

**网页。** 「设置」菜单新增「我的名字」，路由 `/name`。不论是否绑定都显示，排在「邮件提醒」后面。页面上有一个输入框、一个保存按钮，下面一行说明："对方会看到这个名字。Google Drive 里的日记 Doc 等那一天下次备份时更新。"保存前用 `DisplayName` 校验，不合格时就地显示原因（"名字最多 20 个字""名字不能为空"）；服务端拒绝时显示同样的文案。新的网页单元 `name` 负责这个页面和就地编辑组件，只引入 `api`、`shell`、`ui`；`relationship` 与 `join` 引入它的编辑组件（D6）。

**接口。**

| 路由名 | 方法与路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| `updateMe` | `PATCH /api/me` | `{ "displayName": "<DisplayName>" }`，`strict`，不能带其他字段 | `200 { "user": UserSummary }`，与 `GET /api/me` 相同；不合格为 `400 VALIDATION_FAILED`；未登录为 `401` |

- 改的是谁，只从会话（`request.user`）里取，请求体没有用户 ID（依据 6）。
- 是非 GET 请求，照常经过来源检查（认证 ADR 不变量 7）。
- 同一请求重复发送结果相同，所以不需要 `requestId`。
- 两个标签页同时改名，以后写入的为准。

**服务端模块。** 新的服务单元 `apps/api/src/display-name/`，只引入 `store` 与 `errors`；`routes` 调用它。它在一个事务里：

1. 读本人当前的 `display_name`。与新值相同就直接返回。
2. `update users set display_name = $1 where id = $caller`。
3. 如果本人有一个正在绑定中的空间，调用 `registerSpaceCopy`（D4）。

`store` 增加改名与"本人当前绑定中的空间"两个查询。依赖方向检查的规则表加上 `'display-name': ['store', 'errors']`，`routes` 的列表里加上 `display-name`；网页那张规则表加上 `name: ['api', 'shell', 'ui']`，并把 `name` 加进 `relationship` 与 `join` 的列表。

为什么不放进 `auth`：`auth` 现在只依赖 `config`、`db`、`errors`，负责登录、会话和"当前用户"入口。放进去就要让它依赖 `store`，还要知道 Google 副本的待写队列，等于把两件事混在一起（依据 5）。单元叫 `display-name` 而不叫 `profile`，免得以后别的个人设置也往里塞；时区、作息与邮件提醒各有自己的单元。

**部分取代认证 ADR D2。** D2 的表里，`users` 的"谁写"一列是"只有当前用户入口（D7）"。现在改为：当前用户入口创建行并更新 `last_seen_at`；`display-name` 只更新 `display_name`。D2 其余内容（默认名字的来源、Google 资料变化不覆盖它、两层用同一个 UUID）不变。认证 ADR 的不变量 10 说的是"业务代码只通过当前用户入口得知调用者"，本文照此执行：`display-name` 拿到的调用者来自 `request.user`。

## 失败与恢复

| 情况 | 结果 | 恢复 |
| --- | --- | --- |
| 名字不合格 | 400，什么都不写 | 网页就地提示，用户改了再存 |
| 事务失败（数据库不可用等） | 名字和 Google 待写都没变 | 网页显示保存失败，原样保留输入，用户再点保存 |
| 保存成功、但网页没收到响应 | 名字已改 | 再存一次结果相同；刷新后看到新名字 |
| Google 待写之后写入失败 | 按 server-backup-and-google-docs 的重试与问题提示处理 | 同日记 Doc 的恢复方式 |
| 改名后又删掉生日纪念日 | 礼物上的场合显示旧名字（D3） | 已知限制；可以手动把礼物场合改成别的 |

## 不变量

1. 只有本人能改自己的名字：`PATCH /api/me` 改的是会话里的用户，请求里没有可以指定别人的字段。
2. 保存的名字去掉首尾空白后是 1–20 个 grapheme，不含 `\p{Cc}`、U+2028、U+2029，去掉空白与 `\p{Cf}` 后不为空；不合格的请求什么都不写。
3. 改名成功后，接口返回给两人的每一处名字都是新名字；除了 `gifts.occasion_name` 之外，没有任何地方保存名字的副本。
4. 两人正在绑定中时，改名与这个空间所有 `Together` Doc 的待写登记在同一个事务里提交；名字没变、没有空间或已解绑时不登记。
5. 改名不产生未读、首页提示或邮件，也不保留以前的名字。
6. 认证层的 Google 资料变化不改写 `users.display_name`；第一次登录的默认名字规则不变。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **给对方起私人昵称（B），或 A 与 B 都做** | 每人可以按自己习惯称呼对方 | 每个出口都要按"谁在看"选名字，还要新建一张表（依据 2）；两人说起名字时对不上（依据 1）。留作以后评估 |
| **不能与对方同名** | 界面上永远分得清两个人 | 颜色和"我"已经能区分；两人之间要加锁，一方可以占住另一方想用的名字，绑定前又无从比较（D2） |
| **按码点或 UTF-16 长度计 20 个字** | 实现最简单 | emoji 组合会被算成好几个字，用户看到的和计数对不上 |
| **改名时也改礼物场合的副本** | 删除生日之后也是新名字 | 名字单元要写心愿与礼物的表（依据 5），只为一个很少见的场景 |
| **改名时什么 Google Doc 都不重写** | 代码最少 | 汇总 Doc 会一直显示旧名字，直到有人改心愿或纪念日，违反"按当前状态"（依据 4） |
| **改名时把所有日记 Doc 也重写** | Drive 里处处是新名字 | 可能有几百份，占 Drive 配额，每份的版本历史多出一版（依据 2、4） |
| **告诉对方"TA 改名为 …"** | 对方不会感到意外 | 要存改名事件和对方是否看过，并扩大未读与邮件的范围（依据 2，D5） |
| **第一次登录时必须确认名字，或首页一次性提示** | 邮箱前缀不会留下 | 每个人多一步，或者要多存一个"已关闭"字段；名字真正要紧的时刻在邀请和接受邀请时（D6） |
| **放进 `auth` 单元** | `users` 表的写入方仍只有一个单元 | `auth` 要依赖 `store` 和 Google 待写，混进与登录无关的职责（依据 5） |
| **`PUT /api/me/name`** | 与 `/api/me/timezone`、`/api/me/sleep` 的子路径一致 | 名字是 `UserSummary` 本身的字段，`PATCH` 同一个资源并返回同一个形状更直接（Ray，2026-11-18 按推荐定） |

## 风险与代价

- 认证 ADR D2 的"谁写"一列不再只有一个写入方，读认证 ADR 的人要看"关联"那一行才知道。
- 没再写过的旧日期，日记 Doc 里一直是旧名字；同一个 Drive 里新旧名字会并存。
- 对方要在下次读数据时才看到新名字，同时开着页面的两人会短暂看到不同的名字。
- 礼物场合的副本在"先改名、后删生日"时显示旧名字。
- 允许重名，两人起了同一个名字时，只能靠颜色和"我"来区分。

## 未解决的问题

- **私人昵称**：以后要做时，需要回答页头、作者图例、邮件、每人 Drive 里的 Doc、纪念日"X 的生日"和礼物场合副本按谁的称呼来显示。现在的默认做法：不做，所有地方都用对方自己设的名字。
- **登录默认名字的清理**：Google 名字超过 20 个字或含控制字符时，第一次登录照常保存（D6 不改认证 ADR 的默认规则）。现在的默认做法：不截断，只在用户改名时要求合规。

## 落地顺序

1. **前置**：google-copy-beyond-diaries 的服务端 PR（#99）合入 `main`，`registerSpaceCopy` 已经存在。
2. **一个 PR 完成服务端与网页**：
   - `packages/contracts`：`DisplayName` schema、`UpdateMeRequest`、路由 `updateMe`；`npm run openapi`。
   - `apps/api`：`display-name` 单元、`store` 的两个查询、`app.ts` 注册路由、依赖方向规则表；模块 README 的 *Public surface* 与 *Invariants*，*Known limitations* 写明 D3 的礼物场合副本与 D4 的日记 Doc。
   - `apps/web`：`name` 单元（`/name` 页面与就地编辑组件）、「设置」菜单项、`/partner` 与 `/join` 的"修改"、保存后刷新的查询；依赖方向规则表；模块 README。
   - `docs`：本 ADR 的事实同步，roadmap 这一行与日期，architecture 的 Current decisions 加上本文；认证 ADR 的"关联"行本 PR 已写好。
   - 完成条件：下面的验收标准都有测试，format、lint、typecheck、`contracts`/`api`/`web` 的测试与 `npm run check -- docs` 通过，e2e 只在全部改完后跑一次。
   - 从此改变的行为：用户能改名字；改名后两人的 Drive 里，`Together` 下的 Doc 换成新名字。

**自主实现约定**：

- 预先批准：上面列出的契约、路由、两个新单元，以及依赖方向规则表的这几行。
- 不需要迁移，不加新依赖（`Intl.Segmenter` 是 Node 26 与目标浏览器内置的）。需要迁移或新依赖时停下来问 Ray。
- AI 可以自行决定：页面与提示的具体文案和布局（沿用数字书页的组件）、`store` 查询的写法、测试的拆分。
- 必须停下来的情况：要写 `users` 之外的表（礼物场合副本除外，它就不该写）；要改 `UserSummary` 的形状；要让 `display-name` 依赖 `store`、`errors` 以外的单元。
- PR 用 Conventional Commits，例如 `feat(api): let users change their display name`、`feat(web): edit your name under 设置`，按项目的规矩用合并提交合入，等 Ray 验收后才合并。

## 验收标准

- A 在 `/name` 把名字改成"小雨"并保存，页头马上显示"小雨"；B 刷新后，作者图例、搭档卡片、心愿、纪念日"小雨 的生日"和两地时间都显示"小雨"（端到端，Chromium）。
- 去掉首尾空白后为空、21 个字、含换行、只有零宽字符的名字被拒绝，返回 400，名字不变；`👩‍❤️‍👨` 加 19 个汉字可以保存（契约单元测试与 `app.inject()`）。不变量 2。
- 请求体带上别的用户 ID 或任何额外字段时被拒绝；改的只是会话里的用户（`app.inject()`）。不变量 1。
- 绑定中改名后，`space_copy_outbox` 里有一条这个空间 `recordType` 为 null 的登记，与名字在同一次提交里；名字没变、未绑定、已解绑时没有登记（真实 PG）。不变量 4。
- 改名后接口里所有返回名字的地方都是新名字：`me`、`binding`、空间参与者、两地时间、心愿、纪念日、共享页面、邀请预览，以及 `notify` 拼出的邮件（真实 PG）。不变量 3。
- 改名后 B 的未读、首页提示和邮件判定都不变（真实 PG）。不变量 5。
- `/partner` 的邀请表单与 `/join` 确认页显示"修改"，就地改名后留在原页面（jsdom 组件测试）。
- 再用 Google 登录一次（模拟登录换一个名字），`display_name` 不变（`app.inject()`，扩展认证 ADR 已有的测试）。不变量 6。

## 补充信息

- 重新评估条件：用户想给对方起私人昵称；首版之后允许一个账号有多个空间或换搭档（那时名字可能要按空间区分）；加入服务器推送，可以把改名实时送到对方页面；汇总或页面 Doc 的重写在配额上成了问题。
- 证据：2026-11-18 与 Ray 逐条确认：名字是 A（自己改、两人看到同一个）；1–20 个 grapheme、不能含控制字符、不查重名；处处现读、礼物场合副本保持现状；`Together` 重写、日记 Doc 等下次写入；不提示对方；第一次登录不拦，在邀请和 `/join` 处"修改"；`/name`、`PATCH /api/me`、新单元 `display-name`、部分取代认证 ADR D2。显示名字的地方由 `grep -rn displayName apps/` 逐一核对。
