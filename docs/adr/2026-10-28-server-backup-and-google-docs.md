# 服务器把数据库持续加密备份到 Cloudflare R2，每人的 Google Drive 只放每天一份可读的 Doc

- 状态：已采纳
- 日期：2026-10-28
- 决策者：Ray
- 范围：备份
- 关联：依赖 ADR-0003；依赖 unread-and-day-page；取代 ADR-0004 的数据快照与恢复要求；取代 diary-collaboration-kernel 的D16 快照内容与备份目标

备份分两层，各管一件事。**服务器备份**负责"服务器坏了数据能找回来"：PostgreSQL 的修改日志大约每分钟一次、在服务器上加密后增量上传到 Cloudflare R2，每天一次完整备份；30 天内可恢复到任意一分钟，每月第一份完整备份永久保留。每周在临时数据库里自动恢复一遍并检查，备份或演练没有按时成功时，由 Healthchecks.io 发邮件通知 Ray。恢复是一条命令，由 Ray 在新机器上执行；两个用户什么都不用做，重新登录即可。**Google 可读副本**负责"在 Google 里直接读、服务不在了也能读"：每人连接自己的 Google Drive，应用每形成一个历史版本，就把那一天写成一份 Google Doc，两篇上下排列、自己的在上面、每人的字用各自的颜色，和应用的日期页一致；Drive 里只有本人能在应用里看到的内容。

本文取代 ADR-0004 的第 3 条（向用户 Google 上传结构化数据快照）、第 8 条的快照保留策略与"恢复要求"一节，以及日记协作内核 D16 中关于个人与空间快照内容的规定：恢复改由服务器备份承担，用户的 Drive 里不再放恢复用的数据文件。ADR-0004 的其余各条（单向输出、Doc 归用户账号、登录与 Drive 授权解耦、outbox 与串行、外部修改不覆盖）沿用并在本文落到实现。

本文不负责：生产环境把 PostgreSQL 放在哪台机器、Google 应用发布为"正式"（都随部署 ADR）；Google 里的修改导回应用；邮件通知（阶段 4）；按月合并 Doc（以后再看）；手机端。

## 背景与问题

日记的唯一主库是一台云服务器上的 PostgreSQL。硬盘损坏、账号被停、误操作或应用 bug 都可能让数据丢失，而这些日记无法重写。阶段 2 结束后两人就要开始在开发环境写真实日记，此时还没有任何异地备份。

ADR-0004 的原方案让应用把"可读 Doc"和"恢复用数据快照"都写进用户的 Google Drive，恢复时从用户 Drive 读回。讨论中发现这把服务的冗余责任推给了用户：恢复时要两个人各自交出 Drive 里的文件，或者写一套复杂的"应用内各自恢复"；同一篇日记在 Drive 里存两份；快照格式和恢复代码都要自写。对一个由 Ray 自己运营、两个人使用的服务，更合适的分工是：运营者用数据库的标准做法做异地备份，用户的 Google 里只放给人读的副本。

协作内核已经在每次提交的同一事务里登记备份任务（`backup_outbox`，个人目标与空间目标），但还没有任何东西消费它。

## 决策依据

1. 服务器坏了、数据库丢了，日记、每个字的作者与写入时间、历史版本、关系与共享设置、已读都能恢复；两人重新登录就能接着一起写，作者限制照样有效。
2. 冗余由服务运营方负责，用户不承担恢复（Ray 于 2026-10-28 决定）。
3. 备份存放在与服务器不同的公司、不同的账号里。
4. 备份离开服务器前已加密，存储商读不到日记内容；密钥由 Ray 离线保管。
5. 日常写作中丢失窗口在分钟级，并能恢复到出事前的某个时间点（例如 bug 写坏数据的前一分钟）。
6. 备份要被定期证明能恢复；备份停止时，即使服务器整台挂掉，运营者也能收到通知。
7. 每人能在自己的 Google 里直接读到自己在应用里能看到的日记，服务不在了也能读。
8. 授权边界不因备份扩大：对方没共享的日记、共享期之外的私人修改不进入你的 Drive；任何人的阅读状态都不进入对方能看到的地方（SHARE-11、内核 D16/D17）。
9. 写日记不等待、不依赖 Google 或备份；"已保存""已成历史""已备份到 Google"分别判断。
10. Google 里的人为修改不被悄悄覆盖；应用不删除用户 Drive 里的文件。
11. 长期授权令牌一旦泄露，影响尽量小；令牌不进入浏览器、日志和接口返回。
12. 少写自制的备份格式与恢复代码，优先用成熟工具；不新增 npm 依赖。
13. 在两人规模、R2 免费额度与 Google 免费配额之内运行。

### D2：服务器备份用 WAL-G 持续备份到 Cloudflare R2

**怎么备份**：PostgreSQL 先把每次修改写进修改日志（WAL）。开启归档后，每当有修改且距上次归档满约 60 秒（`archive_timeout = 60`），PostgreSQL 就把当前日志文件交给 WAL-G；WAL-G 压缩、用 libsodium 密钥加密后上传到 R2。没有修改时不归档、不上传。每天 03:00（服务器时间）做一次完整备份（`wal-g backup-push`），用 WAL-G 的增量完整备份只传变化过的数据页。恢复时取一份完整备份，再按顺序重放之后的修改日志，停在指定时间点。

**为什么是 WAL-G 加 R2**：WAL-G 是 PostgreSQL 持续归档的成熟工具，直接支持 S3 兼容存储与客户端加密，恢复到任意时间点是它的本职功能，不用我们写备份格式与恢复代码（依据 5、12）。R2 由 Cloudflare 提供，与服务器（Oracle Cloud）不是同一家公司，Ray 已有账号、域名也在那里；免费额度约 10 GB，下载不收费（依据 3、13）。

**加密**：数据在服务器上加密后才离开（`WALG_LIBSODIUM_KEY`，32 字节）。密钥存在 Ray 的密码管理器和服务器上权限为 600 的环境文件里，不进仓库、不进 R2。**密钥丢失等于备份全部作废**，恢复手册第一页写明这一点（依据 4）。

**保留**：
- 最近 30 天：保留每天的完整备份与全部修改日志，可恢复到其中任意一分钟。
- 更早：每月第一份完整备份用 `wal-g backup-mark` 标为永久，连同使它一致所需的日志永久保留，可恢复到那一刻的状态。
- 清理：每天备份后运行 WAL-G 自带的 `delete before FIND_FULL <31 天前>`，只删 31 天以外、未标永久的备份与日志（多留一天，保证第 30 天的最早一分钟之前仍有一份备份）。不写自制的删除逻辑。

**运行位置**：备份配置属于"存放真实数据的那个 PostgreSQL"。阶段 2 起真实日记在开发服务器的 compose 数据库里，所以先在那里启用；部署 ADR 确定生产数据库位置后，配置随之迁移。为不影响开发和测试，`compose.yaml` 不变，改用一个叠加文件 `ops/backup/compose.backup.yaml`：把镜像换成"`postgres:18.6-alpine3.24` + 固定版本的 WAL-G"，加上归档参数与环境文件。

落地时确认：镜像沿用现有数据库的 Alpine，而不是原计划的 Debian。现有数据目录的排序规则是 musl 下的 `en_US.utf8`，换成 glibc 会改变文本排序，让文本索引失序。WAL-G 只发布 glibc 版本，所以在 `golang:1.25.11-alpine3.24` 里从固定的 v3.0.9 源码（提交 `3e49318…`，构建时校验）静态链接 libsodium 构建。脚本用 TypeScript（`node ops/backup/*.ts`），与仓库其他脚本同一语言，选备份、判断每月与校验都有单元测试。

日志文件名义上固定 16 MB，强制切换的文件也是这个长度（PostgreSQL 文档："a minute or so" 是合理设置）。实现时实测一天写作的上传量与 R2 占用，若明显偏大，把 `archive_timeout` 调到几分钟，并在本文与路线图里记下实测值。

### D3：每周自动恢复演练，失败由 Healthchecks.io 通知

**演练**：每周日 04:00，服务器用 D4 的同一个恢复命令，把 R2 上的最新备份恢复到一个临时容器和临时数据目录，然后运行检查脚本：
- 每篇日记的当前代次都能从快照与提交重建，存储的校验值全部一致；
- 每个可见字都有作者与写入时间；
- 用户、空间、日记、提交的数量不少于上一次演练记录的数量；
- 恢复到的最新提交不早于线上数据库五分钟前的最后一次提交（说明日志在持续上传）。落地时确认：原计划"离演练开始不超过约一天"在两人几天没写时会误报，改为与仍在运行的线上数据库比较；真正恢复时线上库已不在，不做这项。

检查完删除临时容器与数据目录，结果与耗时写入服务器上的演练日志。

**通知**：在 Healthchecks.io 建两个检查——"每日备份"（期望每天一次，宽限 2 小时）、"每周演练"（期望每周一次，宽限 6 小时）。每日完整备份、保留清理和归档状态检查（`pg_stat_archiver` 里最近一次失败不晚于最近一次成功）都成功后，才打"每日备份"的卡；任一失败时打 `/fail`。演练全部通过才打"每周演练"的卡。超时没收到打卡或收到失败，Healthchecks 给 Ray 发邮件。

选它而不是让服务器自己发通知：最危险的情况——服务器整台挂掉、定时任务没启动、备份进程卡死——服务器根本发不出消息；"没收到成功就报警"能覆盖它们（依据 6）。打卡地址只放在服务器环境文件里。

### D4：恢复是一条命令，由 Ray 判断并执行

```sh
node ops/backup/restore.ts --to latest                     # 硬盘坏了：恢复到最新
node ops/backup/restore.ts --to "2026-10-28 21:04 UTC"     # bug 在 21:05 写坏数据：恢复到之前
```

命令完成：从 R2 取所需的完整备份、按时间点重放日志、启动数据库、运行 D3 的检查、输出恢复到的时间与耗时。每周演练调用的就是它，所以它每周都被实际运行一次。

只有两件事留给人：判断服务器确实坏了（全自动接管需要常开的备用机，且在服务器只是暂时卡住时容易误判、让两边同时写入，代价超过两人日记的需要）；选择恢复到哪个时间点。新机器也由 Ray 开出。

恢复后两人用 Google 重新登录即对应原账号（`users` 与认证表都在数据库里），Google Drive 连接也随数据库恢复（令牌密文在库里，密钥在新服务器的环境文件里重新放入；密钥丢了就各自重新连接一次）。恢复手册 `ops/backup/README.md` 写明：准备新机器、放入环境文件、运行命令、确认检查结果、启动 API 与后台进程。阶段收尾时 Ray 照手册在空环境演练一次，记录耗时，作为以后定恢复时间目标的依据。

### D5：每人连接自己的 Google Drive，Drive 里是本人在应用里能看到的内容

以 10 月 28 日为例：你写了一篇，TA 也写了一篇并共享给你，TA 还在你那篇里插了一句；TA 10 月 20 日有一篇没共享。

| | 你的 Drive | TA 的 Drive |
| --- | --- | --- |
| 你的 10-28（含 TA 插的那句） | 有 | 你共享给 TA 时有，内容是 TA 获准看到的版本 |
| TA 的 10-28 | TA 共享的版本 | 有 |
| TA 的 10-20（未共享） | 无 | 有 |

- 本人日记：已提交的最新版本。
- 对方日记：只经获准状态读取入口（内核 D17）取当前共享轮次的版本；停止共享后停在冻结版本，并注明"已停止共享"；解绑后同样保留。应用不删除你 Drive 里的这些副本，与应用里"停止共享后保留只读历史"一致。
- 不进入 Drive：对方未共享的日记、共享期之外的私人修改、已删除的私人文字、任何人的阅读进度。

没有绑定搭档的人也能连接，只备份自己的日记。没有连接 Google 照样写日记，备份页注明"未开启 Google 备份"。

原因：依据 7、8。各存各的让两人对等，不用选"存在谁那里"，也不会因为一方取消连接而让另一方读不到。共享的那几天两人各存一份，只是文字，代价可以忽略。

### D6：每天一份 Doc，和日期页一样上下排列，按年/月分文件夹

```
Between Pages / 2026 / 10 / 2026-10-28 周三

  2026 年 10 月 28 日 星期三                     ← 标题 1
  ■ Ray   ■ TA                                    ← 图例，作者颜色与应用一致

  Ray 的日记                                      ← 标题 2
  今天加班到很晚……（TA 插的那句用 TA 的颜色）

  TA 的日记                                       ← 标题 2
  今天去了公园……
  （已停止共享）                                  ← 仅冻结时
```

- **一天一份**，本人的日记在上，对方的在下；只有一方写时只有那一篇。日期与每篇的名字用标题样式，Google Docs 的大纲可以直接跳转。
- **内容**：日期、图例、每篇的正文与换行、每个字的作者颜色（与应用里按空间位次分配的颜色相同）、Unicode 原样。不放写入时间、删掉的字、历史版本。
- **文件夹**：`Between Pages / 年 / 月 /`，一个文件夹最多 31 份；文件名 `YYYY-MM-DD 周X`，按名字排序即按日期排序。
- 每次更新在同一份 Doc 里整体替换正文，Google Docs 自带的版本历史会留下每一版。

原因：依据 7。用户以前在 Google Docs 里就是上下写的，Doc 与日期页一致，两边看到的是同一种样子。按月一份读起来更连贯，但外部修改会让整月另存，且更新时正在阅读的人眼前会跳，留待以后再看。

### D7：每形成一个历史版本写一次 Doc，只写改动的那一天

- **时机**：某天的某篇日记有新提交，等这些提交进入一个历史版本（内核 D6：停笔 2 分钟，或连续写作每 5 分钟一段）后，再写这一天的 Doc。冻结的共享立即可写，因为停止本身就是一个历史版本。与首页未读的冷静期是同一条规则，所以整个应用只有一种"版本"。
- **只写改动的**：任务按"哪个人的 Drive、哪一天"合并，同一天多次提交只写最新一次；其他日子一个字节都不传。渲染出的内容与上次写入的完全相同（例如写了又撤销）就不写。
- **第一次连接**：把本人能看到的全部日期各写一份，之后只写改动的。
- **"已备份到 Google 9:22"**：指这一天在你 Drive 里的 Doc 已写入、覆盖到 9:22 那个历史版本。任务登记、正在写、写了一半都不算。

最坏情况下，Google 副本比应用晚约 2～5 分钟；数据安全由 D2 的服务器备份保证（分钟级），Doc 不承担恢复。

### D8：Google 上被改或被删时，另存或重建，从不覆盖、从不删除

应用每次写入前要求 Doc 仍是自己上次写完的修订（Docs API `writeControl.requiredRevisionId`；有人改过时 Google 拒绝写入），所以检查和写入之间被改也不会被覆盖。

| 情况 | 结果 |
| --- | --- |
| Doc 在 Google 里被改过（有人加批注、改字） | 旧 Doc 内容一字不动，改名为"2026-10-28 周三（在 Google 改过，已停止更新）"；新建一份"2026-10-28 周三"继续更新；备份页记一条"10 月 28 日的 Doc 被改过，已另存一份新的" |
| Doc 被删除（在回收站或彻底删除） | 下一次写入或每日检查时重新生成一份；备份页记一条 |
| 文件夹被删除 | 重建文件夹，其中的 Doc 按上一行处理 |

**每日检查**：每天一次，后台进程向 Google 要本人 Drive 里应用建的文件清单（只要元数据，不下载内容），与记录的 Doc 和修订对比，发现被删就排队重建，发现被改就按上表另存。一篇日记以后不再修改，它的 Doc 也不会一直缺着。

### D9：首页的"备份"页、日记上的状态、需要动手时首页提醒

**备份页**（首页与"空间"并列）：
- 连接状态：未连接 / 已连接（显示 Google 账号邮箱）/ 需要重新连接。
- 进度："全部日记已备份到 9:22 的版本"或"还有 2 天等待备份"。
- 问题记录：Doc 被改另存、被删重建、Google 空间已满、暂时连不上正在重试。
- 按钮："在 Google Drive 打开文件夹"、"现在备份"（不等历史版本形成，立即处理所有等待中的日期）、"断开连接"。

**日记页与日期页**：在"已保存"旁显示"已备份到 Google 9:22"与"在 Google Docs 打开"；未连接时显示"未开启 Google 备份"。

**首页横条**：只在需要用户动手时出现——需要重新连接、Google 空间已满。暂时连不上、正在自动重试的问题只记在备份页。

**测试状态的 7 天限制**（Ray 于 2026-10-28 决定先接受）：Google 应用保持"测试"状态时，Drive 授权 7 天后过期。连接后第 6 天起备份页与首页提醒"Google 授权将在 X 日过期，请重新连接"；过期后显示"需要重新连接"，积压的日期在重新连接后续传，写日记不受影响。由配置 `GOOGLE_DRIVE_TESTING=true` 打开这条提醒；部署时把 Google 应用发布为正式后关掉。

备份状态只对本人可见，对方看不到你是否连接、何时备份（依据 8）。

### D10：令牌只以密文保存，只在后台进程里短暂解密

1. **最小权限**：Drive 授权只申请 `https://www.googleapis.com/auth/drive.file`，只能访问应用自己建的文件；它是 Google 列为非敏感的权限。
2. **与登录分开**：单独的授权流程，不经 Better Auth（认证 ADR：登录不保存 Google 令牌）。授权请求带 `state` 与 PKCE，`access_type=offline`；回调校验 `state`、会话用户与发起者一致，换得的令牌属于哪个 Google 账号就记为连接的账号。
3. **加密存储**：刷新令牌用 AES-256-GCM（`node:crypto`）加密后存入 PG，每条带随机 nonce 与密钥编号；密钥 `GOOGLE_TOKEN_KEY` 只在服务器环境变量里，不进数据库、仓库或 R2。只拿到数据库或数据库备份的人解不开令牌；数据库备份上传前又整体加密一次（D2）。
4. **只在后台进程里解密**：API 进程只写入密文（授权回调时），从不解密；后台进程用时解密、换取短期访问令牌，两者都只在内存里。任何 HTTP 响应、WebSocket 消息、浏览器存储里都没有令牌。
5. **不进日志**：日志序列化时去掉令牌、授权码与 `Authorization` 头；出错时只记录 Google 返回的错误码。
6. **断开**：向 Google 的撤销接口作废令牌，再删除密文与访问状态；Drive 里的文件和 Doc 映射保留。撤销请求失败也删除密文，并在备份页提示可以到 Google 账号的"第三方访问"里手动移除。
7. **换密钥或丢密钥**：旧密文全部作废，连接状态变为"需要重新连接"，各自重新连接一次即可，日记不受任何影响。

## 技术设计

**进程**：后台进程 `apps/api/src/worker.ts`，与 API 同一代码库、分开启动（ADR-0006 第 20 条），开发时 `npm run dev:worker`。不引入任务队列库：用 `FOR UPDATE SKIP LOCKED` 取任务，失败重试间隔从 1 分钟翻倍到最多 1 小时，Google 限流（429）按其 `Retry-After`。

**任务流**：
1. 提交事务里登记的 `backup_outbox` 行（已有）由后台进程转为"某人某天待写"：个人目标 → 日记主人的那一天；空间目标 → 该轮次接收方（搭档）的那一天。转完把 outbox 行标为已处理。
2. 冻结、重开、解绑没有新提交，由相应事务直接为接收方登记"那一天待写"；首次连接为本人能看到的全部日期登记。
3. 一天的待写项在其中所有新提交都进入历史版本后才处理（或用户点了"现在备份"）。处理时经获准状态读取入口取本人与对方两篇，渲染 Doc 内容，算出内容校验值，与上次写入的相同就只更新"已覆盖的版本"。
4. 写入：Doc 不存在则建（`documents.create` 后用 Drive 移进文件夹）；存在则一次 `batchUpdate`（带 `requiredRevisionId`）整体替换正文、设置标题样式与字色，记录返回的新修订号。

**表**（一次迁移，本文预先批准）：

| 表 | 内容 |
| --- | --- |
| `google_connections` | 用户、Google 账号 ID 与邮箱、刷新令牌密文、nonce、密钥编号、授权范围、状态（正常 / 需要重新连接）、连接时间、最近错误 |
| `google_folders` | 用户、路径（`Between Pages`、`2026`、`2026/10`）、Drive 文件夹 ID |
| `google_day_docs` | 用户、日期、Doc ID、上次写入的修订号、内容校验值、覆盖的本人版本与对方轮次和版本、写入时间、状态（当前 / 已另存） |
| `google_day_work` | 用户、日期、最早可处理时间、尝试次数、下次尝试时间、最近错误 |
| `backup_outbox`（改） | 状态增加"已处理"、处理时间 |
| `backup_events` | 用户、时间、类型（另存、重建、空间已满等）、日期；备份页的问题记录 |

**接口**（contracts 与 OpenAPI 随实现）：`GET /api/backup`（备份页状态）、`POST /api/backup/google/start`（返回授权地址）、`GET /api/backup/google/callback`、`POST /api/backup/google/disconnect`、`POST /api/backup/run`（现在备份）；`GET /api/days/:date` 的每篇增加本人 Drive 中的备份状态与 Doc 链接。

**模块**（`apps/api/src`）：`google`（调用 Google OAuth、Drive、Docs 的 REST 接口与令牌加解密，不访问数据库）；`backup`（连接、待写队列、渲染、状态，属于服务层，经 `reader` 取正文、经 `history` 判断是否已成历史）；`worker`（组装入口，与 `server` 同级）。登记进 `checks/verify-dependency-direction.ts`。调用 Google 用 `fetch`，不装 `googleapis`。

**运维目录** `ops/backup/`：`compose.backup.yaml`、`Dockerfile`（`postgres:18.6-alpine3.24` + 从源码构建的 WAL-G v3.0.9）、`backup.ts`（每日备份、标永久、清理、归档状态检查、打卡）、`restore.ts`、`verify.ts`（D3 的检查）、`drill.ts`（每周演练、打卡）、`systemd/` 定时器示例、`README.md`（恢复手册与首次配置）、`backup.env.example`（只有变量名）；测试用的 `compose.test.yaml` 让 WAL-G 写本地目录，`npm run test:backup` 跑完整循环。

**新配置**：`GOOGLE_TOKEN_KEY`（API 与后台进程）、`GOOGLE_DRIVE_TESTING`（D9）；服务器环境文件中的 `WALG_LIBSODIUM_KEY`、R2 的 `WALG_S3_PREFIX`、`AWS_ENDPOINT`、`AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`、`AWS_REGION=auto`、`AWS_S3_FORCE_PATH_STYLE=true`，以及两个 Healthchecks 打卡地址。Google OAuth 客户端沿用登录用的同一个（`GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`），在 Google Cloud 里加上 Drive 回调地址。

## 失败与恢复

| 情况 | 结果与恢复 |
| --- | --- |
| R2 暂时不可用或密钥失效 | PostgreSQL 保留未归档的日志并持续重试，写日记不受影响；当天"每日备份"打 `/fail`，Ray 收到邮件后修复；归档恢复后积压日志自动补传。积压期间服务器硬盘占用增加，恢复手册写明检查方法 |
| 服务器整台挂掉 | Healthchecks 一天内没收到打卡，发邮件；Ray 在新机器上按手册恢复到最新 |
| 应用 bug 写坏数据 | Ray 恢复到出错前一分钟（30 天内）；恢复到另一台机器或临时目录，确认后再切换 |
| 每周演练失败 | 不打卡并打 `/fail`；演练日志指出哪项检查失败；在修复前视为"备份不可证明可用" |
| 备份加密密钥丢失 | R2 上的备份全部无法使用；立即生成新密钥，做一次新的完整备份，旧备份作废 |
| Google 限流、网络失败 | 退避重试；备份页显示"暂时连不上，正在重试"，不弹横条 |
| Drive 授权撤销或过期（含测试状态 7 天） | 连接状态变为"需要重新连接"，首页横条；待写日期保留，重新连接后续传 |
| Google 空间已满 | 待写日期保留并停止重试到用户处理；首页横条 |
| Doc 被改、被删 | 见 D8 |
| 后台进程中途崩溃 | 待写项没有标完成，重启后重做；同一天重复写入产生同样的内容，不产生副本 |
| 令牌密钥更换或丢失 | 所有连接变为"需要重新连接"（D10） |

## 不变量

1. 存放真实数据的 PostgreSQL 有修改时，修改日志约一分钟内被加密上传到 R2；R2 上的对象没有密钥无法解读。
2. 恢复命令能在空数据目录里，从 R2 恢复到最新或 30 天内任意指定时间点，恢复后每篇日记都能重建、每个可见字都有作者与写入时间。
3. 每日备份与每周演练的成功都送达 Healthchecks；任一缺失或失败时，运营者在宽限期后收到通知，不依赖服务器存活。
4. 恢复不需要用户做任何操作；恢复后用户登录即对应原账号与原关系。
5. 一个人的 Drive 里只出现本人日记的已提交版本和对方共享给本人的获准版本；未共享的日记、共享期之外的私人修改、任何人的阅读进度都不出现。
6. 每个人每个日期至多一份"当前"Doc；重复处理不产生副本，较旧的版本不覆盖较新的内容。
7. Doc 只在其内容所含提交都已进入历史版本（或用户要求立即备份）后写入；"已备份到 Google"只在对应 Doc 写入成功后显示。
8. 应用只在 Doc 仍是自己上次写入的修订时写入；被改过的 Doc 内容不被改动，只被改名，另建新 Doc 继续更新。
9. 被删除的 Doc 在下一次写入或每日检查时重建；应用不删除用户 Drive 里的任何文件。
10. 写日记、保存确认与历史版本不等待 Google；Google 不可用时 PG 提交照常完成。
11. 刷新令牌只以密文存在 PG，密钥只在服务器环境变量里；令牌与授权码不出现在任何 HTTP 响应、WebSocket 消息、日志与浏览器存储中，API 进程从不解密令牌。
12. 断开连接向 Google 撤销令牌并删除密文，不删除 Drive 文件；重新连接后积压的日期续传。
13. Drive 授权只请求 `drive.file`；回调校验 `state`、PKCE 与发起的会话用户。
14. 备份连接与状态只对本人可见；对方的任何接口都不反映你是否连接或何时备份。
15. Doc 与应用的日期页一致：日期、图例、本人在上的顺序、每个字的作者颜色、换行与 Unicode。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **恢复用数据快照放进每人 Drive**（ADR-0004 原方案） | 用户自己持有完整数据，服务和运营者都不在了也能恢复 | 依据 2：冗余推给用户，恢复要两人交文件或复杂的应用内恢复；依据 12：自写快照格式与恢复代码；同一篇在 Drive 里存两份 |
| **每小时 `pg_dump` 上传** | 最简单，没有常驻归档 | 依据 5：丢失窗口一小时，不能恢复到任意时间点 |
| **pgBackRest** | 同样成熟，功能更多 | 两者都满足依据；WAL-G 单个二进制、配置更少。WAL-G 不支持 PostgreSQL 18 时改用它 |
| **备份到 Oracle 自家对象存储** | 免费约 20 GB，不用新账号 | 依据 3：与服务器同一家公司、同一账号，账号被停时一起丢失 |
| **备份到 Google Drive** | 不用新账号 | 依据 12：WAL-G 不支持，要靠 rclone 拼接或自写整库导出；依据 5：自写时只能按小时 |
| **备份到自己的另一台机器** | 不经第三方 | 依据 6：机器离线时日志堆在服务器上，可能占满硬盘拖垮数据库；那台机器自身也需要备份 |
| **备用服务器自动接管** | 恢复最快 | 依据 13：常开备用机的成本；暂时卡顿时误判接管、两边同时写会破坏数据 |
| **服务器自己发通知** | 不依赖第三方 | 依据 6：服务器挂掉、定时任务没启动、进程卡死时发不出任何消息 |
| **Cloudflare Worker 检查 R2** | 留在已有账号里、同样独立于服务器 | 依据 12：检查与发信代码要自写和维护；Healthchecks 不用写代码 |
| **一位成员的 Drive 存共享内容，再用 Google 共享给另一位** | 共享内容只存一份 | 依据 7：被选中的人取消连接后另一人读不到，还要手动在 Google 里共享 |
| **一篇一份 Doc** | 每份更小、映射更简单 | 依据 7：与日期页不一致，共享的那天要开两个文件 |
| **一个月一份 Doc** | 像日记本一样连续读 | 外部修改会让整月另存，更新时正在阅读的人眼前会跳；用户决定先按天，以后再看 |
| **停笔 1 分钟就写 Doc** | Google 副本早约 1 分钟 | 数据安全已由服务器备份承担（依据 5）；与历史版本不一致会多出一种"版本"概念 |
| **被改过的 Doc 暂停更新并提示用户** | 由用户决定 | 依据 7：用户没注意到时，可读副本长期停在旧内容 |
| **用 Better Auth 关联账号申请 Drive 权限** | 复用现成的 OAuth 代码 | 依据 11 与认证 ADR：令牌会进登录账号表，登录与 Drive 授权混在一起 |
| **`googleapis` SDK** | 类型完整，少写请求代码 | 依据 12：体积大的新依赖；用到的接口只有几个 |

## 风险与代价

- **R2 是唯一的异地副本**：Cloudflare 账号出问题时只剩服务器本身。可以以后加第二份存储（例如 Oracle 对象存储），代价很小。
- **加密密钥是单点**：丢了它备份全部作废。手册要求放进密码管理器，并在首次配置后做一次用密码管理器里的密钥恢复的演练。
- **测试状态的 7 天限制**：部署前每周要重新连接一次 Google；忘了的话 Google 副本会停，但服务器备份不受影响。
- **日志上传量**：强制切换的日志文件名义 16 MB，压缩后的实际大小要实测；必要时拉长间隔，丢失窗口相应变为几分钟。
- **`drive.file` 绑定 OAuth 客户端**：应用只能访问自己那个 Google Cloud 项目建的文件。若删除或更换该项目，旧 Doc 仍在用户 Drive 里可读，但应用不能再更新它们，只能新建。
- **每周演练占用资源**：临时恢复会占用服务器的磁盘与 CPU 几分钟；两人规模下可以接受。
- **Doc 整体替换**：每次更新替换整天的正文，Google 版本历史里看到的是整段变化，而不是逐字差异。
