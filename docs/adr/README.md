## 何时写 ADR

在同一个 PR 里写（或更新）ADR，如果改动涉及：

- 在两个说得通的方案之间选了一个（库、模式、数据结构、协议）；
- 故意**不做**一件读代码的人会预期要做的事；
- 新增或去掉一个抽象、模块边界或职责归属；
- 接受一个以后的人可能想推翻的限制或取舍。

判断标准：三个月后另一个 agent 看到这段代码，会不会问"为什么不用 B？"会，就写。重命名、格式化、只有一种正确写法的 bug 修复不需要。

已有 ADR 覆盖的决定就更新它，不另写一份；决定本身变了，就写新 ADR，在旧 ADR 的状态行注明被哪一份取代，两边互相链接。

## 格式

`checks/verify-decision-format.ts` 检查以下格式：

- 文件名 `NNNN-kebab-topic.md`，编号递增，并登记在上面的索引表里；
- 第一行 `# ADR-NNNN：<标题>`；
- 有一行以 `日期：` 开头并包含 `状态：`；
- 有 `## 背景`；
- 有以 `## 替代方案` 开头的小节，而且**不能为空**：没有写清"打败了什么"的决定，最容易被重新争论。

其余小节（决策、后果、验证）按需要写。代码因为某个 ADR 而看起来反常时，在旁边加一行注释写明 ADR 编号。
