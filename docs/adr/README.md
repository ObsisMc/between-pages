# 架构决策记录

ADR 只回答一件事：**为什么这样决定，以及当时打败了哪些方案。**"现在是什么样"看 [architecture.md 的 Current decisions](../architecture.md#current-decisions)；模块接口和不变量看各模块 README；验证数据在 [validation/](../validation/)。

## 原则

1. 一份 ADR 只写一个决定。
2. 采纳后不改正文；决定变了，写新 ADR 取代它。
3. 不写会变的东西：配置项、版本号、测试路径、测试数据各有归属（见文末）。
4. 规则尽量由 `checks/` 自动检查。

## 什么时候写

**要写**：

- 在两个说得通的方案之间做选择（库、模式、数据结构、协议）；
- 故意不做一件读代码的人会预期要做的事；
- 新增或去掉模块边界、抽象或职责；
- 接受一个以后可能被推翻的限制；
- 跨大版本且行为有变的升级。

**不写**：配置值调整、小版本升级、实现细节、只有一种正确写法的修复。

大决定需要先确认时，单独开只含 ADR 的 PR，以 `提议` 评审；实现中出现的决定，ADR 和代码放在同一个 PR。

## 文件名与引用

- 新 ADR：`YYYY-MM-DD-<slug>.md`，例如 `2026-10-24-authentication-and-sessions.md`。slug 在所有 ADR 中唯一，引用时用 slug。日期是首次提交的日期；不用递增编号，避免并行分支撞号。
- `0001`～`0006` 是旧格式，保留原名并冻结，引用写 `ADR-0006`。
- 目录不分子目录，用"范围"字段分类。某个模块积累五份以上只关它自己的 ADR 时，再考虑移到该模块下。

## 模板

正文结构参照 [MADR 4.0](https://adr.github.io/madr/)。复制以下内容开始写：

```markdown
# <决定本身，用陈述句>

- 状态：提议
- 日期：YYYY-MM-DD
- 决策者：Ray
- 范围：认证
- 关联：依赖 ADR-0003

## 背景与问题

要解决的问题和约束；不提方案也能读懂。

## 决策依据

1. <目标或约束，编号，供后文引用>

## 备选方案

- **方案 A**：对照决策依据说明优劣。
- **方案 B**：……

## 决策结果

选择方案 A：<一句话结论>。

- <要点：选了什么、范围到哪里为止>

### 约束

1. <这个决定带来的、必须一直成立的规则>

### 后果

得到什么、付出什么、有哪些风险。

### 确认方式

- 约束 1：<由哪类测试或检查验证；只写文字，不写文件路径>

## 补充信息

- 重新评估条件：<出现什么情况就重开这个决定>
- 证据：<spike、validation 报告的链接>

## 实施记录

（只追加；只记录待定项定下来的结论。）
```

写法要求：

- **决策结果写多少**：标准是"只读决策结果和约束，能否判断一个实现是否违背了这个决定"。能判断就够了，不能就补充。超过十来条通常说明混进了实现细节或其实是两个决定。大段设计细节（协议格式等）放模块 README 或设计文档，这里链接。
- **约束**可选；写了就编号，并在"确认方式"里逐条说明怎么验证。
- **备选方案**必须对照决策依据说明输在哪；方案复杂时可另起"各方案优缺点"一节。
- **重新评估条件**必填。

## 范围取值

`领域`、`协同`、`存储`、`备份`、`认证`、`技术栈`。需要新范围时，在同一个 PR 里更新这里和 `checks/adr-lib.ts` 的 `SCOPES`。

## 状态与关联

| 状态 | 含义 |
| --- | --- |
| 提议 | 讨论中，可以随意修改 |
| 已采纳 | 决定生效；合并 PR 时由 `提议` 改为此值 |
| 已拒绝 | 讨论后不采纳；保留，防止同一方案被反复提出 |
| 已废弃 | 不再适用且没有替代；在正文开头加一行原因和日期 |
| 已取代 | 被新 ADR 整体取代 |

"关联"行用全角分号 `；` 分隔，每项是以下形式之一（`<引用>` 为 `ADR-NNNN` 或 slug）：

- `依赖 <引用>`
- `取代 <引用>`，部分取代写 `取代 <引用> 的<哪部分>`
- `被 <引用> 取代`（状态应为 `已取代`），部分被取代写 `<哪部分>被 <引用> 取代`（状态仍为 `已采纳`）

取代关系必须两边都写，检查脚本会核对。

## 采纳后怎么改

采纳后只允许修改：状态行、关联行、失效链接、错别字，以及在"实施记录"末尾追加。其他改动需要给 PR 打 `adr-amend` 标签并说明理由（`verify-adr-immutable`）。

| 情况 | 怎么做 |
| --- | --- |
| 按 ADR 实现的普通 PR、重构、修 bug | 不动 ADR |
| ADR 里的待定项定下来了 | 实施记录追加一行：日期、结论、PR 号 |
| 实现与决策结果或某条约束冲突 | 同一个 PR 里写新 ADR 取代（全部或部分） |
| 实现完成 | 不写；"实施"列由测试标记自动得出 |

判断标准：**只读原 ADR 的决策结果和约束，会不会做错？**会就写新 ADR，不会就不动或只追加实施记录。

## 实施状态

验证某条约束的测试或检查，在标题里写 `[adr:<slug>#<约束编号>]`，例如 `it('[adr:authentication-and-sessions#1] refuses a different subject with an existing email', …)`。ADR 不链接测试，所以测试改名、移动不影响 ADR；删除某条约束唯一的测试时，索引里的覆盖数会在该 PR 中下降。`verify-adr-tags` 检查标记指向存在的 ADR 和约束编号。`prototypes/` 下的测试不计入：spike 证明的是可行，不是产品已经实现。

## 信息归属

| 信息 | 放在哪 |
| --- | --- |
| 为什么选 A 不选 B | ADR |
| 待定项的最终结论 | ADR 的实施记录 |
| 现在的架构、当前生效的决定 | [architecture.md](../architecture.md#current-decisions) |
| 模块接口、不变量、已接受的限制 | 模块 README |
| 测试数据和验证证据 | [validation/](../validation/) |
| 产品功能是否达标 | [acceptance.md](../acceptance.md) |
| 一次改动的理由 | 提交信息和 PR 描述 |
| 漏到 `main` 的 bug | [postmortem/](../postmortem/README.md) |

## 自动检查

- `verify-decision-format`：开头五行、状态取值、文件名、新格式的固定小节、取代关系双向一致、architecture.md 不链接已取代或已废弃的 ADR。
- `verify-adr-index`：上面的索引等于生成结果。
- `verify-adr-tags`：测试里的 `[adr:…]` 标记有效。
- `verify-adr-immutable`：已采纳 ADR 只有允许的改动，否则需要 `adr-amend` 标签。
