# 架构决策记录

一份 ADR 既写**为什么这样决定、打败了哪些方案**，也写**怎么实现**：提议阶段它就是这项工作的完整设计和实现计划，实现后它描述最终系统承诺。"现在整体是什么样"看 [architecture.md 的 Current decisions](../architecture.md#current-decisions)；模块接口看各模块 README；验证数据在 [validation/](../validation/)。

这套写法综合了 DeepSeek Harness 的 Agent Notes（生命周期、交付计划、验收标准、实现后同步事实）和 ora-space specs 的 ADR（分项决策、编号不变量、备选方案表）。

## 原则

1. 一份 ADR 只写一个决定；互相独立、可以分别评审的选择写成 D1、D2… 分项。
2. **决定一经采纳就不再改**；实现后，文中的事实（路径、表名、配置项）随代码同步；决定本身变了，写新 ADR 取代它。
3. 提议阶段写到"不看代码也能评审、照着就能实现"的程度：数据模型、流程、接口、配置都可以写进来；实现后删掉计划和推测，只留最终系统承诺。
4. 项目进度只记在 [roadmap.md](../roadmap.md)，根 README 保留同步日期的一行概况；讨论和变更证据放 issue/PR，不在 ADR 另写进度。
5. 规则尽量由 `checks/` 自动检查。

## 什么时候写

**要写**：

- 在两个说得通的方案之间做选择（库、模式、数据结构、协议）；
- 故意不做一件读代码的人会预期要做的事；
- 新增或去掉模块边界、抽象或职责；
- 接受一个以后可能被推翻的限制；
- 一项需要设计才能动手的功能（例如登录、空间与邀请、协同协议）；
- 跨大版本且行为有变的升级。

**不写**：配置值调整、小版本升级、只有一种正确写法的修复。

先单独开只含 ADR 的 PR，以 `提议` 评审；评审通过、合并时改为 `已采纳`。实现中才出现的小决定，ADR 和代码放在同一个 PR。

## 文件名与引用

- 新 ADR：`YYYY-MM-DD-<slug>.md`，例如 `2026-10-24-authentication-and-sessions.md`。slug 在所有 ADR 中唯一，引用时用 slug。日期是首次提交的日期；不用递增编号，避免并行分支撞号。
- `0001`～`0006` 是旧格式，保留原名并冻结，引用写 `ADR-0006`。
- 目录不分子目录，用"范围"字段分类。

## 状态与生命周期

| 状态 | 含义 | 正文怎么改 |
| --- | --- | --- |
| 提议 | 评审中 | 随意改 |
| 已采纳 | 决定生效，按它实现 | `## 决策依据`、`## 不变量`、`## 备选方案` 冻结；其他小节可随实现推进修正（例如落地顺序、未解决问题的结论） |
| 已实现 | 代码已落地并验证 | 转入时精简：删掉 `## 落地顺序`、`## 验收标准` 和已失效的推测，改成现在时，新增 `## 验证`；之后 `## 决策` 里的事实随代码同步。三个冻结小节仍然冻结 |
| 已拒绝 | 讨论后不采纳 | 冻结；保留它是为了防止同一方案被反复提出 |
| 已废弃 | 不再适用且没有替代 | 冻结；正文开头加一行原因和日期 |
| 已取代 | 被新 ADR 整体取代 | 冻结 |

实现偏离了已采纳的决定：细节偏差（文件拆分、配置名），转为 `已实现` 时写进 `## 决策` 并说明原因；违反了某条不变量或改变了决定，写新 ADR 取代（全部或部分）。

改动冻结小节需要给 PR 打 `adr-amend` 标签并在 PR 里说明理由（`verify-adr-immutable`）。

## 模板

复制以下内容开始写。`提议` 和 `已采纳` 用这套结构：

```markdown
# <结论，用陈述句>

- 状态：提议
- 日期：YYYY-MM-DD
- 决策者：Ray
- 范围：认证
- 关联：依赖 ADR-0003

开头一段：最终方案、关键行为、影响面，以及本 ADR 不负责什么。

## 背景与问题

要解决的问题和约束；不提方案也能读懂。

## 决策依据

1. <目标或约束，编号，后文按编号引用>

## 决策

### D1：<规则，用陈述句>

先写规则和外部可观察的行为，再写为什么（约束、失败模式、代价），
容易误解的地方给出边界或反例（表格或短代码块）。
数据模型、流程、接口、配置写在相关的 D 里，或作为 `## 决策` 下的独立小节。

## 失败与恢复

（涉及状态、事务或外部副作用时写）每种失败情况的结果和恢复方式。

## 不变量

1. <简短、肯定、能单独验证的系统承诺>

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **方案 A** | 承认它更好的地方 | 对照决策依据编号说明输在哪 |

## 风险与代价

## 未解决的问题

（可选）只写明确留给以后的边界，每条给出实现时的默认做法。

## 落地顺序

分阶段；每个阶段写范围、完成条件、从此改变的行为。
需要 AI 自主实现时，在这里写"自主实现约定"：预先批准的依赖和迁移、
AI 可以自行决定的范围、必须停下来的情况、PR 怎么组织。

## 验收标准

可观察的完成状态，以及每条不变量由哪类测试验证。

## 补充信息

- 重新评估条件：<出现什么情况就重开这个决定>
- 证据：<spike、validation 报告的链接>
```

`已实现` 时删掉 `## 落地顺序` 和 `## 验收标准`，在 `## 补充信息` 之前加：

```markdown
## 验证

每条不变量由哪类测试或检查保证（只写文字，不写文件路径）。
```

写法要求：

- **先给结论，再交代边界**：读完开头一段就该知道决定是什么、不管什么。
- **每个 D 都回答"为什么"**，尤其是数据来源、身份边界、持久化影响和错误处理。
- **不变量**是简短、肯定的系统承诺，不写实现步骤或模糊愿望；验证某条不变量的测试在标题里带 `[adr:<slug>#<编号>]`。
- **备选方案**承认对方的优势，否决理由落到决策依据上，不只写"复杂"。
- **详细程度**的标准：评审者不看代码能否判断设计对不对；实现者照着写能否不再提问。能就够了。
- `## 落地顺序`、`## 验收标准`、`## 未解决的问题` 只在实现前有用，转为 `已实现` 时删除或改写。
- **重新评估条件**必填。

## 范围取值

`领域`、`协同`、`存储`、`备份`、`认证`、`技术栈`。需要新范围时，在同一个 PR 里更新这里和 `checks/adr-lib.ts` 的 `SCOPES`。

## 关联

"关联"行用全角分号 `；` 分隔，每项是以下形式之一（`<引用>` 为 `ADR-NNNN` 或 slug），没有关联写 `无`：

- `依赖 <引用>`
- `取代 <引用>`，部分取代写 `取代 <引用> 的<哪部分>`
- `被 <引用> 取代`（状态应为 `已取代`），部分被取代写 `<哪部分>被 <引用> 取代`（状态不变）

取代关系必须两边都写，检查脚本会核对。被取代或废弃的 ADR 不能出现在 architecture.md 的 Current decisions 里。

## 实施状态

验证某条不变量的测试或检查，在标题里写 `[adr:<slug>#<不变量编号>]`，例如 `it('[adr:authentication-and-sessions#3] refuses a different subject with an existing email', …)`。ADR 不链接测试，测试改名、移动不影响 ADR；删除某条不变量唯一的测试时，索引里的覆盖数会在该 PR 中下降。`prototypes/` 下的测试不计入：spike 证明的是可行，不是产品已经实现。

## 自动检查

- `verify-decision-format`：开头五行、状态取值、文件名、按状态要求的小节（`提议`/`已采纳` 要有落地顺序和验收标准，`已实现` 要有验证、不能有落地顺序和验收标准）、`## 决策` 下至少有 `### D1`、不变量连续编号、备选方案是带"优势"列的表格、重新评估条件、取代关系双向一致、architecture.md 不链接已取代或已废弃的 ADR。
- `verify-adr-index`：上面的索引等于生成结果。
- `verify-adr-tags`：测试里的 `[adr:…]` 标记指向存在的 ADR 和不变量编号。
- `verify-adr-immutable`：已离开 `提议` 的 ADR，冻结小节没有被改；`已拒绝`/`已废弃`/`已取代` 的正文没有被改；否则需要 `adr-amend` 标签。
