# 两地时间按浏览器时区自动显示对方当地时间，各自设一组作息算出今天都醒着的时段

- 状态：已采纳
- 日期：2026-10-29
- 决策者：Ray
- 范围：领域
- 关联：依赖 spaces-and-invitations；依赖 space-records

绑定中的两人在首页日记列表上方看到一小条：对方当地的时间、所在时区的地区名和随昼夜变化的色调，以及"下次见面"（数据来自见面计划）和快到的纪念日（数据来自纪念日）。点开是详情页：两人各自的作息和今天两人都醒着的时段，分别用各自的当地时间显示。时区由浏览器在每次打开应用时自动上报，不用设置；作息每人设一组。时区和作息是个人设置，不是双人空间记录：只在绑定期间给当前搭档看，解绑后双方都看不到，重新绑定后恢复。

本文不负责：见面倒数与见面日历（属于见面计划的设计）、纪念日本身（anniversaries），本文只规定首页小条给它们留的位置；手动状态（睡了、在忙、有空聊，用户 2026-10-29 决定不做）；天气与精确位置；"两人都醒着"的提示；"上次见面是 N 天前"；通知。

## 背景与问题

异国的两个人最常遇到的问题是"现在找 TA 合不合适"：不知道对方那边几点、是不是在睡，约视频要来回算时差。用户于 2026-10-29 确认这个功能要做到四件事：知道现在能不能找 TA、感觉离 TA 更近、盼着下次见面、方便安排视频时间。其中"盼着下次见面"的倒数与日历和见面计划共用日期，归入见面计划。

现状：`users` 表没有时区，只有日记在创建时记下 `created_timezone`；网页在打开或补写日记时用浏览器的 `Intl.DateTimeFormat().resolvedOptions().timeZone` 上报时区，契约里已有校验 IANA 时区的 `TimeZone`。规格 §8.2 要求时间统一按 UTC 保存，展示按查看者的 IANA 时区推导并处理夏令时。

## 决策依据

1. 不用设置就能看到对方当地时间；对方出差换了时区，打开应用后自动跟上（用户 2026-10-29 选择自动取浏览器时区）。
2. 约视频时直接看到今天两人都醒着的时段，不用自己换算时差（用户 2026-10-29 选择各自设作息、显示重叠时段）。
3. 设置尽量少：每人一组作息，不分工作日与周末（用户 2026-10-29）。
4. 首页一眼可见，但不挤占日记列表（用户 2026-10-29 选择首页顶部一小条）。
5. 不收集比时区更精确的位置（用户 2026-10-29 不要天气）。
6. 分开以后不再持续让对方知道自己在哪个时区（用户 2026-10-29 选择解绑后不再显示）。
7. 时间按 UTC 保存，展示按 IANA 时区推导并处理夏令时（规格 §8.2）。

## 决策

### D1：时区由浏览器自动上报，存在本人账号上

网页在每次打开应用、以及页面从后台回到前台时，读取浏览器的 IANA 时区；与上次上报的不同才发送。服务端用契约中的 `TimeZone` 校验，存进本人的 `users` 行（`timezone`、`timezone_updated_at`），只接受本人会话为自己上报。对方下次打开应用之前，显示的是上次上报的时区。

不提供手动设置或固定时区的选项。

原因：依据 1、7。浏览器时区随系统设置变化，出差时通常自动更新；只存时区名、不存经纬度，满足依据 5。

### D2：作息每人一组，用当地时间表示

每人可设一组平时的睡觉时间：入睡与起床的当地时刻（精确到 15 分钟），可以跨午夜（如 0:00–8:00、23:30–7:00）。不设也可以，此时不计算重叠时段。作息按"本人当时的时区"解释：本人换了时区，作息跟着在新时区的当地时间生效。

原因：依据 2、3。一组作息覆盖大多数情况；周末的重叠会偏保守，用户接受。

### D3：重叠时段按真实时刻计算，用各自当地时间显示

详情页显示"今天"两人都醒着的时段：以查看者当地的今天 0 点起 24 小时为范围，把双方的睡觉时段换算成真实时刻（处理夏令时与跨午夜），取补集的交集。每段同时显示两边的当地时间，例如"你 20:00–23:30 · TA 9:00–12:30"。任一方没设作息时，只显示两边时间，并提示"设好作息后会显示你们都醒着的时间"。

计算是纯函数，在网页里做，输入只有双方时区、作息和当前时刻。

原因：依据 2、7。只用时区差相减会在夏令时切换日算错；按真实时刻计算没有这个问题。

### D4：首页顶部一小条，昼夜色调只由时区与作息推导

绑定中时，首页日记列表上方显示一小条：

- 对方当地时间与时区对应的地区名（例如"TA 那边 凌晨 3:12 · 东京时间"），随时间走；
- 按对方当地时刻分清晨、白天、傍晚、夜里四种色调；对方设了作息且当前在其睡觉时段内，显示"大概在睡"；
- "下次见面"一行，内容由见面计划提供（确切日期显示"还有 N 天"，大概日期显示"大概 3 月"，没有就不显示）；见面计划实现之前不显示这一行；
- 纪念日一行，在某个纪念日的提醒期内出现，一次只显示一个（anniversaries D3）；纪念日实现之前不显示这一行。

点开小条进入详情页（D3）。从未绑定过、或已解绑的账号不显示小条和详情页入口。

具体色调、地区名的文字与样式由阶段 4 的前端调整决定；本文只规定显示哪些信息。

原因：依据 4、5。色调只用时区就能算出，不需要位置。

### D5：时区与作息是个人设置，只在绑定期间给当前搭档

时区与作息属于账号本人，不是双人空间记录，不适用 space-records 的"解绑后只读归档"：

| 情况 | 对方能看到我的时区与作息吗 |
| --- | --- |
| 绑定中 | 能 |
| 解绑后 | 不能，双方都看不到对方的 |
| 原来的两人重新绑定 | 能，显示最新上报的 |
| 第三人 | 永远不能 |

服务端在返回对方的时区与作息前，在同一次读取里确认两人之间有未结束的绑定期间；没有就不返回，并且响应与"对方从未上报"一致。

原因：依据 6。这是会随行程变化的实时信息，分开后继续提供等于持续告诉对方自己在哪个时区。

## 数据与接口

- **迁移**：`users` 增加 `timezone`（文本，可空）、`timezone_updated_at`、`sleep_start_minute`、`sleep_end_minute`（当地一天中的分钟数，0–1425，15 的倍数，可空，两者同时为空或同时有值）。
- **接口**（形状定义在 `packages/contracts`）：
  - 上报本人时区：请求只含 `timezone`；
  - 设置或清除本人作息；
  - 读取两地时间：返回本人的时区与作息，以及绑定中时对方的时区与作息；解绑或未绑定时对方部分为空。
- **模块**：服务端的读取与上报放在现有管理账号与关系的服务旁（实现时按 api README 选定归属，不放进 `space-records`，因为这里没有空间记录）；网页新增 `two-clocks` 模块（首页小条、详情页、重叠计算纯函数），只导入 `api`。

## 失败与恢复

| 情况 | 结果 | 恢复 |
| --- | --- | --- |
| 浏览器给出无法识别的时区 | 不上报，保留上次的 | 无需处理 |
| 上报失败 | 下次打开或回到前台时重试 | 无需处理 |
| 对方从未上报时区 | 小条显示"TA 还没打开过新版本"，不显示时间 | 对方打开应用后自动出现 |
| 读取时对方刚好解绑 | 绑定检查与读取在同一事务，返回不含对方信息 | 页面转为不显示小条 |

## 不变量

1. 对方的时区与作息只在两人之间存在未结束的绑定期间时返回给对方；解绑后与第三人一律得不到，响应与"未上报"不可区分。
2. 时区只由本人会话为自己上报，且必须是契约 `TimeZone` 接受的 IANA 时区。
3. 作息为同时为空或同时有值的两个当地时刻，按 15 分钟取整，可以跨午夜。
4. 重叠时段按真实时刻计算，夏令时切换日与跨午夜作息结果正确；任一方没有作息时不显示重叠时段。
5. 两地时间只使用时区与作息，不收集或保存更精确的位置。
6. 未绑定过或已解绑的账号看不到小条与详情页。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **手动设置时区** | 不会自动透露所在时区 | 出差忘了改就显示错（依据 1） |
| **自动上报，另可手动固定** | 灵活 | 多一个设置项，目前没有需要固定的场景（依据 3） |
| **手动状态：睡了、在忙、有空聊** | 比作息更实时 | 用户 2026-10-29 决定暂不需要 |
| **工作日与周末各一组作息，或按星期几分别设** | 周末重叠更准 | 设置更麻烦；用户选择一组（依据 3） |
| **只显示两边时间，不算重叠** | 最简单 | 约视频仍要自己换算（依据 2） |
| **发起并确认视频时间** | 更完整 | 已是小日程功能，没有通知时对方未必及时看到 |
| **天气或日出日落** | 更有陪伴感 | 需要城市级位置与外部服务（依据 5） |
| **解绑后仍显示，或停在解绑时的时区** | 保留一点联系 | 分开后仍持续或曾经透露所在时区（依据 6） |
| **时区与作息作为双人空间记录** | 沿用 space-records 的全部规则 | 它们属于个人且实时变化，解绑后只读归档会继续暴露最后的位置（依据 6） |

## 风险与代价

- 浏览器时区跟随系统设置；系统时区设错时显示也错。
- 对方很久没打开应用时，显示的可能是旧时区；本文不提示上报时间（见未解决的问题）。
- 地区名来自时区名（`Asia/Tokyo` → 东京时间），同一时区覆盖多个城市时只显示代表城市或国家。
- `users` 表新增四列，迁移须在实现前确认（AGENTS.md）；本 ADR 采纳即视为预先批准。

## 未解决的问题

- 对方上次上报时区已经很久（例如一周以上）时是否提示"按 N 天前的时区"。默认做法：不提示，实际使用中发现误导再加。
- 色调的分段时刻（清晨、白天、傍晚、夜里）。默认做法：5–8 点清晨、8–17 点白天、17–20 点傍晚、其余夜里，阶段 4 可调。

## 落地顺序

1. **本 ADR 采纳**：与第一批其他功能的设计一起评审（用户 2026-10-29 决定第一批设计完再合并 space-records）。
2. **实现**：一个 PR 完成迁移、契约、上报与读取接口、`two-clocks` 网页模块（小条、详情页、重叠计算）与依赖方向规则；"下次见面"与纪念日两行分别等见面计划与纪念日实现后接入。本功能不使用 `space-records`，不需要等它落地。
3. 实现后本文转为"已实现"，路线图对应行与 README 状态行同步。

## 验收标准

- 换浏览器时区后重新打开页面，对方的小条显示新时区与当地时间（浏览器测试，不变量 2）。
- 上报非 IANA 时区或替别人上报被拒（API 测试，不变量 2）。
- 解绑后双方读取两地时间都不含对方信息，第三人同样；重新绑定后恢复（API 测试，不变量 1）。
- 重叠计算：跨午夜作息、夏令时切换日、两人相差 13 小时以上、任一方没设作息（单元测试，不变量 3、4）。
- 未绑定过的账号首页没有小条（组件测试，不变量 6）。
- 验证某条不变量的测试标题带 `[adr:two-clocks#<编号>]`。

## 补充信息

- 重新评估条件：要做手机端或通知（可能需要更实时的状态）；用户需要按星期几区分作息或手动状态；需要天气等更精确的位置信息；出现系统时区普遍不准导致显示错误。
- 证据：2026-10-29 与用户逐条确认（四个目标、倒数与日历归见面计划、自动时区、不做状态、一组作息、重叠时段、昼夜色调、首页小条、解绑后不显示）。
