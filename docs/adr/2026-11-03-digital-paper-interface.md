# 数字书页以内容布局承载成熟组件，并保留轻拟物双窗与圆团子

- 状态：提议
- 日期：2026-11-03
- 决策者：Ray
- 范围：领域
- 关联：依赖 unread-and-day-page；依赖 partner-local-dates；依赖 ADR-0006；取代 opening-book-home 的D1 日期列表、D3 版式与D4 书签；取代 book-frontend-workspace 的D1 展开双页、D2 书签与目录呈现、D3 左右并排与D7 书页视觉

提议把前端调整为暖纸色、衬线标题与清晰操作组件组成的数字书页：顶栏四个入口，主页呈现此刻与日记入口，日记页由日期索引和一个可在「连续读」与「这一天」之间切换的主区组成，空间功能按内容排版。双窗采用轻拟物数字插画的材质方向，橙蓝团子保留五官和小手，轮廓变得饱满圆润。[设计包](../design/2026-11-03-digital-paper/README.md)收录可交互页面、逐页截图、最终一轮效果稿与实现约束。导航、主页、日记页形态与主页时间线已由 Ray 在 2026-11-03 确定（D1、D2）；组件依赖仍待单独批准。

## 背景与问题

[书本工作区 PR #58](https://github.com/ObsisMc/between-pages/pull/58)、[全站书页 PR #61](https://github.com/ObsisMc/between-pages/pull/61)与[书签修正 PR #62](https://github.com/ObsisMc/between-pages/pull/62)仍在其他分支评审。固定双页、页内独立滚动与整页目录形成清晰的书本外观，也增加手机正文之前的控制数量，并让内容较多的一页无法利用另一页的空白。

Ray 希望可以采用 shadcn 一类成熟组件，保留产品辨识度，并要求窗口避免直接复制整张图片作为前端。扁平双窗被认为过于简约；随后接受以 Waffle Journal 为质感参考的轻拟物双窗方向，又提出让团子采用同样的数字插画质感并更圆。本 ADR 把这些约束与仍待讨论的布局建议分开，避免把预览当成已完成的应用。

2026-11-03 对照书本 PR 逐项取舍后，Ray 决定：保留所有日记的连续阅读（book-frontend-workspace 依据 3 不变）；日记页用日期索引加两种视图的主区；主页不露日记正文，但列出最近的日期与新内容；主页保留共同醒着的时间线；导航改为顶栏。书本 PR 中的逻辑（#54 接口、#56 连续列表、#58 日期编辑与位置保持、#59 未读按钮、#60 的修复）与布局无关，继续使用；书本外观（#57 的书与目录、#61、#62）由本 ADR 取代。

## 决策依据

1. 反复阅读与书写时，正文和对方的新内容应容易找到，主要操作应尽量少。
2. 品牌辨识度来自稳定的纸色、字体、作者色、双窗与角色，不要求所有功能服从实体书的版式。
3. 采用成熟交互组件可以减少重复实现，但不能引入未经批准的依赖或改变产品权限。
4. 用户希望保留细微材质、柔和光影和厚度，窗口应有可独立调整的结构层。
5. 作者、共享、未读、历史与保存的来源仍由既有服务端规则决定，布局调整不能改变语义。

## 决策

### D1：采用四个主要入口与按功能组织的次级导航

所有登录后的页面顶部是同一条导航，主要入口为「此刻、日记、一起、设置」；一起包含心愿与礼物、纪念日、两地时间，设置包含双人空间与备份。导航取代书签与目录（opening-book-home D4、book-frontend-workspace D2 的呈现），主行动仍直接写在页面上。

入口的可见规则沿用 book-frontend-workspace D2 的目录项规则（[#57](https://github.com/ObsisMc/between-pages/pull/57) 的 `SiteContents` 已实现）：只列当前能进入的页面；两地时间只在绑定中出现；心愿、纪念日与双人空间在有空间时出现，解绑后仍通向获准的只读记录；未绑定不展示对方数据。入口未读提示沿用服务端判定，不泄露尚未揭晓的准备状态。登录与邀请不在导航里，只在对应认证流程出现；预览中的评审入口不进入应用。理由：依据 1、3、5。

### D2：主页列出最近的日期但不露正文，日记页用日期索引和两种视图的主区

**主页**保留双窗的情绪表达，提供「继续写今天」与「读 TA 的新内容」，再列出最近几个有日记的日期：每个日期只显示日期、写了的人（团子头像与名字）和对方新内容的提示，不显示日记正文或摘要，也不增加标题字段。opening-book-home D1 中首页不渲染正文与摘要的规则不变，只放开其中「不列按日期排列的卡片」一项。「读 TA 的新内容」进入连续读，并定位到最近一处未读（`GET /api/days/next-unread`）。两地时间沿用 opening-book-home D2：双方时钟、共同醒着的时间线与「现在」，复用 #57 的 `HomeClocks`；纪念日摘要沿用现有一行。未绑定时按 opening-book-home D5 显示邀请入口。

**日记页**（`/days`、`/days/:date`）左侧是常驻的日期索引，主区只有一个，在两种视图间切换：

| 视图 | 内容 | 沿用 |
| --- | --- | --- |
| 连续读（`/days`） | 所有日记按日期由新到旧连续显示全文，按需双向加载，跳到日期，上下未读按钮，正在写的折叠 | book-frontend-workspace D4、D5、D8；#56 `DayFeed`、#59 未读按钮 |
| 这一天（`/days/:date`） | 这一天的双人日期页：两篇上下排列，各自的作者、可见性、未读、历史、光标与保存状态 | unread-and-day-page D6；#58 `DayEditor` |

在索引或连续读里选一天进入「这一天」，返回回到连续读原来的位置；列表位置存在浏览器历史状态里，不写进网址（book-frontend-workspace D3 的这部分不变，#58 已实现）。D8 中的「左页」指「这一天」视图，「在左页打开」即打开这一天。窄窗口里日期索引收成可展开的日期选择，主区占满宽度；从连续读进入这一天再返回的单页路径按 book-frontend-workspace D6。取代的只是宽窗口左页编辑、右页列表并排的版式（D3）。理由：依据 1、2、5。

### D3：空间功能按内容安排，状态在对应内容旁说明

心愿先展示已有记录，以分类切换与按需打开的新增表单组织；纪念日显示日期、当地倒数与历年入口；两地时间保留双方时区、跨日和作息推算；空间管理明确自己的范围及其变更确认；备份保留服务端备份、保存、历史版本、Google 可读副本的区别。窄窗口按顺序自然展开，避免为了左右页强行固定分区。这取代 book-frontend-workspace D7 中「沿用书页语言」的视觉要求；D7 列出的各功能领域边界不变。

「我的」指自己拥有的那篇日记；「只看我写的文字」是作者过滤，二者须有明确名称。正常备份详情可以收起，保存失败、仅存本机、只读、共享停止与需要用户处理的备份异常持续可见。理由：依据 1、3、5。

### D4：窗框、天空、光照与团子分别实现，字体与头像沿用书本稿

双窗以暖橙与青蓝区分两人；窗框有圆润边缘、细微纹理、内沿和窗台厚度，光影克制。角色保持简单五官、小手、橙蓝配色及柔软哑光质感，采用最新一轮饱满、略扁的圆轮廓。天空的昼夜应来自对应人的当地时间；橙蓝身份不随昼夜互换。

生成的 PNG 是材质与造型参考，不能整张充当正式首页或窗口实现。默认用 SVG/CSS 分层绘制窗框、窗台、天空与光照；细纹理可评估程序生成的可缓存噪声。团子作为独立组件或独立透明素材评估，不与窗口焊成一张图片。本 PR 不承诺 SVG/CSS 能逐像素重现生成图，不批准引入 3D 运行时、纹理依赖或新的 npm 依赖。

字体与头像沿用 #61 中 Ray 于 2026-11-02 批准的做法，实施时从该分支取回：标题与正文用随项目提供的完整 Noto Serif SC，按 Google Fonts 的 `unicode-range` 切片自托管，浏览器只下载用到的切片；作者头像是单个团子轮廓，作者槽 1 暖橙、槽 2 雾蓝，可读名称是显示名，名字始终以文字写在旁边，轮廓改为本轮的圆形。理由：依据 2、3、4。

### D5：原型中的模拟状态不能成为生产逻辑

页面中的日期、账号名、正文、历史、作息、邀请与备份反馈都是虚构演示数据。直接编辑正文、点击模拟登录、切换礼物准备和弹窗提交只演示布局，不连接 API，也不验证身份、归属或持久化。实现时须复用现有 callApi、会话、日记内核、共享范围确认和未读上报的职责；每个 UI 状态来自相应真实状态，不能复制原型的前端“成功”赋值。理由：依据 3、5。

## 不变量

1. 作者身份、保存成功、共享范围与未读判定沿用既有权威来源。
2. 页面切换、菜单和历史预览保留未提交文字、编辑状态与阅读位置。
3. 隐藏、过滤、遮挡或尚未加载的对方文字不会因改版被报告为已读。
4. 私密礼物准备和未共享日记不进入对方的摘要、圆点或导航信息。
5. 本机保存失败、未确认同步、只读和共享停止具有持续可见的说明。
6. 正式窗口由可独立调整的结构层构成，生成的整张效果稿不成为窗口组件。
7. 两人的橙蓝身份稳定，天空昼夜与纪念日倒数遵循已有时区规则。
8. 新增依赖、正式功能与验收完成状态有各自的明确决策和验证，不从设计原型推定。
9. 主页不渲染任何日记正文或摘要；最近的日期只显示日期、写了的人与新内容提示。
10. 在连续读与这一天之间往返，连续读回到离开时的位置。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 全站沿用固定双页和整页目录 | 书本隐喻强，已有实现和浏览器验收 | 作为本提议的比较基线；长表单和手机顶部操作的容量问题仍需解决（依据 1） |
| 全站直接套用默认组件与平面图标 | 实现较快，组件一致 | 已展示的极简双窗被用户认为缺少质感，需保留自己的视觉语言（依据 2、4） |
| 将生成的完整双窗或整个页面作为背景图 | 初始呈现接近效果稿 | 窗框、角色、主题和昼夜难以独立调整，不符合用户对实现的要求（依据 4） |
| 所有物件使用实时 3D | 光照与形变可控 | 为当前静态装饰引入新的运行和维护成本，没有对应需求（依据 3） |
| 日记页只有日期索引和单日正文，不再连续阅读 | 结构最简单 | Ray 2026-11-03 决定保留连续阅读；逐篇点开违背 book-frontend-workspace 依据 3（依据 1） |
| 日记页保留编辑与连续读左右并排 | 改动最少 | 宽窗口同时出现两个正文区，与只设一个主区的目标相反（依据 1） |
| 主页显示最近日记的文字摘要 | 不进日记页就能读到片段 | 推翻首页不露正文的隐私约定，还要另定摘要是否算已读；只提示新内容已能满足发现（依据 1、5） |

## 风险与代价

- 质感效果稿比程序绘制的图层更自由，须在实际尺寸、亮暗主题及浏览器性能之间取舍。
- 预览用虚构内容覆盖主要页面，尚未覆盖每种空状态、解绑、断网和权限拒绝；真实表单也比模拟交互更复杂。设计包中的主页截图仍显示文字摘要与平面窗口，以本 ADR 为准。
- 书本 PR 的外观实现与其浏览器版面测试（`e2e/book.spec.ts` 的书页、书签部分）作废，需按新版面重写。
- 手机示意用于评审信息层级，不改变路线中手机支持后置的安排，也不代表真实手机验收完成。

## 落地顺序

1. 书本栈只保留逻辑：Ray 验证后按 #53、#51、#52、#54、#56、#58（含 #57）、#59、#60、#49 的顺序合并；#60 的手动清单只需验阅读、未读、编辑、离线等行为，书本外观项可跳过。关闭 #61、#62，保留分支以取回 D4 的字体与头像。完成条件：上述 PR 已合并，`main` 上有 opening-book-home 与 book-frontend-workspace。
2. 本 ADR 合到 `main` 时改为已采纳，并在同一 PR 同步 architecture.md 的当前决定。按组件的当前消费者评估 shadcn 依赖及确切版本；依赖增加仍按 AGENTS.md 的审批边界处理。本提议不提前批准安装。
3. 先完成组件主题、顶栏导航、分层双窗与主页（复用 `HomeClocks`、`SiteContents` 的可见规则），再做日记页：日期索引与两种视图，复用 `DayFeed`、`DayEditor` 与未读按钮；删除 `BookSpread`、书签与目录。以既有作者、保存、未读和位置保持场景回归。
4. 再落实心愿、纪念日、两地时间、空间与备份；登录和邀请复用认证与关系流程。每个行为变更同步模块 README 和对应测试。
5. 在桌面 Chromium、WebKit 与目标窄窗口检查长文、键盘、中文、时区和异常状态；性能目标由实施前的实际组件基线确定，不以模拟页面的速度替代。

## 验收标准

- 本设计包：所有页面可打开，主要导航、分类切换、表单和范围预览可演示；截图与实际导出一致；相应验证写在设计包的验证记录中。
- 不变量 1、4、5：正式实施时由现有真实 API / PG 场景及渲染界面错误状态测试回归，不能只测试模拟文案。
- 不变量 2、3、10：正式实施时用浏览器验证未提交文字、焦点、阅读锚点、隐藏内容与未读上报，以及连续读与这一天往返后的列表位置。
- 不变量 6、7：检查真实窗口结构层及身份色映射，回归昼夜、跨午夜、夏令时和对方日期倒数。
- 不变量 8：PR 清楚区分设计、模拟验证和真实业务验收；新增依赖有明确批准与确切版本。
- 不变量 9：组件测试与浏览器测试检查写过日记的账号打开主页时没有日记正文，最近日期只显示日期、头像与名字和新内容提示。
