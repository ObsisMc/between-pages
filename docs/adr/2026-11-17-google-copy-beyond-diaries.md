# 每人的 Google Drive 也放共享页面、心愿单、礼物墙与纪念日，内容与本人在应用里看到的一致，未揭晓的礼物只进送的人自己的 Drive

- 状态：提议
- 日期：2026-11-17
- 决策者：Ray
- 范围：备份
- 关联：依赖 server-backup-and-google-docs；依赖 space-records；依赖 shared-pages；依赖 wishes-and-gifts；依赖 anniversaries；依赖 diary-collaboration-kernel；取代 space-records 的D7 与不变量 8；取代 shared-pages 的D4 与不变量 7 中不进 Google 可读副本的部分；取代 shared-pages 的不变量 5 中已删除页面对 Google 副本也按不存在处理的部分；取代 server-backup-and-google-docs 的D5 与不变量 5 中 Drive 只放日记的部分

Google 可读副本从"每天一份日记 Doc"扩展到用户在应用里写字的所有地方：每个共享页面一份 Doc，心愿单、礼物墙（含卡片）、纪念日各一份汇总 Doc，都放在各自 Drive 的 `Between Pages/Together/` 下，日记的 `Between Pages/年/月` 不变。边界和日记副本相同：Drive 里是本人此刻在应用里能看到的内容，包括对方写的字，按作者着色或标明是谁写的。准备中的礼物和卡片在揭晓前只进送的人自己的 Drive，收的人的 Drive 与备份状态里看不出任何迹象。共享页面每形成一个历史版本写一次；汇总 Doc 在这一功能最后一次改动 2 分钟后整份重写。应用里删除的页面，Doc 保留并改名为"已在应用中删除"；删除的心愿、礼物、纪念日从汇总里消失，Google Docs 的版本历史里还找得到。备份页按类显示进度并说明这些内容会进两人各自的 Drive、应用里删除收不回，共享页面像日记一样显示"已备份到 Google"。一个 Google 账号同一时间只能被一个用户连接，两人的副本不会落进同一个 Drive。写入链路、令牌、外部修改另存与被删重建、失败提示全部沿用 server-backup-and-google-docs。

本文部分取代 space-records 的 D7 与不变量 8（双人空间记录不进 Google 可读副本），以及 shared-pages 的 D4 与不变量 7 中"页面不进 Google 可读副本"的部分；shared-pages 不变量 7 的其余部分（页面不进日记列表、日记未读、共享轮次，也不写入 `backup_outbox`）不变。还部分取代 shared-pages 不变量 5：已删除的页面对两人的接口读取仍按不存在处理，只有 worker 为写 Google 副本可以读到它删除前的最后一次提交（D7）。也部分取代 server-backup-and-google-docs 的 D5 与不变量 5：Drive 里除了本人日记与对方共享的获准版本，还有本文的 `Together` 内容，日记部分的边界不变。

本文不负责：两地时间与作息（个人设置，不是写下的内容）、纪念日的提醒天数、团子的戳与摸、动作历史、删除提示、未读与已读；见面计划及之后的功能（各自在设计里决定，默认沿用本文的汇总 Doc 写法）；链接预览图片；Google 里的修改导回应用；按月合并日记 Doc。

## 背景与问题

server-backup-and-google-docs 让每人连接自己的 Google Drive，每天写一份日记 Doc，"服务不在了也能读"。之后上线的双人空间功能都没有进 Drive：space-records D7 当时判断用户暂时不需要在 Google 里翻这些记录，shared-pages D4 沿用了这一点。

2026-11-17 Ray 定下新一批工作，其中一项是扩展 Google 副本："尽可能让用户拿到他们自己写的东西"。现在用户能写字的地方除日记外有：共享页面（正文与标题）、心愿（名称、链接、备注、想要程度）、礼物与卡片、纪念日（名称、备注、日期）。要回答的问题：哪些内容进、对方写的进不进、在 Drive 里怎么排、什么时候写、送礼的惊喜怎么不提前泄露、删除和解绑时怎么办、备份页怎么显示。

约束：日记 Doc 的写入链路已在生产运行（连接、令牌密文、worker、`requiredRevisionId` 写入、另存、重建、每日检查、失败提示）；Drive 授权只有 `drive.file`；空间记录的写入在持有绑定期间共享锁的事务里，页面提交在持有文档锁的事务里（shared-pages 不变量 11），登记任务不能引入新的锁顺序。

## 决策依据

1. 尽可能让用户拿到自己写的东西：在应用里写下的文字，在自己的 Google 里也能读到，服务不在了也能读（Ray，2026-11-17）。
2. 授权边界与日记副本相同：一个人的 Drive 里只有本人此刻在应用里能看到的内容（server-backup-and-google-docs 依据 8、不变量 5）。
3. 惊喜不泄露给收的人：揭晓前的礼物与卡片只进送的人自己的 Drive；收的人的 Drive 里没有它，也不能从自己的备份状态看出有人在准备（wishes-and-gifts D2，space-records D9）。
4. 沿用已有的写入链路与失败处理，不新增 Google 权限、不新增 npm 依赖（server-backup-and-google-docs 依据 11、12）。
5. 应用里的操作不等待、不依赖 Google（同上依据 9）。
6. 应用不删除用户 Drive 里的文件；Google 里的人为修改不被悄悄覆盖（同上依据 10）。
7. 页面不混进日记列表、日记未读与日记副本，这一点仍靠结构保证（shared-pages 依据 7）。
8. 在两人规模与 Google 免费配额之内运行。

## 决策

### D1：进 Drive 的是共享页面、心愿、礼物与卡片、纪念日

| 进 | 不进 |
| --- | --- |
| 共享页面：标题与整页正文 | 收的人那边：揭晓前的礼物、卡片与"我在准备"（D3） |
| 心愿：名称、链接、备注、想要程度 | 动作历史、删除提示、未读与已读 |
| 礼物：已揭晓的进两人的礼物墙；准备中的只进送的人自己的（D3）；名称、链接、谁送给谁、日期、场合、卡片 | 纪念日的提醒天数（个人设置）、两地时间与作息 |
| 纪念日：种类、名称或谁的生日、日期、备注 | 团子的戳与摸（没有文字、不留历史） |
| | 链接预览的图片，"第 N 天"这类随日子变化的计算值 |

原因：依据 1。进的都是某个人写下的文字；不进的要么不是谁写的（历史、提示、状态），要么是个人设置，要么会让 Doc 每天无故改变。链接预览的标题与网站名是文字，随链接一起写；图片只是外站地址，服务不在后也不保证可读，不写。

### D2：内容是本人在应用里能看到的全部，对方写的也进

| 内容 | 你的 Drive | 对方的 Drive |
| --- | --- | --- |
| 共享页面（两人的字穿插） | 整页，每个字按作者着色 | 同一页，各存一份 |
| 你的心愿、TA 的心愿 | 两份心愿单都有 | 两份都有 |
| 已揭晓的礼物与卡片（无论谁送谁） | 有 | 有 |
| 纪念日（无论谁记的） | 有 | 有 |
| 你正在为 TA 准备的礼物、卡片与"我在准备" | 有（礼物墙的"准备中"一节） | 无，揭晓后才有 |

内容一律经与接口相同的、按查看者过滤的读取入口取得：共享页面经共享页面服务按本人读取，心愿、礼物、纪念日经各功能服务的列表读取（含私密过滤，space-records D9）。所以 Doc 里不可能出现本人在应用里读不到的东西：私密的记录与动作（`private_to` 不为空）只有 `private_to` 那个人读得到，也就只进他的 Drive（D3）。

原因：依据 1、2。共享页面里两人的字是穿插的，只留自己的会变成碎片；心愿单、礼物墙与纪念日在应用里两人本来都看得到，和日记副本"对方共享给你的那篇也进"是同一条边界。各存各的，一方断开连接不影响另一方（与 server-backup-and-google-docs D5 相同的理由）。

### D3：揭晓前的礼物与卡片只进送的人自己的 Drive，收的人揭晓后才有

- 送的人的 Gifts Doc 开头有一节"准备中（还没揭晓，只在你的 Drive 里）"，列出他正在准备的礼物与卡片；他的 Wishes Doc 里，对方那条心愿上标出"我在准备"。与他在应用里看到的一致。
- 收的人的 Drive 里没有这份礼物、卡片和"我在准备"的任何痕迹；准备、改卡片、取消准备都不为收的人登记待写，所以他的备份页、进度与问题记录也不因此变化。
- 揭晓（送的人点揭晓，或收的人点"收到了"）是公开动作，同一事务里为两人登记礼物墙待写：送的人那边从"准备中"移到礼物墙，收的人那边第一次出现。揭晓后的卡片修改照常为两人登记。
- 取消准备：从送的人的"准备中"一节消失，留在他自己那份 Doc 的版本历史里；收的人从未有过。

原因：依据 1、3（Ray 于 2026-11-17 决定）。卡片草稿是送的人自己写的字，应当拿得到；要防的是收的人看到，而收的人的 Drive 与备份状态完全不受影响。送的人自己的 Drive 可能在共用设备、共享屏幕时被看到，这与他在应用里打开礼物页是同一种风险，由他自己掌握。

### D4：Drive 里的位置：`Between Pages/Together/`，每个页面一份，另有三份汇总

```
Between Pages/
  2026/10/2026-10-28 周三          ← 日记，不变
  Together/
    Shared pages/
      旅行清单                      ← 每个共享页面一份，文件名是页面标题
      未命名页面
      周末计划（已在应用中删除）     ← D7
    Wishes                          ← 两人的心愿单
    Gifts                           ← 礼物墙，含卡片
    Anniversaries                   ← 纪念日
```

- 文件夹与汇总 Doc 的名字用英文（Ray，2026-11-17）；Doc 的正文是中文，与应用一致。页面 Doc 的文件名是页面标题，没有标题时用应用里的占位名"未命名页面"；同名的页面在 Drive 里是两个同名文件，应用按记下的 Doc ID 区分，从不按名字找。
- 文件夹沿用 server-backup-and-google-docs D7 的规则：按记下的 Drive 文件 ID 找，用户移动或改名后跟着它，只有删掉才在原位置重建。

各 Doc 的版式：

```
旅行清单                                         ← 标题 1：页面标题
（已解绑，内容不再更新）                          ← 仅解绑后，紧跟标题，D7；四种 Doc 都一样
■ Ray   ■ TA                                     ← 图例，作者颜色与应用一致
（正文，每个字用作者的颜色）

心愿单                                           ← Wishes
Ray 的心愿                                        ← 标题 2，本人在上
  灰色围巾  ♥♥♥♥                                  ← 标题 3：名称与想要程度
  https://…（网站名 · 预览标题）
  备注：深灰，长款
TA 的心愿                                         ← 标题 2

礼物墙                                           ← Gifts，按礼物日期从新到旧
  2026 年 10 月 28 日 · TA 的生日                  ← 标题 2：日期与场合
  灰色围巾  Ray 送给 TA                           ← 名称、谁送给谁、链接
  卡片（Ray 写）：……                              ← 卡片正文，用送的人的颜色
（送的人的 Gifts 开头另有"准备中（还没揭晓，只在你的 Drive 里）"一节，D3）

纪念日                                           ← Anniversaries，按月日排
  在一起的日子  2024 年 5 月 20 日                 ← 标题 2：名称、日期
  TA 的生日  3 月 14 日                           ← 生日没写年份时只有月日
  备注：……（谁记的）
```

心愿单里已"收到了"的心愿不在心愿单，只在礼物墙，与应用一致。场合是纪念日时显示纪念日现在的名称，纪念日已删除时显示礼物上记下的名称副本（wishes-and-gifts D5）。

原因：依据 1。共享页面是成段的文字，像日记一样一页一份最好读；心愿、礼物与纪念日是短条目，每条一份会让 Drive 里散落几百个小文件，三份汇总就像应用里的三个页面。日记已经占用了 `Between Pages` 下按年命名的文件夹，`Together` 与导航"一起"对应，不会和年份冲突。

### D5：页面每形成一个历史版本写一次；汇总在最后一次改动 2 分钟后写

- **共享页面**：页面与日记在同一个协同内核上，有现成的历史版本（内核 D6：停笔 2 分钟，或连续写作每 5 分钟一段）。页面 Doc 写到它最新的历史版本，规则与日记 Doc 完全相同（server-backup-and-google-docs D7）；改标题、删除没有新提交，立即可写。
- **汇总 Doc**：心愿、礼物、纪念日没有版本，是一次次保存。某个功能有改动时，为两人登记这份 Doc 待写，可处理时间设为"现在起 2 分钟"；之后的改动把它往后推，但最迟不晚于这一批第一次改动后 10 分钟，所以连续整理心愿单也不会一直不备份。
- **现在备份**：备份页的"现在备份"同时处理所有等待中的日期、页面与汇总，不等历史版本或 2 分钟。
- **首次连接与上线**：首次连接时把本人能看到的所有页面与三份汇总各写一份（与日记一起）；本文上线时，已连接的人由迁移登记同样的待写，自动补写现有全部内容。重新连接（含断开后再连同一个账号）时，除了能看到的页面，还为这个人这个账号所有仍是"当前"的页面 Doc 登记待写：断开期间被删除的页面读不到、不在列表里，靠这一步才会写入删除前的最后一次提交并改名（D7）。

原因：依据 1、5、8。页面沿用日记的规则，整个应用仍只有一种"版本"；汇总的 2 分钟与停笔时间相同，一次整理多条只写一次。

### D6：汇总 Doc 每次按当前状态整份渲染，整体替换

汇总 Doc 不按条目增量更新：每次都按这个功能当前的状态整份渲染，与日记 Doc 用同一种写法，在一次带 `requiredRevisionId` 的 `batchUpdate` 里整体替换正文、设置标题样式与字色。渲染出的内容校验值与上次写入的相同（例如改了又改回）就不写。改过或删掉的条目，在 Google Docs 自带的版本历史里能看到之前的每一版。

两人规模下一份心愿单或礼物墙有几百条，也远小于 Google Docs 的单份上限。

代价：在 Google 里改了汇总 Doc 的任何一个字，整份按 server-backup-and-google-docs D8 另存（改名为"Wishes（在 Google 改过，已停止更新）"），新建一份继续更新；版本历史里看到的是整段变化，而不是某一条的差异。

原因：依据 4、6（Ray 于 2026-11-17 确认）。按条目增量更新要在 Doc 里定位每一条，用户在 Google 里改动后位置就不可信，还要自己维护差异；整份渲染与日记 Doc 共用写入、校验与另存，没有新的失败情况。

### D7：删除、改名与解绑

| 情况 | Drive 里的结果 |
| --- | --- |
| 页面改了标题 | Doc 跟着改名，正文开头的标题也更新 |
| 页面在应用里被删除（谁删的都一样） | 先把删除前的最后一次提交写进 Doc（不等历史版本；还没有 Doc 就先建一份），再改名为"<标题>（已在应用中删除）"，不再更新；之后它在 Drive 里被删也不重建 |
| 心愿、礼物、卡片、纪念日被删除 | 从汇总 Doc 里消失；版本历史里还能找到 |
| 心愿"收到了" | 从心愿单移到礼物墙 |
| 解绑 | 所有 `Together` 下的 Doc 保留，标题下面注明"（已解绑，内容不再更新）"；空间记录本来就只读，此后不再变化 |
| 原来的两人重新绑定 | 去掉这行说明，继续更新 |
| 断开 Google 连接 | 与日记相同：不删除任何文件；重新连接后续传 |

原因：依据 2、6（Ray 于 2026-11-17 确认）。页面是成段的文字，删掉的页面保留一份，与应用"不删除 Drive 文件"一致，也让对方删掉的页面里你写的字仍留在你的 Drive；汇总 Doc 反映应用里现在的样子，删掉的条目留在版本历史里已经足够。

### D8：备份页按类显示进度，共享页面显示备份状态

- **备份页**：进度从"全部日记已备份到 9:22 的版本"改为按类列出：日记、共享页面、心愿单、礼物墙、纪念日，每类显示"已备份到 9:22"或"还有 N 项等待"。问题记录写出是哪一页或哪份汇总（"共享页面「旅行清单」的 Doc 被改过，已另存一份新的"），页面名称在显示时按页面 ID 取当前标题；页面已删除、读不到时，用这份 Doc 上次写入时记下的标题。
- **共享页面**：在页面上与日记一样显示"已备份到 Google 9:22"与"在 Google Docs 打开"，失败时说明原因；未连接时显示"未开启 Google 备份"。
- **心愿、礼物墙、纪念日页**：不加状态，只在备份页看。
- **首页横条与邮件**：规则不变（需要重新连接、空间已满、连续失败满一天），这些 Doc 的失败与日记的一样计入：首页横条与邮件提醒（email-reminders D7）共用的 `BackupAttention` 同时读日记待写与 `google_item_work`，任一项空间已满或连续失败满一天都算。
- **说明**：备份页的 Google 副本部分写明"共享页面、心愿、礼物墙与纪念日会进你们两人各自的 Drive（各自连接后）；在应用里删除，不会从对方 Drive 的版本历史里消失"。心愿、纪念日、共享页面、已揭晓的礼物和已揭晓礼物的卡片，删除确认框各加一行"已经备份到对方 Google Drive 的内容不会因此删除"；准备中的礼物和卡片只在自己的 Drive 里，删除时不加。不加"不进对方 Drive"的开关。
- 备份状态只对本人可见：对方的任何接口都不反映你是否连接、何时备份、有几项等待（server-backup-and-google-docs D9）。

原因：依据 1、2（Ray 于 2026-11-17 确认）。共享页面像日记一样会长时间写，值得在页面上看到是否已备份；三份汇总是条目，按类的总览就够了。日记只在主人选了共享日期后才进对方 Drive，而这些内容一写下就会进两人的 Drive，删除也收不回（Google Docs 的版本历史归对方所有，应用不删 Drive 文件），所以要在用户删除和查看备份时说清楚。

### D9：一个 Google 账号同一时间只能被一个用户连接

另一位用户已经连接了某个 Google 账号时，再用它连接会被拒绝。回调页显示"这个 Google 账号已被另一位用户连接，请换一个账号"，不说出是谁连接的。断开连接、撤销完成后，这个账号才可以再被连接。

为什么：两人连接同一个 Google 账号时（用对方的电脑登录、测试时共用一个账号），两份副本落进同一个 Drive。送礼人的"准备中"一节会被收礼人看到（违反 D3）；日记副本也有同样的问题，一方没共享的日记会落进对方能打开的 Drive（server-backup-and-google-docs 不变量 5）。这条规则把两者一起堵住。

提示不说"TA"：能看到这句提示的人本来就登录着那个 Google 账号，所以只告诉他"有另一位用户"，不透露对方是否连接（D8，server-backup-and-google-docs 不变量 14）。

实现：`google_connections` 的 Google 账号 ID 加唯一约束，"撤销中"的连接也占用这个账号，直到撤销完成、行被删除；`POST /api/backup/google/finish` 遇到冲突时返回新错误码 `GOOGLE_ACCOUNT_IN_USE`，只丢弃刚拿到的令牌，不保存、不撤销：同一个 Google 账号对同一个 OAuth 客户端的授权是一份，撤销会连带断掉已连接那位用户的授权。迁移前若已有重复连接，按连接时间保留最早的一条，其余整行删除（相当于未连接，同样不向 Google 撤销；令牌列不能为空，所以不留"需要重新连接"的空壳），并各记一条备份记录。应用不删 Drive 文件，所以被删掉连接的那个人以前写进那个共用 Drive 的 Doc（可能含他没共享的日记）仍在那里；这条备份记录写明"之前写进 <Google 邮箱> 的副本仍在那个 Drive 里，需要的话请自己删除"，他换自己的账号重新连接即可。

原因：依据 2、3。

## 技术设计

**登记待写：一个与功能无关的空间副本 outbox。** 新表 `space_copy_outbox` 记"某个空间的某条记录变了"，由下面四处在各自的事务里写入：

| 谁写 | 什么时候 | 记什么 |
| --- | --- | --- |
| `space-records` 共用服务 | 每次新建、修改、删除或动作 | 空间、记录类型、记录 ID、`private_to`（照抄这次写入的） |
| `commit`（页面分支） | 每次页面提交，与 `notePageWritten` 同一事务 | 空间、`shared_page`、页面 ID |
| `bindings` | 解绑与重新绑定的事务 | 空间，记录类型为空（表示这个空间的全部 `Together` Doc） |
| 链接预览的写回（`store` 的写回函数） | worker 把读到的预览写回心愿或礼物时，同一事务 | 空间、记录类型、记录 ID、记录的 `private_to` |

`space-records` 只照抄 `private_to`，不认识任何功能，所以它仍"不知道功能"。链接预览那一行写在 `store` 的写回函数里，`link-preview` 模块仍不 import 任何东西，依赖方向不变。表没有外键：写入时持有绑定期间共享锁或文档锁，外键检查会去锁 `spaces`/`users` 行，与关系流程的锁顺序冲突（与 `backup_outbox` 相同的理由）。

worker 的转换步骤（与 `backup_outbox` 的转换并列）把每行转成 `google_item_work`：`private_to` 为空时给每个已连接的成员，不为空时只给 `private_to` 那个人（D3）；`wish` → `wishes` 和 `gifts`（送的人"准备中"一节显示关联的心愿）；`gift` → `gifts` 和 `wishes`（送的人揭晓关联心愿的礼物时，心愿记为已收到却不写心愿的历史）；`gift_card` → `gifts`；`anniversary` → `anniversaries` 和 `gifts`（礼物墙显示纪念日的现名）；`shared_page` → `page:<页面 ID>`；记录类型为空 → 这个空间的全部项。转完标为已处理。

不用 worker 按 `space_changes`/`space_actions` 的序号扫描：序号在事务开始时分配，提交顺序可能与序号不同，按游标扫描会漏掉晚提交的小序号；outbox 的"待处理"状态没有这个问题。

**表**（一次迁移，本文预先批准）：

| 表 | 内容 |
| --- | --- |
| `space_copy_outbox`（新） | ID、空间、记录类型（可空）、记录 ID（可空）、`private_to`（可空，照抄写入时的；不为空时只为这个人登记，D3）、状态（待处理 / 已处理）、登记时间、处理时间 |
| `google_item_work`（新） | 用户、项（`page:<ID>`、`wishes`、`gifts`、`anniversaries`）、最早可处理时间、本批第一次登记时间（D5 的 10 分钟上限）、"现在备份"标记、尝试次数、最近错误；主键为用户与项，没有外键 |
| `google_item_docs`（新） | Doc ID、用户、Google 账号 ID、项、状态（当前 / 已另存 / 已在应用中删除）、上次写入的标题（页面 Doc 用，页面删除后问题记录与改名都靠它）、上次写入的修订号、内容校验值、覆盖到的时间、写入时间；每人每账号每项至多一份"当前" |
| `google_folders`（不改结构） | 新路径 `Between Pages/Together`、`Between Pages/Together/Shared pages` |
| `backup_events`（改） | 增加可空的"项"列，问题记录指向页面或汇总；新类型"Google 账号已被另一位用户连接"（迁移处理重复连接时用），带一个可空的 Google 邮箱列，因为连接行删掉后只剩这里记着是哪个账号 |
| `google_connections`（改） | Google 账号 ID 唯一（D9） |

迁移同时为每个已连接、有空间的人登记全部 `Together` 项（D5 的上线补写）。

**处理一项**：worker 取到期的项（`FOR UPDATE SKIP LOCKED`，与日记待写同一循环、同一退避与限流规则），按项渲染：

- 页面：经共享页面服务按本人读取页面；页面已删除时，经共享页面服务新增的副本专用入口（只给 worker，只对这个空间的两个人，返回删除前最后一次提交的标题、正文与作者）写入这份正文，再做 D7 的改名并把记录标为"已在应用中删除"；否则取最新历史版本（`history` 判断，与日记相同；"现在备份"取最新提交）的正文与作者，渲染标题、图例与着色正文。还有版本在形成时，在那一段结束时再看一次。
- 汇总：经 `wishes`、`anniversaries` 服务按本人读取当前列表，渲染 D4 的版式；送的人自己的准备中礼物只出现在他的"准备中"一节。
- 空间已解绑时在标题下面加上 D7 的说明行。

之后与日记 Doc 相同：校验值未变就只更新覆盖时间；否则开令牌、按需建 Doc（`files.create` 直接放进文件夹，建好先记库）、带 `requiredRevisionId` 整体替换、记下新修订号。页面标题变了另调一次 Drive 改名；改名后重新读一次修订号记下，不把应用自己的改名当成 Google 里的修改。被改另存、被删重建、每日检查都覆盖 `google_item_docs`；状态为"已在应用中删除"的 Doc 不再写、不重建。

**模块**（`apps/api/src`）：渲染放在 `backup`（新文件 `render-together.ts`，纯函数）；`backup` 新增对 `shared-pages`、`wishes`、`anniversaries` 三个服务只读入口的依赖，在 `checks/verify-dependency-direction.ts` 登记（本文预先批准）；三个功能互不依赖的规则不变。`google` 模块不变。

**接口**（contracts 与 OpenAPI 随实现）：`GET /api/backup` 增加按类的进度（类、等待数、覆盖到的时间）与问题记录的项；`GET /api/shared-pages/:id` 增加本人的 `google`（Doc 链接、覆盖到的时间、失败原因），与 `GET /api/days/:date` 的形状相同；`POST /api/backup/run` 同时处理 `google_item_work`；`BackupAttention`（首页横条与备份邮件共用）把 `google_item_work` 的空间已满与连续失败计入（D8）。

## 失败与恢复

| 情况 | 结果与恢复 |
| --- | --- |
| Google 限流、网络失败、空间已满、授权撤销 | 与日记 Doc 相同（server-backup-and-google-docs 的失败表）：退避重试或等用户处理；备份页按项列出，共享页面上提示 |
| 汇总 Doc 在 Google 里被改 | 整份另存、新建一份继续（D6） |
| 页面 Doc 或汇总 Doc 被删 | 下一次写入或每日检查时重建；已在应用中删除的页面除外 |
| worker 中途崩溃 | outbox 行或待写项没有标完成，重启后重做；同一项重复写入内容相同，不产生副本 |
| 转换时某成员没有连接 | 不登记；之后连接时首次连接会写全部内容 |
| 揭晓与送的人改卡片同时发生 | 揭晓前的卡片修改只为送的人登记；揭晓事务为两人登记；收的人的 Doc 只按揭晓后读到的状态渲染 |
| 页面在写入前被删除 | 经副本专用入口写入删除前的最后一次提交，再改名（D7） |
| 用另一位用户已连接的 Google 账号连接 | 拒绝，丢弃刚拿到的令牌（不撤销，以免断掉已连接那位的授权）；回调页提示换一个账号（D9） |

## 不变量

1. 一个人的 Drive 里，`Together` 下的内容只来自本人此刻在应用里能读到的页面与记录，经与接口相同的按查看者读取入口取得。
2. 私密的记录与动作（准备中的礼物、它的卡片、"我在准备"）只进入 `private_to` 那个人的 Drive，只为他登记待写；收的人的 Drive、待写项、备份进度与问题记录在揭晓前都不因它变化，揭晓后礼物才进入收的人的礼物墙 Doc。
3. 每人每个 Google 账号每项（每个共享页面、Wishes、Gifts、Anniversaries）至多一份当前 Doc；重复处理不产生副本，较旧的内容不覆盖较新的。
4. 页面 Doc 只在其内容所含提交都已进入历史版本后写入；汇总 Doc 在登记后至少 2 分钟、最迟本批第一次登记后 10 分钟写入；"现在备份"与已在应用中删除的页面（写删除前的最后一次提交，D7）例外。"已备份到 Google"只在对应 Doc 写入成功后显示。
5. 应用只在 Doc 仍是自己上次写入的修订时写入；被改的另存、被删的重建，已在应用中删除的页面除外；应用不删除 Drive 里的任何文件。
6. 应用里删除的页面，其 Doc 写到删除前的最后一次提交后改名为"已在应用中删除"并停止更新，已删除的页面仍不出现在任何接口里；删除的条目从对应汇总 Doc 中消失。
7. 页面仍不出现在日记列表、日记未读、共享轮次与日记 Doc 里，也不写入 `backup_outbox`；页面与空间记录的改动不登记任何日记待写。
8. 空间记录与页面的写入不等待 Google；登记 `space_copy_outbox` 与改动在同一事务，Google 不可用时写入照常完成。
9. 备份状态只对本人可见；对方的任何接口都不反映你是否连接、何时备份、有几项等待。
10. 空间解绑后 `Together` 下的 Doc 保留并注明已解绑，不再变化；原来的两人重新绑定后继续更新。
11. Drive 授权仍只请求 `drive.file`；Drive 里只写 Doc 与文件夹。
12. 同一个 Google 账号同一时间至多被一个用户连接；连接被拒时不保存令牌、不撤销已有的授权，提示不透露是谁连接的。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| **只放自己写的字** | 最贴近"自己写的"，Drive 里没有对方的文字 | 依据 1：共享页面两人的字穿插，只留自己的会成碎片；依据 2：日记副本已经包含对方共享的那篇，两种边界会让人困惑 |
| **页面整页、条目只放自己的** | 页面可读，条目只含自己写的 | 礼物墙上的卡片多半是对方写给你的，剔掉就失去意义；依据 2 的同一条边界更好解释 |
| **揭晓前谁的 Drive 都不进** | 泄露面最小：送的人共用设备、共享屏幕时 Drive 里也没有 | 依据 1：卡片草稿是送的人自己写的字；依据 3 只要求不让收的人看到，收的人那边已完全不受影响（Ray，2026-11-17） |
| **每人可选"我写的不进对方 Drive"** | 作者能控制对方 Drive 里有什么 | 共享页面两人的字穿插，要按字遮掉，Doc 会成碎片；依据 2 与日记副本的边界不一致；Ray 选择只加说明（2026-11-17） |
| **每条记录一份 Doc** | 在 Google 里改一条只另存那一条 | 依据 1：几百个小文件，不如三份汇总好读；每条都要建、改名、检查，Google 调用多得多（依据 8） |
| **页面之外全部合成一份 Doc** | 文件最少 | 任何一处被改都让全部另存；心愿、礼物、纪念日在应用里是三个页面，合在一起反而不好找 |
| **汇总按条目增量更新** | 版本历史里能看到单条差异 | D6：用户在 Google 里改动后位置不可信，要自写差异逻辑；依据 4：整份替换与日记共用写入与另存 |
| **礼物墙按年分份** | 往年基本不变，另存影响小 | 两人规模下一份就够；Ray 选择一份（2026-11-17） |
| **每天写一次** | Google 调用最少 | 最多晚一天；页面与日记应当一致按历史版本写（D5） |
| **删除的条目留在汇总的"已删除"一节** | 不用翻版本历史 | 与应用里看到的不一致；版本历史已能找回 |
| **worker 按 `space_changes` 序号扫描** | 不加 outbox，写入路径不改 | 序号分配顺序不等于提交顺序，游标会漏掉晚提交的行；outbox 的待处理状态与 `backup_outbox` 一致、可靠 |
| **导出成 Markdown 或 JSON 文件放进 Drive** | 格式简单，便于再导入 | 依据 1：用户要在 Google 里直接读，且日记已经是 Doc；导入不在范围内 |

## 风险与代价

- **汇总 Doc 易被整份另存**：在 Google 里随手改一个字，整份心愿单就另存一份；被改得多时 `Together` 下会有几份"已停止更新"的旧版。
- **Google 调用增多**：每次汇总改动至少一次写入，页面按历史版本写；两人规模下远低于配额，但每日检查要多列几十个文件。
- **页面同名**：两个同名页面在 Drive 里是两个同名文件，只能按内容区分。
- **对方的文字在你的 Drive 里**：与日记副本相同的取舍；Drive 是你的，对方无法收回已经写进去的内容（删除页面只改名，不清空）。
- **整体替换**：版本历史里看到的是整段变化。
- **批注也算改过**：按 server-backup-and-google-docs D8，在 Google 里给汇总 Doc 加一条批注，也会让整份改名停更、另建一份。想在心愿单上批注的人会被这一点困扰；规则不变，先观察实际使用。
- **想共用一个 Google 账号的人**：D9 之后两人不能再连接同一个 Google 账号，各自要用自己的账号。

## 未解决的问题

- 见面计划及以后的功能：在各自的设计里决定是否进入；默认做法是在 `Together` 下加一份汇总 Doc，沿用本文的 outbox 与写法。
- 链接预览图片：不写；以后若要，再评估下载图片的存储与授权。
- 礼物墙很长时是否按年拆：等实际条目数接近 Docs 上限的十分之一再看。

## 验收标准

- 两个账号都连接 Google：建一个共享页面、两人各写几句，2～5 分钟后两人的 `Between Pages/Together/Shared pages/` 里各有一份同名 Doc，作者颜色与应用一致；改标题后 Doc 跟着改名；删除页面后 Doc 改名为"（已在应用中删除）"、内容不变。
- 许愿、改心愿、记纪念日后约 2 分钟，两人的 Wishes、Anniversaries 更新；删除一条后它从汇总里消失。
- 为对方准备一份礼物并写卡片：约 2 分钟后送的人的 Gifts 出现"准备中"一节、Wishes 里那条心愿标出"我在准备"；收的人的 Drive、备份页的进度与问题记录都没有变化；取消后从送的人的"准备中"消失；揭晓后两人的 Gifts 礼物墙都有这份礼物与卡片。
- 备份页写明这些内容进两人各自的 Drive、删除收不回；心愿、纪念日、共享页面、已揭晓的礼物与卡片的删除确认框有那一行提示，准备中的没有。
- 解绑后两人的 `Together` Doc 标题下面注明已解绑；重绑后继续更新。
- 备份页按类显示进度；共享页面显示"已备份到 Google"与 Doc 链接。
