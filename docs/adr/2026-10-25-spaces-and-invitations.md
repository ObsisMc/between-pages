# 用双人名额约束和一次性邀请建立共享空间

- 状态：提议
- 日期：2026-10-25
- 决策者：Ray
- 范围：领域
- 关联：依赖 ADR-0001；依赖 ADR-0003；依赖 ADR-0006；依赖 authentication-and-sessions

空间创建者立即占一个名额，另一位用户登录、预览邀请并明确接受后占第二个名额。邀请有期限、可撤销、一次性消费；加入与消费在同一个 PostgreSQL 事务提交。两位成员权限平等，空间 ID 和邀请链接都不能代替成员权限。

本文是双人空间与邀请的设计和实现计划，覆盖数据、HTTP 契约、桌面 Web 和验证。日记创建、编辑器、协同连接、Google 备份、成员退出/移除、空间删除与账号删除不在本次实现范围。文中新增的产品选择是待评审的实施默认，不表示已经实现或已经获得采纳。

## 背景与问题

登录已经提供稳定的领域 userId 和会话，但登录成功不能证明用户能访问某个空间。[规格 §3](../diary-spec.md#3-用户与权限-auth)要求空间最多两人、明确接受邀请、邀请可过期和撤销，并且并发接受不能挤入第三人。

本次要打通“登录 → 创建空间 → 手动分享邀请 → 对方确认加入 → 双方看到同一空间”。建立成员权限入口，供后续日记接口使用；尚无日记时只展示空间与成员，不把空壳页面描述为可写日记。

## 决策依据

1. 每个空间最多两位成员，双方都有独立稳定身份；成员关系来自服务端，不能由客户端指定。
2. 加入必须有明确同意；打开链接、预览、登录和第三方链接扫描均不能产生成员关系。
3. 邀请过期、撤销、消费和最后名额的竞态必须有唯一结果，失败不能留下半完成状态。
4. 成员身份决定空间访问权；邀请不得泄露正文、登录资料或读取状态。
5. 首版只做创建和加入，不引入成员替换、角色体系、邮件发送服务或新的基础设施。
6. 沿用现有契约、认证、PG 和测试边界；迁移及实现步骤应可在采纳后连续执行。

## 决策

### D1：空间最多两人，账号可参与多个空间

“双人”约束施加在空间上，不施加在账号上。当前规格没有限制一个账号只能参与一个空间，因此提供空间列表及显式选择，不新增全局唯一绑定限制。不同空间的正文、邀请和未来读取进度相互隔离。

创建空间时服务端取会话 userId，原子创建空间和槽位 1 的成员关系。加入者占槽位 2。两位成员均能查看空间、成员和邀请状态；任一成员可管理邀请，但空间满员后不能再生成邀请。createdBy 仅记录来源，不是管理员角色。不接受 userId、成员列表、槽位或颜色等客户端授权字段。

首版无空间命名、改名或资料设置入口。列表以“我与 {对方显示名}”或“等待另一位加入”展示，并以 spaceId 路由区分同名空间。允许单人等待期间访问空间，日记能力由后续 ADR 决定，不以满员为本文新增的写作门槛。

原因：依据 1、5，成员平等且不需要可转移的所有权；多空间避免把尚未确认的账号限制固化进数据库。

### D2：成员占据数据库约束的两个稳定槽位

领域表放在 `apps/api/src/db/schema.ts`，通过现有迁移生成命令创建。所有时间为 timestamptz，所有领域用户外键指向 `users`，不指向认证表。

| 表 | 字段与约束 |
| --- | --- |
| `spaces` | `id` UUID 主键；`created_by` → users；`creation_request_id` UUID；`created_at`；唯一 `(created_by, creation_request_id)` |
| `space_memberships` | `space_id` → spaces；`user_id` → users；`slot` smallint，仅允许 1、2；`joined_at`；主键 `(space_id, user_id)`；唯一 `(space_id, slot)` |
| `space_invitations` | `id` UUID 主键；`space_id` → spaces；`created_by` → users；`token_hash` 唯一；`created_at`、`expires_at`；可空 `revoked_at`、`accepted_at`、`accepted_by` → users |

邀请检查约束：expires_at 晚于 created_at；accepted_at 与 accepted_by 同时为空或同时非空；已消费和已撤销不能同时成立。部分唯一索引 `(space_id) WHERE revoked_at IS NULL AND accepted_at IS NULL` 保证每空间至多一条未关闭邀请；过期行仍占索引，生成新邀请时先关闭它，不依靠时间触发索引更新。

成员关系只插入、不更新槽位、不删除。用户外键与空间外键均不配置级联删除，未来删除/解绑须另行设计以保留作者映射。两槽位加唯一约束直接保证最多两人，即使业务检查遗漏也不能出现第三人。

成员颜色返回稳定的 `authorSlot: 1 | 2`，前端将槽位映射为两种字体色；同空间同用户跨设备不变。槽位只是作者展示映射，后续文字作者仍然是 userId。具体颜色由编辑器视觉实现选择；不同主题可用不同色值。

创建请求携带客户端生成的 requestId；同用户重复请求返回原空间，不重复创建。该 ID 的当前消费者是重复点击和提交后响应丢失的重试；跨账号不复用创建结果。列表按 created_at、id 稳定排序。

原因：依据 1、3，用简单约束封住人数上限；数据库中不保存冗余 memberCount、isFull 或可漂移的颜色身份。

### D3：邀请是手动分享的随机凭证，七天过期

服务端用 Node 内置 crypto 生成 32 字节随机值，编码为 43 字符 base64url token；数据库仅保存 SHA-256 摘要。期限固定为创建后七天，不增加可配置期限或自定义邀请文案。签名自包含 token 不适合本次必须即时撤销、一次性消费的状态需求。

生成接口只在提交成功后返回原始 token 和 expiresAt；Web 用当前同源地址拼出 `/join#token=<token>`。原始 token 不进入 API 路径、查询串、服务端日志、错误内容或空间查询结果。所有本功能响应设置 `Cache-Control: no-store`；含 token 的请求不记录 body，错误也不回显输入。

分享通过“复制邀请链接”，由用户自己发送；应用不发邮件、消息或 Google 邀请。页面明确写“任何拿到链接并登录的人都能申请加入，请只发给对方”，不伪称邀请绑定了某个邮箱。

每空间只有一个未关闭邀请。首次生成后再点“重新生成”需确认旧链接将失效；服务端锁空间行、撤销旧邀请、插入新邀请后一起提交。原始链接不能从摘要恢复，刷新后只能看到期限与状态并选择重新生成。生成成功但响应丢失时，先重查状态，再由用户明确重新生成，客户端不自动重放生成操作。

撤销按 inviteId 精确定位，重复撤销同一条成功返回 `{ revoked: true }`；不能把“撤销旧邀请”误作用于刚重新生成的邀请。已消费的邀请返回 INVITE_USED。空间满员时拒绝生成，保留历史邀请用于失败判断，不做定时清理任务。

原因：依据 2～5，手动分享满足当前需求；摘要存储和 URL fragment 减少凭证被请求日志带出的机会；轮换、撤销需要可定位的服务端记录。

### D4：预览不加入，接受在同一事务中消费邀请和占用名额

预览和接受都需要登录。预览只返回邀请者的 UserSummary、期限，或明确的失效原因；不返回完整成员列表、空间内容或 Google 状态。预览没有锁定名额的含义，用户点击“接受并加入”时必须重查。

服务端先按 token 摘要查邀请所属空间，再在事务内以固定顺序锁 `spaces` 行、锁目标邀请行；所有生成、撤销、接受操作遵守同一顺序。锁后重新读取并校验，过期判断使用数据库实际当前时间（在获得锁之后取时间，不能沿用事务开始时刻）。

接受处理顺序：

1. 找不到邀请返回 INVITE_INVALID；已撤销、已消费、已过期分别返回对应错误，expires_at 等于当前时间也视为过期。
2. 当前用户已在该空间返回 ALREADY_MEMBER，不消费仍有效的邀请，创建者不能邀请自己来占第二个名额。
3. 两个槽位都被占用返回 SPACE_FULL；否则插入当前用户为槽位 2。
4. 写 accepted_at、accepted_by，与成员插入一起提交；提交后才返回空间。

重复接受已消费邀请，即使是同一个用户，也返回 INVITE_USED，不再执行加入。响应丢失时用户重查空间列表确认是否已加入，再打开空间；不把“一次性”实现成可反复接受。B、C 并发争取同一邀请，最多一人成功。接受与撤销/轮换竞争，以先持有空间锁并成功提交的有效操作为准。

原因：依据 2、3，数据库约束保证人数，空间锁统一串行化名额与邀请状态，避免先加人后消费或先消费后失败。

### D5：成员权限由独立的领域入口执行

在 `apps/api/src/spaces/` 增加唯一的空间成员查询与校验入口。路由先沿用 requireUser 确定身份，再调用成员校验；不读取认证表，不把“已登录”等同于“已入空间”。不存在空间和非成员访问统一返回 404 NOT_FOUND，响应不区分空间是否存在。

空间列表只查询当前用户所属空间；详情和邀请管理均按 `(spaceId, request.user.id)` 校验。接受邀请是显式创建成员关系的唯一例外，依据有效邀请授权，不要求预先是成员。邀请无效时不返回其 spaceId 或邀请者信息。

未来日记路由必须从数据库加载 diary.spaceId 再调用此入口，不能相信客户端另传的 spaceId；WebSocket、导出和备份接入时分别补测试。本文只验证现有空间接口，不声称已验证尚未存在的日记和协同入口。

原因：依据 4、6，认证层只回答“是谁”，成员权限在领域层复用；防止只知道 UUID 的第三人访问。

### D6：所有接口沿用契约表和统一错误格式

以下新增路由全部为 `access: 'user'`，成功为 200。请求对象采用严格 schema，额外 actor、userId 等字段返回 400 VALIDATION_FAILED。UUID、token 格式和请求形状都由 `packages/contracts` 定义；所有写接口及 POST 预览沿用可信 Origin 检查。

| route name / 方法与路径 | 输入 | 成功响应 |
| --- | --- | --- |
| `listSpaces` GET `/api/spaces` | 无 | `{ spaces: SpaceSummary[] }` |
| `createSpace` POST `/api/spaces` | body `{ requestId: UUID }` | `{ space: SpaceSummary }`，幂等返回同一空间 |
| `getSpace` GET `/api/spaces/:spaceId` | params `{ spaceId: UUID }` | `{ space: SpaceSummary, invitation: InvitationSummary \| null }` |
| `createInvitation` POST `/api/spaces/:spaceId/invitations` | params `{ spaceId }`；body `{}` | `{ invitation: InvitationSummary, token: string }` |
| `revokeInvitation` POST `/api/spaces/:spaceId/invitations/:inviteId/revoke` | params `{ spaceId, inviteId }`；body `{}` | `{ revoked: true }` |
| `previewInvitation` POST `/api/invitations/preview` | body `{ token }` | `{ inviter: UserSummary, expiresAt: UTC ISO string }` |
| `acceptInvitation` POST `/api/invitations/accept` | body `{ token }` | `{ space: SpaceSummary }` |

SpaceSummary 为 `{ id: UUID, createdAt: UTC ISO string, members: { user: UserSummary, authorSlot: 1 | 2 }[] }`，成员按槽位排列；列表只返回当前用户的空间。InvitationSummary 为 `{ id: UUID, expiresAt: UTC ISO string, status: 'pending' | 'expired' }`；详情仅返回最新未撤销、未消费的邀请，已过期的标 expired，无则 null；不返回摘要或原始 token。满员状态由成员数推导，不再存一份。

新增错误码：INVITE_INVALID（404）、INVITE_EXPIRED / INVITE_REVOKED / INVITE_USED / SPACE_FULL / ALREADY_MEMBER（409）。前端按 code 给中文提示，不展示内部错误 message。邀请错误在登录且提交凭证后可区分；空间详情及管理的非成员错误仍统一 NOT_FOUND。错误校验优先级依次为现有 Origin 检查、登录、请求 schema、资源权限、D4 中的业务检查；非法 JSON 等解析错误沿用现有处理。

扩展 RouteDefinition 以支持实际需要的 params、body 和错误响应声明；Fastify 注册处消费 schema，并让 OpenAPI 反映所有状态。扩展 callApi 支持类型推导的 params、JSON body 和参数编码，不再由页面拼接路径；保留现有 `callApi(name)` 消费方式，测试中的 fetch 注入位置可随之调整，不引入第二套客户端。所有 wire shapes 只在契约包定义。

原因：依据 6，第一次参数化路由和写请求应扩展现有 owner，避免接口与类型分别演进。

### D7：桌面 Web 完成创建、分享、确认和进入空间

- `/`：登录后显示空间列表与“创建双人空间”；创建按钮在请求期间禁用，同一次未确认操作重试保留同一 requestId。创建成功进入 `/spaces/:spaceId`。
- `/spaces/:spaceId`：显示一或两位成员。单人时显示生成、复制、撤销/重新生成邀请；刷新读取状态，不能恢复复制旧 token。双人时显示“你们已在同一空间”，保留日记功能尚未开放的说明。详情 404 显示无权访问或不存在，并提供返回列表。
- `/join#token=…`：读取 fragment 后立即用 replaceState 移除 URL 中的凭证；在当前标签页 sessionStorage 的单一 pending-invitation 项暂存，支持登录往返和刷新。入口显示当前登录身份、邀请者、期限及“接受并加入”，不会自动接受。已有暂存邀请但打开不同链接时，以新链接替换。
- 未登录的邀请入口：先暂存 token，再进入登录；登录成功回到 `/` 时，只在存在合法格式的 pending token 时固定跳 `/join`。不新增任意 returnTo/open redirect，不改变无待处理邀请时的登录行为；Google 登录和开发登录都走相同续接逻辑。
- 接受成功清除暂存并 replace 导航到空间；终态邀请错误清除暂存并提示重新索取链接；ALREADY_MEMBER 时清除暂存、刷新列表让用户选择空间。暂时性网络错误保留 token，可重新预览；接受超时先刷新列表确认，不自动重复提交。退出登录清除 pending token 和 Query 缓存，沿用既有退出处理。

sessionStorage 仅保存这条待处理邀请，不保存会话或日记；不把 token 放入 Query key、分析事件或 console。邀请预览用 mutation 或组件内瞬时状态，避免 token 被查询缓存持久化。若 sessionStorage 不可用，仍允许已登录用户在当前页面内存中预览/接受；未登录时提示登录后重新打开原邀请，不假称能保留链接。

普通空间数据归 TanStack Query；成员变化在本端成功后失效列表和详情查询，窗口重新聚焦时重新拉取。首版不新增轮询、WebSocket 或自动刷新计时器；等待方可用“刷新状态”按钮查看对方是否加入。未来编辑器接入时再使用协同通知。

原因：依据 2、5、6，明确接受与当前账号可见，登录不会意外加入；单标签页暂存解决现有登录固定回首页的续接问题，代价是 token 暂时存在浏览器存储中。

## 失败与恢复

| 失败 | 结果与恢复 |
| --- | --- |
| 创建事务失败或提交前进程退出 | 空间和首位成员一起回滚；同 requestId 重试 |
| 创建提交后响应丢失 | 同 requestId 重试返回原空间，或刷新列表找回 |
| 生成邀请后响应丢失或刷新 | 查询仅能看到期限；用户确认后重新生成，旧链接失效 |
| 接受插入成员后数据库失败 | 成员和消费一起回滚；原邀请仍按其期限可用 |
| 接受已提交但响应丢失 | 列表可发现空间；再次提交只能得 INVITE_USED，不重复占位 |
| 预览后邀请过期、撤销、轮换或被别人使用 | 接受重查并返回明确错误；不沿用预览结果授权 |
| 操作时会话失效 | 401；不创建或加入空间，重新登录后重查；本次没有日记草稿 |
| 复制链接失败 | 显示可手动复制的当前链接，不宣称已复制；离开页面后只能重新生成 |
| 已加入错误空间 | MVP 无自助退出或换人；确认页提前说明加入后暂不能自助解绑，后续流程单独设计 |

## 不变量

1. 每个空间始终最多两位不同用户，且同一用户在同一空间只有一个稳定槽位。
2. 创建空间和创建者成员关系同成败，同用户同 requestId 的创建只产生一个空间。
3. 身份、成员槽位和权限由服务端决定，客户端不能指定或伪造成员身份。
4. 只有明确接受有效邀请才能新增第二位成员；预览、登录和打开链接不创建成员。
5. 加入成员与消费邀请同事务提交，邀请至多成功消费一次。
6. 过期、撤销或已消费的邀请不能新增成员，轮换提交后旧邀请不能新增成员。
7. 同一空间至多有一个未关闭邀请，撤销只影响指定邀请。
8. 非成员不能查看空间详情、成员列表或管理邀请，空间列表不包含他人的空间。
9. 邀请原始 token 不进入数据库、服务端请求 URL、日志、查询缓存或普通空间响应。
10. 成员可见信息仅包含稳定 ID、显示名和作者槽位，不包含登录资料、活跃时间或读取状态。
11. 所有新增接口要求有效会话，非安全方法要求可信 Origin，成功仅在 PG 提交后返回。
12. 接受与撤销、轮换及其他接受并发时仍满足人数和一次性消费约束。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 每账号只能属于一个空间 | 首页与选择更简单，天然只有一个搭档 | 依据 1 仅限制每空间人数；这会新增未确认的全局限制，误建空间也无法靠现有流程恢复 |
| 用邮件地址指定受邀人并自动发送 | 链接泄露后仍可限制目标身份，邀请更有指向性 | 依据 5，需要邮件设施和身份匹配规则；已有认证决定不把邮箱当稳定身份 |
| 打开链接或登录回调后自动加入 | 少一次点击 | 违反依据 2，错误账号和链接预览可能产生绑定 |
| 只在应用里 count 后插入 | schema 更少 | 依据 3，多请求可能同时读到空名额；缺乏数据库人数兜底 |
| JWT 邀请不存服务器状态 | 签名校验方便，不用查邀请表 | 依据 3，撤销与一次性消费仍需服务器状态，没有减少本次主要责任 |
| 创建者独占邀请和管理权 | 可以控制成员准入 | 依据 5，双人空间无需管理员、转移和角色生命周期；邀请前本来只有创建者一位成员 |

## 风险与代价

- 邀请属于持有者凭证，链接被转发时无法知道谁是原定对象；预览确认、短期有效、撤销和重新生成降低风险，但不保证链接绝不泄露。需要指定收件人时重议方案。
- token 在登录往返时暂存在 sessionStorage，同源脚本可读取；必须禁止记录 URL fragment/请求 body，保持纯文本渲染，不新增第三方分析脚本。存摘要不能阻止浏览器端泄露。
- 多空间意味着列表和权限隔离需要测试；没有自助解绑时，用户必须在确认页清楚知道加入哪个邀请。
- 固定槽位适用于不替换成员的首版。后续成员退出/替换必须保留历史作者身份，不能把槽位直接重新解释成另一个作者。
- 首版不新增应用级创建速率限制或空间数量配额，公开部署前需根据部署与滥用威胁评估补充；随机凭证不替代资源用量控制。

## 未解决的问题

- 日记日期、时区设置、正文颜色、Drive 备份目标随对应功能实现；默认空间不保存这些尚无消费者的配置。
- 自助退出、移除、删除和成员替换需要新的设计；本次不提供接口，也不通过手工删成员绕过作者保留规则。

## 落地顺序

### 自主实现约定

本 ADR 保持提议，先完成设计评审。采纳后按以下顺序实施，迁移授权从采纳时生效；编写本文不执行迁移或安装依赖。

- **预先批准的迁移**：D2 的三张表、外键、检查约束、唯一及部分唯一索引；既有 users 和 auth_* 表不改。
- **依赖**：复用现有包与 Node 内置 crypto，不新增运行或开发依赖。
- **预先批准的改动**：D6 的契约、callApi 和路由注册扩展及 OpenAPI 重新生成；D7 的路由和登录续接；相关模块 README；采纳时在 architecture.md 的 Current decisions 增加本决定。CI、hooks、checks/ 和 prototypes/ 不在批准范围。
- **AI 自行决定**：上述责任内的文件拆分、SQL/Drizzle 实现细节、布局与文案；测试使用现有 mock OIDC、真实 PG 和 Playwright。
- **停止条件**：无法满足任一不变量、需要新依赖或超出 D2 的 schema 变化，或需要实现本文明确后置的成员生命周期。常规实现和测试修复不需额外确认。
- **交付**：设计单独评审；采纳后的实现另开一个面向 main 的 PR，按下列阶段组织 Conventional Commits，Evidence 列出验证与未跑项，附 D 小节/不变量/测试的对应关系。由 Ray 评审、以 merge commit 合并，AI 不自行合并。

### 阶段 1：契约、成员存储和空间 API

范围：D1、D2、D5、D6 的空间接口、迁移与真实 PG 测试。更新 contracts/API README，生成 OpenAPI。完成条件：空库和已有登录库均可迁移；创建幂等、成员权限和数据库两槽位约束通过真实入口验证。从此登录用户能创建和查询自己的空间。

### 阶段 2：邀请事务和权限验证

范围：D3、D4、D6 的邀请接口，日志与失败测试。完成条件：AUTH-02/03 的服务端场景、过期边界、竞态和事务回滚验证通过，测试通过独立数据库连接并发请求，使用可控同步点或持锁事务构造竞争，不靠 sleep 或重试掩盖。邀请接口只在提交后返回成功。

### 阶段 3：Web 闭环和验收

范围：D7、Web README、组件与浏览器测试。完成条件：双浏览器上下文从真实页面完成创建、复制、登录续接、明确接受、刷新查看同一空间；错误和响应丢失的恢复不产生重复空间或成员。执行 format、lint、typecheck、test:db、test:e2e:db、check docs；本次不改变协同，原型 PG/浏览器套件不作为本 ADR 的实现证据。

全部实现验证后按 ADR 生命周期更新为已实现，精简计划并同步最终路径与契约事实；不把现有产品验收清单整组勾选，AUTH-01/05 的日记和 WebSocket 部分仍留给后续。

## 验收标准

测试标题使用 `[adr:spaces-and-invitations#N]` 标记对应不变量，测试同时引用 AUTH 编号。现有索引只统计正式测试，不以本文作为实施证据。

| 不变量 | 验证方式 |
| --- | --- |
| 1、2 | 真实 PG schema + app.inject：直接插第三槽位/重复成员被拒；并发同 requestId 创建仅一空间；创建失败没有孤立记录 |
| 3、8、10、11 | 契约和真实路由：额外 actor/userId 被拒，A/B/C 隔离、陌生 UUID、缺少/撤销会话、错误 Origin；全体新增响应无登录/活跃/读取资料；提交受阻时不返回成功 |
| 4 | API + 组件 + 浏览器：预览/登录前后都无新成员；必须点击确认；创建者接受不占第二位 |
| 5、6、7 | 真实 PG + app.inject：过期前后及等于过期时刻、消费/撤销/轮换、重复接受、重复精确撤销、过期邀请替换、成员插入后强制失败回滚 |
| 9 | 真实生成/预览/接受路径：数据库只含摘要；普通响应不含 token；捕获日志与请求 URL 不含原始值；浏览器清理 fragment、Query 缓存与终态暂存 |
| 12 | 独立连接并发测试：至少 20 个不同用户争最后名额仅一人成功；接受与撤销、轮换的两种先后顺序；重查成员/邀请表确认一致 |

浏览器在现有 Playwright + 隔离 PostgreSQL 上覆盖：

| 编号 | 场景与期望 |
| --- | --- |
| E1 / AUTH-02 | A 创建并复制邀请；B 未登录打开后完成开发登录，看到 A 与当前身份，点击前不入空间，点击后双方刷新看到 A/B |
