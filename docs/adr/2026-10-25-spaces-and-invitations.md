# 个人日记独立存在，双人空间按日期和授权版本共享

- 状态：已实现
- 日期：2026-10-25
- 决策者：Ray
- 范围：领域
- 关联：取代 ADR-0001 的日记归属与日期唯一性；依赖 ADR-0003；依赖 ADR-0006；依赖 authentication-and-sessions

每人每天一篇个人日记，未绑定也能写。首版每个账号首次绑定后只对应这一位固定搭档，每个账号至多属于一个永久双人空间。双方分别选择共享日期：可以全部开放、多段区间、单日选择、持续共享并排除个别日期。停止共享或解绑时，对方保留当时的只读版本；再次开放须本人确认，随后显示最新版本并恢复更新，可以包含分开期间的变化。解绑后只允许与原搭档恢复原空间，不自动重新开放日记；更换搭档与误绑纠正暂缓，见[未来功能清单](../future-features.md)。

个人视图显示本人最新正文及固定搭档保留的文字；对方的共享视图只能含日记主人与固定搭档的文字；历史归档使用冻结版本，不提供历史搭档切换。空间还拥有未来的共同计划、赠礼等关系数据，解绑保留，重绑恢复。

以上产品规则已由用户讨论确认；数据、接口和落地方案已采纳，尚未实现。本文只定义关系与共享生命周期及本次关系/配置交付；协同状态的物理编码须在日记内核设计中落实，计划、赠礼、账号删除和 Google 集成分别随后实现。

## 交付边界

**本 ADR 已实现的交付是“关系管理＋共享范围配置”，不包含实际日记共享。** D1、D4、D6 以及其他小节涉及正文的承诺是后续日记集成必须遵守的产品约束，不是本次实现说明；本文没有给出可直接编码的 Yjs schema、版本、编辑映射或同步协议。

| 本次交付 | 可观察的完成状态 |
| --- | --- |
| 邀请 | 生成、七天过期、撤销、轮换、一次性接受；开发登录支持多个独立账号测试 |
| 绑定与恢复 | 双方确认、首次绑定后固定唯一搭档、并发与事务保护；同人重绑复用 spaceId 并新增期间 |
| 解绑与空间历史 | 单方二次确认解除当前关系；双方可查看参与者和绑定历史，旧空间记录保留且不向第三人开放 |
| 共享范围配置 | 单日、多段、持续及排除的选择、规范化、各自确认、持久化、revision 冲突与请求幂等；不公开对方设置 |
| 桌面流程 | 登录续接、邀请/接受、解绑/重绑、唯一空间的当前或归档入口、自己的范围日历 |

不在本次交付：个人日记创建/正文、双人日记拼接、穿插编辑、作者保护实现、授权正文视图、只看本人、Yjs/光标/离线队列、真实 live/frozen 版本及其冻结/重开、搜索/导出/备份、共同计划/赠礼功能。它们保留在产品规格及后续验收中，不以假正文或空快照补齐。

本次“空间归档/恢复”仅指关系状态和已有关系记录的保留/恢复，不代表已有日记快照、可读正文或计划/礼物页面。范围保存只表示配置已提交，不代表任何正文已经开放；界面持续说明“范围已设置，日记共享尚未开放”，不显示“已共享”“已冻结日记”等未有证据的成功状态。

可独立验收链路：A 邀请 B → 双方分别确认范围并绑定 → 查询关系与本人设置 → 解绑并查看关系历史 → A/B 重绑复用原空间、分别重新确认或暂不设置本期范围。这个链路不依赖日记表、编辑器或 Yjs。

[日记协作内核 ADR](./2026-10-26-diary-collaboration-kernel.md)已采纳，明确正文存储、版本与编辑映射、不可变版本、授权代次、消息协议和离线恢复；实际日记共享随其阶段 4 实现。接入时已有范围仅作为本人确认的参考，不能把“配置已保存”直接升级为“正文已发布”，必须明确展示并确认实际开放后才启用。

## 背景与问题

原 [ADR-0001](./0001-diary-domain-and-time.md)规定每空间每天一篇共同文档。新的产品规则是个人日记独立存在，双人空间提供共享视图，双方仍可在对方日记正文中穿插想法，不能修改对方文字，历史内容只读，不支持回滚。

仅用成员关系或一个“是否共享”开关无法表达：分段日期范围、取消开放后仍可读的历史、重新开放最新内容、同人重绑、首次绑定后固定搭档。必须区分日记归属、文字作者、永久参与者、当前绑定，以及某篇日记具体授权给谁的哪个版本。

## 决策依据

1. 每人每天有自己的日记，创建和继续写作不依赖搭档；ownerId 和不可变 authorId 各有含义。
2. 首版首次绑定后搭档固定，解绑不释放更换对象的资格；原双方重绑恢复唯一空间和关系数据，不换参与者、不克隆空间。
3. 双方分别决定自己的共享日期，不要求对等开放；首次可开放全部历史，范围按日记记录的日期判断。
4. 停止共享保留只读历史，重新开放经本人确认后可见最新版本，包括分开期间的变化；绑定本身不自动重开日记。
5. 搭档不能取得未授权正文版本、私人范围设置、未共享日记数量或阅读过滤行为；第三人无权访问。
6. 邀请、绑定、共享变更与解绑的并发及失败不能造成越权、半绑定或假保存；离线待发文字不能静默丢失。
7. 沿用现有认证、契约、PG 和模块责任；先完成设计再分阶段实现，未有消费者的功能不预建空模块。

## 决策

### D1：后续个人日记归个人，每人每天一篇，双方视图保留日记边界

个人 Diary 有稳定 diaryId、ownerId、diaryDate，唯一键为 `(ownerId, diaryDate)`。ownerId 来自会话，不接受客户端指定主人。有效 IANA 时区和服务端 UTC 时间推导“今天”；diaryDate 创建后固定，createdAt 记录实际创建时刻，两者不混用。补写过去日期不改变其归档日期。

authorId 是每个字符实际作者，不因日记归属、隐藏、绑定或解绑而变化。comment 指在正文任意字符边界插入的想法，不增加独立评论线程或回复树；主人也不能修改对方文字，历史只读，不支持回滚。解绑后固定搭档仍作为历史作者存在，个人入口可保留其 comment 并编辑本人的最新文字。

双人页面按 diaryDate 拼接双方获准共享的两篇，保留 ID、主人和编辑边界。实施默认按永久参与者槽位排序；同日缺少一篇只显示已有的可读内容，不把另一人的私人日记或未授权占位信息补进来。编辑、撤销、未读和光标不能按拼接字符串下标跨两篇处理。

原因：依据 1、3，视图组合不应改变日记身份、作者保护或日期唯一性。

### D2：首版每账号只属于一个永久双人空间，解绑仅结束协作期间

spaceId 永久对应两个不同 userId，按 UUID 顺序规范化并建立用户对唯一约束，参与者不可替换。两人权限平等，无管理员；稳定槽位供作者配色，权限依据 userId。

首次确认绑定才创建空间；同人重绑查回同一 spaceId，新增 BindingPeriod。期间有独立 periodId、startedAt、endedAt 和 endedBy；每空间至多一个开放期间，每账号至多一个当前绑定。每个账号至多属于一个永久空间；关闭期间不清除双方固定搭档身份。

任一方二次确认即可单方面解绑，无需对方批准。解绑结束期间、解除双方当前绑定、撤销剩余邀请、冻结正在更新的日记共享，不删除日记、空间或关系数据。计划/赠礼等归档后只读，重绑后恢复业务操作；它们本期尚不实现。

A/B 首次绑定后，解绑也不能再与 C 绑定；C 不能读取或加入 AB。A/B 重绑前两人都必须无开放期间，不替任何人自动解绑。空间 active/archived 从开放期间推导；空间 active 不代表双方已经重新开放日记。

原因：依据 2、4，固定搭档消除多搭档正文隔离与跨关系回复范围的复杂度；永久归档阅读权不等同于当前协作写入权，periodId 防止旧请求影响恢复后的期间。

### D3：共享日期是包含集合减去排除集合，不按创建时间筛选

每位主人在每个空间拥有独立 DateSelection：

```typescript
type DateRange = { from: ISODate | null; to: ISODate | null };
type DateSelection = { include: DateRange[]; exclude: DateRange[] };
```

端点包含当天；null 分别表示无下界/无上界。单日用相同起止日期，多个区间表示不连续选择；全部历史与未来用 `{ from: null, to: null }`；从某日起持续共享用开放上界；全部不开放用空 include。判断为 diaryDate 属于 include 的并集且不属于 exclude 的并集。

只接受真实的 `YYYY-MM-DD` 公历日期及起止顺序正确的区间；服务端规范化排序、合并重叠/相邻区间，排除优先。日历日计算不把 UTC 午夜换算成查看者日期。同一已确认期间内，以包含减排除后的实际日期集合比较变化，不以 JSON 数组顺序或无效排除项判断；相同结果的重复保存不重新开启共享或制造冻结记录。

按固定 diaryDate 判断补写日记：今天补写范围内的旧日期，若主人当前已确认持续共享该选择，就自动开放；范围外保持私人。开放上界自动涵盖未来日期，无需每天再授权。尚无日记的已选日期不创建空日记，停止共享时也不创建虚假的冻结版本。

共享日历的选择表示“正在持续更新的日期”，不是“对方仅能看到的日期”：以前开放过的未选日期可能仍有冻结历史。

原因：依据 3、4，用户在日历选择的是记录日期，动态选集与可保留的历史访问必须分别表达。

### D4：后续日记的首次开放、停止更新和再次开放使用同一状态机

每个 `(spaceId, diaryId)` 可有多个按序的 ShareEpoch，至多一个 live。它记录 owner、recipient、periodId、授权代次、openedAt、最新已提交的授权视图版本；关闭后固定 closedAt 和 frozenVersion。never-shared 不必建行。

| 动作 | 对方的可读结果 | 后续更新及写权 |
| --- | --- | --- |
| 首次选中已有日记 | 当前主人＋该搭档的最新授权版本 | live；当前搭档可添加/修改自己的文字 |
| 已选日期后来补写日记 | 新建后的授权版本 | live；遵守相同作者保护 |
| 取消日期或解绑 | 关闭 live，保留停止时的版本 | frozen，只读，不再获取后续变化 |
| 再次选中并明确确认 | 新建 epoch，指向当前最新授权版本 | 恢复 live，包括分开期间符合范围的变化 |
| 同一已确认期间重复保存相同选择 | 已有 live 或 frozen 状态不变 | 不重复冻结或新开 epoch |

重新开放更新共享视图指针，不覆写原冻结版本，也不修改个人日记。普通列表展示该日记当前有效的 live 版本，无 live 则展示最后的 frozen 版本，并标注状态；旧冻结记录继续保留，不默认把历次版本全部展开为重复日记。没有补充共享的额外功能，开放范围内最新版本就是本次明确授权。

取消共享不能收回对方已经收到的文字、文件或冻结副本。首次未共享过的内容不因猜到 diaryId 而可读；第三人不能借 epoch 取得授权。

原因：依据 4、6，一个状态机覆盖日历调整和解绑，保留历史与恢复最新互不矛盾。

### D5：双方分别确认范围，重绑与重新开放是两件事

首次邀请表单默认“全部历史＋以后持续共享”，显示实际含义，用户可以改为任意日期集合或暂不开放。发起者先确认自己的选择再生成邀请，接收者先确认自己的选择再接受；双方范围互相不可见、不要求相同。邀请中保存发起者本次明确确认的选择，绑定消费时使用，不能擅自套用用户后来编辑的其他草稿。

同人重绑恢复空间和关系数据；双方各自先前选择可供本人参考，但不得作为自动重开的依据。每人可选“仅恢复关系，暂不开放日记”，对应本次不启用任何 live epoch，旧冻结日记仍可读；之后本人可独立确认开放。若在本次邀请/接受流程已经明确确认最新范围，就可在建立新期间时应用该人的选择，不需重复确认。旧期间的确认不适用于新期间。

绑定期间扩大范围、重新选中冻结日期前，提示“将开放这些日期的最新内容，可能包含未共享或分开期间的修改”。缩小范围前提示“对方保留当前只读版本，之后停止更新”。保存完整 selection 是明确授权动作，UI 先展示变化再确认；不新增可伪造的 confirm=true 来代替权限校验。

设置采用 expectedRevision 和 requestId：旧页面保存返回冲突并要求重载，不覆盖另一设备新选择；同请求重试返回原变更结果，不重复切版本。授权包含 confirmedPeriodId：新期间第一次确认即使日期集合与旧期间完全相同，也是一份新的授权，不能按“相同选择”跳过。本次范围修改只提交策略修订与幂等记录。后续实际共享接入后，冻结和新开 epoch 必须与策略修订保持同事务边界，届时由配套设计实现并验证。

原因：依据 3、4、6，关系同意、范围同意和版本更新的同意有不同作用域。

### D6：后续日记只有主人与固定搭档两位作者，最新视图与冻结归档分别寻址

| 入口 | 正文版本与作者范围 |
| --- | --- |
| A 的个人最新日记 | A 的最新正文＋固定搭档 B 保留的文字；A 只可改自己的文字，解绑后仍可继续写；历史只读，不支持回滚 |
| 只看我的文字 | 只显示查看者 authorId 的文字，包括其写在对方日记里的内容 |
| B 在 AB 读取 A 的 live 日记 | 当前授权版本中的 A＋B，仅当前期间与 epoch 下允许协作 |
| B 在 AB 读取 A 的 frozen 日记 | 冻结时的 A＋B；A 后来修改也不进入该版本 |

首版没有其他搭档文字、历史 partner 选择器或按搭档维护的正文分支。个人入口的最新正文与空间冻结归档有不同身份；在个人入口编辑不改写已冻结副本，不恢复搭档写权。

“只看我的文字”为个人只读阅读模式，不删除隐藏内容、不影响对方显示、权限或备份，不向对方发送过滤通知。恢复完整作者视图并具备对应写权才可编辑；归档始终只读。个人入口可在显示固定搭档 comment 时编辑本人的文字，不要求先隐藏 comment。

服务端只输出当前获准日期与版本的内容、作者和锚点；不向搭档发送停止共享后的个人最新状态或未授权日期正文，再依靠 CSS/前端隐藏。视图 ID 也不能成为获取另一版本的凭证。具体 Yjs 编码与版本同步方式仍由后续内核 ADR 设计，本次固定搭档决定不表示已完成技术验证。

原因：依据 1、5，日记主人不等于全文作者，个人最新正文与对方冻结副本的权限仍须分别执行；固定搭档使多搭档投影不再属于首版问题。

### D7：对方只能知道实际共享内容与冻结状态

对方可见 live 日记和先前收到的 frozen 日记，frozen 标注“已停止共享，内容不再更新”。具体 include/exclude、未共享日记数量、存在与否和主人阅读过滤行为仅本人可见。

对从未共享的日期不显示“有私密日记”、锁定占位、隐藏数量，也不通过列表总数、搜索、错误、未读或 WebSocket 通知泄露。日历空白与无日记同样处理。曾共享后冻结的日期继续可见，这不是公开私人范围设置。

本人可查询自己的范围、草稿和变化预览；邀请预览不携带发起者的 selection。UserSummary 继续仅含 id/displayName，不加邮箱、登录方式、活跃时间或读取回执。

原因：依据 3、5，共享授权不要求双方对等公开生活，也不应制造额外的在线或阅读回执。

### D8：邀请七天有效、可撤销、一次性，不绑定邮箱

用内置 crypto 生成 32 字节随机 token，base64url 编码；PG 只保存 SHA-256 摘要。链接七天有效，不绑定指定邮箱或账号，由用户手动分享。确认页显示当前账号、邀请者和 new/restore 模式；打开链接、登录或预览均不绑定。

每人至多一条未关闭邀请，重新生成立即关闭旧邀请；撤销按 inviteId 精确定位，重复撤销同一条不影响新链接。双方任一人已有当前绑定时不能绑定，不能接受自己的邀请；任一人已有的永久空间对应另一位用户时，即使已解绑也拒绝。绑定成功消费本邀请并关闭双方其他未使用邀请；只能成功使用一次。

生成携带 requestId，邀请行唯一 `(createdBy, requestId)`；重试仅返回元数据与 token=null，不能用旧请求重新生成/轮换。首次原始响应丢失后由用户明确重新生成，使用新 requestId。重复接受返回已使用，接受提交后响应丢失通过查询当前绑定恢复。

token 不进入服务端路径/查询串、数据库明文、日志、Query/mutation 缓存或普通关系响应。所有相关响应 no-store；凭证格式/JSON 校验错误也不回显输入。七天有效期、撤销、并发及过期相等边界在服务端执行。

原因：依据 2、6，手动分享满足本期需求；不引入邮件设施或邮箱身份匹配，持有者接受前必须确认身份。

### D9：本次关系与配置事务保持原子性，后续共享写入继承版本边界

本次绑定事务按 UUID 顺序锁双方 users，之后锁既有 space、period，再重查邀请有效性、双方当前绑定及双方永久空间；已有永久空间须同为本次用户对，否则拒绝；查找/创建唯一用户对空间，新建期间，写入双方 active binding，消费本邀请并撤销双方其他未使用邀请，保存各自本次确认的范围配置，一起提交。不创建 Diary、ShareEpoch 或正文版本。任一步失败整体回滚，提交后才返回成功。

本次解绑携带 expectedPeriodId，只结束该期间、解除该期间两位当前绑定及关闭剩余邀请，保留双方范围配置及变更记录供本人参考。重复结束旧期间返回原关闭结果；即使双方已经重绑，也不能结束新期间或清理新邀请。非参与者不能操作。当前交付没有正文，不能把结束期间当作已冻结正文。

本次范围修改锁操作者 users 行，再锁当前 space/period、本人 policy；在同一事务记录 policy 修订与幂等结果。锁后重查当前期间及 expectedRevision；不读取或修改任何日记版本。

后续集成约束：日记范围修改还须锁受影响的日记行（按稳定 ID 顺序）；凡改变某篇日记共享状态的流程都必须锁到这篇日记的行。正文提交只锁日记行，不锁任何 users 行。关系操作先取得所有需要的 users 锁，其他流程不能持有 space/diary 锁后反向请求 users 锁。具体锁序、多篇开放的两阶段流程与验证见[日记协作内核 ADR](./2026-10-26-diary-collaboration-kernel.md) D5、D9。

取消、解绑与写入竞争时，先成功提交的合法写入进入冻结版本；边界提交后不再接受旧 epoch 的写入。再次开放创建新授权代次，旧队列不能自动套用新权限或被伪装成新请求，未确认原文保留恢复草稿。共享内容和 outbox 只在事务提交后确认及广播。

冻结应持久化不可变、可重建的已提交版本及必要作者/位置引用，并阻止这些版本被后续压缩清理。引用固定版本也可以，但“日记 ID＋停止时间”不足以重建旧状态。读、同步补发、搜索、导出和备份都使用相同版本解析，不得在快照不可用时回退到个人最新全文。

原因：依据 4～6，单纯在 UI 隐藏或只检查握手不能保护共享变更后的版本和权限。

### D10：先落地关系与范围存储，日记共享结构随内核一起实现

首阶段六张表由迁移 `0003_spaces_and_sharing` 建立。领域外键只引用 users，不级联删除日记、空间或作者；时间为 timestamptz，日记日期为 DATE。

| 首阶段关系表 | 核心字段与约束 |
| --- | --- |
| `spaces` | id；user_low/user_high → users；检查 user_low < user_high；用户对唯一；created_at |
| `binding_periods` | id、space_id、started_at、可空 ended_at/ended_by；后两者同空/同非空，ended_at 不早于 started_at；每空间最多一条未结束期间；唯一 `(id, space_id)` |
| `active_bindings` | user_id 主键；period_id/space_id 联合外键 → binding_periods；事务只为永久两位参与者建立行，关闭期间时删除当前行 |
| `binding_invitations` | id、created_by、request_id、token_hash、confirmed_selection（可空）、created_at/expires_at、撤销/消费时刻及 accepted_by；请求唯一、摘要唯一、每发起者至多一条未关闭邀请；消费与撤销互斥 |
| `sharing_policies` | 主键 `(space_id, owner_id)`；selection、revision、confirmed_period_id（可空）；本人须为参与者；本次仅记录本期间的范围配置确认，不是正文 live 授权 |
| `sharing_policy_changes` | id、space_id、owner_id、request_id、前后 revision、selection、确认的 period_id、created_at；唯一 `(owner_id, request_id)`，供保存响应丢失后幂等恢复；本人可读 |

邀请消费时刻与 accepted_by 同空/同非空；expires_at 晚于 created_at，过期行轮换时先关闭，不依赖会随当前时间变化的部分索引；撤销与轮换都记为撤销时刻，撤销时刻不早于到期时刻的邀请仍按“已过期”报告。永久用户对字段保证两位不同参与者，active_bindings 的 user_id 主键兜底每人至多一个当前绑定。每账号至多属于一个永久空间，由绑定事务持有双方 users 锁后同时查询 user_low/user_high 两个参与者位置保证；任何既有空间对应其他人都拒绝，解绑保留 spaces 行。仅有用户对唯一键不足以保证这一规则，须以真实 PG 竞争与解绑后改绑拒绝测试验证。跨表参与者一致性及双方行同成败由统一领域事务与真实 PG 测试保证，不声称 CHECK 可以查询其他表。

后续日记阶段再创建 Diary、不可变授权视图版本、ShareEpoch 及其稳定位置映射；至少约束 owner/date 唯一、space/diary 最多一条 live epoch，frozen 版本不变。详细 Yjs schema、版本和增量协议须在协同设计中明确，不把授权版本与冻结隔离算作原型已经验证。本 ADR 的数据权限、状态机和版本承诺是该设计的约束。

首次暂不设置时，policy 初始为空 include/exclude、revision=0、confirmed_period_id=null；重绑暂不设置时保留原 selection 供本人参考，原 confirmed_period_id 不等于新期间。本次确认后记录当前 periodId，只产生范围配置修订，不产生正文授权；后续内核不能仅凭这个字段直接发布实际日记。

没有日记数据时可以实现关系及保存已确认范围，不预建空正文或快照服务；任何正式共享读写开放之前，必须先完成版本隔离、授权代次和冻结集成。不能先把全文广播上线再补权限。

原因：依据 6、7，一份设计说明责任和依赖，实际代码由第一个真实消费者引入。

### D11：接口统一由 contracts 定义，范围只在本人响应出现

所有下列接口 access=user，非安全方法沿用可信 Origin 检查，成功 200；请求 strict schema 拒绝额外 actor、ownerId、成员列表等字段。扩展现有 RouteDefinition、注册处和 callApi 支持参数/body/错误响应，不另写路径或客户端。OpenAPI 由契约生成。

| 方法与路径 | 请求 | 成功结果 |
| --- | --- | --- |
| GET `/api/binding` | 无 | `{ binding: BindingSummary \| null, invitation: InvitationSummary \| null }`，仅本人发起的最新未关闭邀请 |
| GET `/api/spaces` | 无 | `{ spaces: SpaceSummary[] }`，仅本人参与的唯一空间（当前或归档） |
| GET `/api/spaces/:spaceId` | spaceId | `{ space: SpaceSummary, periods: PeriodSummary[] }`，不含范围 |
| POST `/api/binding/invitations` | `{ requestId, sharingSelection: DateSelection \| null }` | `{ invitation, token: string \| null }`；null selection 表示仅建立关系不重新开放 |
| POST `/api/binding/invitations/:inviteId/revoke` | inviteId；body `{}` | `{ revoked: true }` |
| POST `/api/binding/invitations/preview` | `{ token }` | `{ inviter: UserSummary, expiresAt, mode: 'new' \| 'restore' }`，不返回发起者范围 |
| POST `/api/binding/invitations/accept` | `{ token, sharingSelection: DateSelection \| null }` | `{ binding: BindingSummary, restored: boolean }` |
| POST `/api/spaces/:spaceId/unbind` | spaceId；`{ expectedPeriodId }` | `{ spaceId, closedPeriodId }` |
| GET `/api/spaces/:spaceId/my-sharing` | spaceId | `{ selection: DateSelection, revision, confirmedPeriodId: UUID \| null }`，只查询本人 |
| PUT `/api/spaces/:spaceId/my-sharing` | spaceId；`{ requestId, expectedPeriodId, expectedRevision, selection }` | `{ revision, changeId }`，同请求返回原结果 |

SpaceSummary 为 `{ id, createdAt, state: 'active' | 'archived', participants: { user: UserSummary, authorSlot: 1 | 2 }[] }`，固定两人、按槽位排序。BindingSummary 为 `{ space: SpaceSummary, periodId }`；PeriodSummary 为 `{ id, startedAt, endedAt: string | null }`，按 startedAt/id 排序。InvitationSummary 为 `{ id, expiresAt, state: 'pending' | 'expired' | 'revoked' | 'used' }`。未展开 ID 为 UUID，时间为 UTC ISO string，revision 为非负整数；本人策略及管理用邀请元数据仅向本人返回，持 token 的接收者预览仅取表中定义的信息。

错误沿用 `{ error: { code, message } }`：新增 INVITE_INVALID（404）；INVITE_EXPIRED、INVITE_REVOKED、INVITE_USED、SELF_INVITE、ALREADY_BOUND、PARTNER_FIXED、BINDING_CONFLICT、PERIOD_CLOSED、POLICY_CONFLICT（409）。不存在和无权读取空间/版本统一 NOT_FOUND，不透露私人日记存在与否。前端按 code 显示文案，不展示内部 message。BINDING_CONFLICT 未实现：所有关系写入先按 UUID 顺序锁住相关用户行，竞争的绑定排队执行，后到者按重查结果得到 ALREADY_BOUND、INVITE_USED 或 INVITE_REVOKED，没有需要单独报告的冲突。

邀请先查有效性（无效、撤销、已用、过期），再查自己和绑定冲突；首次绑定与重绑均检查双方永久空间，已有其他固定搭档返回 PARTNER_FIXED，不返回其身份或空间信息；预览不能占位，接受重查。归档只允许 GET 本人旧设置；新 PUT 变更要求当前期间。重复 requestId 必须校验请求内容一致，不把相同 ID 用于另一空间或另一 selection；不一致按 VALIDATION_FAILED 拒绝。范围幂等查重在执行新变更前进行，但仍校验本人和资源权限；已提交旧请求只返回原 revision/changeId，不伪装成当前设置或重新应用到新期间。

日记、共享版本和协同消息接口随内核设计定义，必须携带可校验的视图上下文及授权代次；不能直接沿用仅 diaryId 的全文读取。本 ADR 不杜撰尚无实现者的编辑载荷。

原因：依据 5～7，单一契约避免协议漂移，分离本人策略与对方可读结果防止旁路泄露。

### D12：桌面交互呈现范围、冻结与确认，退出清理凭证

首页提供个人日记入口；未绑定（含解绑后）时右列只放一张搭档小卡：一行状态（还没有搭档 / 与 TA 的空间（已解绑）/ 已发出邀请，某日前有效）加「邀请搭档」入口，整个邀请流程（选范围、生成、撤销、恢复原空间）在「设置 → 搭档」页（`/partner`，只在没有当前绑定时列入设置菜单；2026-11-08 起，此前整个面板常驻首页）。未绑定不阻断写作；尚未实现正文时如实说明。首次邀请/接受显示未来日记共享范围的默认全部历史与持续选项，可改选或暂不设置；日历支持单日、多段、持续区间和排除，只有本人看到设置（2026-11-08 起范围直接在日历上点选：自选时切换「添加共享 | 添加排除」，点两天成一段、同一天两次为单日、首点后可选「从这天起一直共享 / 到这天为止」，排除模式单击排除一天，日历下按段列出 chip 可删，排除日画成删除线淡色；日历固定 UTC，日期始终是字符串；此前为日期输入框表单）。所有相关页面说明“范围已设置，日记共享尚未开放”，保存按钮文案为“保存范围”，不得暗示已经发布正文。重绑表单展示“恢复原空间”及本人旧设置参考，本次明确选择只确认范围配置；后续实际正文发布仍须明确确认。

本次日历仅展示保存的范围，不展示假日记、live/frozen 日记列表、作者过滤开关或正文导出入口。后续日记集成时才展示持续更新与 frozen 标识；首版无 partner 选择器，个人最新视图及唯一空间归档分别呈现，阅读操作不广播。绑定确认页核对双方账号并说明“首版绑定后不支持更换搭档”；当前不提供误绑纠正或人工重置流程。

邀请使用 `/join#token=…`：读取后 replaceState 清除 fragment，当前标签页 sessionStorage 暂存一条 pending token 供登录往返；有合法 pending token 时登录回首页固定续接 `/join`，不接受任意 returnTo。成功或终态错误清理，网络错误可保留；退出清理暂存和 Query 缓存。不把 token 放进 Query/mutation 的 key 或 variables 缓存。sessionStorage 不可用时已登录可内存完成，未登录提示登录后重新打开原链接。

生成/轮换、接受、解绑和共享设置提交期间禁用重复按钮；提交超时先重查当前绑定或本人变更结果，不无条件重试轮换。生成返回 token=null 时说明无法恢复链接，需明确重新生成。初期关系状态使用 Query、聚焦刷新和手动刷新，不新增轮询或关系 socket；未来共享 socket 必须实时执行服务端授权变化。

原因：依据 3～7，用户必须知道何时开放的是最新内容，以及停止更新不等于收回历史。

## 失败与恢复

本次关系与配置：

| 情况 | 结果与恢复 |
| --- | --- |
| 绑定时两人竞争或中途写库失败 | period、双方当前绑定、邀请消费和本次配置同回滚；至多一对成功 |
| 预览后邀请失效或一方已绑定 | 接受重查失败，不自动替任何人解绑或扩大范围 |
| 邀请生成已提交但原始响应丢失 | 同 requestId 仅取元数据；新请求明确轮换，不恢复明文 token |
| 接受提交后响应丢失 | GET binding 找回；旧 token 不能再次创建期间 |
| 范围保存响应丢失或另一设备修改 | 同 requestId 查回原结果；不同请求旧 revision 得 POLICY_CONFLICT，不覆盖新设置 |
| 解绑失败或响应丢失 | 未提交则整体回滚，已提交则查询原期间；重放旧请求不结束后来建立的新期间 |
| 离线时改变范围配置 | 不声称已保存，联网校验并 PG 提交后才确认；本次不创建正文队列 |

后续正文集成约束，不作为本次故障测试完成条件：

| 情况 | 必须实现的行为 |
| --- | --- |
| 冻结版本登记失败 | 范围缩小/解绑整体失败，不能先报成功或回退到最新全文 |
| 取消或解绑后旧正文队列补发 | 拒绝旧期间/epoch，原文保留恢复草稿，不转投新授权 |
| 再次开放时有私人变化 | 本人确认后开放最新主人＋固定搭档版本；确认前只读旧冻结版本，不自动发布私人变化 |

## 不变量

以下编号仅覆盖本次可独立交付的关系与范围配置。正文归属、授权版本、冻结、重开和离线恢复的产品约束保留于 D1/D4/D6 等小节，须由后续内核 ADR 建立对应实现不变量及正式验证，不能计入本次通过数。

1. 首版每账号至多属于一个永久双人空间，首次绑定后搭档固定；解绑后只能与原搭档恢复，每空间的参与者始终是同一对不同用户。
2. 同一用户对仅有一个 spaceId，同人重绑复用空间并新增 periodId，不改写历史期间。
3. 打开链接、登录及预览不绑定；邀请七天有效、可撤销、可轮换且至多成功消费一次。
4. 新期间、双方当前绑定、邀请消费及其他邀请关闭、本次确认的范围配置同事务提交，失败无半绑定。
5. 双方分别确认自己的配置，关系恢复不自动将旧配置标为本期间已确认；不设置范围也能建立关系。
6. 日期选择支持单日、多段、无上界及排除，按日历日期集合规范化和比较，不以配置保存时间解释范围。
7. 任一参与者可确认解绑，空间、历史期间、范围及修订记录保留，不因解绑删除或改换永久参与者。
8. 旧期间请求、旧 revision 和重复 requestId 不能覆盖新关系或新设置；相同 ID 的不同载荷拒绝。
9. 参与者可查询当前及历史关系，第三人无权访问；范围、排除和配置修订只向本人返回，不出现在对方或邀请预览响应。
10. 原始 token 不进入数据库、服务端 URL、日志、Query 缓存或普通响应；接口要求有效会话，非安全方法校验可信 Origin。
11. 绑定、解绑及范围配置只在 PG 提交后确认，失败或响应丢失有可查询的结果和幂等恢复路径。
12. 本次界面明确范围只已配置、日记共享尚未开放，不提供假正文、快照或冻结/重开成功声明。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 每空间每天一篇，日记依附关系 | 共享模型简单 | 违反依据 1，未绑定写作和各自每天一篇无法独立表达 |
| 解绑后允许更换搭档或同时允许多个搭档 | 支持关系变化，误绑后可另选账号 | 违反依据 2 的首版固定搭档边界，增加多搭档文字隔离、视图映射和回复范围的复杂度；更换与误绑纠正另行设计 |
| 只支持连续日期范围或按 createdAt 筛选 | UI/查询较简单 | 不符合依据 3，无法日历多选、排除和按补写日期共享 |
| 不开放后删除对方副本 | 表面上撤回更彻底 | 违反依据 4，也不能收回对方已导出的内容 |
| 重绑自动恢复全部日记或永久禁止分开期间内容 | 分别简化恢复或隐私策略 | 均违反依据 3、4 的独立确认和重新开放最新版本 |
| 把个人最新 CRDT 发给已停止共享的搭档再前端隐藏 | 同步实现复用较多 | 违反依据 5，停止共享后的未授权变更已经送出 |
| 解绑删空间、同人重绑新建 | 只存当前状态 | 违反依据 2、4，不能恢复原关系数据和冻结历史 |
| 全量最后写入覆盖、只存停止时间 | 实现和存储少 | 违反依据 6，不能保证并发、作者保护与可重建冻结版本 |

## 风险与代价

- 授权版本、冻结记录和重新开放代次需要额外状态及存储；固定搭档消除了多搭档隔离，不消除停止共享后的版本隔离。
- 首次绑定选错账号后，首版无法自助纠正，也不预设人工重置入口；确认页须明确核对账号和固定搭档规则。后续问题记录在未来功能清单。
- 最新主人文字可能在语义上提及别人；服务端保证其他作者字符不泄露，不判断用户自己写下的文字是否谈论过去关系。
- 日期范围授权会自动包含范围内后来补写的日记，UI 必须明确；取消日期也不能收回先前已收到的副本。
- 随机邀请可被转发，接受前的身份确认和事后解绑用于处理错误关系；不声称 token 绑定了某个邮箱。
- Google 等外部服务上的旧副本不随应用解绑自动撤回；备份实现需另行设计凭据生命周期和个人/空间导出隔离，不能默认以旧凭据导出重新开放的内容。

## 验证

12 条不变量均有标题带 `[adr:spaces-and-invitations#N]` 的正式测试，关系和范围在真实 PostgreSQL 上验证，界面在组件测试与 Chromium、Firefox、WebKit 浏览器测试中验证：

1. 固定搭档：PG 约束拒绝同一用户与反序用户对；API 测试中 A/B 解绑后 A/C、C/A、B/C 被拒，C 已固定于 D 时从未绑定的 E 双向被拒。
2. 唯一空间与新期间：PG 约束保证用户对唯一、每空间至多一个未结束期间；API 测试中重绑复用 spaceId、新建 periodId 并保留旧期间。
3. 邀请生命周期：PG 约束保证只关闭一次；服务测试覆盖七天前 1 毫秒有效、恰好七天过期、轮换后仍报过期；API 测试覆盖预览与重复接受不绑定、撤销与重复撤销、轮换、接受自己的邀请与未知 token；组件测试覆盖重试生成不再显示链接。
4. 同事务提交：API 测试中 20 人同时接受同一邀请只成功一对，A 同时接受 B、C 只建一个空间，A/B 互相接受只建一个期间；在第二条当前绑定插入时注入失败，空间、绑定、邀请消费与范围均无残留。
5. 分别确认：API 测试覆盖双方不同范围、不设置范围也能绑定、重绑不把旧确认标为本期；组件测试覆盖仅在邀请与接受时可“暂不设置”。
6. 日期集合：单元测试覆盖排序、合并重叠与相邻日期（含跨月和闰日）、开放端及按日期集合比较；API 测试覆盖规范形式存储；组件测试覆盖单日、持续、排除及排除优先。
7. 单方解绑保留数据：API 测试中解绑后双方无当前绑定，空间、期间与双方范围保留；组件测试覆盖二次确认。
8. 旧请求与幂等：API 测试覆盖重复 requestId 返回原结果、不同载荷拒绝、旧 revision 冲突、旧解绑重放不结束新期间、已结束期间的保存在重绑前后均被拒；组件测试覆盖保存携带所依据的 revision。
9. 访问与隐私：契约测试保证只有本人范围响应可含范围；API 测试中第三人一律 NOT_FOUND，对方与邀请预览的响应不含本人日期；浏览器测试中第三人打开空间页看到“找不到这个空间”。
10. token 与会话：API 测试覆盖库中只有摘要、no-store、十个接口均需会话、写接口校验 Origin；组件测试覆盖 fragment 读取后移除并仅暂存于本标签页。
11. 提交后确认：同第 4 条的注入失败测试，以及生成、保存、解绑的重试恢复测试。
12. 界面说明：组件测试与三种浏览器中 A、B、C 三账号的完整链路（邀请登录续接、分别保存范围、绑定、解绑、重绑、当前与历史关系），页面始终显示“范围已设置，日记共享尚未开放”，不出现日记、快照或冻结状态。
