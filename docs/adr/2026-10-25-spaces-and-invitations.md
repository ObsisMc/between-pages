# 个人日记独立存在，双人空间随绑定归档和恢复

- 状态：提议
- 日期：2026-10-25
- 决策者：Ray
- 范围：领域
- 关联：取代 ADR-0001 的日记归属与日期唯一性；依赖 ADR-0003；依赖 ADR-0006；依赖 authentication-and-sessions

每人每天有一篇独立于绑定关系的个人日记。一个账号同时只能绑定一人，双方确认后创建双人空间；与同一人重新绑定时恢复同一空间。空间合并展示双方获准共享的日记，并承载共同计划、赠礼记录等关系数据。解绑不删除数据：共享版本锁定，双方仍可查看，个人日记可以继续更新，但后续变化不向旧搭档开放，重新绑定也不补传。

上述产品规则来自本次讨论，已获用户确认；本文的数据表、接口和实现方案仍以提议评审。本次实现范围为邀请、绑定、解绑、空间归档与恢复；日记编辑器、共享版本的物理编码、共同计划、赠礼和 Google 集成随后实现。本 ADR 规定它们必须遵守的边界，不创建尚无消费者的日记或计划表。

## 背景与问题

登录已经提供稳定的领域 userId，但尚无关系和共享权限。[原 ADR-0001](./0001-diary-domain-and-time.md)将空间作为日记容器，一天只有一篇共同文档。用户现已明确：个人日记不依赖绑定，双人空间是共享入口；每人每天一篇，前端可拼接展示，双方可在对方日记中穿插想法。

账号需要解除绑定、保留双方共同数据，并可与同一人重新绑定恢复原空间。仅保留成员表或在解绑后继续读取同一份最新正文，会泄露分开期间的内容。必须分别表达永久参与者、当前绑定、每次绑定期间及各期间实际共享的版本。

## 决策依据

1. 日记属于个人，绑定或解绑不能创建、迁移、删除日记，也不能改变已有字符作者。
2. 每个账号同时只绑定一人；历史空间可以有多个，但同一对用户始终对应同一空间。
3. 双方都需同意绑定；任一方可二次确认后单方面解绑，无需对方批准。
4. 解绑后双方可查看、导出当时已经共享的内容；后续私人变化不开放，再绑定也不开放，本期没有补充共享功能。
5. 空间拥有共同计划、赠礼等关系数据，解绑归档不删除，与同一人重新绑定恢复；新搭档不能访问旧空间。
6. 邀请期限、撤销、一次性消费、绑定竞争和解绑必须受事务及数据库约束保护。
7. 沿用现有认证、契约、PG 和测试边界；先落地关系闭环，日记与其他业务按依赖后续接入。

## 决策

### D1：个人日记、字符作者和双人空间分开建模

个人日记有稳定 `diaryId`、`ownerId` 和固定 `diaryDate`，唯一键是 `(ownerId, diaryDate)`，不再是 `(spaceId, diaryDate)`。未绑定也可写个人日记，数据库不要求日记依附某个空间。日期继续由服务端 UTC 时间和请求者有效 IANA 时区推导，创建后不变。

ownerId 表示日记归属，不代表拥有所有文字的修改权。对方插入的 comment 是正文中有独立作者的想法，不新增评论线程或回复树；每个字符的 authorId 不变，日记主人也只能修改自己写的文字。历史作者不要求仍是当前搭档。

空间中的同日期页面按稳定参与者槽位拼接两篇获准共享的日记，保留日记边界和各自 ID；光标、编辑、撤销仍指向具体日记及其共享上下文，不把拼接后的字符串作为一个协同文档提交。某人当天尚无共享日记时只展示另一篇，不能读取其私人日记来补齐。

空间保存共享关系和共享版本，不取得个人日记所有权。共同计划、赠礼记录等真正属于空间；本次只保留这些功能的归属规则，不实现功能或预建表。

原因：依据 1、5，个人创作与一段关系的共享生命周期不同；区分 ownerId 和 authorId 保留原有作者保护。

### D2：一对用户拥有一个永久空间，每次绑定是一个新期间

空间有两个不可替换的参与者，按 userId 的 UUID 顺序确定槽位 1、2；参与者集合不可修改，颜色按空间内稳定槽位映射，真实作者仍使用 userId。双方权限平等，没有管理员。

首次接受邀请时才创建空间，不预建单人空间。空间状态由其是否有开放期间推导：开放期间存在则 active，否则 archived。解绑结束本次期间；与同一人重新绑定复用原 spaceId、参与者和数据，新增一个期间，不重开旧期间、不改变旧截止版本。

| 关系变化 | 结果 |
| --- | --- |
| A 与 B 首次绑定 | 创建空间 AB、期间 AB-1，双方当前绑定指向 AB-1 |
| A 或 B 解绑 | 结束 AB-1；AB 归档，双方当前绑定解除 |
| A 与 C 绑定 | 创建或恢复 AC；C 不能读取 AB |
| A 与 B 重绑，但任一人仍与别人绑定 | 拒绝，不替任何人自动解绑 |
| A、B 都无当前绑定并重新确认 | 恢复原 AB，新增 AB-2；AB-1 继续锁定 |

同账号可访问多个历史归档空间，但最多一个当前空间。恢复 AB 是恢复同一关系的数据，不是将参与者换入 AC，也不是克隆一个新的 AB。

原因：依据 2、5，稳定空间标识保留关系历史；期间标识可阻止旧请求、离线编辑和订阅在重绑后误获新权限。

### D3：解绑锁定共享版本，重新绑定不合并私人变化

解绑事务为本次期间确定最后已提交的共享版本边界。归档读取、搜索、未读、导出及未来备份只能取这一边界内实际共享的内容，不能按 diaryId 读取个人最新全文，不能只在前端隐藏新字。

个人版本和空间可读的共享版本必须可分别寻址。同一日记可以在个人视图继续变化，同时在旧空间保持固定快照。两边均保留对方已经写下的字符及作者；隐藏功能不能变成删除或重写作者。

重新绑定恢复各个历史期间及其锁定版本；解绑期间新建日记、修改、删除和其他私人内容均不回填，旧快照不自动升级。与其他搭档共享的内容同样不能带入原空间。未来新共享内容必须绑定新的 periodId，旧期间的同步队列不能转投新期间。

这需要版本与共享上下文隔离，不能把解绑期间的 CRDT 全量状态合并到恢复后的共享文档，再按写入时间过滤可见字：删除集、锚点和历史同样可能泄露或影响旧版本。旧共享日记目前只恢复为历史只读版本；本期不提供对这些版本重新开放编辑或补充共享的入口。

日记共享存储随后由日记/协同 ADR 设计并实现。启用第一条正式日记共享写入前，必须先实现版本截断、个人继续编辑、归档读取和期间校验的完整集成，不能先上线“总是读最新版本”再补归档。当前没有日记表，关系实现中的解绑只关闭空的共享期间；不增加无消费者的快照适配器或可关闭归档的配置。

原因：依据 1、4，保存空间记录本身不足以保存隐私边界；时间点只解释事件，持久化版本才决定实际可见内容。

### D4：只看自己的文字是个人只读视图

绑定期间、个人日记和历史归档均提供“完整内容 / 只看我的文字”。按当前查看者 userId 过滤 authorId，不按 ownerId 过滤；写在对方日记里的想法同样属于“我的文字”。

隐藏只改变自己的显示，不修改正文、对方显示、共享权限或归档版本，不产生正文写入、未读或备份。过滤视图保持只读，恢复完整内容且当前上下文仍允许写入后才能编辑；归档始终只读。解除绑定后仍能隐藏旧搭档的文字。

原因：依据 1、4，阅读过滤与删除、授权是独立责任；避免隐藏字符后的选区和编辑位置产生歧义。

### D5：关系存储用永久参与者、绑定期间和当前绑定约束

以下四张关系表在 `apps/api/src/db/schema.ts` 定义，通过现有生成命令生成迁移；时间用 timestamptz，领域用户外键只指向 users，不指向 auth_*。

| 表 | 字段与约束 |
| --- | --- |
| `spaces` | `id` UUID 主键；`user_low`、`user_high` → users；检查 user_low < user_high；唯一 `(user_low, user_high)`；`created_at` |
| `space_periods` | `id` UUID 主键；`space_id` → spaces；`started_at`；可空 `ended_at`、`ended_by` → users；唯一 `(id, space_id)`；每空间至多一条 ended_at 为空的部分唯一索引 |
| `active_bindings` | `user_id` → users，主键；`period_id`、`space_id` 联合外键 → space_periods `(id, space_id)`；每用户只有一个当前绑定 |
| `binding_invitations` | `id` UUID 主键；`created_by` → users；`request_id` UUID，唯一 `(created_by, request_id)`；`token_hash` 唯一；`created_at`、`expires_at`；可空 `revoked_at`、`accepted_at`、`accepted_by` → users |

space_periods 检查 ended_at、ended_by 同空或同非空，ended_at 不早于 started_at；ended_by 必须由事务校验为两位参与者之一。active_bindings 仅由绑定事务为永久参与者各插入一行；期间关闭时删除对应两行，永久参与者字段不删除。读取权限从 spaces 两位参与者判定，不能把任意 active_bindings 行当作第三位参与者。两用户字段保证一个空间恰好只有两位永久参与者，user_id 主键保证一个账号不能同时占两个当前绑定。

邀请检查 expires_at 晚于 created_at、accepted_at 与 accepted_by 同空或同非空、不能同时消费和撤销。每个 created_by 至多一条未关闭邀请的部分唯一索引：revoked_at、accepted_at 都为空；过期行仍占索引，重新生成时先撤销旧行。

生成邀请的 requestId 是同一次按钮操作及响应丢失重试的标识。通过邀请行的唯一键记录请求，重复 requestId 不轮换或重新生成凭证，只返回该邀请元数据和 `token: null`；若首次原始响应已丢失，用户明确重新生成并使用新的 requestId。这样旧请求在解绑或重新绑定后重放也不能恢复旧邀请；若已处于绑定中，生成接口仍优先返回 ALREADY_BOUND。

所有外键不级联删除用户、空间和历史期间。个人日记、共享版本、计划、礼物、颜色设置不在本次迁移中。

原因：依据 2、5、6，数据库兜底唯一配对、一个当前绑定和一个开放期间；邀请在配对前属于发起用户，没有 spaceId。

### D6：随机邀请由用户分享，双方确认后原子建立或恢复绑定

邀请使用内置 crypto 生成 32 字节随机 token，base64url 编码；数据库只存 SHA-256 摘要。七天有效、手动复制、没有邮箱绑定是本方案仍待评审的实施默认。链接为 `/join#token=<token>`，不自动发邮件或消息。原始 token 不进服务端 URL、日志或普通查询；所有响应 no-store，错误不回显输入。

未绑定用户可以生成或轮换自己的邀请；绑定中拒绝生成。轮换关闭旧邀请，精确 inviteId 撤销不影响新邀请。撤销重复请求成功；已消费返回 INVITE_USED。任一方有有效邀请不代表已绑定，不预留另一人的名额。

预览需要登录，只返回发起者 UserSummary、期限、`mode: 'new' | 'restore'`，不暴露历史内容。打开链接、登录或预览不创建关系。接受者必须不是发起者，双方都必须没有当前绑定。预览页面明确显示当前账号、对方和是否恢复原空间，点击“确认绑定”后才提交。

所有关系写操作先锁相关 users 行；涉及两人的，按 UUID 顺序锁，之后依次锁已有 space、当前 period、邀请行。生成/撤销只锁发起用户再锁邀请；接受前通过 token 摘要定位发起者，解绑前定位空间参与者，获得锁后都重查身份、邀请和当前状态。过期时间在锁后取数据库实际当前时间判断，等于期限也无效。

接受事务：校验邀请有效 → 拒绝自己、校验双方未绑定 → 按用户对查找或创建空间 → 创建新 period → 为两位永久参与者插入 active_bindings → 消费本邀请并撤销双方其他未关闭邀请 → 提交后返回。因两人都可能另有邀请，只有锁住双方用户后才能进行最后一步。失败整体回滚，唯一约束竞争不向客户端暴露 SQL 错误。

重复消费返回 INVITE_USED；提交后响应丢失则重查当前绑定，不自动重复创建。A 同时接受 B、C 的邀请，或 B、C 同时接受 A 的邀请，只能有一对成功；A/B 相互发邀请并同时接受也只能建立一个期间。恢复 AB 时，若任一方与 C 绑定，返回 BINDING_CONFLICT，不自动解绑、换人或消费仍有效的邀请。

原因：依据 2、3、6，原子占用双方的当前绑定比仅检查空间是否满员更符合单一搭档规则。

### D7：任一方可确认解绑，旧请求不能解绑新的期间

解绑请求携带 `expectedPeriodId`。事务按 D6 顺序锁两位参与者及空间/期间，验证操作者是永久参与者、请求期间属于本空间；只关闭指定期间并删除该期间两人的 active_bindings，同时撤销双方尚未关闭的邀请。不删除空间、永久参与者或历史数据。

重复解绑已经结束的同一期间返回 `{ spaceId, closedPeriodId }`，不改变后续期间。若该期间已经结束且双方又绑定，重放旧请求也不能关闭新期间或清理新邀请。不是参与者或空间/期间不存在返回 NOT_FOUND。

有日记后，解绑必须与共享写入使用同一期间锁：先提交的合法写入进入归档边界，解绑提交后旧期间不再接受写入或广播新正文。服务端仍需保留被拒绝的本地待同步内容为恢复草稿，不能伪称已共享。快照边界登记失败则整个解绑回滚。所有旧订阅在每次发送前也要校验期间及可读版本，不能只拦写入。

解绑后双方可进入旧空间查看/导出已共享历史，不能新增或修改计划、赠礼等空间业务数据。重绑后恢复原数据和新业务操作，但旧日记版本不解锁，也不重新沿用旧期间的授权或 Google 凭据。

原因：依据 3～6，结束关系不依赖对方在线；期间 ID 阻止网络重试影响新的关系状态。

### D8：权限同时区分本人、永久参与者和当前期间

认证只回答“是谁”。在 `apps/api/src/spaces/` 统一提供空间参与者与当前期间校验，业务代码不访问认证表。

| 上下文 | 可读 | 可写 |
| --- | --- | --- |
| 个人日记 | 日记主人读取个人版本 | 主人只改自己文字；不受是否绑定限制 |
| 活跃空间当前共享内容 | 两位永久参与者，且版本属于本期间获准共享集合 | 当前绑定及 periodId 有效，并通过作者保护 |
| 历史期间日记 | 两位永久参与者，只读当时锁定版本 | 不可写，重绑也不解锁 |
| 归档空间的计划/赠礼等 | 两位永久参与者 | 不可写，重绑后才恢复业务操作 |
| 非参与者/新搭档 | 无权读取旧空间及其共享版本 | 无 |

本人可读个人版本不代表旧搭档能读；双方曾经绑定也不代表能读取对方所有 diaryId。未来接口必须先解析资源的 owner/space/period/共享版本，再授权，不信任客户端另传的 actor 或 spaceId。不存在和无权限的资源统一 NOT_FOUND，登录资料、活跃时间和读取回执不外泄。

原因：依据 1、4、5，永久参与者保留归档阅读权，当前绑定只赋予当前期间的业务写入权。

### D9：HTTP 契约沿用现有路由表与 callApi

全部新接口为 access=user，成功 200，Origin、会话和错误处理沿用认证 ADR。body 使用严格 schema，额外 actor/userId/参与者等字段拒绝；wire shapes 只在 contracts 定义。

| route name / 方法与路径 | 输入 | 成功响应 |
| --- | --- | --- |
| `getBinding` GET `/api/binding` | 无 | `{ binding: BindingSummary \| null, invitation: InvitationSummary \| null }` |
| `listArchivedSpaces` GET `/api/spaces/archived` | 无 | `{ spaces: SpaceSummary[] }`，只含本人的非当前空间 |
| `getSpace` GET `/api/spaces/:spaceId` | params `{ spaceId }` | `{ space: SpaceSummary, periods: PeriodSummary[] }` |
| `createInvitation` POST `/api/binding/invitations` | body `{ requestId: UUID }` | `{ invitation: InvitationSummary, token: string \| null }`，仅首次响应有原始 token |
| `revokeInvitation` POST `/api/binding/invitations/:inviteId/revoke` | params `{ inviteId }`；body `{}` | `{ revoked: true }` |
| `previewInvitation` POST `/api/binding/invitations/preview` | body `{ token }` | `{ inviter: UserSummary, expiresAt: UTC ISO string, mode: 'new' \| 'restore' }` |
| `acceptInvitation` POST `/api/binding/invitations/accept` | body `{ token }` | `{ binding: BindingSummary, restored: boolean }` |
| `unbind` POST `/api/spaces/:spaceId/unbind` | params `{ spaceId }`；body `{ expectedPeriodId: UUID }` | `{ spaceId: UUID, closedPeriodId: UUID }` |

SpaceSummary：`{ id, createdAt, status: 'active' | 'archived', participants: { user: UserSummary, authorSlot: 1 | 2 }[] }`；固定两人，按槽位排序。PeriodSummary：`{ id, startedAt, endedAt: UTC ISO string | null }`；按 startedAt、id 排序。BindingSummary：`{ space: SpaceSummary, periodId: UUID }`。InvitationSummary：`{ id, expiresAt, status: 'pending' | 'expired' | 'revoked' | 'used' }`，不含摘要；getBinding 仅返回发起者最新未关闭邀请，无则 null，过期可见以便轮换。所有未展开 ID 为 UUID、时间为 UTC ISO string。

新增错误码：INVITE_INVALID（404），INVITE_EXPIRED / INVITE_REVOKED / INVITE_USED / SELF_INVITE / ALREADY_BOUND / BINDING_CONFLICT / PERIOD_CLOSED（409）。生成者绑定中返回 ALREADY_BOUND；接受时任一人已有当前绑定返回 BINDING_CONFLICT；日记接入后旧期间写入返回 PERIOD_CLOSED。无效、撤销、消费、过期按此顺序判邀请；自己、双方绑定冲突在有效邀请后判断。预览也检查这些条件，但不消耗凭证；接受再次完整检查。

扩展 RouteDefinition 与注册处，声明真实需要的 params、body 和错误 schema，OpenAPI 同步生成。扩展 callApi 的类型化参数和 JSON body，保留现有无参数调用；页面不另写 fetch 或拼 API 路径。响应形状不能承载个人最新日记或未来功能数据。

原因：依据 7，扩展现有责任归属，减少重复协议；解绑返回明确的期间而不是可能已经变化的空间状态。

### D10：桌面入口以个人日记为主，关系空间有独立的当前与归档入口

首页保留个人日记入口，不把“必须先绑定”作为写作门槛；本次尚未实现日记时如实展示尚未开放。未绑定可邀请对方、处理自己发出的邀请及进入历史空间；绑定中直接提供当前空间，不展示多搭档选择器。空间页面列出双方和历次期间，active 时显示“解除绑定”，archived 时显示归档说明；归档阅读权不依赖当前搭档。

解绑需单独二次确认，说明“双方当前绑定将解除；已共享内容保留且锁定；之后的个人更新不再共享”。成功失效 binding/空间相关 Query 数据；另一端重新聚焦或手动刷新更新状态，服务端权限立即执行，不以界面是否刷新为准。

邀请入口读取 `/join#token=…`，立即 replaceState 清除 fragment，在当前标签页 sessionStorage 的单一 pending-invitation 项暂存登录往返。登录回首页后有合法格式的 pending token 才固定转 `/join`，不引入任意 returnTo。预览明确是否恢复原空间以及不会公开分开期间内容。

接受成功或终态邀请错误清除暂存，暂时性网络错误保留并允许重查；接受超时先查当前绑定。退出登录清除暂存和 Query 缓存；token 不进入 Query/mutation 缓存、key、分析事件或 console，只在组件瞬时状态及登录续接存储中存在。sessionStorage 不可用时，已登录可内存完成，未登录提示登录后重新打开原链接。

原始 token 丢失只能明确重新生成，不能恢复旧链接；生成按钮禁用并持有同一 requestId 防重复，轮换需确认旧链接将失效。普通关系数据归 Query，首版不新增关系轮询或 WebSocket，保留“刷新状态”。隐藏文字由日记模块实现，本次不创建无正文的假过滤开关。

原因：依据 1～4、7，个人写作和关系入口分开，解除或恢复关系的后果在用户确认前可见。

## 失败与恢复

| 失败 | 结果与恢复 |
| --- | --- |
| 邀请生成提交后响应丢失 | 同 requestId 仅回元数据；明确重新生成获得新凭证，旧请求不能轮换新邀请 |
| 预览后对方已绑定、邀请失效 | 接受重查，提示失败，不自动替任何人解绑 |
| 插入第一位 active_binding 后数据库失败 | 期间、两位当前绑定和邀请消费同回滚，无半绑定 |
| 接受提交后响应丢失 | getBinding 找回；重复邀请返回 INVITE_USED，不新增期间 |
| 解绑提交前失败 | 当前绑定与未来快照边界整体回滚，不显示解绑成功 |
| 解绑响应丢失后双方又重绑 | 重放旧 expectedPeriodId 返回旧关闭结果，不改变新期间 |
| 重绑时存在私人修改或第三方内容 | 保留个人版，旧空间仅取归档版；不自动合并、补传或重用最新快照 |
| 解绑后旧客户端补发 | 拒绝向旧期间共享，保留恢复草稿；不得转投当前新期间 |
| 数据库或归档版本不可用 | 返回错误，不回退读取个人最新全文 |

## 不变量

1. 个人日记以主人和日期唯一，生命周期不依赖绑定；字符作者与日记主人分别记录且作者不可变。
2. 每个账号同时至多一个当前绑定，每个空间永久只有同一对不同参与者。
3. 同一对用户重新绑定复用原 spaceId，新增期间，不克隆空间、不改写旧期间。
4. 打开链接、预览和登录不绑定；有效邀请只能被明确接受一次。
5. 绑定期间、双方当前绑定和邀请消费在同一 PG 事务提交，失败不留下半绑定。
6. 过期、撤销、消费、轮换后的旧邀请不能绑定，重放生成请求不能轮换或恢复邀请。
7. 任一参与者确认即可解绑；解绑不删除日记、空间、历史参与者或空间业务数据。
8. 解绑的截止共享版本保持锁定，后续个人修改和私人日记对旧搭档不可见，重绑也不补传。
9. 旧期间的请求、待同步操作和订阅不能取得新期间的写入权，旧解绑重试不能结束新期间。
10. 只看我的文字按实际作者过滤，只影响本人显示，不改数据；过滤视图和归档只读。
11. 两位永久参与者保留归档阅读权，非参与者和新搭档不能访问旧空间及其共享版本。
12. 原始邀请 token 不进入数据库、服务端 URL、日志、Query 缓存或普通关系响应。
13. 关系接口要求有效会话，非安全方法要求可信 Origin；成功发生在 PG 提交后，可见用户资料不含登录、活跃或读取状态。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 每空间一篇日记，空间拥有正文 | 共享和权限结构简单 | 不符合依据 1，每个人需要独立日记，未绑定也应可写 |
| 一个账号同时参与多个活跃空间 | 可与不同搭档写作 | 不符合依据 2，当前需求明确为固定一位搭档 |
| 解绑删除空间或重绑新建空间 | 只维护当前关系较省状态管理 | 违反依据 4、5，会丢失共同历史且无法恢复原空间 |
| 归档只存时间点，读取个人最新全文 | 存储和查询更少 | 违反依据 4，私人修改、删除、CRDT 历史和导出都可能越过边界 |
| 重绑直接合并当前个人日记 | 不必维护多个可读版本 | 违反依据 4，补传分开期间内容，本期也不提供同意补传的入口 |
| 双方批准后才能解绑 | 能防止一方误点退出 | 不符合依据 3，一方不应阻止另一方解除关系；用二次确认处理误操作 |
| 邀请预先绑定邮箱并自动发送 | 更明确地约束收件人 | 依据 7，会新增身份匹配和邮件服务；当前采用手动分享的随机凭证 |

## 风险与代价

- 永久空间和多个绑定期间增加状态，但能保留历史并区分重新绑定的权限。不能仅用一个 active 布尔值恢复旧队列。
- 私人版本与共享历史的隔离是正式日记实现前置要求，原型没有证明该新模型；旧原型只作为作者保护和协同行为参考，不能作为新归档语义的验收证据。
- 用户已收到或导出的内容无法远程收回；解绑保证应用不继续开放后续变化，不承诺删除对方已经保存的历史副本。
- 邀请为持有者凭证，转发可能被错误账号接受，确认页必须显示身份；七天期限、手动分享和无邮箱绑定仍可在评审中调整。
- 保留多个历史空间会增加存储，账号删除、保留期限和资源限额随后设计，本次不自行删除历史或新增配额配置。

## 未解决的问题

- 首次绑定时是否共享绑定前的日记、同日已存在的私人日记如何接入、新期间如何在个人日记中继续产生可共享内容：需日记/协同 ADR 明确版本和编辑入口；在该设计采纳及隔离测试通过前不开放这些共享路径，不默认回填全文。
- 旧共享日记暂不重新开放编辑，也没有补充共享功能；若将来需要，必须另行讨论，不以恢复空间为授权。
- 计划和赠礼只确定归属与保留规则，具体功能后续设计；Google 个人备份、空间导出及重绑后的凭据需在备份实现前设计，不能沿用旧授权自动接收个人最新内容。

## 落地顺序

### 自主实现约定

已确认的产品规则写入规格；技术设计仍保持提议，采纳前只修改文档。采纳后按下列关系实现阶段执行；日记共享不在本次自主范围。

- **预先批准的迁移**：D5 的四张关系表及其约束与索引，request_id 直接放在邀请表；既有 users、auth_* 不改。不创建日记或其他业务表。
- **依赖**：复用现有包与内置 crypto，不新增依赖。
- **预先批准的代码**：D9 契约及 OpenAPI 生成、现有注册入口和 callApi 扩展，D10 邀请续接、关系/归档页面，相关模块 README；不修改 CI、hooks、checks/ 或 prototypes/。
- **AI 自行决定**：既定职责内的文件拆分、SQL/Drizzle 表达和测试组织；不自行决定补传、已有私人日记共享或新增删除入口。
- **停止条件**：违反不变量、需要额外迁移/依赖、正式日记已有数据而归档边界尚未实现，或需要解决未讨论的产品共享规则。
- **交付**：在当前设计 PR 评审，采纳后另开一个实现 PR，按阶段拆 Conventional Commits；Evidence 写已跑与未跑项，附决策/不变量/测试映射。Ray 评审并以 merge commit 合并，AI 不自行合并。

### 阶段 1：契约和关系存储

范围：D2、D5、D8、D9。完成条件：空库及现有登录库可迁移；稳定用户对、一个当前绑定和一个开放期间的约束在真实 PG 上验证；参数化契约、callApi、OpenAPI 和模块 README 同步。

### 阶段 2：邀请、绑定、解绑与原空间恢复

范围：D6、D7 的当前无日记场景。完成条件：真实 app.inject + PG 验证邀请生命周期、双向/多方竞争、失败回滚、重复生成/接受/解绑及重绑同 spaceId；A/B→解绑→A/C→解绑→A/B 不丢旧空间、不交叉授权。

### 阶段 3：桌面闭环

范围：D10，组件与 Playwright 多账号上下文。完成条件：创建邀请、登录续接、确认绑定、二次确认解绑、双方归档访问、同人重绑恢复；已登录用户不能绑定第二人，归档入口不能看别人的空间。执行 format、lint、typecheck、test:db、test:e2e:db、check docs。

### 后续依赖：个人日记与共享版本

此阶段不属于当前关系实现 PR。先设计并采纳个人/共享版本和新期间编辑方案，再实现 D1、D3、D4 及 D7 的共享提交边界、旧订阅限制和离线草稿恢复，最后才启用正式共享写作。之后接入计划/赠礼及 Google；在各自功能上线前补相应归档/恢复测试。

本 ADR 只有在所有不变量均实现并验证后才能转为已实现；完成关系闭环不等于日记或隐私边界已通过产品验收。

## 验收标准

正式测试标题使用 `[adr:spaces-and-invitations#N]`，并引用对应 AUTH/DATE/EDIT 验收编号。下表区别当前可实现验证和未来日记依赖，不把未存在的能力记为通过。

| 不变量 | 验证方式 |
| --- | --- |
| 1、8、10 | 后续日记数据库/接口/组件测试：两人同日两篇；解绑后个人新增、改删、对方 comment 保留与隐藏；归档保持原文；过滤不写数据且只读 |
| 2、3、5 | 当前 PG + app.inject：约束、事务回滚；A/B 重绑复用空间但期间不同；与 C 的关系独立；同用户并发争不同搭档只一对成功 |
| 4、6 | 当前 API/浏览器：预览不绑定、期限前后及等于期限、撤销、消费、轮换、重放生成请求、双方绑定冲突、自己接受被拒 |
| 7、9 | 当前 PG + API：任一方解绑、重复旧期间请求不关闭新期间；后续日记集成验证截止版本、旧写入/订阅被拒与草稿恢复 |
| 11、13 | 当前所有路由：A/B/C 和历史/当前关系隔离、会话失效、错误 Origin、提交受阻不返回成功；后续验证共享读取/导出/搜索也不读私人最新全文 |
| 12 | 当前真实生成路径：DB 只有摘要、捕获日志及请求 URL 无 token，浏览器清除 fragment/终态暂存且不进入 Query 缓存 |

并发测试使用独立连接和可控同步点，不加 sleep 或重试：至少 20 人争 A 的邀请；A 同时接受 B/C；A/B 互邀；生成/撤销/接受竞争；解绑与重绑和旧请求竞争。每次重新查询 PG 确认唯一当前关系及邀请结果。

后续日记验收必须包含：A/B 分享 V1 → 解绑锁定 V1 → A 私下新增、修改和删除产生 V2，并与 C 互动 → A/B 重绑仍只能从 AB 看 V1；个人视图可读自己的后续版本，双方未来新共享内容属于新期间；复制、导出、备份、搜索、同步均不能将 V2 私人内容带回 AB。仅检查页面隐藏不算通过。
