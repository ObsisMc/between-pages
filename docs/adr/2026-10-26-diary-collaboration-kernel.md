# 个人日记以增量协作保存，共享从获准的正文状态开始

- 状态：提议
- 日期：2026-10-26
- 决策者：Ray
- 范围：协同
- 关联：依赖 spaces-and-invitations；依赖 ADR-0002；依赖 ADR-0003；依赖 ADR-0006；依赖 authentication-and-sessions

每人每天一篇个人日记，文字作者只有主人与固定搭档。同一同步起点内用 Yjs 增量合并，服务端校验作者与授权，PG 提交后才确认保存；编辑先落本机日志，再按序组成发送批次，一批一个 PG 事务、一个版本，任一笔失败整批不提交。首次开放和重新开放时，在隔离副本里清除已删除内容，生成保留原字符 ID 的干净基线，只授权当时的已提交正文及本轮后续版本；面向搭档的一切输出只经一个获准状态读取入口，内部版本号不出服务端。停止共享保留只读冻结版本；跨边界未提交的输入保留为恢复草稿；历史只读，没有回滚。本文部分取代 ADR-0006 第 15、17 条（D12）。

不在本文范围：关系与日期选择（见[关系 ADR](./2026-10-25-spaces-and-invitations.md)）、更换搭档与误绑纠正（见[未来功能清单](../future-features.md)）、富文本、完整未读界面、Google worker 与凭据、手机端和性能深度优化。设计依据的临时验证见[设计验证记录](../validation/diary-kernel-design-2026-10-26.md)与[批次验证记录](../validation/diary-kernel-batch-2026-10-26.md)，它们不等于产品验收。

## 背景与问题

ADR-0006 确定一篇日记使用一个 `Y.Text('body')`，客户端生成普通更新，服务端验证后接受。固定搭档后，不再需要按不同搭档隔离正文，但私人期间与共享期间仍存在数据边界。

例如 A/B 共享到 V10 后停止，A 写入私人文字形成 V11，再删除形成 V12。重新开放时，B 可以读 V12 以及新一轮共享期间的版本，不能读 V11，也不能从二进制同步状态、删除历史、撤销、版本号或历史条目数中得知那段私人文字或私人编辑。B 先前合法取得的 V10 冻结副本仍然保留。

保留历史与禁止向搭档发送私人历史是两个职责。Yjs 的增量合并、状态向量及快照不能代替应用的版本访问控制；`gc: false` 下，仅检查屏幕当前可见的纯文本不足以证明同步载荷安全。

## 决策依据

1. 主人始终只有一篇持续更新的个人日记；冻结记录与同步起点切换不产生可独立编辑的正文分支。
2. 每个字符作者不可变，所有编辑入口与个人撤销执行作者保护，主人也不能修改搭档文字；历史只读，不提供回滚例外。
3. 搭档只取得明确授权的当前正文与共享期间历史，私人编辑、已删除内容及其存在痕迹不能通过底层数据、版本号或计数旁路泄露。
4. 保存、冻结与重开有统一 PG 提交边界；重试、并发与服务端崩溃不能造成假保存或旧全文覆盖。
5. 同一同步起点内离线输入自动合并；跨边界不能直接合并时保留原始输入和上下文，不能静默丢弃。
6. 复用正式栈与现有责任边界；只把有证据支持的机制写成承诺，参数以实测确定。

## 决策

本文用四个名称区分不同的"分组"（D13）：**操作**是编辑器的一次改动；**写入时段**是共用一个显示时间的连续输入；**发送批次**是一个 PG 事务提交的若干操作；**历史点**是历史列表的一项。"实时保存"指每个发送批次提交成功即一次保存，不是第五种分组。

### D1：日记身份稳定，个人最新正文与冻结归档分别寻址

Diary 保持 `diaryId`、`ownerId`、`diaryDate`、创建时区及 UTC 时间；唯一 `(ownerId, diaryDate)`。创建主人来自会话，日期创建与补写沿用关系 ADR，不依赖是否绑定。

每篇正文仅有主人及固定搭档两位作者。主人在个人入口可看最新正文及搭档保留的 comment，解绑后仍可改自己的字，不要求隐藏 comment。搭档只能在当前有效共享下修改自己写的字；冻结归档整体只读。双人页面拼接两篇获准日记时保留各自 ID 与编辑边界。

原因：依据 1、2，历史副本保留与当前正文编辑不能混为一谈，ownerId 不代表任意文字的修改权限。

### D2：提交版本、共享轮次和同步起点各有职责，内部版本号不出服务端

| 名称 | 作用与消费者 | 是否对外 |
| --- | --- | --- |
| 内部版本 `version` | 每篇日记服务端串行分配的整数；锁、排序、冻结记录与备份任务使用 | 否 |
| 同步起点 `generationId` | 当前基线与后续增量的上下文；更新、位置、撤销及本地队列匹配 | 是 |
| 起点内序号 `seq` | 每个起点内从 0 递增的提交序号；ACK、补同步与客户端基线比较使用 | 是 |
| 公开提交 ID `publicId` | 每次提交的随机 UUID v4；历史点寻址使用 | 是 |
| 共享轮次 `epochId` | 某篇日记这一次开放的授权记录 ID；搭档订阅、编辑与历史权限检查 | 是 |
| 日记日期 `diaryDate` | owner/date 唯一与共享范围判断 | 是 |
| 策略修订 `policyRevision` | 本人日期选择的配置版本；旧设置保存冲突检测 | 是 |
| 关系期间 `periodId` | 原双方这一次绑定的期间；解绑、恢复与成员写权检查 | 是 |

内部版本号不出现在任何对外接口：搭档若看到 E1 结束于 10、重开后第一次保存是 15，就能推出私人期间提交了 4 次。起点只在开放与重开时切换，停止共享后的私人提交仍在旧起点内，搭档收不到这些提交，因此搭档看到的 `seq` 没有空档；重开后 `seq` 从 0 重新开始。

每个成功的新发送批次对应一个 PG 事务和一个提交，不为每笔操作或按键另建版本；原批重试返回原提交。Yjs state vector 只用于同一起点内计算缺少的更新，不证明已经保存。epochId 使用该次共享授权记录的唯一 ID；新基线保留原字符 ID 也不使旧起点的请求继续有效，起点与授权记录不能互相替代。

原因：依据 3～5，"现在是否开放"无法识别停止后又重开时补发的旧请求；可数的版本号本身就是私人活动的痕迹。

### D3：同一起点内使用普通 Yjs 更新，服务端验证后才接受

每个起点包含一个 `Y.Text('body')`，正常运行关闭垃圾回收，仅允许纯文本与普通换行。编辑器使用自写 ProseMirror 绑定，将实际编辑步骤转换为插入/删除，不依赖前后全文差异猜测改动。

流程：本地编辑 → 本地日志持久化 → 按序组成并持久化发送批次 → 服务端在锁内、在隔离候选状态中逐笔检查 → 整批 PG 提交 → ACK 与获准广播（D9、D13）。客户端输入保持乐观，"已保存到服务器"只来自提交后的确认。

校验继承 ADR-0006：新字符的 clientID 必须绑定给当前会话用户；删除只能覆盖本人字符；拒绝格式、属性、额外顶层类型及尚不存在的引用，不让未验证更新进入房间或等待队列。个人撤销、粘贴、输入法组字、Unicode 与普通输入走同一作者边界。

**clientID 登记**：按 `(diaryId, clientID)` 登记，不做全局唯一；每个 Y.Doc 实例（每次打开、刷新、新标签页、新起点）使用 Yjs 新生成的 ID，不复用。登记在提交事务内、日记锁下完成：未绑定的新 clientID 绑定给会话用户，已绑定给对方的按 `EDIT_REJECTED` 拒绝整批。只读不写的实例不登记。本地日志按每笔更新的实际内容读取 clientID，不沿用打开时缓存的值，因为 Yjs 发现撞号时会自动换号。

32 位随机 clientID 若要求全局唯一，全系统登记到 10 万个时撞号概率约 69%；一篇日记对应一天，写过字的实例通常几次到几十次，按 50 个计撞号概率约千万分之三，撞号时整批进恢复草稿即可。

服务端不能原样广播客户端上传的字节：验证复现了重复的旧数据可能夹带已删除的私人文字，虽然不改变干净的接受状态，直接转发仍会泄露。对外输出一律从已接受的状态重新编码（D17）；服务端只保存原始更新的摘要，不把原始字节当作输出或重放数据。

原因：依据 2～5，在正常路径保留标准增量合并；"接受后状态安全"与"收到的字节可安全转发"必须分别判断。

### D4：首次开放和重新开放清理已删除内容，保留原字符 ID

从服务端已提交状态建立隔离副本，通过 Yjs 的垃圾回收把其中已删除文字的内容替换为删除占位，再编码干净基线；保留当前可见文字、原字符 ID、作者绑定与相对顺序。不采用重新插入全部纯文本、重编号或种子作者构造。

开放授权覆盖当时最新的已提交正文，包括仍存在的主人与搭档文字，不覆盖私人期间已经删除的文字或中间版本。旧起点的完整状态与增量留在服务端归档，只供主人读取。

1. 在锁外读取已提交状态，在允许垃圾回收的独立 Y.Doc 中载入并编码基线（D5 第一阶段）。
2. **自检**：新基线中的已删除条目必须只剩删除占位（`ContentDeleted`），不带原文字；不通过即按构建失败处理（`SHARE_OPEN_FAILED`），通过后记下 sha256。
3. 在开放事务中写入新起点：基线快照与 sha256、来源版本、日记的当前起点指针；基线作为新起点 `seq` 0 的提交行写入。恢复正常运行的 `gc: false`，旧起点只读归档，不再接受写入。
4. 所有设备先对账本地 pending（D7），再销毁旧运行实例、从新基线加载、使用新 clientID，并从新起点重新累计撤销。

不能只把干净基线合并到旧实例：Yjs 合并不会擦掉旧实例已保留的删除内容。ID 保留也不取消起点与轮次检查，Yjs 本身不会拒绝旧待发编辑。字符 ID 保留使作者、写入时间与阅读范围仍按原 ID 区间关联，不额外制造作者或写入时间。

此路线清除未授权的已删除正文，**不隐藏历史结构信息**：clientID、时钟、删除长度等仍可能透露发生过编辑及大致规模。若未来要求隐藏这些痕迹，需重新评估重编号路线。

原因：依据 1～3、6，保留原 ID 避免重建作者和字符来源映射；隔离清理、安装前自检与输出重编码共同保护私人历史，长期历史由受控归档承担。

### D5：冻结与重开遵守同一事务和授权边界，多篇开放原子生效

每个 `(spaceId, diaryId)` 至多一条 live epoch；记录 period、基线提交、关闭后固定的冻结版本。首次从未共享无需建立假的冻结记录。

| 动作 | 正文与授权结果 |
| --- | --- |
| 首次开放 | 建立干净基线、新起点与新 epoch，只授权基线和本轮后续提交 |
| live 期间合法编辑 | 提交带当前 epochId，提交后才广播 |
| 取消日期或解绑 | 关闭 epoch，固定最后已提交版本，终止搭档写权与后续更新 |
| 主人在私人期间编辑 | 更新个人最新正文，提交的 epochId 为空，不向旧共享目标发送 |
| 本人确认重开 | 从当前已提交正文建立新起点和 epoch，不覆写旧冻结记录，不补授私人历史 |
| 保存相同有效日期集合 | 沿用关系 ADR 的幂等语义，不无故新开 epoch 或清空撤销 |

与写入并发时，由日记行锁决定边界：写入先提交则进入冻结版本；停止先提交则旧共享写入被拒。仅断开 socket 不足以完成权限变更。

**多篇开放分两阶段。** 首次邀请默认"全部历史＋以后持续共享"，所以绑定时就要开放双方全部已有日记，可能是数百篇。

1. **第一阶段（不加锁、不写任何持久状态）**：读取范围内每篇的已提交版本，按 D4 在内存中构建并自检干净基线。进程在此期间崩溃只丢失计算，PG 不变，客户端重试即可。
2. **第二阶段（一个 PG 事务）**：按 D9 锁序锁住主人 users 行、space、period、本人 policy 及范围内全部日记行；逐篇复查版本号与起点，与第一阶段一致才使用内存中的基线，变化的篇在锁内重建；然后一次写入基线、起点、epoch、策略变更与幂等结果。不复查会把旧版本的基线装成当前状态，丢失其间已保存的文字。

对外只有"开放前"和"开放后"两种状态，客户端的"正在准备"只是提示。开放请求复用关系 ADR 的 `requestId`、`expectedRevision` 与 `sharing_policy_changes` 唯一约束，在第二阶段同一事务写入；COMMIT 后回复前崩溃，客户端用 requestId 查回原结果。任一篇基线构建或自检失败则整体不开放，返回 `SHARE_OPEN_FAILED` 并带失败日期。绑定采用同一流程：接受邀请时为双方确认范围内的日记预构建基线，第二阶段即绑定事务。停止共享与解绑只冻结、不重建，仍在一个事务内完成。

首次开放和重新开放先展示受影响的日期范围，说明将共享当前正文及后续编辑、不开放私人期间历史，并简短说明撤销从新起点开始。确认后暂缓本页面新的编辑，等待本页面当前待发内容提交，再提交开放；服务器以执行时的最新已提交状态为准，不等待其他设备上线，跨新起点的旧待发内容按 D7 处理。停止共享直接请求服务端关闭，不等待搭档保存或上线。开放与停止均在服务端成功后才显示成功；不存在的已选日期不创建空正文，未来创建时按已确认的共享政策开放；配置交付阶段保存的旧设置不能直接视为正文发布授权。

原因：依据 3～5，开放不是把旧请求重新变成合法请求；全部篇数一起生效，用户点一次确认才有确定的结果；锁只在写入期间持有，绑定时的数百篇不会长时间阻塞双方写入。

### D6：历史版本只按已有授权读取，重开不补授私人历史

主人可读取本人日记的已提交历史。搭档只可读取每个获准 epoch 的基线及该轮期间的提交；关闭后保留该轮只读访问权。重新开放增加新一轮权限，不扩大旧轮边界，也不授予私人期间的中间版本。

例如：E1 结束于 V10，私人 V11 含后来删除的字，重开 E2 基线为 V12。B 可读旧 E1 已获准历史、V12 及 E2 后续获准版本，不可读 V11；不得通过同步基线、历史接口、导出、搜索、条目数或原始存储下载获得未授权内容。

历史读取输出该版本的只读正文、作者及时间，由服务端渲染，不开放原始 CRDT 数据。历史版本只读，不提供整篇回滚、按作者回滚或将某个历史版本设为当前正文的入口，主人与搭档均无例外。浏览历史不改变当前正文、共享状态或撤销起点。复制历史文字后粘贴到当前正文，按当前用户的新输入处理。

**历史点在读取时计算**，不用定时任务：按服务端提交时间，持续编辑每五分钟一组，取组内最后一次提交；连续两分钟没有正文提交，以最后一次提交补末点；同一提交不重复成点。双方正文编辑都参与判断，光标移动不参与。共享首次开放、停止、重开独立成点，不跨私人/共享边界合并。历史点用其代表提交的 `publicId` 寻址；列表先按查看者授权过滤，再分组、计数、分页，私人期间的提交连"存在"都不出现；分页游标不透明，内部编码（提交时间, publicId），每页重查授权；冻结版本用 epochId 寻址。

**展示规则**：

- 从当前这篇日记进入其获准历史；右侧时间列表按日期分组，最近在前，分批加载，每项显示时间与参与修改的人；选择后在正文区域只读预览完整历史正文，保留原作者颜色并标明历史状态。双日记页面分别进入对应日记。
- 首版不做逐字差异高亮。无可查看历史时显示空状态，不制造历史点。
- 预览期间收到新编辑，保持当前预览，只提示当前正文有更新；返回当前时恢复原编辑位置并保留本地待发队列；已停止共享的搭档返回其获准冻结正文。时间按查看者本地时区展示。

历史点和已获准冻结版本长期保留，不自动过期；存储格式见 D9、D16。

原因：依据 2、3，只读历史满足长期查阅并保持统一作者保护；读取时计算历史点没有"补点任务失败"这种故障，也天然按授权过滤。

### D7：应用管理 IndexedDB 编辑日志，先落本机再发送

应用自管的本地日志统一负责已确认基线、待发操作、发送批次、提交回执和恢复草稿；不使用 y-indexeddb，不让两个持久化拥有者分别保存同一笔编辑。

**存储组织**：每个账号一个 IndexedDB 数据库（如 `between-pages-journal:<userId>`），代码层面不可能读到另一个账号的数据；退出登录时锁住该库。库内五个存储：基线、待发、草稿、回执、批次；待发按 `(diaryId, localSequence)` 建索引；每篇日记至多一个未确认的发送批次；本地回执在批次确认、基线前移后清理。日志结构有独立的版本号，只做前向迁移（D10）。

**浏览器要求**：IndexedDB 与 Web Locks（Chrome/Edge 69+、Firefox 96+、Safari 15.4+）；缺少 Web Locks 时进入只读模式并提示升级，避免两个标签页同时发送。打开时调用 `navigator.storage.persist()` 降低存储被清理的风险。

| 过程 | 规则 |
| --- | --- |
| 输入 | 立即显示；操作在本机落库成功后才允许发送，落库前不能声称已保存到本机 |
| 顺序 | 同账号、同日记跨标签页共享持久化 localSequence；序号分配、计数递增及 pending 插入同事务；不按随机 operationId 排序 |
| 发送协调 | 同账号、同日记共用 Web Lock，同一时间只有一个发送批次在途（D13） |
| 发送批次 | 形成批次在一个事务内完成，首次发送前持久化 batchId、上下文、有序成员与字节；重试及崩溃恢复使用原批，不重新打包 |
| 确认 | 删除成员、删除批次、写回执、前移基线在同一事务内完成，事务 complete 才算本地确认；不提前删除或重新插字 |
| 失败 | 按错误码的恢复类别处理（D10），不越过未确认的批次，也不删除后续 pending |
| 本机未落盘 | 保留可复制的内存原文，阻止自动重载、发送或基线切换覆盖它；存储恢复后持久化原操作，不改 ID |
| 切换起点 | 先查每笔 pending 与未确认批次的服务器提交结果；已保存的只记回执，不转草稿；其余转恢复草稿 |
| 原子切换 | 转草稿、移除已处理 pending 与安装新基线同事务；查回执期间队列变化则中止切换、重新读取 |
| 旧标签页 | 每次写入事务内重查当前起点与轮次，不把旧上下文写入新 pending；旧输入保留为草稿 |

| 到达时的情况 | 结果 |
| --- | --- |
| 起点相同且写权有效 | 普通断网按已持久化顺序自动合并 |
| 共享 epoch 已结束，即使后来又开放 | 不改标后重发，未提交原文保留草稿 |
| 起点已切换，包括主人的其他设备 | 查询提交结果后保存旧输入，再载入干净基线 |
| 原操作已提交但 ACK 丢失 | 重发原批或查询原回执，不重复正文、版本或备份副作用 |
| 本地落库或草稿事务失败 | 当前内存原文、原基线及待发内容不被自动替换；提示复制/下载或等待存储恢复 |

**恢复草稿**仅提供查看、复制与本人明确删除，标明日记、时间、原因、旧上下文及未进入当前正文。意图由编辑器绑定在翻译 ProseMirror 步骤时同步记录，不靠全文前后缀比对：插入可复制本人新增文字；删除展示原本打算删除的文字，不自动删除当前正文；替换展示前后内容，仅允许将本人新增部分作为恢复文本复制。每条草稿另存前后约 20 字上下文，方便定位；对方文字只作上下文。用户手动粘贴时，在当前授权下创建本人的新操作；不自动重放旧更新、不一键覆盖全文、不恢复旧作者。只有本人明确删除才移除草稿。

主人的个人入口写权来自 owner 身份，搭档写权来自 live epoch；旧共享请求不能悄悄改成个人入口，跨起点的旧请求也不因 owner 身份豁免。

原因：依据 4、5，明确区分已确认、待确认和恢复数据；日志顺序、原子确认和发送锁保证依赖编辑不会被随机排序或多标签页并发打乱。

### D8：撤销与光标服从同步起点和版本上下文

个人撤销只跟踪本人的新编辑，不撤销搭档操作。首次开放与重开后创建新的撤销上下文，不能跨基线继续 Ctrl+Z/Redo；旧内容通过获准历史查看。提示合并在 D5 的开放确认界面。

光标采用同一起点内的稳定相对位置，附带授权上下文，仅向具有当前读取权限的连接临时转发；冻结后不再传入私人光标；重开清理旧光标，不在旧坐标上猜整数位置。查看只读历史或"只看本人"模式时不发送正文编辑。

正文与光标共用一条 WebSocket 连接，消息分别处理。正文可靠持久化并补齐；光标只保留最新位置，可合并或丢弃过时的中间位置，不落 PG、不产生正文版本、未读或备份，不在正文发送批次后等待；断线或过期时清除。光标若引用接收端尚未取得的新字符，暂存最新有效位置，待相关已提交正文到达后再显示；补同步、拒绝或上下文切换时重新判断或清理。

原因：依据 2、3、5，撤销和位置属于具体同步上下文；保留旧字不等于保留可直接继续运行的旧撤销栈。

### D9：PG 负责版本顺序、幂等和持久化确认

**存储**（列类型与索引随迁移生成，阶段见落地顺序）：

| 表 | 内容 |
| --- | --- |
| `diaries` | owner/date 唯一、当前内部版本与当前起点指针 |
| `diary_generations` | 起点 ID、来源版本、干净基线快照与 sha256；旧起点只读归档 |
| `diary_client_bindings` | `(diary_id, client_id)` → 用户 |
| `diary_commits` | 主键 `(diary_id, version)`；`public_id`；`generation_id`、`seq`（唯一 `(diary_id, generation_id, seq)`）；`epoch_id`（私人期间为空）；`batch_id`、`author_id`（唯一 `(diary_id, batch_id)`，开放基线为空）；`batch_digest` 与摘要算法版本；服务端重新编码的 `delta` 与 `delta_sha256`；`committed_at`。一批一行，批回执即此行 |
| `diary_operations` | 主键 `(author_id, diary_id, operation_id)`；所属 version、批内序号、原始更新的 sha256（不存原始字节）、客户端写入时间、服务端接收时间 |
| `diary_character_ranges` | `(diary_id, client_id, clock 区间, operation_id)`；写入时间经 operation_id 取得 |
| `diary_snapshots` | 定期完整快照与 sha256，起步每 100 次提交一份 |
| `share_epochs` | baseline 提交、period、接收者、live/frozen、冻结版本 |
| `diary_read_ranges` | `(user_id, diary_id, client_id)` → 已读 clock 区间（`int8multirange`） |
| `backup_outbox` | 日记、内部版本、目标类型（个人/空间）、空间目标的 spaceId 与 epochId、状态 |

某版本的正文由不晚于它的最近快照加之后的增量重建；任何 sha256 不符即明确报 `VERSION_UNREADABLE`，不回退到别的版本。首版不压缩，以后单独设计压缩，不能破坏获准历史与离线恢复。

**批次摘要**是对 contracts 定义的规范字节串求 sha256，内容依次为起点、轮次与按序的（操作 ID, 更新 sha256）；前后端共用一份实现，不对 JSON 直接求哈希。摘要算法带版本号并随提交行存储，重试时按存储的版本比较，否则改算法后旧批次重试会被误判为冲突。

**锁序**（READ COMMITTED 下显式加锁）：

| 流程 | 依次加锁 |
| --- | --- |
| 提交发送批次（主人或搭档） | 只锁日记行 `FOR UPDATE` |
| 新建日记 | 主人 users 行 `FOR KEY SHARE`，再插入；`(owner, date)` 唯一约束防重复 |
| 开放第二阶段、修改范围、停止共享 | 主人 users 行 `FOR UPDATE` → space、period → 本人 policy → 范围内日记行按 ID 顺序 `FOR UPDATE` |
| 绑定、解绑、重绑 | 双方 users 行按 UUID 顺序 `FOR UPDATE` → space → period → 有 live epoch 的日记行按 ID 顺序 |
| 读历史、同步、打开日记 | 不加锁，在同一快照内读 |
| 上报已读 | 只更新本人的已读区间行 |

凡改变某篇日记共享状态的流程都必须锁到这篇日记的行；epoch 只在持有日记锁时修改，不单独加锁。日记行永远是最后一把锁，任何流程都不在持有日记锁后再请求 users、space 或 period，因此不会死锁。提交不锁 users 行：否则同一主人所有日记的写入会互相排队，并与会话的 `last_seen_at` 更新互相等待。新建日记的 `FOR KEY SHARE` 被开放与绑定的 `FOR UPDATE` 挡住，所以开放第二阶段期间新建的日记要么在其前、被一起开放，要么在其后、按新策略处理。提交的 `lock_timeout` 起步 5 秒，超时返回 `INTERNAL`；开放第二阶段的超时按实测确定。

**提交链**：

1. 客户端持久化发送批次后发送，失败或重启沿用原 batchId、成员顺序和字节。
2. 服务端校验会话、资源访问与消息格式，取得日记锁。
3. 锁内先按 `(diary_id, batch_id)` 查已提交的批：存在且摘要一致则返回原结果，不要求旧授权重新变为 live，并明确其旧上下文；摘要不一致返回 `BATCH_CONFLICT`。再查成员中是否有已提交的操作，有则返回 `OPERATION_ALREADY_COMMITTED`。
4. 对新批，检查写权、起点与轮次，从已提交状态在候选状态中逐笔验证并登记新 clientID。内存中的活动状态必须与 PG 版本一致，不一致从 PG 重新加载，不以陈旧内存代替 PG。
5. 全部通过后，在同一事务内写入提交行（重新编码的增量）、逐笔操作行、字区间、新 clientID 绑定与 outbox。任一校验或写入失败，整个新批不提交，没有合法前缀成功。
6. PG 提交后返回完整批 ACK，再发布提交事件（D10）。客户端原子记录回执、移除对应 pending 后，再推进后续批次。

**重复投递属于正常路径**：临时验证中服务端在 COMMIT 后断开连接，Chromium 未经应用即重发了同一请求。所以第 3 步的回执查询必须在锁内进行，否则同一批在两条连接上同时到达时，两边都可能看不到对方的回执。提交后若进程在广播前崩溃，其他连接通过补同步取回已提交更新，不依赖内存广播。PG 不可用不降级为内存保存成功。

原因：依据 4，Yjs 更新幂等不能代替应用的批次查重、事务提交与锁顺序；把批回执并入提交行，就不可能出现"有回执没提交"。

### D10：协议先校验身份和上下文，再解析编辑或返回结果

所有 HTTP/WS wire shapes 只定义在 packages/contracts，HTTP 经 callApi；WebSocket 消息是带协议版本号的 Zod 联合类型。

| 消息/入口 | 必需语义 |
| --- | --- |
| 打开个人日记 | 会话主人＋日期/日记 ID，返回当前正文、起点、`seq` 与服务端作者信息 |
| 打开共享/冻结版本 | space、diary、epoch 上下文，服务端解析访问权；客户端不能指定 actor 或 author |
| 订阅/补同步 | 协议版本、diary、起点、适用 epoch、已知 `seq`；只在授权匹配且起点相同时交换差量 |
| 提交发送批次 | batchId、上下文及有序操作，每笔含 operationId、Yjs 更新与写入时间；actor 由会话确定 |
| ACK / 查询提交结果 | batchId、成员、起点、`seq`、publicId；完整批成功，没有部分成功；按批 ID 或操作 ID 查询 |
| 上下文变化/拒绝 | 停止或重开通知、错误码与可重新打开的授权入口；客户端先保存 pending，再切状态 |
| 光标 | 当前日记、起点及适用 epoch 下的临时相对位置；不信任客户端声明的用户或作者 |
| 历史读取 | 列表按不透明游标分页；按 publicId 或 epochId 读取，每次校验权限，返回服务端渲染的只读内容 |

**接收方筛选**：广播与补同步都按提交行在事务内记录的 `epoch_id` 与起点决定接收方，推送时不另查 PG。主人的设备收同一起点的全部提交；搭档的设备只收同一起点且 `epoch_id` 等于其订阅 epoch 的提交。私人提交的 `epoch_id` 为空，无论停止通知是否及时到达，都不会发给搭档；停止前已提交、仍在发送队列中的内容属于冻结版本，照常发出，已发出的内容不承诺收回。

**会话**：WebSocket 握手检查会话与 Origin；每次写入重新检查有效会话与资源写权（auth ADR 不变量 8）。退出或撤销会话在事务提交后发布"会话失效"事件，持有该会话的连接立即关闭并丢弃发送队列；每个连接每 60 秒复查一次会话作为兜底。

**错误码**沿用 `{ error: { code, message } }`；contracts 中每个错误码固定一个恢复类别（写法同 `errorStatus`，用 `satisfies Record<ErrorCode, …>` 约束），客户端只按类别处理：

| 类别 | 客户端行为 | 错误码 |
| --- | --- | --- |
| retry | 原批退避重试 | `INTERNAL` |
| reconcile | 先查回执，再决定是否转草稿 | `STALE_CONTEXT`、`OPERATION_ALREADY_COMMITTED` |
| stop | 停止当前批及后续批，提示需要处理 | `EDIT_REJECTED`（带仅供诊断的 `reason`）、`BATCH_CONFLICT`、`PAYLOAD_TOO_LARGE`、`VALIDATION_FAILED` |
| reauth | 暂停同步，提示重新登录同一账号 | `UNAUTHENTICATED` |
| upgrade | 保留本地日志，提示刷新，不强制刷新 | `PROTOCOL_UNSUPPORTED` |
| show | 直接显示，不重试 | `SHARE_OPEN_FAILED`（带失败日期）、`VERSION_UNREADABLE`、`NOT_FOUND`、`POLICY_CONFLICT`、`PERIOD_CLOSED` |

无权资源与不存在资源一律返回 `NOT_FOUND`，不泄露私人日记的存在。日志不记录正文、原始更新、token 或恢复草稿。

**大小与兼容**：WebSocket 单条消息硬上限 1 MB；服务端只支持当前一个协议版本；只有不兼容的改动才升版本——服务端严格解析客户端消息、拒绝多余字段，客户端宽松解析服务端消息、忽略未知字段，所以服务端增加字段不升版本。按批 ID 或操作 ID 查询回执的接口长期兼容，因为很久未联网的设备随时可能带着旧批次回来对账。

原因：依据 2～5，连接认证、资源权限、共享轮次与同步起点分别检查；授权在提交时已经确定，推送时再查得不到新信息。

### D11：模块职责沿用现有边界，包内按职责划分子模块，首版单 API 实例

packages/collab 负责 Y.Text 模型、更新校验、作者来源、基线清理与自检、批次摘要等纯协同逻辑，不依赖 app、PG、HTTP 或 UI。contracts 只拥有 wire schemas 与错误码表。API 负责会话、授权、事务、提交链、获准状态读取（D17）与 socket。web 负责编辑器绑定、本地日志、恢复提示与只读历史展示。不从 prototypes 导入代码。

**包内按职责划分子模块，高内聚、低耦合。** 每个子模块只拥有一项职责，通过少量公开接口协作；划分依据是职责，不为"模块化"把逻辑切成只用一次的小函数（engineering-standards 的既有规则仍然适用）。

packages/collab 全部是纯函数，没有任何 I/O：

| 子模块 | 职责 |
| --- | --- |
| validate | 纯文本与作者校验（D3） |
| baseline | 隔离副本清理与自检（D4） |
| digest | 批次摘要的规范字节串与算法版本（D9） |
| authorship | clientID 区间到作者的推导 |

apps/api 分三层，只能从上往下引用：

| 层 | 子模块 | 职责 |
| --- | --- | --- |
| 传输 | ws、http 处理器 | 解析消息、校验会话、调用服务，不写业务规则 |
| 服务 | commit | 提交链（D9） |
| 服务 | sharing | 多篇开放的两阶段流程与冻结（D5） |
| 服务 | reader | 获准状态读取（D17），唯一产出搭档可见内容的地方 |
| 服务 | history | 历史点计算（D6） |
| 服务 | outbox | 备份任务登记（D16） |
| 服务 | events | 进程内事件（本节下文），不引用其他服务 |
| 存储 | store | 唯一写 SQL 与管理锁序的地方（D9），不引用服务层 |

传输层不直接引用存储层；除 reader 外，任何子模块都不产出面向搭档的内容。

apps/web：

| 子模块 | 职责 |
| --- | --- |
| editor-binding | ProseMirror 与 Y.Text 之间的转换，产出带意图的操作；不了解网络与 IndexedDB |
| journal | IndexedDB 日志（D7）；不了解 ProseMirror |
| sender | 发送批次与 Web Lock（D13）；依赖 journal 与 contracts |
| sync-client | WebSocket、补同步与上下文变化处理 |
| 界面 | 恢复草稿、保存状态、历史视图；只通过上述子模块的公开接口使用它们 |

包与包之间、以及上述子模块之间的引用方向由 `checks/verify-dependency-direction` 检查（architecture 中已列为 collab 落地时的待办），不只依靠评审。每个子模块单独测试：collab 用纯单元测试；api 的各服务用真实 PG 单独测试；journal 不依赖编辑器、editor-binding 不依赖网络。各包 README 的 *Public surface* 与 *Allowed dependencies* 列出子模块的公开接口与允许的依赖；子模块不另写 README。

首版只运行一个 API 实例，worker 按 ADR-0006 第 20 条另起进程。提交事件与会话失效事件在进程内传递，收在 API 的同一个模块里，对外只有发布与订阅两个函数。数据正确性不依赖实例数量：提交靠日记行锁排队，缓存在锁内核对版本，重连从 PG 补同步；实例数只影响实时推送与会话失效通知能否送达连在别的实例上的设备。以后需要多实例时只换该模块的内部实现（例如 PG `LISTEN/NOTIFY`），协议与表结构不变；现在不预建。部署须先停后启，不让新旧实例并存；万一并存，数据仍然安全，只是实时显示要等下次重连。

原因：依据 6，协同算法、权限事务与界面各只有一个责任拥有者；传输、业务规则与存储分开，才能分别测试与替换；不预建没有当前消费者的适配器。

### D13：操作逐笔落本机，网络自动按序组成发送批次

| 名称 | 是什么 | 由谁决定 | 影响什么 |
| --- | --- | --- | --- |
| 操作 | 编辑器的一次改动（打一个字、一次输入法上屏、一次粘贴），一个 Yjs 更新和一个操作 ID | 编辑器绑定 | 本地日志、查重、作者保护 |
| 写入时段 | 连续写下、共用一个显示时间的一段文字；暂停约 30 秒、换日记、换位置、切换模式时开始新时段 | 客户端 | 只影响点击文字时显示的写入时间 |
| 发送批次 | 一次发送、一个 PG 事务提交的若干操作 | 发送队列 | 保存确认、提交、重试 |
| 历史点 | 历史列表的一项（D6） | 服务端读取时计算 | 只影响历史列表 |

第一笔操作在本机落库后立即发送；等待确认期间继续显示并持久化新输入；当前批次确认落库后，把此时已积累的 pending 按 localSequence 组成下一批。不为凑批增加等待，也不让每个按键单独等一次网络往返。只合并同账号、同日记、同起点与轮次的操作。

同一时间只有一个发送批次在途；服务器在候选状态中按顺序验证，同批中先通过的操作可以作为后续操作的依赖。客户端取得提交回执并完成本地确认后才推进后续批次；失败时保留未确认内容，不越过它发送。一个新批对应一个 PG 事务、一个提交；任一笔作者、上下文、依赖或数据校验失败，整批不提交、不广播、不返回部分成功；永久校验失败停止该批及后续批，保留恢复内容，不无限重试。每笔操作的 ID、来源与写入时间仍逐笔保留。

**上限**：组批上限是软上限，起步 100 笔、64 KB，只决定一批装多少，实测后调整；单笔超过它时单独成批，不拆分。超过 1 MB 硬上限的粘贴在输入时拦下，不生成本地操作，提示分段粘贴，剪贴板内容保留；1 MB 约 30 万个中文字，是十万字验收规模的三倍。不在生成时自动拆分大段粘贴：那会让一次粘贴分段出现、撤销需要特殊处理，并可能出现粘贴了一半；大量旧文导入以后另做功能。

**写入时间**：同一写入时段内各操作的客户端写入时间取时段开始时间，仍按操作逐行存储；替换产生的新文字是新操作，记新的写入时间。

原因：依据 4、5，自动小批减少逐键往返积压；固定批次与整批原子提交使失败、ACK 丢失和重启只有确定的结果。

### D14：当前正文优先加载，增量重连与输入显示不等待历史

首次打开只加载当前获准正文及必要元数据，服务端用当前起点的基线和后续增量构建当前状态；历史列表分批加载，历史正文选择时再读取。不得把未获准的归档作为"快速加载"数据发往客户端。

同起点且权限有效的普通重连按已知 `seq` 补齐缺少的提交，保留本地输入并按 D13 续发，不用服务端旧全文覆盖待发内容。共享状态或起点变化时，先查提交结果并保留旧输入，再安装新获准基线，不能沿用普通差量流程绕过边界。

历史预览独立加载，不替换当前可编辑运行状态或 pending。输入立即在本机显示，串行的只是发送与确认。正常输入路径避免每次按键复制、存储或传输全部正文，避免每批重放全部历史或用完整正文 ACK；基线清理只在开放边界执行，历史与外部备份不阻塞输入与提交。

原因：依据 4～6，可靠保存不应以等待网络来限制打字；当前正文、历史预览和离线补发各自只加载所需数据。

### D15：未读与写入时间跟随原字符身份

当前活动页面实际可见约一秒才标已读；只记录当前用户自己的阅读进度，不向搭档提供阅读回执。已读按 `(查看者, 日记, clientID)` 存已读的 clock 区间（`int8multirange`），多设备上报取并集，不能用最大操作号或版本号清空所有未读。该表不按 epoch 区分，重开时自然保留。单篇的未读由客户端用获准正文与本人已读区间计算；跨日记的"有新内容"标记以后从提交记录推导。完整未读界面后续交付，本内核保证所需的字符身份与时间映射不丢失。

以 A 的日记重新向 B 开放为例：

| 重新开放时的文字 | B 的未读结果 |
| --- | --- |
| 以前已读、当前仍保留的 A 文字 | 保持已读 |
| 以前未读、当前仍保留的 A 文字 | 保持未读 |
| 私人期间新增、当前仍保留且首次获准的 A 文字 | 算未读，原写入时间较早也不例外 |
| 私人期间写入后又删除的文字 | 不输出、不产生未读 |
| 删除旧字后重新输入的 A 文字 | 新字符，算未读 |
| B 自己的文字 | 不为 B 产生未读 |

已删除、在当前获准正文中不再可见的文字从待阅读范围排除，这不伪造用户已经阅读。只对获准内容计算未读，私人活动不进入对方计数或通知。

**写入时间**：提交事务内为每笔操作新插入的字记录（日记, clientID, clock 区间, 操作 ID），客户端写入时间与服务端接收时间存在操作行。客户端时间只用于显示，不参与排序或权限；它晚于服务端接收时间超过 1 分钟时照常保存，显示改用接收时间并加说明。新基线保留原 ID，这些记录跨起点仍有效，不把首次授权时间冒充写入时间。

原因：依据 3、5，文字写入与用户是否读过是两个维度；保留原 ID 同时避免整篇重新未读和漏掉刚刚开放的旧时间文字。

### D16：长期历史独立于 Google，备份任务绑定授权版本

历史点和冻结版本由服务端长期保持可重建（D9），未连接 Google 也可读取获准历史；每个起点的干净基线也存为快照。

outbox 与提交、共享边界同事务登记。**个人目标**：主人日记的每次提交登记一条。**空间目标**：只有 live epoch 内的提交登记，开放第二阶段为每篇登记基线；停止共享后不再登记，最后一个获准版本即冻结版本。worker 只经获准状态读取入口（D17）取空间目标的数据，不读个人最新全文、原始上传字节或私人历史；同一目标按日记串行，只处理最新一条，写入前比较已完成的版本，旧任务不能覆盖新结果。

例如共享在 V20 停止，私人编辑到 V21，旧共享备份不能输出 V21；V25 重开后可以备份获准的 V25，但不能顺带打包 V21 的私人历史或已经删除的私人正文。

**阅读进度**：个人快照只含本人的已读进度；空间快照不含任何人的已读进度。空间备份放在其中一人的 Google 账号里，含有对方的进度就等于向账号主人提供阅读回执。

"已保存"来自 PG 提交，"历史点"来自对已提交版本的分组，"已备份"来自指定目标版本真正完成备份，三者分别记录，不以任务已登记冒充上传完成。Google Doc 与恢复快照的完成语义沿用 ADR-0004 与功能规格；本内核负责可靠登记任务，不实现 Google 上传。

原因：依据 3、4，异步执行不能扩大原授权，外部备份可用性也不能决定日记保存或服务端历史是否存在。

### D17：面向搭档的输出只经一个获准状态读取入口

API 中只有一个模块能产出给搭档的正文或字节。它的输入是（日记, 查看者, epoch 或版本）；查看者不是主人时，拒绝读取旧起点的状态。

| 出口 | 输出内容 |
| --- | --- |
| 搭档打开日记 | 当前起点的干净基线加之后的获准增量 |
| 补同步 | 只在当前起点的状态上计算差量（D10 的接收方规则） |
| 广播 | 提交行中存储的、服务端重新编码的增量 |
| 历史读取 | 服务端渲染的只读正文、作者与时间 |
| 空间备份快照 | epoch 所在起点的基线加截至获准版本的增量（D16） |
| ACK | 不带正文 |

以后新增任何面向搭档的出口，都必须经过这个入口，不能直接读取日记的完整状态。

原因：依据 3，D3 只规定"对外重新编码"，若由各出口分别实现，最容易出现某个出口直接读取了完整状态；集中在一处才能按出口逐一验证。

## 失败与恢复

| 情况 | 结果 | 错误码（类别） |
| --- | --- | --- |
| 断网、超时或服务端暂时不可用 | 保留 pending，重连后查询或重试原批；不重新打包、不越过未确认批次 | 网络错误或 `INTERNAL`（retry） |
| PG 写入失败或提交前进程崩溃 | 事务回滚，不 ACK、不广播；客户端保留原批，重试后提交一次 | `INTERNAL`（retry） |
| 提交成功但 ACK 丢失 | 重试返回原结果，不重复插入；上下文已变也不误当未保存 | —（重试成功，标记 replayed） |
| 同一批被重复投递（含浏览器自动重发） | 锁内查回执，只提交一次 | — |
| 批内作者、依赖或数据校验失败 | 整批拒绝，没有部分成功；停止后续批次，保留可查看和复制的恢复内容 | `EDIT_REJECTED`（stop） |
| 停止共享或重开后到达的旧批次 | 不提交；查回执后转恢复草稿 | `STALE_CONTEXT`（reconcile） |
| 写入与停止共享并发 | 只存在"已进入冻结版本"或"被拒"两种结果 | `STALE_CONTEXT`（reconcile） |
| 提交等锁超时 | 不提交，原批稍后重试 | `INTERNAL`（retry） |
| 开放第一阶段中进程崩溃 | PG 不变，客户端重试 | 网络错误（retry） |
| 开放 COMMIT 后、回复前进程崩溃 | 已完整开放；客户端用 requestId 查回原结果 | — |
| 基线构建或自检失败 | 整个开放不生效，说明哪一天失败 | `SHARE_OPEN_FAILED`（show） |
| 新基线加载时本机有旧 pending | 先持久化恢复草稿与上下文，成功后切换；失败则保留内存原文并提示复制/下载 | — |
| 其他设备离线跨过重开 | 不等待其上线；恢复网络后保留旧输入供本人处理，不自动重放 | `STALE_CONTEXT`（reconcile） |
| 登录过期、会话失效、登出或账号切换 | 暂停同步，提示重新登录同一账号；锁住旧账号的本地库，不静默清理未上传文字 | `UNAUTHENTICATED`（reauth） |
| 冻结或历史版本重建失败 | 明确读取失败，不回退到个人最新正文 | `VERSION_UNREADABLE`（show） |
| 客户端协议过旧或本地日志结构升级 | 保留待发原文，提示刷新，不强制刷新、不重新打包 | `PROTOCOL_UNSUPPORTED`（upgrade） |
| 粘贴超过 1 MB | 输入时拦下，剪贴板保留 | —（本地拦截） |

同步界面区分"正在同步""已保存到服务器""暂时无法同步""需要处理"，原因可展开，不在正常输入时反复弹窗；这些状态不代替 D7 的"本地尚未落盘"标识。提交结果不确定时显示"正在确认保存结果"，先查回执，再判断是否转草稿。

## 不变量

1. 同主人同日期仅一篇个人日记；绑定、停止共享与重开不改变其身份，也不产生可独立编辑的正文分支。
2. 每个字符的作者由服务端登记的 clientID 绑定推出，绑定只来自会话。
3. 任何编辑入口，包括个人撤销与粘贴，都不能修改或删除对方的文字。
4. 历史版本只读，没有回滚入口。
5. 同一起点内合法的并发与离线输入最终合并；旧全文或历史不覆盖当前输入。
6. "已保存"只在增量、操作记录、版本与 outbox 同一 PG 事务提交后报告。
7. 未通过校验或未提交的内容不被广播。
8. 一个发送批次只产生一个提交；任一笔失败则整批不提交，没有部分成功的 ACK。
9. 发送批次的身份、上下文与有序成员在首次发送前持久化；重试与崩溃恢复沿用原批，不重新打包。
10. 同一批次或同一操作的重试不重复产生提交、正文或 outbox；不同载荷复用同一 ID 被拒。
11. 停止共享后，搭档保留最后获准的冻结版本，收不到之后的提交，也不能再写入。
12. 首次开放与重开只授权当时的已提交正文及本轮后续提交；私人期间的版本与已删除文字不出现在任何面向搭档的输出中。
13. 重开不扩大旧轮次的历史权限；已获准的冻结记录保留且不可变。
14. 面向搭档的打开、补同步、广播、历史与空间备份只经获准状态读取入口产生。
15. 内部版本号不出现在任何对外接口；面向搭档的序号、条目与计数不反映私人期间的提交。
16. 写入与冻结竞争只有两种结果：写入在冻结版本内，或写入被拒。
17. 多篇日记的开放全部生效或全部不生效，并且只在服务端提交后显示成功。
18. 新基线保留现有字符的原 ID、作者与写入时间，并在安装前通过"已删除条目不含原文字"的自检。
19. 撤销从新起点重新累计，只影响本人的操作。
20. 旧轮次或旧起点的未提交操作不自动进入新一轮；它们以恢复草稿保留，只能查看、复制与本人明确删除。
21. 已提交但未收到 ACK 的操作经回执对账，不进入恢复草稿。
22. 本地序号分配与 pending 写入在同一事务内；同账号同日记按持久化序号发送，同一时间只有一个发送批次在途。
23. 本地确认与移除对应 pending 在同一事务内；未落盘的输入阻止基线切换。
24. 每次 WebSocket 写入都重新校验会话与资源写权；会话失效后连接不再收到推送。
25. 光标不产生正文提交、未读或备份。
26. 已读范围按原字符身份跨设备合并、跨轮次保留；任何快照都不含对方的阅读进度。
27. 历史点与获准冻结版本长期可重建，不依赖 Google。
28. 备份任务绑定版本与授权上下文；空间目标只输出获准版本；任务登记不等于备份完成。
29. 当前正文的加载与输入显示不等待历史、PG 或备份。
30. 暂时失败按原批重试，登录失效暂停同步，永久失败停止后续批次；结果不确定时先查回执再报告。
31. 协议升级与本地日志迁移不丢失、不重新打包已持久化的待发内容。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 重新开放直接发送完整旧 Yjs 状态 | 保留原字符 ID、光标和撤销，改动最少 | 违反依据 3，`gc: false` 下包含私人期间已删除的内容，仅隐藏历史界面不够 |
| **隔离副本 GC 清理并保留原 ID** | 保留作者与位置关系，避免全量重编号 | 已选择；17 项临时检查支持；接受仍可推断结构信息的边界 |
| 重建全部可见字符并分配新 ID | 能进一步隔离历史 ID/时钟痕迹 | 当前不需要隐藏所有结构痕迹，作者/位置/时间迁移成本更高；保留作需求改变后的比较方案 |
| 手工过滤改写 Yjs 二进制内部结构 | 可以精确选择原结构 | 需自行维护引用与删除依赖；已有 GC 路线的验证依据 |
| 由 y-indexeddb 管理全部本机状态 | 接线较少，能恢复本机文档 | 不解决 PG 回执、原子 pending 移除、跨起点转草稿和有序发送 |
| 每个按键单独等待 ACK 再发一笔 | 顺序容易理解 | 网络较慢时积压；违反依据 4 的体验前提 |
| 批内合法前缀先提交、后续单独恢复 | 可保留部分合法操作 | 部分 ACK、重组和依赖恢复增加结果分支；代价是单笔拒绝阻止整批及后续批次 |
| 多篇开放在一个大事务内逐篇构建基线 | 实现最简单，同样全部成功或全部失败 | 锁持有时间随篇数增长，绑定时数百篇会长时间阻塞双方写入与关系操作 |
| 先原子授权，基线之后逐篇补建 | 事务最小，篇数再多也不怕 | 每篇多出"已授权、基线未就绪"状态，搭档读取与编辑需要额外路径；没有证据表明需要 |
| 提交时锁主人的 users 行 | 与关系 ADR 原句一致 | 同一主人所有日记的写入互相排队，并与 `last_seen_at` 更新互相等待；正确性已由日记行锁保证 |
| clientID 全局唯一 | 映射表最简单 | 32 位随机号在全系统规模下必然撞号 |
| 服务端分配 clientID | 彻底避免撞号 | 离线时拿不到 ID 就不能写字，违反依据 5 |
| 对外使用内部整数版本号 | 无需额外 ID | 违反依据 3，版本号之差暴露私人期间提交次数 |
| 服务端同时支持当前与上一个协议版本 | 旧标签页不用刷新 | 多维护一套旧处理代码；两人使用、部署不频繁，刷新一次不丢字 |
| 大段粘贴在生成时自动拆分 | 没有用户可见上限 | 分段出现、撤销特殊处理、可能粘贴一半；为超出产品规模的情况增加复杂度 |
| 首版即支持多实例（LISTEN/NOTIFY） | 可零停机部署 | 部署目标是单台服务器，没有当前消费者；接口已留在同一模块，以后可替换 |
| 光标随正文一起落库和排队提交 | 单一流程容易追踪 | 光标只需最新位置，持久化增加等待与历史噪声 |
| 重开清空已读或按最新版本号统一标已读 | 状态更少 | 前者把已读旧字全算新增，后者漏掉未看到的插入 |
| 每位搭档维护独立正文副本 | 不同关系天然分开 | 首版只有固定搭档；增加多份写入和合并责任，不符合依据 1、6 |
| 重开后自动把旧 epoch 更新换标再提交 | 用户恢复操作少 | 违反依据 3、5，旧授权与旧字符定位不能自动变成新授权 |
| 全文快照最后写入覆盖 | 协议简单 | 违反依据 2、4、5，会覆盖并发输入 |
| 首版提供整篇或按作者回滚 | 能更快捷地恢复旧内容 | 历史只读已确认；回滚增加作者权限、并发、撤销与待发队列的复杂度 |
| 每次重开永久丢弃旧 pending | 新状态最容易载入 | 违反依据 5 |

## 风险与代价

- 临时验证没有覆盖正式的 Fastify、WebSocket、ProseMirror 绑定、Firefox/WebKit 与完整共享链路；这些在实施阶段验收，不能把临时证据算作不变量已实现。
- 保留原 ID 和删除占位仍暴露部分时钟、长度等结构信息；本文保证未授权正文与版本内容隔离，不宣称历史活动规模不可推断。
- **Safari 可能清空本地存储**：用户连续 7 天使用 Safari 却没有访问本站时，Safari 可能清空站点的本地存储，未同步的内容会丢失；`persist()` 能否豁免需实测。应用只能醒目提示"有内容尚未同步"并在联网时立即同步，风险只能缓解。
- 绑定或大范围重开时，用户要等第一阶段构建完成；第二阶段锁住范围内全部日记，期间这些日记的保存排队，输入不受影响。
- 首版单实例，部署时所有连接断开几秒，客户端重连补同步。
- 清除新一轮撤销上下文会失去快捷撤回旧操作的能力；旧内容仍只读可查。
- 长期保留历史、冻结引用、增量、操作行与字区间增加存储；以后的压缩需单独证明版本可重建。
- 跨重开边界的离线输入需要手动恢复；提示必须区分已提交、待发和草稿。
- 整批原子拒绝可能挡住其中原本合法的输入；必须保留恢复内容，不能以无限重试或跳过依赖掩盖失败。
- 私人阶段写下的正文仍留在当前正文中时，经确认开放可以被搭档看到；本文保证不泄露未授权历史，不判断当前文字的语义。
- 光标独立传输不等于总能立即准确显示；延迟目标只在注明的测试条件下验收。

| 参数 | 实现时的默认值 | 实测内容 |
| --- | --- | --- |
| 组批软上限 | 100 笔、64 KB | 远端延迟与批大小的关系 |

| K19 协议与日志升级 | 3 | 31 | 浏览器：旧协议标签页收到 `PROTOCOL_UNSUPPORTED` 后保留待发并在刷新后发送；IndexedDB 结构升级时旧标签页停止发送；改摘要算法后旧批次重试仍返回原结果 |

性能目标已由用户确认，尚未实测。以真实编辑器、PG 和 WebSocket 测量，记录设备、浏览器、文档规模、历史积累、并发、网络设置、样本量及 p95/p99；至少包含十万字符日记。网络条件稳定、双方各约 500ms RTT 时测远端指标，不把两端 RTT 与单程延迟混用。

| 指标 | 验收目标与口径 |
| --- | --- |
| 本机输入可见 | 从有效输入到本机可见绘制，p95 ≤ 50ms、p99 ≤ 100ms；不等待本机落库、网络或 PG |
| 远端正文可见 | 双方各约 500ms RTT，从发送端有效输入到接收端正确显示，p95 ≤ 2 秒 |
| 普通光标移动 | 双方各约 500ms RTT，已知正文上的位置变化到接收端显示，p95 ≤ 1 秒 |
| 边输入边移动光标 | 单独记录新正文与光标最终正确对应的延迟，暂不设数值目标 |

这些是注明条件下的统计目标，不承诺离线、网络抖动、丢包或故障时的硬上界。

代表性端到端链路：A/B 在 E1 编辑到 V10 → A 停止共享 → A 私写秘密形成 V11 并删除为 V12 → A1 保留离线 pending → A2 保存本机输入并确认重开 E2 → B 仅取得干净当前正文和新一轮历史 → A1 联网后旧输入进入恢复草稿 → 本人复制粘贴加入当前正文 → 验证作者、持久化、旧冻结记录、撤销及载荷隐私。
