# 个人日记以增量协作保存，共享从获准的正文状态开始

- 状态：提议
- 日期：2026-10-26
- 决策者：Ray
- 范围：协同
- 关联：依赖 spaces-and-invitations；依赖 ADR-0002；依赖 ADR-0003；依赖 ADR-0006；依赖 authentication-and-sessions

每人每天保留一篇个人日记，首版文字作者仅为主人与固定搭档。同一协同状态内使用 Yjs 增量同步，服务端检查作者与授权，PG 提交后才确认保存。停止共享保留只读版本；首次开放和重新开放只授权当时的当前正文及本轮后续版本，不开放此前的私人编辑历史。重新开放后撤销重新累计，跨边界未上传的输入保留为恢复草稿。历史版本仅供只读查看，首版不支持整篇或按作者回滚。

**本文是设计提议，不是编码授权。** 主要产品规则已确认：保留原字符 ID 的干净基线、应用管理的本地日志、固定批次身份与整批原子提交、只读历史、恢复草稿及授权边界。干净基线、本地日志及固定批次的故障恢复已有临时验证证据；正式 PG/WS/编辑器集成及性能目标尚未验证。整份 ADR 仍为提议，协议与存储细节、ADR-0006 的关系和验证缺口仍须收敛，不据此执行依赖安装、生产代码或迁移。证据及范围见[设计验证记录](../validation/diary-kernel-design-2026-10-26.md)与[批次验证记录](../validation/diary-kernel-batch-2026-10-26.md)。

## 背景与问题

ADR-0006 确定一篇日记使用一个 `Y.Text('body')`，客户端生成普通更新，服务端验证后接受。固定搭档后，不再需要按不同搭档隔离正文，但私人期间与共享期间仍存在数据边界。

例如 A/B 共享到 V10 后停止，A 写入私人文字形成 V11，再删除形成 V12。重新开放时，B 可以读 V12 以及新一轮共享期间的版本，不能读 V11，也不能从二进制同步状态、删除历史或撤销中恢复那段私人文字。B 先前合法取得的 V10 冻结副本仍然保留。

保留历史与禁止向搭档发送私人历史是两个职责。Yjs 的增量合并、状态向量及快照不能代替应用的版本访问控制；`gc: false` 下，仅检查屏幕当前可见的纯文本不足以证明同步载荷安全。

## 决策依据

1. 主人始终只有一篇持续更新的个人日记；冻结记录与协同状态切换不产生可独立编辑的正文分支。
2. 每个字符作者不可变，所有编辑入口与个人撤销执行作者保护，主人也不能修改搭档文字；历史只读，不提供回滚例外。
3. 搭档只取得明确授权的当前正文与共享期间历史，私人编辑及已删除内容不能通过底层数据旁路泄露。
4. 保存、冻结与重开有统一 PG 提交边界；重试、并发与服务端崩溃不能造成假保存或旧全文覆盖。
5. 同一协同状态内离线输入自动合并；跨边界不能直接合并时保留原始输入和上下文，不能静默丢弃。
6. 复用正式栈与现有责任边界；先验证新边界，再采纳与实现，不将原型结论扩展成未经验证的承诺。

## 决策

下列小节中的产品行为按确认表执行；具体编码、字段及流程是评审候选。涉及 ADR-0006 的扩展必须先解决 D12，不能据本文草稿直接覆盖已采纳决定。

### D1：日记身份稳定，个人最新正文与冻结归档分别寻址

Diary 保持 `diaryId`、`ownerId`、`diaryDate`、创建时区及 UTC 时间；唯一 `(ownerId, diaryDate)`。创建主人来自会话，日期创建与补写沿用关系 ADR，不依赖是否绑定。

每篇正文仅有主人及固定搭档两位作者。主人在个人入口可看最新正文及搭档保留的 comment，解绑后仍可改自己的字，不要求隐藏 comment。搭档只能在当前有效共享下修改自己写的字；冻结归档整体只读。双人页面拼接两篇获准日记时保留各自 ID 与编辑边界。

原因：依据 1、2，历史副本保留与当前正文编辑不能混为一谈，ownerId 不代表任意文字的修改权限。

### D2：提交版本、共享轮次和协同状态标识各有职责

| 名称 | 作用与消费者 |
| --- | --- |
| 提交版本 `version` | 日记的某次持久化状态；供保存确认、冻结、历史读取和备份引用 |
| 日记日期 `diaryDate` | 日记归档日期；供 owner/date 唯一与共享范围判断 |
| 策略修订 `policyRevision` | 本人的日期选择配置版本；供旧设置保存冲突检测 |
| 关系期间 `periodId` | 原双方这一次绑定的期间；供解绑、恢复与成员写权检查 |
| 共享轮次 `epochId` | 某篇日记这一次开放的授权记录 ID；供搭档订阅、编辑与历史权限检查 |
| 同步起点 `generationId` | 当前基线与后续增量的上下文标识；供更新、位置、撤销及本地队列匹配；改变起点不要求重编号全部字符 |

epochId 不必另设整数计数器，使用该次共享授权记录的唯一 ID 即可。generationId 用于识别基线切换后的旧更新上下文；即使新基线保留原字符 ID，旧请求也不得因此继续有效，与授权记录不能互相替代。

version 由服务端对每篇日记串行分配；Yjs state vector 仅用于同一 generation 内计算缺少的更新，不是 PG 提交版本，不证明已经保存。每个成功的新批次对应一个 PG 事务和一个提交版本，不为每笔操作或按键另建版本；原批重试返回原版本。对外版本寻址与列表不能绕过授权，具体对外版本寻址见 Q2，历史分组不改变实时保存频率。

原因：依据 3～5，“现在是否开放”无法识别停止后又重开时补发的旧请求；正文提交也不等于日期选择或关系期间变化。

### D3：同一协同状态内使用普通 Yjs 更新，服务端验证后才接受

每个 generation 包含一个 `Y.Text('body')`，正常协同状态关闭垃圾回收，仅允许纯文本与普通换行。D4 在独立副本中清理基线，不直接清理权威历史归档。编辑器使用自写 ProseMirror 绑定，将实际编辑步骤转换为插入/删除，不依赖前后全文差异猜测改动。

已选择的流程：本地编辑 → 本地 journal 持久化 → 按顺序组成并持久化固定批次 → 服务端依次在隔离候选状态中检查 → 整批 PG 提交 → ACK 和获准广播；具体提交链见 D9/D13。客户端输入保持乐观，“已保存到服务器”只来自提交后的确认。任一笔校验失败，整批不提交、不提升房间状态、不广播。

验证继承 ADR-0006：新字符 clientID 必须为服务端绑定给当前用户且允许其写入的 ID；删除仅覆盖其本人字符；拒绝格式、属性、额外顶层类型及尚不存在的引用，不允许未验证更新污染房间或进入等待队列。个人撤销、粘贴、composition、Unicode 与普通输入走同一作者边界。

服务端不能原样广播客户端上传的字节包。验证复现了：旧重复数据可能夹带已删除私人文字，虽然不会改变干净的接受状态，直接转发仍会泄露。对外同步、ACK 如携带正文、持久化重放与备份输出，应从已接受的干净状态重新编码获准增量，不能回用原始请求包。操作幂等可记录原请求摘要，不把原包当作安全输出。

原因：依据 2～5，在正常路径保留标准增量合并；“接受后状态安全”与“收到的原字节包可安全转发”必须分别判断。

### D4：首次开放和重新开放清理已删除内容，保留原字符 ID

**用户已选择的路线**：从服务端已提交状态建立隔离副本，通过 Yjs 的垃圾回收清除其中已删除文字的实际内容，再编码干净基线；保留当前可见文字、原字符 ID、作者绑定与相对顺序。该方案已通过临时内核验证，不采用重新插入全部纯文本、重编号或种子作者构造。

开放授权覆盖当时最新的已提交正文，包括仍存在的主人与搭档文字，不覆盖私人期间已经删除的文字或中间版本。原始协同状态与必要增量继续留在服务器历史归档，不直接发给搭档。

候选落地流程（PG 事务集成仍待设计）：

1. 在统一写入边界内确定最新已提交版本，保存旧历史及冻结所需引用。
2. 在服务器内部创建允许垃圾回收的独立 Y.Doc，载入该版本后编码基线，检查未包含已删除私人正文；不把清理过程或旧状态作为同步更新广播。
3. 以干净基线建立唯一当前协同状态，恢复正常运行的 gc:false，登记新 generation、新 epoch 及其基线版本；不改变 diaryId，不继续接受旧起点写入。
4. 所有参与设备先处理本地确认结果与旧 pending，再销毁旧运行实例、从新基线加载，并重建个人撤销上下文。
5. 后续增量从干净接受状态重新生成；不把用户上传的原始包原样中继给其他设备。

不能只把干净基线合并到旧实例：Yjs 合并不会擦掉旧实例已保留的删除内容。原历史缓存可以按权限另行保存，但不能成为新同步状态的输入。ID 保留也不取消 epoch/generation 检查，Yjs 本身不会拒绝旧待发编辑。

字符 ID 保留使作者仍可由原 clientID 绑定推出；原写入时间、阅读范围等既有元数据仍按原 ID 区间关联，不额外制造作者或写入时间。光标重建、未读与历史读取的正式集成仍需验证，不能将临时模型的相对位置检查等同于完整阅读体验验收。

此路线清除未授权的已删除正文，**不保证隐藏历史结构信息**：clientID、时钟、删除长度等仍可能透露发生过编辑及大致规模。当前用户在明确该边界后选择此方案；若未来要求隐藏这些痕迹，需重新评估重编号路线。

原因：依据 1～3、6，保留原 ID 避免重建所有作者和字符来源映射；隔离清理与输出重编码共同保护私人历史，长期历史由受控归档承担。

### D5：冻结与重开遵守同一事务和授权边界

每个 `(spaceId, diaryId)` 至多一条 live epoch；记录 period、baselineVersion、当前可读已提交版本，关闭后固定 frozenVersion。首次从未共享无需建立假的 frozen 记录。

| 动作 | 正文与授权结果 |
| --- | --- |
| 首次开放 | 建立干净基线及新 epoch，只授权基线和本轮后续版本 |
| live 期间合法编辑 | 保存新版本并更新本轮可读边界，提交后才广播 |
| 取消日期或解绑 | 关闭 epoch，固定最后已提交版本，终止搭档写权与后续更新 |
| 主人在私人期间编辑 | 更新个人最新正文，不更新旧 epoch 或向旧共享目标发送正文 |
| 本人确认重开 | 从当前已提交正文建立新起点和 epoch，不覆写旧冻结记录，不补授私人历史 |
| 保存相同有效日期集合 | 沿用关系 ADR 的幂等语义，不无故新开 epoch 或清空撤销 |

与写入并发时，由事务锁序决定边界：写入先提交则进入 frozen；停止先提交则旧共享写入被拒。仅断开 socket 不足以完成权限变更。

首次开放和重新开放先展示受影响的日期范围，说明将共享当前正文及后续编辑，不开放私人期间历史；确认界面简短说明撤销从新协作起点开始，不另加一次确认。点击确认后暂缓本页面新的编辑，等待本页面当前待发内容完成提交，再提交开放；保存或开放失败则保留输入及原共享状态，允许重试。

服务器以执行开放事务时的最新已提交状态为准，包括其他设备已经提交的内容，不等待所有设备上线。跨新起点的旧待发内容按 D7 保留恢复草稿。停止共享直接请求服务端关闭，不等待搭档保存或上线；写入与停止竞争仍按上述事务边界处理。

开放与停止均在服务端成功后才显示成功；断网时说明暂时无法完成，不先切换成功状态。范围涉及多篇日记时，已存在日记的开放/冻结与策略确认应同事务生效；不存在的已选日期不创建空正文，未来创建时按已确认的实际共享政策开放。配置交付阶段保存的旧设置不能直接视为正文发布授权。

原因：依据 3～5，开放不是把旧请求重新变成合法请求，冻结必须有可重建的内容依据。

### D6：历史版本只按已有授权读取，重开不补授私人历史

主人可读取本人日记的已提交历史。搭档只可读取每个获准 epoch 的基线及该轮期间已提交的版本；关闭后保留该轮只读访问权。重新开放增加新一轮权限，不扩大旧轮边界，也不授予私人期间的中间版本。

例如：E1 结束于 V10，私人 V11 含后来删除的字，重开 E2 基线为 V12。B 可读旧 E1 已获准历史、V12 及 E2 后续获准版本，不可读 V11；不得通过同步基线、历史接口、导出、搜索、版本总数或原始存储下载获得未授权内容。

历史读取优先输出该授权版本的只读正文、作者及时间，不直接开放包含其他时期内容的原始 CRDT 数据。Yjs snapshot 是重建工具，必须连同必要历史保存；不能只存“日记 ID＋时间”就声称冻结可恢复。历史压缩不得使仍可访问的版本或离线同步边界失效。

**已确认**：历史版本仅只读查看，首版不提供整篇回滚、按作者回滚或将某个历史版本设为当前正文的入口，主人与搭档均无例外。浏览历史不改变当前正文、共享状态或撤销起点。若用户复制历史文字后粘贴到当前正文，仍按当前用户的新输入处理，不能冒充历史作者或改写搭档文字。

**展示规则已确认**：

- 右侧时间列表按日期分组，每项显示时间与参与修改的人；选择后在正文区域只读预览完整历史正文，保留原作者颜色并标明历史状态，提供返回当前正文的入口。
- 持续编辑每五分钟形成历史展示点，取该组最后成功提交的正文；连续两分钟没有新的正文提交，再以最后已提交版本补末点。同一版本已有历史点则不重复生成。分组和停笔判断以服务端提交时间为准，双方正文编辑均参与判断，光标移动不参与。
- 共享首次开放、停止、重开独立成点，不能跨私人/共享边界合并。历史点引用已提交版本，不为定时补点重新提交正文；五分钟和两分钟均不延迟实时保存。
- 不将每批增量或每次按键都展开为一项；实时保存、网络小批次、五分钟历史分组是三个不同概念。首版逐字差异高亮后置，不与作者配色叠加。
- 主人与搭档的列表分别按权限生成，版本条目、数量、修改者、时间、边界标签与预览均不得泄露私人期间的活动；不能先列私人条目再提示无权访问。
- 从当前这篇日记进入其获准历史；双日记页面分别进入对应日记，不混淆主人或版本。列表最近在前，分批加载更早条目，选择时再加载对应正文；无可查看历史时显示空状态，不制造历史点。
- 历史预览期间收到新编辑，保持当前预览，只提示当前正文有更新。返回当前时恢复原编辑位置并保留本地待发队列；已停止共享的搭档返回其获准冻结正文，仍只读。时间按查看者本地时区展示。

**保留规则已确认**：历史点和已获准冻结版本长期保留，不设若干天后自动过期删除。正文、作者、原写入时间及可访问历史必须可准确重建。后续可以单独设计底层压缩，但不能以显示分组或压缩为由破坏仍获准的历史与离线恢复；具体对外版本 ID 和压缩格式见 Q2/Q7。

原因：依据 2、3，只读历史满足长期查阅并保持统一作者保护；时间分组减少列表噪声，不减少保存频率或扩大历史权限。

### D7：应用管理 IndexedDB 编辑日志，先落本机再发送

**用户已选择应用管理的本地日志**，统一负责已确认内容、pending、提交回执和恢复草稿。不将 y-indexeddb 的本机加载完成事件当作 PG 保存成功，也不让两个独立持久化拥有者分别保存同一笔编辑。具体 IndexedDB 访问封装待实现评审，不据此安装新依赖。

本地按账号、diaryId、generationId、个人/共享入口及适用 epoch 隔离，记录已提交基线、操作 ID、原 Yjs 更新、localSequence、设备 clientID、作者上下文及可读的变更前后内容和插入/删除/替换意图。草稿不能只保存新基线已无法引用的二进制。草稿中的他人文字仅用于上下文，重新加入仍受作者保护。

| 过程 | 已选择的规则 |
| --- | --- |
| 输入 | 立即显示；编辑与待发记录在本机落库成功后才允许发送，落库前不能声称已保存到本机 |
| 顺序 | 同账号、同日记跨标签页共享持久化 localSequence；序号分配、计数递增及 pending 插入同事务；不按随机 operationId 排序 |
| 发送协调 | 同账号、同日记共用发送锁；已验证模型使用 Web Locks，覆盖的浏览器范围见证据；正常小批发送按 D13 扩展 |
| 固定批次 | 发送前持久化 batchId、原上下文、有序成员与载荷绑定；重试及崩溃恢复使用原批，不重新打包 |
| 确认 | 服务端 PG 提交后的批回执与移除对应 pending 同 IndexedDB 事务，事务 complete 才算本地确认完成；不提前删除或重新插字 |
| 失败 | 网络、服务端或本地确认落库失败时停下发送，不越过未确认依赖，也不删除后续 pending；原 ID、原更新用于重试 |
| 本机未落盘 | 保留可复制的内存原文，阻止自动 reload、send 或基线切换覆盖它；存储恢复后可持久化原操作，不改 ID |
| 切换起点 | 先查每笔 pending 的服务器提交结果；确认已经保存的操作只记回执，不再次转草稿；其余保留恢复草稿 |
| 原子切换 | 旧 pending 转草稿、移除已处理 pending 与安装新基线同事务；查回执期间队列变化则中止切换、重新读取，不漏掉新增输入 |
| 旧标签页 | 在每次写入事务内重查当前 generation/epoch，不把旧上下文写入新 pending；旧输入保留为草稿 |

| 到达时的情况 | 结果 |
| --- | --- |
| generation 相同且写权有效 | 普通断网按已持久化顺序自动合并 |
| 共享 epoch 已结束，即使后来又开放 | 不改标后重发，未提交原文保留草稿 |
| generation 已切换，包括主人的其他设备 | 查询提交结果后保存旧输入，再载入干净基线；保留原字符 ID 不使旧请求自动有效 |
| 原操作已提交但 ACK 丢失 | 重发原 ID/原更新或查询原回执，不重复正文、版本或备份副作用 |
| 本地落库或草稿事务失败 | 当前内存原文、原基线及待发内容不被自动替换；提示复制/下载或等待存储恢复 |

恢复草稿仅提供查看、复制与本人明确删除，标明日记、时间、原因、旧上下文及未进入当前正文。展示本人的待确认修改：插入可复制本人新增文字；删除展示原本打算删除的文字，不自动删除当前正文；替换展示前后内容，仅允许将本人新增部分作为恢复文本复制。草稿里的他人文字只作为上下文，不冒充本人的可恢复输入。

用户手动在当前正文定位并粘贴时，在当前授权下创建本人的新编辑；不自动重放旧更新、不一键覆盖全文、不恢复旧作者。加载新基线或复制草稿不自动清理草稿，只有本人明确删除才移除；正式编辑器和存储失败交互仍须验证。

主人的个人入口写权来自 owner 身份，搭档写权来自 live epoch；旧共享请求不能悄悄改成个人入口。即使 owner 身份仍有效，跨 generation 的旧请求也不自动豁免。

原因：依据 4、5，明确区分已确认、待确认和恢复数据；日志顺序、原子确认和发送锁保证依赖编辑不会被随机排序或多标签页并发打乱。

### D8：撤销与光标服从协同状态和版本上下文

个人撤销只跟踪本人的新编辑，不撤销搭档操作。重新开放后创建新的撤销上下文，不能跨基线继续 Ctrl+Z/Redo；旧内容通过获准历史查看。首次开放采用新 generation 时同样重置撤销，提示合并在 D5 的开放确认界面。

光标采用同一 generation 内的稳定相对位置，附带授权上下文，仅向具有当前读取权限的连接临时转发；冻结后不再传入私人光标。重开清理旧光标，不能在旧坐标上猜整数位置。当前端查看只读历史或“只看本人”模式时不发送正文编辑。

正文与光标可共用一条 WebSocket 连接，但消息分别处理。正文可靠持久化并补齐，光标只保留最新位置，可合并或丢弃过时的中间位置，不落 PG、不产生正文版本、未读或备份。普通光标移动不在正文批次的持久化队列后等待；断线或过期时清除临时位置。

光标位置依赖接收端已经取得的正文。若引用刚输入、尚未收到的新字符，暂存最新有效光标，待相关已提交正文到达后再准确显示；不为了消息先到而猜位置，也不绕过正文的提交后广播规则。补同步、拒绝或上下文切换时须重新判断或清理该临时位置。

已有字符的作者、写入时间和阅读身份不能因基线迁移变成“刚刚新写”，具体未读规则见 D15。完整未读功能后续交付，迁移必须保留其所需来源信息，不能以暂未实现为由永久丢失映射。

原因：依据 2、3、5，撤销和位置属于具体协同上下文；保留旧字不等于保留可直接继续运行的旧撤销栈。

### D9：PG 负责版本顺序、幂等和持久化确认

候选逻辑存储如下，不是已批准 SQL schema；精确字段、索引与迁移须待评审完成。

| 记录 | 保存责任 |
| --- | --- |
| Diary | owner/date 唯一、当前 version 与 generation 指针 |
| CollaborationGeneration | 干净基线、来源版本、状态格式与作者绑定；旧记录用于重建 |
| ClientBinding / CharacterMetadata | 原 clientID 的服务端作者绑定、设备写权、原字符 ID 区间的写入与接收时间；不重编号或新增种子作者 |
| DiaryCommit | 每批一个提交版本，从已接受状态重新编码的安全增量、generation、适用 epoch、操作者、原操作 ID/摘要与提交时间；保留逐笔来源，不把原请求包作为输出或重放数据 |
| CommitReceipt | 固定 batchId、有序操作成员及载荷绑定、原上下文与提交结果；服务于批重试及逐笔提交结果查询，operationId 查重仍有效 |
| ShareEpoch | baseline、期间、接收者、live/frozen、关闭版本；持久化授权边界 |
| ImmutableVersion | 重建冻结与获准历史所需的快照和增量引用，避免清理后只剩空指针 |
| Outbox | 与正文及共享边界同事务登记的备份事件；具体 worker 另行实现 |

同篇日记使用统一提交序列，不能让两个 API 实例各维护一份权威内存正文并覆盖 PG。遵循关系 ADR 锁序：先 diary owner 的 users 行，涉及当前关系时再 space/period，随后 diary/epoch；关系操作先按稳定顺序取齐 users 锁，再取空间和日记锁。范围批处理以稳定 diary ID 顺序加锁，不反向请求 users 锁。

服务端在锁内基于已提交状态检查 generation、epoch、会话与作者；增量、幂等结果、版本、作者/时间记录及 outbox 同事务提交。隔离候选状态验证失败或 PG 失败时，不提升房间内存状态，不广播“已提交”。

已确认的提交链如下，精确 SQL 和协议字段仍待 Q6：

1. 客户端持久化固定批次后发送，失败或重启沿用原 batchId、成员顺序和字节。
2. 服务端校验有效会话、资源访问与载荷绑定，先查询已提交回执；若是已完成的原批重试，按当前身份和原结果读取权限返回原结果，不要求旧授权重新变为 live。
3. 对尚未提交的新批，按统一锁序取得锁，重新检查写权、generation/epoch，从该日记已提交状态依次验证全部操作。活动状态缓存必须与 PG 版本匹配，不能每次从全部历史重放或以陈旧内存代替 PG。
4. 全部通过后，在一个 PG 事务内写入安全增量、一个新提交版本、原子批回执及逐笔映射、作者/时间记录与 outbox。任一校验或写入失败，整个新批不提交，无合法前缀成功。
5. PG 提交后返回完整批 ACK，并从已接受的安全状态生成获准广播；广播前仍检查授权。客户端原子记录回执和移除对应 pending 后，再推进后续批。

重复投递属于正常路径，不只在故障时出现：临时验证中服务端在 COMMIT 后断开连接，Chromium 未经应用即重发了同一请求。因此第 2 步的回执查询须在取得日记锁后执行（或再执行一次），否则同一批在两条连接上同时到达时，两边都可能看不到对方的回执；已提交批次在 epoch 关闭后重试，同样返回原结果。

operationId 的候选唯一范围为认证用户＋diaryId＋operationId，绑定原 generation、epoch 与载荷摘要。相同 ID 不同载荷拒绝。已提交重试经当前身份与原结果可读权限检查后返回原提交结果；明确返回其旧上下文，不能把旧 ACK 解释成当前新一轮保存成功。未提交且上下文过期则进入恢复路径。

提交后若进程在广播前崩溃，其他连接通过补同步取回已提交更新，不依赖内存广播队列作为唯一事实。快照/增量/冻结引用的格式须可校验且可重建；PG 不可用不降级为内存保存成功。

原因：依据 4，Yjs 更新幂等不能代替应用操作查重、事务提交或多实例一致性。

### D10：协议先校验身份和上下文，再解析编辑或返回版本

所有 HTTP/WS wire shapes 仅定义在 packages/contracts，HTTP 经 callApi；以下是消息职责提议，尚不安装 WebSocket 依赖、不生成空 API。

| 消息/入口 | 必需语义 |
| --- | --- |
| 打开个人日记 | 会话主人＋日期/日记 ID，返回当前获准正文、版本、generation、服务器作者信息 |
| 打开共享/冻结版本 | space、diary、epoch/version 上下文，服务端解析访问权；客户端不能指定 actor 或 author |
| 订阅/补同步 | 协议版本、diary、generation、适用 epoch、已知状态；只在授权匹配且 generation 相同时交换差量 |
| 提交更新 | 固定 batchId、原上下文及有序操作列表，每笔保留 operationId、Yjs 更新和写入时间；会话确定 actor，localSequence 不决定服务端权限；整批原子语义见 D13 |
| ACK / 查询提交结果 | 原 batchId、操作成员、唯一已提交 version 与原上下文；完整批成功，无部分成功 ACK；回执仅在 PG 提交后产生，支持逐笔查明所属原批结果 |
| 上下文变化/拒绝 | 停止或重开通知、稳定错误码与可重新打开的授权入口；先保存 pending，再切状态 |
| 光标 | 当前日记、generation 及适用 epoch 下的临时相对位置；独立处理最新位置，引用正文未到时暂存；不信任客户端声明的用户或作者 |
| 历史读取 | 明确请求版本，每次校验该版本权限；返回获准只读内容，不透传私人历史 |

WebSocket 握手检查会话与 Origin；每次写入重新检查有效会话与资源写权，不能只认连接建立时身份。共享补发和广播前重查授权，冻结后不得继续把私人更新放进旧连接发送队列；网络已发出的旧授权内容不能承诺收回。

错误采用现有 error 契约，分类恢复行为见“失败与恢复”；协议不兼容时保留本地输入并提示升级，不强制刷新。消息大小、二进制编码、精确错误码和兼容窗口见 Q6。无权资源与不存在资源不泄露私人日记存在性，日志不记录正文、原始更新、token 或恢复草稿。

原因：依据 2～5，连接认证、资源权限、共享轮次与协同状态分别检查，不能靠用户猜不到 ID 防护。

### D11：模块职责沿用现有边界

packages/collab 负责 Y.Text 模型、更新验证、作者来源与基线转换等纯协同逻辑，不依赖 app、PG、HTTP 或 UI；由首个真实消费者引入。contracts 只拥有 wire schemas；API 负责会话、授权、事务、版本读取与 socket；web 负责编辑器绑定、本地 journal、恢复提示与只读历史展示。

不从 prototypes 导入代码，不预建没有消费者的恢复适配器或配置开关；后续借用原型攻击与故障场景作为行为基线。具体 packages/collab 导出、测试项目与方向约束待实现设计收敛后确定，不能为了文档草稿改变 checks/ 或 CI。

原因：依据 6，协同算法、权限事务与界面各只有一个责任拥有者。

### D12：采纳前明确对 ADR-0006 的补充和取代范围

继承 Yjs 13.6.x 精确版本、纯文本 body、正常协同状态 gc:false、客户端普通更新、自写 ProseMirror 绑定、服务器作者检查、PG 提交后 ACK 与 outbox。隔离副本清理、服务端输出重编码、本地日志与小批发送属于本次补充设计。

采用的 generation 方案扩展为“一篇日记只有一个当前 Y.Text，旧起点只读归档”，保留原 ID 及作者绑定，隔离清理副本而不清理历史归档。客户端上传标准更新，但服务端不原样中继字节包；正常运行、清理副本与输出编码的边界必须写清。临时验证支持其可行性，不等于 ADR-0006 已涵盖新协议。

本文仍是讨论稿，因此不先修改旧 ADR 的取代关系或冻结正文。整份 ADR 采纳前须列清 ADR-0006 第 10～17 条受影响的部分：本地 journal、按 generation 保存的当前 Y.Text、保留原 ID 的基线、撤销重置、隔离副本 GC 和输出重编码；明确哪些是细化、哪些须双向部分取代，并更新 architecture 的生效决策。当前只记录用户已选择的路线，不把尚未讨论完的整份 ADR 改成已采纳。

原因：依据 6，产品规则已确认不等于实现路径已经采纳，草稿不能悄悄覆盖已采纳决定。

### D13：本地逐笔记录，网络自动按顺序小批发送

**用户已接受**：第一笔编辑本地持久化后立即发送；等待确认期间继续显示并持久化新输入；当前批次确认落库后，将此时已积累的 pending 按 localSequence 组成下一批。无需为了凑批人为增加等待时间，也不是每次按键都单独等待一次网络往返。

每笔保留原 operationId、原更新字节、写入时间、generation/epoch 与顺序；重试不得重新生成编辑或 ID。批次仅是传输组织，不等于五分钟历史点，也不改变服务端逐笔作者/依赖检查。只合并同账号、同日记和同授权/同步上下文的待发操作，不混入其他上下文。

同账号、同日记共用发送锁，每次只推进一个发送批次；服务器在候选状态中按操作顺序验证，已知前序依赖可以来自同批先前通过的操作。客户端只有取得相应 PG 提交回执并完成本地确认后，才推进后续依赖；失败保留未确认内容，不越过它发送后续批次。

**用户已确认整批原子提交**：一个新批对应一个 PG 事务、一个提交版本。某笔作者、上下文、依赖或数据校验失败，则整批不提交、不广播、不返回部分成功。逐笔 operationId、来源及写入时间继续保留，不因一个提交版本而合并作者或时间。

batchId、原上下文、成员顺序及载荷绑定必须在首次发送前持久化。重试和崩溃恢复沿用原批，不将可能已提交的成员重组进新批；同批 ID 不同成员或载荷被拒。ACK 丢失或本地确认失败时查询/重试原批，原提交只生成一次版本和 outbox。永久校验失败则停止该批及后续依赖，保留恢复内容，不无限重试。

批次同时受操作数和字节上限约束，大量离线编辑按持久化顺序拆成多个批，划分在固定批次形成前完成。具体阈值、单笔超限处理和协议细节在 Q6 设计与正式集成实测中确定，不凭估计写死参数。批量原子性与故障恢复的临时证据见[批次验证记录](../validation/diary-kernel-batch-2026-10-26.md)，不代表正式集成通过。

原因：依据 4、5，自动小批减少逐按键往返积压；原子提交与固定批次使失败、ACK 丢失和重启只有明确结果，避免部分保存和重新打包引入重复提交。

### D14：当前正文优先加载，增量重连与输入显示不等待历史

首次打开只加载当前获准正文及必要元数据，服务端可用有效基线和必要后续增量构建当前状态；历史列表分批加载，历史正文选择时再读取。不得把未获准的归档作为“快速加载”数据发往客户端。

同 generation 且权限有效的普通重连补齐缺少的更新，保留本地输入并按 D13 续发，不能用服务端旧全文覆盖待发内容。state vector 只参与差量计算，不代替提交回执。共享状态或 generation 变化时，先查提交结果并安全保留旧输入，再安装新获准基线；不能沿用普通差量流程绕过边界。大量离线内容有界分批发送。

历史预览独立加载，不替换当前可编辑运行状态或 pending。输入立即在本机显示，持久化和发送在后续推进；串行的是发送与确认，不阻止继续输入。本机落库失败的保留与保护沿用 D7。

正常输入路径避免每次按键复制、存储或传输全部正文，避免每批重放全部历史或用完整正文 ACK。基线清理在开放边界执行；历史分组和外部备份不阻塞输入与普通提交。内部快照频率、批上限及大文档参数由实测确定，性能验收见下文。

原因：依据 4～6，可靠保存不应以等待网络来限制打字；当前正文、历史预览和离线补发各自只加载所需数据，同时保持授权与恢复边界。

### D15：未读跟随原字符身份，跨轮次与设备保留阅读进度

沿用产品规则：当前活动页面实际可见约一秒才标已读；只记录当前用户自己的阅读进度，不向搭档提供阅读回执。按稳定字符 ID 或区间记录，跨设备取已读范围并集，不能用最大操作号或版本号清空所有未读。完整未读界面后续实现，本内核必须保留所需身份和时间映射。

重新开放不清空已读，也不把已有字符重新生成或标成刚写。以 A 的日记重新向 B 开放为例：

| 重新开放时的文字 | B 的未读结果 |
| --- | --- |
| 以前已读、当前仍保留的 A 文字 | 保持已读 |
| 以前未读、当前仍保留的 A 文字 | 保持未读 |
| 私人期间新增、当前仍保留且首次获准的 A 文字 | 算未读，原写入时间较早也不例外 |
| 私人期间写入后又删除的文字 | 不输出、不产生未读 |
| 删除旧字后重新输入的 A 文字 | 是新的字符，算未读 |
| B 自己的文字 | 不为 B 产生未读 |

已删除、在当前获准正文不再可见的文字从待阅读范围排除，避免无法完成的定位；这不伪造用户已经阅读。只对获准内容计算和返回未读，私人活动不进入对方计数或通知。范围可合并存储，不要求每个字符单独一行。原字符写入时间与服务端接收时间分别保留，不把首次授权时间伪装成写入时间。

原因：依据 3、5，文字写入与用户是否读过是两个维度；保留原 ID 同时避免整篇重新未读和漏掉刚刚开放的旧时间文字。

### D16：长期历史独立于 Google，备份任务绑定授权版本

历史点和冻结版本由服务端长期保持可重建，未连接 Google 也可读取获准历史。底层压缩保留正文、作者、原写入时间及访问边界，不能只依赖某个外部文件还存在。

outbox 事件绑定明确的日记、目标、版本与授权上下文，正文和共享边界同事务登记。worker 后续执行时仍解析目标的获准版本，不直接读取个人最新全文，也不把原始上传包或私人历史归档作为共享快照输出。停止共享后，旧目标最多输出仍获准的版本；重开可输出新起点及之后的获准变化，不补授中间私人历史。

例如共享在 V20 停止，私人编辑到 V21，旧共享备份不能输出 V21；V25 重开后可以备份获准的 V25，但不能顺带打包 V21 的私人历史或已经删除的私人正文。多个任务的执行不能让旧版本覆盖已完成的新版本，具体 worker 调度与凭据生命周期留在备份模块设计。

“已保存”来自 PG 提交，“历史点已形成”来自对已提交版本的分组引用，“已备份”来自指定目标版本真正完成备份，三者分别记录，不以任务已登记冒充上传完成。Google Doc 和恢复快照的完成语义沿用 ADR-0004 和产品规格。本次内核负责可靠登记任务，不实现 Google 上传。

原因：依据 3、4，异步执行不能扩大原授权，外部备份可用性也不能决定日记保存或服务端历史是否存在。

## 失败与恢复

| 情况 | 必须得到的结果 |
| --- | --- |
| 断网、超时或服务端暂时不可用 | 保留 pending，自动重连后查询/重试原批；不重新打包或越过未确认依赖 |
| PG 写入失败或提交前进程崩溃 | 不 ACK、不广播成功，客户端保留 pending；重连查重后补发 |
| 提交成功但 ACK 丢失 | 查回原版本，不重复插入；上下文变化也不将已提交输入误当未保存 |
| 批内作者、依赖或数据校验失败 | 整批拒绝，无合法前缀或部分成功；停止后续依赖，保留可查看和复制的恢复内容，不无限重试 |
| 冻结或干净基线构造失败 | 关系/范围/开放事务整体不成功，不先显示已停止或已开放 |
| 写入与停止共享并发 | 只存在提交前已进入冻结版本，或停止后拒绝两种结果 |
| 新基线加载时本机有旧 pending | 先持久化恢复草稿与上下文，成功后切换；草稿保存失败则保留内存原文并提示复制/下载 |
| 其他设备离线跨过重开 | 不等待其上线；恢复网络后保留旧输入供本人确认，不自动重放 |
| 会话失效、登出或账号切换 | 拒绝新写入，隔离/锁定旧账号缓存；不静默清理未上传文字 |
| 登录过期 | 暂停同步，提示重新登录同一账号；不把暂时无法认证当作内容已被拒绝或已保存 |
| frozen 重建失败 | 明确读取失败，不回退个人最新正文；修复版本引用后恢复读取 |
| 客户端协议或数据格式不兼容 | 保留待发原文，提示升级或恢复；不强制刷新、不尝试把旧增量当全文覆盖 |

同步界面区分“正在同步”“已保存到服务器”“暂时无法同步”“需要处理”，原因可展开，不在正常输入时反复弹窗；这些同步状态不代替 D7 的本地尚未落盘/仅本机保存标识。提交结果不确定时显示“正在确认保存结果”，先查回执，再判断是否转草稿，不把断线直接解释为未保存。

## 不变量

下列是本 ADR 拟保证的系统承诺，不是实现证据；历史只读、不支持回滚已确认，具体技术实现仍待评审。

1. 同主人同日期仅一篇个人日记，绑定、停止共享与重开不改变其身份或产生可独立编辑的正文分支。
2. 每个字符的作者由服务端可信来源决定，所有编辑入口和个人撤销不能修改搭档文字，基线迁移保留原作者；历史版本只读，不提供回滚例外。
3. 同一 generation 中的合法并发与离线输入最终合并，旧全文和只读历史不能覆盖当前输入。
4. 已保存只在增量、幂等、版本与 outbox 成功 PG 提交后确认，未验证或未提交内容不作为已提交正文广播。
5. 停止共享后搭档保留最后获准冻结版本，不再取得后续私人更新，也不能继续写入。
6. 首次开放与重开只授权当时当前正文及本轮后续版本，不泄露之前的私人历史或已删除私人文字。
7. 重开不扩大旧共享轮次的历史权限，旧轮已获准的冻结记录保留且不可变。
8. 重开后撤销从新协作起点累计，个人撤销和重做只影响自己的新操作。
9. 旧 epoch 或 generation 的未提交更新不自动进入新一轮，包括主人的其他设备；原始输入及上下文保留为仅查看、复制和明确删除的恢复草稿，不自动重放或覆盖当前正文。
10. 首次开放和重开先预览范围、确认本页面待发内容已提交，以服务器执行时已提交状态为起点，不等待所有其他设备上线；开放与停止只在服务端成功后显示成功。
11. 同 operationId 重试不会重复提交或跨轮重新生效，同 ID 不同载荷被拒，已提交但丢失 ACK 的操作有可查询结果。
12. 握手与每次写入均校验有效身份和资源权限，读取、同步、历史与导出遵守同一获准版本边界。
13. 基线清理保留当前字符原 ID、作者及原写入时间，不把已有文字当新增；新实例重载、干净状态输出重编码与旧上下文拒绝共同隔离私人删除内容。
14. 共享变更与写入竞争具有唯一事务边界，失败不产生半冻结、半开放或伪保存成功。
15. 历史按服务端正文提交时间每五分钟分组，两分钟停笔后引用最后提交版本补末点、同版本不重复；共享边界独立，右侧只读预览不被新编辑切走，列表及计数不泄露私人活动。
16. 历史点及获准冻结版本长期保留、不自动过期；底层压缩不破坏获准正文、作者、时间和历史重建。
17. 本地序号分配、计数递增与 pending 插入原子完成，跨标签页按持久化顺序推进，不按随机 ID 发送。
18. 本地确认与移除对应 pending 同事务；转草稿前核对原提交结果，草稿与新基线同事务切换，队列变化或未落盘输入阻止覆盖。
19. 网络将同上下文的已持久化编辑自动按序小批发送，保留每笔身份与原更新；后续依赖批次等待提交回执和本地确认，不影响输入与本机继续持久化。
20. batchId、上下文和有序成员在首次发送前持久化；一个新批只有一个原子 PG 提交版本，任一笔失败整批不提交，无部分成功；原批重试不重复版本或副作用。
21. 光标是独立处理的临时消息，不产生正文提交、未读或备份；引用正文尚未到达时等待正文，只有获准连接可接收有效上下文的位置。
22. 已读范围跟随原字符身份跨设备合并、跨共享轮次保留；首次获准且尚未读过的对方可见文字产生未读，已删除文字不留下不可定位未读。
23. 历史在未连接 Google 时仍长期可重建；备份任务绑定版本及授权，不能读取个人最新状态泄露私人变化或补授私人历史，任务登记不代表备份完成。
24. 当前正文加载不要求取得全部历史，普通重连同起点增量合并；历史预览和新基线加载不丢失当前输入或待发内容，输入显示不等待 PG、历史或备份。
25. 暂时失败按原批恢复，登录失效暂停同步，永久校验失败停止后续依赖；升级、重连和结果查询均保留本地输入，只有确定提交结果后才报告保存或安排恢复。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 重新开放直接发送完整旧 Yjs 状态 | 保留原字符 ID、光标和撤销，改动最少 | 违反依据 3，gc:false 下可能包含私人期间已删除的内容，仅隐藏历史界面不够 |
| **隔离副本 GC 清理并保留原 ID** | 保留作者与位置关系，避免全量重编号 | 已选择，17 项临时检查（含 1 项完整性检查）支持；接受仍可推断结构信息的边界，PG/客户端正式集成继续验证 |
| 重建全部可见字符并分配新 ID | 能进一步隔离历史 ID/时钟痕迹 | 当前不需要隐藏所有结构痕迹，作者/位置/时间迁移成本更高；保留作需求改变后的比较方案 |
| 手工过滤改写 Yjs 二进制内部结构 | 可以精确选择原结构 | 需自行维护引用与删除依赖，当前已有 GC 清理路线的验证依据，不为首版增加该责任 |
| 仅由自动 Yjs 持久化 provider 管理全部本机状态 | 接线较少，能恢复本机文档 | 不独立解决 PG 回执、原子 pending 移除、跨起点转草稿和有序发送；采用统一应用日志 |
| 每个按键单独等待 ACK 再发一笔 | 顺序容易理解 | 网络较慢时积压，采用同上下文自动小批发送；依赖顺序和确认边界仍保留 |
| 批内合法前缀先提交、后续单独恢复 | 可保留部分合法操作，减少某些重试 | 当前选整批一个版本，避免部分 ACK、重组和依赖恢复增加结果分支；代价是单笔拒绝阻止整批及后续依赖 |
| 光标随正文一起落库和排队提交 | 单一流程容易追踪 | 光标只需最新位置，持久化增加等待与历史噪声；分别处理消息，并在显示时等待所引用正文 |
| 重开清空已读或按最新版本号统一标已读 | 状态更少 | 前者把已读旧字全算新增，后者漏掉未看到的插入；采用原字符范围合并 |
| 每位搭档维护独立正文副本 | 不同关系天然分开 | 首版只有固定搭档；增加主人正文多份写入和合并责任，不符合依据 1、6 |
| 重开后自动把旧 epoch 更新换标再提交 | 用户恢复操作少 | 违反依据 3、5，旧授权与旧字符定位不能通过修改 ID 自动变成新授权 |
| 全文快照最后写入覆盖 | 协议简单 | 违反依据 2、4、5，会覆盖并发输入，不能保留真实字符来源 |
| 首版提供整篇或按作者回滚 | 能更快捷地恢复旧内容 | 用户最新决定历史只读；回滚增加作者权限、并发、撤销与待发队列的复杂度，首版不纳入 |
| 每次重开永久丢弃旧 pending | 新状态最容易载入 | 违反依据 5，合法本地输入不能为简化同步而静默丢弃 |

## 风险与代价

- 干净基线与本地日志已有临时验证支持，但未验证正式 PG、WebSocket、ProseMirror、Firefox/WebKit 或完整共享链路；固定批次的临时验证使用了真实 PG 与 Chromium IndexedDB，但服务端没有 Fastify、WebSocket 或正式会话。不能将这些检查算作产品不变量已实现。
- 保留原 ID 和删除占位仍暴露部分时钟、长度等结构信息；当前保证未授权正文与版本内容隔离，不宣称历史活动规模不可推断。
- 清除新一轮撤销上下文会失去快捷撤回旧操作的能力，首次开放与重开的说明并入确认界面；旧内容仍只读可查。
- 保留服务器历史、冻结引用、增量与来源映射增加存储；任何压缩或清理策略都需单独证明版本可恢复。
- 跨重开边界的离线输入可能需要手动恢复，普通断网不应退化为手动复制；提示必须区分已提交、待发和草稿。
- 历史只读意味着无法一键恢复旧正文；可以查看旧内容，当前编辑仍受作者保护。未来需要回滚时另行设计，不预留首版回滚协议或权限分支。
- 私人阶段正文重新出现于当前正文时，经确认开放可以被搭档看到；保证的是不泄露未授权历史，不判断当前文字是否在语义上提及私人经历。
- 整批原子拒绝可能阻止其中原本合法的输入；必须保留恢复内容，不能以无限重试或跳过依赖掩盖失败。批大小需结合性能与恢复实测确定。
- 光标传输独立不等于始终能立即准确显示；刚输入位置受对应正文到达时间限制。延迟目标只在注明的测试条件下验收，不是网络抖动、离线或故障时的硬保证。

## 验收标准

未来正式测试标题使用 `[adr:diary-collaboration-kernel#N]` 覆盖对应不变量；文档存在和检查通过都不算行为通过。

| 场景 | 不变量 | 所需证据 |
| --- | --- | --- |
| K1 日记身份与日期 | 1 | API＋真实 PG：未绑定可写、owner/date 并发唯一、解绑重开身份不变；DATE-01～06 |
| K2 作者保护与基线迁移 | 2、13 | 纯内核攻击测试＋浏览器：保留 B 字符作者、时间、顺序；A 的普通编辑不能删改 B，伪造设备 ID 被拒；EDIT-01～12 |
| K3 增量与正常离线 | 3 | 多客户端与浏览器：并发插入/删除、Unicode、composition、重复/乱序、同账号设备恢复；SYNC/SAVE 对应场景 |
| K4 保存确认与故障 | 4、11、20、25 | PG＋进程故障：提交前无 ACK/广播，提交后 ACK 丢失只保存一次，数据库失败保留 pending；先查原批回执，区分未知结果、暂时失败和永久拒绝 |
| K5 冻结与事务竞争 | 5、7、14 | 独立 PG 连接＋真实 socket：取消/解绑与写入竞争、冻结失败回滚、断线补发不越权、原冻结记录不变 |
| K6 私人历史隔离 | 6、7、12 | 实际载荷解码与历史 API：私写 V11 后删除，重开 V12；B 在基线/删除历史/版本/导出中均不能取得 V11 私人文字，仅获原有历史及新一轮获准版本 |
| K7 撤销新起点 | 8 | 编辑器＋浏览器：重开 Ctrl+Z/Redo 不能触及基线与上一轮操作，不能撤销搭档文字 |
| K8 跨边界本地恢复 | 9、10、11、25 | A1/A2/B 真实 IndexedDB 与 socket：范围预览和撤销说明、发起端先保存、其他端离线不阻塞开放；停止不等搭档；失败不显示成功；旧输入按插入/删除/替换进入查看复制草稿，明确删除前保留；已提交但未 ACK 的输入不重复恢复 |
| K9 会话与资源隔离 | 12 | API＋socket：退出/撤销后每次写入拒绝、错误 Origin、第三人、猜版本 ID、历史及补同步越权均被拒；auth ADR 不变量 8 |
| K10 来源与历史可重建 | 7、13、16 | PG＋跨 generation 重建：原 ID、作者及原写入时间不变，长期冻结与获准历史在重启后仍可读，不制造新文字未读 |
| K11 历史展示与长期保留 | 12、15、16、24 | 组件＋浏览器＋PG：服务端时间五分钟分组、两分钟停笔最后版本去重、独立共享边界；最近在前的按需列表、空状态、时区、原作者颜色和完整只读预览；新更新不切走预览，返回不丢输入；无私人元数据泄露，长期准确重建 |
| K12 本地因果顺序与原子日志 | 9、11、17、18 | 正式 IndexedDB＋严格服务端：反向 UUID、插入后修改/删除、ACK 丢失与事务中止、跨标签依赖，拒绝未解决引用，失败不越过队首；本地写入失败保留原文、禁止自动切基线 |
| K13 自动小批发送 | 3、4、11、17、18、19、20 | 已有临时验证证据，正式以 PG＋IndexedDB＋socket 复验：第一批即时、后续按序收集，固定批在发送前落库；中途拒绝整批零提交，无部分成功 ACK；提交/ACK/本地确认各阶段崩溃和重试只产生一个版本与副作用；多标签、长离线链与切起点不误确认、不越过依赖 |
| K14 正文与光标协调 | 12、21 | 双浏览器＋socket：普通移动不等待 PG，过时位置合并、断线清理；引用新字符的光标待获准正文到达再定位，关闭/重开不泄露私人位置；分别测移动与边输入边定位 |
| K15 跨轮次阅读身份 | 12、13、22 | 字符范围模型＋后续阅读集成：重开已读旧字不重置，未读旧字及首次开放的私人新增仍未读；删除排除、重新输入是新字、本人的字不自生未读；活动页可见约一秒、跨设备范围并集，不公开回执 |
| K16 历史与备份边界 | 4、6、7、16、23 | PG/outbox＋后续 worker 集成：未连接 Google 仍可读历史；V20 停止、V21 私改、V25 重开，旧目标不取 V21，新目标不带私人历史；旧任务不覆盖新版本，状态不混淆提交、历史点和真正备份完成 |
| K17 加载与性能 | 3、19、24 | 正式编辑器＋PG＋WebSocket：打开当前不加载全部历史，普通重连安全增量补齐，跨起点保留原输入；长日记、长期编辑、离线积压及双方输入按下述口径实测，记录环境和延迟分布 |

性能目标由用户确认，尚未实测，不是已有保证。以真实编辑器、PG 和 WebSocket 测量，记录设备、浏览器、文档规模、历史积累、并发、网络设置、样本量及 p95/p99；至少包含十万字符日记。网络条件稳定、双方各约 500ms RTT 时测远端指标，不能把两端网络配置或 RTT 与单程延迟混用。

| 指标 | 验收目标与口径 |
| --- | --- |
| 本机输入可见 | 从有效正文输入到本机可见绘制，p95 ≤ 50ms、p99 ≤ 100ms；不等待本机落库、网络或 PG |
| 远端正文可见 | 双方各约 500ms RTT，从发送端有效输入到接收端正确显示，p95 ≤ 2 秒；包含本机日志、排队、校验、PG 与网络 |
| 普通光标移动 | 双方各约 500ms RTT，已知正文上的位置变化到接收端显示，p95 ≤ 1 秒；包含位置合并等待 |
| 边输入边移动光标 | 单独记录新正文与光标最终正确对应的延迟；不得只测光标消息抵达而忽略正文依赖，暂不编造独立数值目标 |

这些是注明条件下的统计目标，不承诺离线、网络抖动、丢包或故障时的硬上界。临时内存清理耗时和本地日志检查不能替代该性能验收；批上限、内部快照频率、首次加载与长离线补齐的预算在实测后收敛。

代表性端到端链路：A/B 在 E1 编辑到 V10 → A 停止共享 → A 私写秘密形成 V11 并删除为 V12 → A1 保留离线 pending → A2 保存本机输入并确认重开 E2 → B 仅取得干净当前正文和新一轮历史 → A1 联网保存恢复草稿 → 本人确认选择加入当前正文 → 验证作者、持久化、旧冻结记录、撤销及载荷隐私。
