# 邀请可以按对方的 Google 邮箱定向发出，对方用这个邮箱登录后在应用里看到并接受；不发邮件，发起方在接受前得不到关于对方的任何信号

- 状态：提议
- 日期：2026-11-18
- 决策者：Ray
- 范围：领域
- 关联：依赖 spaces-and-invitations；依赖 authentication-and-sessions；依赖 email-reminders；取代 spaces-and-invitations 的 D8 不绑定邮箱的部分

发起方在「设置 → 搭档」填对方登录 Google 用的邮箱（可同时选自己的共享范围），服务端存一条**定向邀请**：收件邮箱、发起方确认的范围、七天有效。**不发邮件。** 对方用这个邮箱的 Google 账号登录后（不管在浏览器还是已安装的 PWA 里），`GET /api/binding` 多返回"寄给我的邀请"，首页顶部出现横幅"{发起方} 邀请你一起写日记 · 查看"，点开是现有的 `/join` 确认页与接受逻辑；对方也可以"不接受"，这条邀请从此只在 TA 那边消失。发起方看到"已邀请 {邮箱}，等 TA 登录"，可以撤销、重新发出，不管这个邮箱有没有账号、登没登录、看没看到，看到的都一样，直到对方接受。邮箱去掉首尾空白、转小写后与 Google 已验证的登录邮箱精确比较，不合并 Gmail 的点号和 `+` 别名。每人仍只有一条未关闭邀请：链接或定向二选一，发新的就关旧的；定向邀请每位发起方滚动 24 小时内至多 5 次。链接邀请原样保留，作为对不上邮箱时的备用。

本文改变[关系 ADR D8](./2026-10-25-spaces-and-invitations.md#d8邀请七天有效可撤销一次性不绑定邮箱) 的"不绑定指定邮箱或账号"；D8 其余规则与关系 ADR 不变量 3（七天、可撤销、可轮换、至多成功一次）不变。本文不负责：发邮件或任何站外通知（D7）；更换搭档与误绑纠正；按邮箱合并账号或改动认证层；拉黑某位发起方；邀请历史列表。

## 背景与问题

邀请现在只有 `/join#token=…` 一种：发起方复制链接，用聊天软件发给对方。对方在聊天软件里点开，进的是系统浏览器而不是已安装的 PWA，两边的登录态不共享，于是要在浏览器里再登录一次，接受之后回到 PWA 又是未绑定的样子，要刷新或重进。Ray 希望对方在自己常用的应用里登录后就看到邀请并接受，链接只作备用（[F-06](../future-features.md#f-06站内邀请不靠链接)）。

关系 ADR D8 当初"不绑定邮箱"的理由是首版手动分享就够、不引入邮件设施或邮箱身份匹配。按邮箱定向就要做邮箱身份匹配，带来三个新问题：发起方会不会借此探出某个邮箱有没有账号；填的地址和对方 Google 账号的写法不同怎么办；陌生人能不能把你的邮箱填进来反复打扰你。邮件提醒（[email-reminders](./2026-11-17-email-reminders.md)）已采纳，但它只给每个用户自己的登录地址发信；"你有一份邀请"会把发信对象扩大到别人随手填的地址。

## 决策依据

1. 对方在自己正用着的应用里（浏览器或 PWA）登录后就能看到邀请并接受，不必经过外部链接。
2. 发起方在对方接受之前，得不到这个邮箱有没有账号、登没登录、看没看到、是否忽略的任何信号（与关系 ADR D7、SHARE-11 不制造阅读回执的边界一致）。
3. 只有 Google 已验证的、与发起方所填一致的登录邮箱能看到和接受这份邀请，不会配给另一个人。
4. 关系 ADR 不变量 3 不变：七天有效、可撤销、可轮换、至多成功消费一次；打开、登录、预览都不绑定，接受仍须本人在确认页核对账号并明确确认。
5. 不向应用之外发任何东西：用户填的地址不成为任何邮件的收件人。
6. 沿用现有的邀请表、绑定事务、拒绝顺序、`/join` 确认页与错误码；登录邮箱仍只经 `auth/` 读出（认证 ADR 不变量 10），领域 `users` 表仍不存邮箱（认证 ADR 不变量 1）。
7. 收到不想要的邀请的人能让它消失，发起方也不能无限次地重发打扰。

## 决策

### D1：每人仍只有一条未关闭邀请，它要么是链接，要么是定向邮箱

`POST /api/binding/invitations` 的请求多一个可选的 `recipientEmail`。没有它，行为与现在完全相同（生成链接，返回一次 token）；有它，生成定向邀请：不生成 token，响应的 `token` 恒为 `null`，邀请行存收件邮箱。两种邀请共用 D8 的生命周期：

| 动作 | 结果 |
| --- | --- |
| 新建任一种邀请（含"重新发出"、改填另一个邮箱、改用链接） | 关闭本人上一条未关闭邀请（记为撤销），再建新的一条；新的一条重新计七天 |
| 同一 `requestId` 重试 | 返回已存的那条（含 `recipientEmail`），`token: null`；`recipientEmail` 或范围与原请求不同为 `VALIDATION_FAILED` |
| 本人已有当前绑定 | `ALREADY_BOUND`（同现在） |
| 填的是本人自己的已验证登录邮箱 | `SELF_INVITE`；这是本人自己的地址，拒绝不泄露任何人的信息 |
| 本人已与另一人有永久空间（已解绑） | 允许建，与链接现在一样；对方接受时得到 `PARTNER_FIXED`（D3） |
| 撤销 | 同现在：按 `inviteId` 只撤本人的那一条 |

"重新发出"不是改原来那一条，而是用新的 `requestId` 建一条同邮箱的新邀请，表单预填原邮箱与原范围，发起方再按一次才发出；这样它仍是一次明确确认（关系 ADR D5），也计入 D6 的次数。

`InvitationSummary` 多一个 `recipientEmail: string | null`（链接为 `null`），只出现在发起方本人的 `GET /api/binding.invitation` 与创建响应里。它的 `state` 仍只有 `pending | expired | revoked | used`，没有"已查看""已忽略"之类的状态（D4、依据 2）。

为什么：依据 6。首版固定搭档，一个人本来就只邀请一个人；一条未关闭邀请让 D8 的部分唯一索引、轮换语义和"绑定关闭双方其他邀请"原样适用，发起方页面也只有一种状态要说。链接与定向并存会让两个可能不同的人同时握有可接受的邀请，见备选方案。

### D2：收件邮箱去首尾空白、转小写后保存，与同样处理过的 Google 已验证登录邮箱精确比较

- 校验：Zod 的 email 格式，最长 254 个字符；不合法为 `VALIDATION_FAILED`，错误不回显输入。
- 规范化只有一步：`trim()` 后 `toLowerCase()`，由 `bindings` 服务里的一个函数完成，写入与比较都经过它。`First.Last@Gmail.com` 与 `first.last@gmail.com` 相同；`firstlast@gmail.com`、`first.last+diary@gmail.com`、`first.last@googlemail.com` 都与 `first.last@gmail.com` **不同**。
- 比较的另一边是认证层记录的登录邮箱，且 `emailVerified` 为真。`auth/email.ts` 的 `createAddresses` 新增 `verifiedEmailOf(userId)`：未验证或未知时返回 `null`，这时这个人匹配不到任何定向邀请。`bindings` 服务通过依赖注入拿到它，不读 `auth_*` 表；邮箱不复制进 `users`。
- 输入框下写明："填 TA 登录 Google 用的完整邮箱。不会发邮件，TA 用这个邮箱登录后会在应用里看到。对不上时可以改用邀请链接。"

为什么：依据 3。去点号、去 `+` 只对 `gmail.com` 成立，Google Workspace 等其他域名的点号是有意义的；做错一次就可能把邀请配给另一个真实的人，而对不上的代价只是改用链接。只忽略大小写，是因为手机输入法常把首字母自动大写，邮箱域名本身也不区分大小写。

### D3：`GET /api/binding` 给收件人列出寄给自己的未关闭邀请，包括此刻接受不了的

`BindingResponse` 多一个字段 `invitationsForMe: IncomingInvitation[]`：

```typescript
type IncomingInvitation = {
  id: UUID;
  inviter: UserSummary;        // { id, displayName }，不含邮箱
  expiresAt: string;
  mode: 'new' | 'restore';     // 与 preview 相同：这两人已有永久空间就是 restore
};
```

列入条件：收件邮箱等于调用者 D2 规范化后的已验证登录邮箱；不是调用者自己发的；未撤销、未接受、未到期；调用者没有忽略过它（D4）。按创建时间从新到旧。

**接受不了的也列出**：调用者此刻有当前绑定、调用者或发起方已与另一人有永久空间时，邀请照样列出；点开后 `/join` 的预览给出现有的拒绝（`ALREADY_BOUND`、`PARTNER_FIXED`）与现有文案，并提供"不接受"。这样发起方说"我邀请你了"时，对方能看到这份邀请和接受不了的原因，而不是什么都找不到。只有邮箱对不上（例如对方用另一个 Google 账号登录）时什么都不显示，因为那份邀请本来就不是寄给这个账号的。

不出现在收件人响应里：发起方的邮箱、发起方确认的范围（关系 ADR D7）、收件邮箱本身。发起方那边的 `invitation` 字段不受收件人任何动作影响。

为什么：依据 1、3。`GET /api/binding` 已在每个登录页面读取、聚焦时刷新（关系 ADR D12），收件人登录后无需新的轮询或推送就能看到。

### D4：定向邀请按邀请 ID 预览、接受和忽略，服务端以调用者的已验证邮箱确认收件人

- `POST /api/binding/invitations/preview` 的请求改为 `{ token } | { inviteId }`；`POST /api/binding/invitations/accept` 改为 `({ token } | { inviteId }) & { sharingSelection }`。带 `token` 的行为完全不变。
- 带 `inviteId` 时，先确认这是一条定向邀请、收件邮箱等于调用者的已验证登录邮箱，且调用者没有忽略过它；任何一条不满足都返回 `INVITE_INVALID`（404），与未知 token 相同，不返回发起方名字。所以猜到或看到别人的 `inviteId` 什么也得不到；链接邀请的 ID 也不能按 ID 接受，定向邀请没有 token，也无法从链接那条路接受。
- 之后的拒绝顺序（`INVITE_EXPIRED`、`INVITE_REVOKED`、`INVITE_USED`、`SELF_INVITE`，再 `ALREADY_BOUND`、`PARTNER_FIXED`，再 `SHARE_OPEN_FAILED`）、绑定事务（锁双方 users 行、重查邀请、找或建空间、新期间、双方当前绑定、消费本条并关闭双方其他未关闭邀请、双方确认的范围开放日记）与链接完全相同。
- 新接口 `POST /api/binding/invitations/:inviteId/dismiss`，body `{}`，返回 `{ dismissed: true }`：只对收件人有效，条件同上，不满足返回 `NOT_FOUND`。在 `withUsersLocked([调用者])` 里写 `dismissed_at`；已忽略、已关闭或已过期的邀请再忽略不报错、不改动。忽略后这条邀请不再出现在 TA 的 `invitationsForMe`，按 ID 预览或接受得 `INVITE_INVALID`。
- 忽略不关闭邀请：发起方看到的仍是 `pending`，直到七天到期或自己撤销。发起方重新发出是一条新的邀请，会再次出现在对方那边，受 D6 的次数约束。

为什么：依据 2、3、4、7。按 ID 而不是新造一种凭证，因为身份已经由会话和已验证邮箱证明；ID 本身不是秘密，所以它可以出现在地址栏，不需要链接那套 fragment 与 sessionStorage 处理。忽略做成只对收件人可见的标记，是唯一既让对方摆脱邀请、又不让发起方得知"这个邮箱有人登录过"的做法。

### D5：网页：首页横幅打开 `/join?invite=<id>`，发起方在「设置 → 搭档」按邮箱邀请

收件人：

- 首页顶部（与备份横幅同一位置，排在它下面）每份 `invitationsForMe` 一行："{displayName} 邀请你一起写日记 · 查看"，`restore` 时为"{displayName} 邀请你恢复你们的空间 · 查看"。只在首页显示，不进导航栏圆点。
- "查看"打开 `/join?invite=<id>`。`JoinPage` 见到 `invite` 参数就按 ID 预览，显示与链接相同的确认页（当前账号、邀请者、新建或恢复、首版固定搭档提示、范围编辑器、"接受邀请"），另加"不接受"：调用 dismiss，回首页。预览得到拒绝时显示现有文案，同样提供"不接受"。
- `inviteId` 不写入 sessionStorage：未登录时 `/join?invite=…` 只提示登录，登录回首页后横幅会再次出现。`#token=…` 的处理（关系 ADR D12）不变。

发起方（`RelationshipPanel`，`/partner`）：

- 默认是"按 Google 邮箱邀请"：邮箱输入框、D2 的说明、范围编辑器、"发出邀请"。下面一行"或者生成邀请链接"切到现有的链接流程。
- 发出后，不管这个邮箱有没有账号，都显示同一句"已发出邀请"，随后状态为"已邀请 {邮箱}，等 TA 登录 · {日期} 前有效"，带"撤销"和"重新发出"；过期后为"给 {邮箱} 的邀请已过期"，带"重新发出"。
- 首页的 `PartnerCard` 在有定向邀请时写"已邀请 {邮箱}，{日期} 前有效"，链接邀请时文案不变。
- 撤销、改用链接、改填邮箱都按 D1 关闭旧的一条。

为什么：依据 1、6。横幅复用确认页，接受仍要经过同一次范围确认与账号核对。

### D6：每位发起方滚动 24 小时内至多创建 5 条定向邀请

创建定向邀请时，在已持有的调用者 users 行锁内数本人最近 24 小时创建的定向邀请（不论现在是否已撤销、已接受）；已有 5 条则拒绝，返回新错误码 `INVITE_LIMIT`（429，恢复类别 `show`），界面写"24 小时内已经发出 5 次邀请，请稍后再试，或改用邀请链接"。同一 `requestId` 的重试返回已存的那条，不新建行，不计数；链接邀请不计数。不对收件邮箱单独限额：那需要告诉发起方"这个地址被别人邀请过太多次"，违反依据 2。

为什么：依据 7。D1 已经保证同一时刻只有一条，限额只针对"对方忽略后反复重发"和轮流填一串邮箱；5 次留出填错两三次的余地。在锁内计数，并发创建也不会超过。

### D7：定向邀请不发任何邮件，也不进入邮件提醒

服务端不向收件邮箱发信，邮件提醒的三类邮件不包含"你有一份邀请"，也不因定向邀请产生任何 outbox 任务或 worker 动作。对方只能经发起方自己告诉 TA（"我在应用里邀请你了，用这个邮箱登录"）。

为什么：依据 5。发给用户随手填的地址，会让任何人能借本站给任意邮箱发带自己名字的信，影响发信域名的信誉；邮件提醒只发给用户本人的登录地址、只写本人能在应用里看到的内容，这条边界保持不变。

### 数据与接口

迁移（编号见落地顺序，名称 `directed_invitations`），只改 `binding_invitations`：

| 改动 | 内容 |
| --- | --- |
| `token_hash` | 去掉 `not null`，唯一约束保留（PG 的唯一约束允许多个 null） |
| 新列 `recipient_email text` | 可空；D2 规范化后的地址 |
| 新列 `dismissed_at timestamptz` | 可空；收件人忽略的时刻 |
| CHECK `binding_invitations_one_way` | `num_nulls(token_hash, recipient_email) = 1`：链接与定向恰好其一 |
| CHECK `binding_invitations_dismiss_directed` | `dismissed_at is null or recipient_email is not null` |
| 部分索引 `binding_invitations_recipient` | `(recipient_email) where revoked_at is null and accepted_at is null`，供 D3 查询 |

已有的行都有 `token_hash`，满足新 CHECK，不需要回填。`binding_invitations_one_open`、`binding_invitations_closed_once` 等约束不变。表仍只由 `src/store/relations.ts` 写。D6 的计数直接查本表，不另建表或索引（每人每天至多几行）。

contracts：`CreateInvitationRequest` 加可选 `recipientEmail`；`InvitationSummary` 加 `recipientEmail: string | null`；`BindingResponse` 加 `invitationsForMe`；新增 `IncomingInvitation`；`PreviewInvitationRequest`、`AcceptInvitationRequest` 改为上面的联合（仍是 strict object，不接受多余字段，也不接受 token 与 inviteId 同时出现）；新路由 `dismissInvitation`；新错误码 `INVITE_LIMIT`（429，`show`）。所有相关响应仍 `no-store`，写接口仍校验 Origin。收件邮箱不写入日志。

## 失败与恢复

| 情况 | 结果与恢复 |
| --- | --- |
| 创建已提交但响应丢失 | 同 `requestId` 重试取回那条（含 `recipientEmail`），不计次数 |
| 对方用另一个 Google 账号登录，或邮箱写法不同（点号、别名） | TA 什么都看不到；发起方那边不变。由发起方改填正确邮箱或改用链接（都会关闭旧的一条） |
| 对方的 Google 账号邮箱未验证 | 同上，匹配不到 |
| 对方打开确认页时，邀请已被撤销、轮换或到期 | 接受得 `INVITE_REVOKED` / `INVITE_EXPIRED`，显示现有文案；刷新后横幅消失 |
| 接受已提交但响应丢失 | 同现在：`GET /api/binding` 查到当前绑定；邀请已消费，不能再建期间 |
| 忽略的响应丢失 | 重试忽略，结果相同 |
| 对方同时收到两位发起方的邀请，接受了其中一份 | 绑定事务只关闭双方各自发出的邀请；另一位发起方的那份仍列出，接受得 `ALREADY_BOUND`，可以忽略，或等它到期 |
| 发起方 24 小时内已发 5 次 | `INVITE_LIMIT`；链接邀请仍可用 |

## 不变量

1. 每位发起方任一时刻至多一条未关闭邀请，它要么只有 token 摘要、要么只有收件邮箱；新建任何一种都先关闭旧的一条。
2. 定向邀请只对已验证登录邮箱（去首尾空白、转小写后）与收件邮箱完全相同的账号列出，也只有这个账号能按 ID 预览、接受和忽略；其他账号用这个 ID 得到与未知邀请相同的拒绝，得不到发起方的名字。
3. 发起方在对方接受之前，从任何响应里得到的邀请状态与内容，都与收件邮箱是否有账号、是否登录、是否看到、是否忽略无关。
4. 定向邀请七天有效、可撤销、可轮换、至多成功消费一次；列出、打开横幅与预览都不绑定。
5. 按 ID 接受与按 token 接受使用同一拒绝顺序和同一绑定事务：新期间、双方当前绑定、本条消费与双方其他邀请关闭、双方确认的范围一起提交。
6. 收件邮箱只出现在发起方本人的邀请元数据里，不出现在收件人或任何第三人的响应、`UserSummary` 与日志中。
7. 忽略只改变收件人本人看到的：被忽略的邀请不再列给 TA、不能再被 TA 接受，发起方看到的状态不变。
8. 每位发起方在任意 24 小时内至多创建 5 条定向邀请；同一 `requestId` 的重试与链接邀请不计数。
9. 定向邀请不产生任何邮件、outbox 任务或站外通知。
10. 业务代码只经 `auth/` 得知登录邮箱及其验证状态；未验证的登录邮箱匹配不到任何定向邀请。

## 备选方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 定向与链接各一条，可以并存 | 对方用错账号时链接还在，发起方不必切换 | 两个可能不同的人同时握有可接受的邀请；部分唯一索引要按类型拆开，发起方页面同时说两种状态；违反依据 6，而依据 1 已由"改用链接"覆盖 |
| 定向邀请同时附带链接 | 一次操作两种送达，最省事 | 持有链接的任何人都能接受，"定向"就只是送达方式、不再是限制，违反依据 3 |
| Gmail 去点号、去 `+` 别名 | 写法不同也能对上 | 只对 `gmail.com` 成立，规则一旦用错就把邀请配给另一个真实的人，违反依据 3；对不上的代价只是改用链接 |
| 完全精确，大小写也区分 | 规则最严 | 手机输入法自动大写首字母就对不上，而邮箱域名本身不区分大小写；严格换不来依据 3 的任何保护 |
| 接受不了的邀请（对方已有搭档等）不列出 | 已绑定的人不被无关邀请打扰 | 发起方说"我邀请你了"时对方什么也找不到，也不知道原因，违反依据 1；打扰由 D4 的忽略与 D6 的限额处理 |
| 不能拒绝，只能等到期 | 最简单 | 不想要的邀请要在首页挂七天，发起方还能重发，违反依据 7 |
| 拒绝即关闭邀请，并告诉发起方 | 发起方知道结果，可以早点改用别的方式 | 等于告诉发起方这个邮箱有账号且登录过，违反依据 2 |
| 给收件邮箱发一封邀请邮件，或以后由邮件提醒提醒已有账号的人 | 对方不必等发起方告知 | 任何人能借本站给任意地址发带自己名字的信，或扩大邮件提醒的收件范围，违反依据 5 |
| 每天 3 次或不限次数 | 3 次更严；不限最简单 | 3 次填错两次就几乎用完；不限则对方忽略后可被无限重发，违反依据 7 |
| 收件人另建一张表 `binding_invitation_recipients` | 原表保持"只有链接"的形状 | 邀请的生命周期（唯一未关闭、只关闭一次、绑定时关闭）要跨两张表维持，`token_hash` 仍要可空或造一个不用的 token，违反依据 6 |
| 只存收件邮箱的摘要 | 数据库里没有明文地址 | 发起方要看到自己填的地址；邮箱可猜、摘要可被逐个比对，保护有限 |

## 风险与代价

- 填错或写法不同时没有任何提示：发起方只看到"等 TA 登录"，对方什么也没看到。只能靠输入框说明、发起方与对方当面核对，以及链接备用。
- 比较以认证层记录的登录邮箱为准。若对方 Google 账号的邮箱后来改了、认证层仍是旧地址，按新地址邀请会对不上，同样改用链接。
- 任何知道你邮箱的已登录用户都能让你在首页看到一条带其显示名的邀请。D6 限制次数，D4 让你忽略；首版不做拉黑。显示名可以模仿别人，确认页核对账号的要求与链接相同。
- 数据库开始保存用户填的、可能不属于任何用户的邮箱地址。关闭的邀请不清除这一列（没有消费者需要清除），它和其他数据一样进服务器备份；只有发起方本人看得到。
- 对方接受另一位发起方的邀请后，其余寄给 TA 的邀请仍列到到期或被忽略（失败与恢复表）。

## 验收标准

- A 在「设置 → 搭档」填 B 的 Gmail（故意写成首字母大写）并发出，看到"已发出邀请"与"已邀请 …，等 TA 登录"；B 在已安装的 PWA 里用该账号登录，首页出现"A 邀请你一起写日记 · 查看"，确认范围后接受，两人绑定。
- A 改填一个没有账号的地址：A 看到的文案、状态与上一条完全相同。
- C 用另一个账号登录看不到任何邀请；C 拿到 A 那条邀请的 ID 去预览或接受，得到"邀请无效"，看不到 A 的名字。
- B 点"不接受"后，B 在另一台设备上也看不到；A 看到的仍是"等 TA 登录"；A 重新发出后 B 再次看到；A 第 6 次发出被拒，提示可以改用链接。
- A 改用链接后，B 首页的横幅消失；链接邀请的行为与现在相同。
- 已绑定的 B 收到 D 的定向邀请：横幅出现，确认页说明已有搭档、不能接受，可以忽略。
- 全程没有任何邮件发出。
- 不变量 1～10 由 API 的真实 PG 测试与 web 测试验证，测试标题带 `[adr:in-app-invitation-by-email#N]`。
