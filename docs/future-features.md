# 未来功能清单

记录日期：2026-10-26。

这里保存讨论中暂缓的功能、真实使用场景和重新设计时要回答的问题，便于后续查阅。条目不代表已承诺交付，不设默认排期；项目进度仍只记录在[开发路线](./roadmap.md)。当前产品规则以[功能规格](./diary-spec.md)为准，设计决定见 [ADR 索引](./adr/README.md)。

当前首版边界：首次绑定后，每个账号只对应这一位固定搭档。双方可以停止共享或解绑，未绑定和解绑后都能独立写作；只能与原搭档恢复原空间，恢复不自动重新开放日记。当前不提供更换对象、误绑纠正或人工重置流程。

## F-01：首次绑定选错账号后的纠正

**场景**：邀请链接被错误账号接受，或用户登录了非预期账号，完成确认后才发现选错搭档。固定搭档规则使解绑本身无法纠正这个错误。

**当前处理**：暂不实现纠正功能。绑定前核对双方账号，并明确说明首版绑定后不支持更换搭档；确认提示不能替代未来的纠正流程，也不承诺可联系客服或通过后台重置。

**重新评估条件**：出现真实误绑需求，或准备正式支持账号/搭档关系纠正时。

**设计前需要回答**：

- 什么属于误绑，是否限于尚未共享正文、尚无协作写入的关系？
- 由谁发起、需要谁确认；一方无法联系或有争议时如何处理？
- 已共享内容、冻结副本、双方 comment、离线待发文字和外部导出怎样保留，哪些内容无法收回？
- 如何区分纠正误绑与更换搭档，避免通过“纠正”绕过正式授权与历史保留规则？

纠正后的账号与关系归属、数据处置及并发边界均未决定，不能提前把“清空搭档字段”当作恢复方案。

## F-02：更换搭档

**场景**：原双方停止协作后，一方希望使用现有账号与另一位用户开始协作，继续保留自己的个人日记。

**当前处理**：首版不支持。A/B 首次绑定后，即使解绑，A/C 与 B/C 绑定仍被拒；原双方可以重新确认恢复 AB。首版内核围绕主人与固定搭档两位作者设计，不预建多搭档视图、正文分支或转授权逻辑。

**重新评估条件**：出现实际更换对象的需求，并愿意承担多关系历史、正文隔离与迁移的产品和技术成本时。

**设计前需要回答**：

- 旧关系的阅读权、冻结版本、comment、共享范围和 Google 副本如何保留，新搭档能看到什么？
- 主人写在旧搭档 comment 旁的回复仍属于统一个人正文，还是需要独立的关系内回复；怎样明确其可见范围？
- 不同搭档视图如何在不发送其他搭档字符及 CRDT 历史的前提下编辑、同步，并保持稳定位置和作者保护？
- 如何迁移首版固定搭档数据，以及拒绝旧期间/授权代次的离线请求，避免旧队列进入新关系？

未来允许更换不等于允许同时拥有多个活跃搭档；两者须分别讨论。采用哪种正文模型、Yjs 同步方式和确认流程，留待独立 ADR 评审。

## 如何维护

- 新增条目写清场景、当前处理、重新评估条件和未决定的问题，不把想法直接写成首版要求。
- 正式决定启动某项功能时，先补设计 ADR，再将实施范围与状态记入开发路线，并在这里链接对应 ADR。
- 功能纳入当前规格后，条目保留原场景与决策入口，避免把未来功能清单维护成第二份进度表。
