# 未来功能清单

记录日期：2026-10-26。

这里保存讨论中暂缓的功能、真实使用场景和重新设计时要回答的问题，便于后续查阅。条目不代表已承诺交付，不设默认排期；项目进度仍只记录在[开发路线](./roadmap.md)。当前产品规则以[功能规格](./diary-spec.md)为准，设计决定见 [ADR 索引](./adr/README.md)。

当前首版边界：首次绑定后，每个账号只对应这一位固定搭档。双方可以停止共享或解绑，未绑定和解绑后都能独立写作；只能与原搭档恢复原空间，恢复不自动重新开放日记。当前不提供更换对象、误绑纠正或人工重置流程。

## F-01：首次绑定选错账号后的纠正

**场景**：邀请链接被错误账号接受，或用户登录了非预期账号，完成确认后才发现选错搭档。固定搭档规则使解绑本身无法纠正这个错误。

**当前处理**：暂不实现纠正功能。绑定前核对双方账号，并明确说明首版绑定后不支持更换搭档；确认提示不能替代未来的纠正流程，也不承诺可联系客服或通过后台重置。

**重新评估条件**：出现真实误绑需求，或准备正式支持账号/搭档关系纠正时。

**设计前需要回答**：

- 什么属于误绑，是否限于尚未共享正文、尚无协作写入的关系？
- 由谁发起、需要谁确认；一方无法联系或有争议时如何处理？
- 已共享内容、冻结副本、双方 comment、离线待发文字和外部导出怎样保留，哪些内容无法收回？
- 如何区分纠正误绑与更换搭档，避免通过“纠正”绕过正式授权与历史保留规则？

纠正后的账号与关系归属、数据处置及并发边界均未决定，不能提前把“清空搭档字段”当作恢复方案。

## F-02：更换搭档

**场景**：原双方停止协作后，一方希望使用现有账号与另一位用户开始协作，继续保留自己的个人日记。

**当前处理**：首版不支持。A/B 首次绑定后，即使解绑，A/C 与 B/C 绑定仍被拒；原双方可以重新确认恢复 AB。首版内核围绕主人与固定搭档两位作者设计，不预建多搭档视图、正文分支或转授权逻辑。

**重新评估条件**：出现实际更换对象的需求，并愿意承担多关系历史、正文隔离与迁移的产品和技术成本时。

**设计前需要回答**：

- 旧关系的阅读权、冻结版本、comment、共享范围和 Google 副本如何保留，新搭档能看到什么？
- 主人写在旧搭档 comment 旁的回复仍属于统一个人正文，还是需要独立的关系内回复；怎样明确其可见范围？
- 不同搭档视图如何在不发送其他搭档字符及 CRDT 历史的前提下编辑、同步，并保持稳定位置和作者保护？
- 如何迁移首版固定搭档数据，以及拒绝旧期间/授权代次的离线请求，避免旧队列进入新关系？

未来允许更换不等于允许同时拥有多个活跃搭档；两者须分别讨论。采用哪种正文模型、Yjs 同步方式和确认流程，留待独立 ADR 评审。

## F-03：历史版本回滚

**场景**：用户希望将当前日记恢复到某个历史状态，或分别恢复本人/搭档文字，而不只是只读查阅。

**当前处理**：用户最终决定首版历史内容只读，不支持整篇或按作者回滚。此前讨论的主人整篇回滚例外已取消；不预建回滚入口、协议或权限分支，统一保留作者保护。

**重新评估条件**：出现真实恢复需求，并愿意重新评估作者权限、并发与本地待发内容的复杂度时。不设交付承诺。

**设计前需要回答**：

- 谁可以恢复谁的文字，是否允许主人删除或恢复搭档内容？
- 回滚期间其他设备的已提交编辑、未确认输入、撤销与离线恢复怎样处理？
- 是否需要整篇恢复或按作者分别恢复，如何保持字符作者、位置、时间与历史授权边界？

具体权限和算法均未决定，未来需要另行 ADR；当前只读规则见[内核 ADR D6](./adr/2026-10-26-diary-collaboration-kernel.md#d6历史版本只按已有授权读取重开不补授私人历史)。

## 2026-11-07 讨论的界面改进

上线当天 Ray 用生产站点提出的六项改动，方向都在讨论中定下，每项一个 PR、一个会话。F-04、F-05、F-07、F-08、F-09 已于 2026-11-09 合入，条目只保留场景和当时的结论作为决策入口，现行行为以所链模块的 README 为准；F-06 尚未开始，它涉及接口和 ADR 决策，先补 ADR。

### F-04：共享日期直接在日历上选

**状态**：已实现（#90，2026-11-09），见 [`apps/web` README](../apps/web/README.md) 的 `sharing-range`。

**场景**：`RangeEditor` 现在是"加一段 → 两个日期输入框 + 两个勾选框"的表单，日历只是只读预览，手机上尤其难用。Ray 希望像酒店应用那样在日历上点两下选一段。

**结论**：改用 shadcn 的 Calendar（`react-day-picker`），Ray 于 2026-11-07 批准这个依赖（连同它的 `date-fns`、`@date-fns/tz`），实现时精确锁版本。交互：三选一（全部 / 自选 / 暂不设置）不变；自选时日历上方一个"添加共享 | 添加排除"切换，点两天成一段、同一天两次为单日，点第一天后给出"从这天起一直共享 / 到这天为止"的开放端入口；排除模式下单击即排除一天；日历下列出各段的 chip 可删。排除日画成删除线淡色。数据模型、`range.ts`、contracts 与服务端不动。

**边界**：日历日是字符串，不换时区（[关系 ADR D3](./adr/2026-10-25-spaces-and-invitations.md#d3共享日期是包含集合减去排除集合不按创建时间筛选)）。Calendar 固定 `timeZone="UTC"`，`Date` 只出现在 `sharing-range/day.ts` 的 `toDate` / `toDay` 两个函数里，其余文件用 ESLint 禁 `new Date(`；"今天"用现有的 `localToday()` 传入。测试里用 UTC+14 与 UTC−11 两个时区各跑一遍。

### F-05：未绑定时首页右列过长，邀请流程移到设置

**状态**：已实现（#89，2026-11-09），见 [`apps/web` README](../apps/web/README.md) 的 `relationship`、`pages` 与 `shell`。

**场景**：未绑定（含已解绑）时首页右列是"此刻"加整个 `RelationshipPanel`（范围编辑器、日历、生成链接），左列只有"最近的几页"，两列长短差很多。邀请一辈子只做一两次，不该常驻首页。

**结论**：首页右列只留一张小卡——一行状态（还没有搭档 / 与 TA 的空间（已解绑）/ 已发出邀请，某日前有效）加一个"邀请搭档 →"。整个邀请流程（选范围、生成、撤销、恢复原空间）移到"设置 → 搭档"页。不违反[关系 ADR D12](./adr/2026-10-25-spaces-and-invitations.md#d12桌面交互呈现范围冻结与确认退出清理凭证)的不变量，但要同步 D12 的落地说明和 `relationship`、`pages`、`shell` 的 README。与 F-04 都改 `RelationshipPanel`，不并行。

### F-06：站内邀请，不靠链接

**状态**：未开始；Ray 于 2026-11-08 把它排除在这一批之外。

**场景**：邀请只能是 `/join#token=…` 链接。对方在聊天软件里点开的是系统浏览器而不是已安装的 PWA，登录态不共享，要再登录一次。Ray 希望对方登录后在应用里直接看到邀请并接受。

**结论**：按对方的 Google 邮箱定向邀请。发起方填邮箱（可同时选范围），服务端存一条定向邀请（收件邮箱、范围、七天过期），**不发邮件**；对方用该邮箱的 Google 账号登录后，`GET /api/binding` 多返回"给我的待处理邀请"，首页横幅"某某邀请你一起写日记 · 查看"，点开复用现有 `/join` 确认页与接受逻辑。发起方看到"已邀请某邮箱，等 TA 登录"，可撤销、可重发。链接方式先保留作备用。

**边界**：不能泄露某个邮箱有没有账号——无论是否注册都显示同一句"已发出邀请"；只按 Google 返回的已验证邮箱精确匹配。这改了[关系 ADR D8](./adr/2026-10-25-spaces-and-invitations.md#d8邀请七天有效可撤销一次性不绑定邮箱)的"不绑定邮箱"，不变量 3（七天、可撤销、至多成功一次）不变，所以先写新 ADR 或带 `adr-amend` 的修订，Ray 确认后再动 contracts → API → 迁移（邀请表加收件邮箱）→ 前端。三项里最大。

### F-07：备份页说清 Google Doc 存在哪里

**状态**：已实现（#87，2026-11-09），见 [`apps/web` README](../apps/web/README.md) 与 [`apps/api` README](../apps/api/README.md) 的 `backup`。

**场景**：[备份 ADR D6](./adr/2026-10-28-server-backup-and-google-docs.md#d6每天一份-doc和日期页一样上下排列按年月分文件夹) 定的位置是 `我的云端硬盘 › Between Pages › 年 › 月`，但备份页连接前一个字都没说，连接后只有"在 Google Drive 打开文件夹"，而且要等第一份 Doc 写出来文件夹才存在。Ray 问能不能让用户设置路径。

**结论**：不做应用内选路径（`drive.file` 看不到用户已有文件夹，要选只能接 Google Picker，不值）。worker 的 `monthFolder` 按 Drive 文件 ID 找文件夹、只查是否进回收站，所以用户在 Drive 里改名或移动 `Between Pages` 文件夹，备份会跟着它；删掉才在根目录重建。要做的是：连接前后都写明默认位置和"可以在 Drive 里移动或改名，备份会跟着；删掉会在根目录重建"；连接成功时就建好根文件夹，让"打开文件夹"链接立刻可用（行为改动，同步 `backup` 模块 README 与 ADR D7 的落地说明，不碰 D6 的决策）。

### F-08：写当天时头像变成空心圆（缺陷）

**状态**：已修复（#88，2026-11-09），见 [`apps/web` README](../apps/web/README.md) 的 `day-feed` 与 `diary`。

**场景**：Ray 在生产站点写今天的日记时，列表里自己的头像是空心圆（"有日记但还没有文字"），而不是实心的作者色。

**判断**（已在真实栈中复现）：空心来自 `GET /api/days` 的 `hasText`，列表只在打开、聚焦和每 45 秒刷新时读它。开始写今天时日记行一建出来就被列表读到（当时没字），之后的输入和提交走编辑器自己的通道，列表的 `hasText` 没人更新，要等下一次刷新才变实心。`DaysWorkspace` 已经拿到编辑器的实时 `BlockReport.hasText`（用于 `bothWrote`），只是没喂给列表的头像；首页"最近的几页"和日期索引用同一个字段，延迟相同。

**修法**：正在编辑的那一天，列表头像以编辑器的实时上报为准；其他设备上的变化仍靠现有刷新。按 AGENTS.md 先在开发环境复现，再写一个先红后绿的组件测试。

### F-09：浏览器标签页图标与 PWA 清单

**状态**：已实现（#86，2026-11-09），见 [`apps/web` README](../apps/web/README.md)。

**场景**：`apps/web/index.html` 的 `<head>` 只有 title，`public/` 里只有字体。线上 `/favicon.ico` 命中 `try_files` 的兜底，返回 200 加 `index.html`，浏览器拿不到图标。

**结论**：用现有的团子（`Mascot` 是 SVG）做图标，放进 `apps/web/public/`：`favicon.svg`、`favicon.ico`（32px）、`apple-touch-icon.png`（180px）、`icon-192.png`、`icon-512.png` 和 `manifest.webmanifest`（名字、纸色 `theme-color`、`display: standalone`），顺手让站点可以装成 PWA。`index.html` 加对应 `<link>`；`ops/deploy` 的 Docker 测试加一条"`/favicon.svg` 返回 `image/svg+xml`"。`public/` 的文件在 `/srv` 根下先于兜底命中，不影响 `/assets/` 规则和[部署 ADR 不变量 8](./adr/2026-11-05-production-deployment.md)。Ray 于 2026-11-08 定为两个团子并排。

## F-10：共享页面的后续能力

**场景**：用共享页面写清单和计划时，可能需要勾掉或改掉对方写的一条、把页面分到目录里、找回误删的页面，或定位长页面中间的新内容。

**当前处理**：第一版是平铺列表里的纯文字页面，每人只改自己的字，没有目录和恢复，未读只到页面级（[共享页面 ADR](./adr/2026-11-04-shared-pages.md)）。Ray 2026-11-04 决定先实践一段时间。

**重新评估条件**：实际使用中反复遇到上面某个需要时。不设交付承诺。

**设计前需要回答**：

- 可勾选的清单要不要进协同模型？勾掉对方写的一条算谁的动作？
- 目录由谁移动和重命名，删目录时页面怎么办，解绑后怎么显示？
- 回收站保留多久，恢复后圆点和删除记录怎么处理？
- 按字未读如何在列表里判定，是否等 PR #55 的未读算法？

## 如何维护

- 新增条目写清场景、当前处理、重新评估条件和未决定的问题，不把想法直接写成首版要求。
- 正式决定启动某项功能时，先补设计 ADR，再将实施范围与状态记入开发路线，并在这里链接对应 ADR。
- 功能纳入当前规格后，条目保留原场景与决策入口，避免把未来功能清单维护成第二份进度表。
