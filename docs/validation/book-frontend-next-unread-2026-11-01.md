# 上下找未读的耗时实测

日期：2026-11-01。本文记录[书页前端工作区 ADR](../adr/2026-11-01-book-frontend-workspace.md) 落地顺序 1 要求的实测：全部已读时 `GET /api/days/next-unread` 的耗时，缓存为空与已满各测一次，目标 p95 不超过 300ms。项目进度只见[开发路线](../roadmap.md)。

## 方法

脚本 [`apps/api/scripts/measure-next-unread.ts`](../../apps/api/scripts/measure-next-unread.ts) 直接调用正式的 `commit`、`sharing`、`bindings` 服务与 `reader`，对一次性 PostgreSQL 运行：

```sh
bash scripts/with-test-postgres.sh node apps/api/scripts/measure-next-unread.ts 1095 20
```

A、B 绑定后，三年（1095 天）每天各写一篇约 1,400 字的日记，共 2,190 篇，然后各自共享全部日期；每隔一天，两人各在对方当天的日记里写一句。所有提交移到一天前，都已成为历史点；B 的已读区间覆盖对方写的全部字。于是 B 往下找未读要走完全部候选（对方共享的 1,095 篇，加上自己日记里对方写过字的 548 篇，共 1,643 篇），最后回答「没有」。

- **缓存为空**：新建 `reader` 后的第一次查找，相当于 API 进程刚启动。
- **缓存已满**：同一个 `reader` 再查 20 次，取 p50 与 p95。
- 作为对照，同时测一页日期列表（20 个日期）的耗时。

## 结果

机器：4 核 Neoverse-N1，Node v24.21.0，PostgreSQL 18（容器）。

| 项目 | 耗时 |
| --- | --- |
| 缓存为空，一次查找 | 6,162 ms |
| 缓存已满，p50 | 174 ms |
| 缓存已满，p95 | 209 ms |
| 一页日期列表 | 261 ms |

最初的实现每篇候选单独查询时间线与已读区间，缓存已满时 120 篇就要约 250ms；改为几次批量查询后，同样 120 篇降到 15ms（p50）。上表是改后的数字。

## 结论

- 缓存已满时达到目标（p95 209ms，不超过 300ms）。
- 缓存为空时未达到目标：一次约 6 秒，每篇要重建正文，约 3.7ms 一篇。只在 API 进程启动后每人第一次查找时出现；之后只有正文、历史点或已读变化的那几篇需要重建。页面按 D5 在进入列表时后台查找，用户点按钮时不等待这一次，但按钮会晚几秒出现。延后：前端完成后按提议中的 ADR #55 处理（2026-11-01）。
