## 结果

[原始观测](./artifacts/diary-kernel-2026-10-26/batch-observations.json)；[TAP 输出](./artifacts/diary-kernel-2026-10-26/batch-results.tap)。18 个场景加 1 项校验器未改动检查，共 19 项通过；连续运行 3 次均为 19/19，归档的是第 3 次。TAP 中的临时目录已替换为 `probe/` 相对路径。

每个场景都直接检查 PG 中的正文、逐字作者、版本号以及 commits、batch_receipts、operation_receipts、outbox 的行数，同时检查浏览器 IndexedDB 中的 pending、批次、回执与草稿，不只看请求是否成功。测试日记都以 A 的“开头”加 B 的“乙写的字”起始，用于检查 B 的文字在每个场景后仍归 B。

| 方面 | 场景与观察结果 |
| --- | --- |
| 发送组织 | 第一笔落库后立即单独成批发送；服务端暂停期间又写的 5 笔照常落库，确认后组成第二批，按 localSequence 顺序，批大小 [1, 5] |
| 数量与字节上限 | 120 笔离线依赖链（中途 7 次重载）在 25 笔、4096 字节上限下分成 7 批，归档运行为 [25, 24, 19, 15, 16, 11, 10]（字节估算随 clientID 编码长度变化，各次略有不同）；各批依次严格校验，版本号连续，逐笔回执 120 条 |
| 发送前持久化批身份 | 批次形成后、发送前让渲染进程崩溃；重开后批 ID、成员与字节完全一致，服务端从未收到请求，之后原批提交一次 |
| 批内中途拒绝 | 3 笔中第 2 笔删除 B 的字，整批 409 `FOREIGN_DELETE` 并指出第 2 笔；PG 状态哈希及所有表行数不变，无广播；第 1、3 笔合法也未提交。批次标为 rejected，之后不再自动发送，后续输入留在本地；本人处理后 4 笔全部进入草稿并保留插入/删除意图 |
| PG 写入失败 | 批次各行已写入后在同一事务内注入 SQL 错误，整体回滚，返回暂时失败，客户端保留原批；之后原批提交一次 |
| 提交前进程被杀 | 事务已写入但未 COMMIT 时服务端被 SIGKILL：PG 无任何残留，重启后原批正常提交一次 |
| 提交后进程被杀 | COMMIT 后、回复前被 SIGKILL：PG 已有版本 1；内存广播随进程丢失，另一设备从 PG 读到已提交正文；客户端重试原批得到原结果（replayed），版本、outbox 均只有 1 |
| ACK 丢失与本地确认失败 | 回复连续丢失后，再让本地确认事务中止：pending、批次与本地版本都保持不变；再次重试得到同一版本，确认后清空 |
| 客户端在服务端提交后崩溃 | 服务端已 COMMIT、尚未回复时让渲染进程崩溃；重开后重发原批，得到原结果，只有一个版本 |
| 批身份冲突 | 同一批 ID 换成员被拒（`BATCH_PAYLOAD_CONFLICT`）；已提交的操作被重新打包进新批也被拒（`OPERATION_ALREADY_COMMITTED`）；两者都不改变 PG |
| 并发重复投递 | 同一批在两条连接上同时到达，PG 行锁使其只提交一次，两方都得到版本 1，其中一方标记 replayed |
| 授权切换 | 停止共享后到达的批次被拒为 `STALE_CONTEXT`，批次保持 open、不标为永久失败；重开后成员转为恢复草稿。已提交但 ACK 丢失的批次在重开时按回执对账，不进入草稿，冻结版本包含它 |
| 提交与停止竞争 | 30 次在 PG 中并发提交与停止共享：每次要么在冻结版本之内，要么被拒，从未在冻结之后提交。三次运行的结果分布为 16/14、14/16、15/15，两种结果都实际出现 |
| 多标签页 | 两个标签页共享序号，一批可同时包含两边的依赖编辑；两边同时发送时只有一个批次在途，3 批各发送一次，没有重复或越过未确认批次；重开后旧标签页的输入只进草稿，不进入新批次 |

## 过程中的发现

1. **Chromium 会自行重发 POST。** 服务端在 COMMIT 后直接断开连接时，Chromium 会把同一请求再发一次，应用层并不知道（推测与复用连接上收到空响应时的重试有关，机制本身未单独验证）；一次应用发送对应两次 HTTP 到达，服务端靠批回执返回原 ACK。首轮运行因此有 1 项失败：场景原本以为客户端会看到网络错误。这说明重复投递在正常路径就会发生，回执查询必须在锁内、在任何校验之前完成。场景随后拆成两项：一项断言这种自动重发，另一项让连续两次回复都丢失，以覆盖真正的 ACK 丢失。首轮的 TAP 输出没有保留。
2. **探针自身的缺陷已修正。** 第二轮有 2 项失败，原因是临时服务端的重放分支在注入断开之前就返回了，不是设计问题；修正后连续 3 次全部通过。
3. **已过期上下文中的已提交批次仍可对账。** 临时服务端先查批回执、再查授权上下文，所以 epoch 关闭后，重试一个已提交的批次仍返回原结果，与 ADR D9 第 2 步一致；本次对账场景走的是回执查询入口。
4. **提交后崩溃会丢失内存广播**，其他设备须通过 PG 补同步取得已提交内容，与 D9 一致。

## 得到的约束

1. 服务端以 `(account, diary, batchId)` 保存批回执，摘要覆盖上下文和按顺序排列的 `(operationId, 更新字节)`；逐笔回执以 `(account, diary, operationId)` 唯一，拒绝重新打包。
2. 提交在日记行锁内依次进行：查批回执、查逐笔重用、查 generation/epoch、在候选状态中逐笔校验、写入增量/回执/outbox/新状态，然后 COMMIT。停止共享取同一行锁并在其中记录冻结版本，由此得到唯一的事务边界。
3. 对外增量从已接受的候选状态重新编码，广播只在 COMMIT 之后发生。
4. 客户端每个 `(account, diary)` 至多一个 open 批次，首次发送前存入 IndexedDB；确认事务一次完成删除成员、删除批次、写回执和推进本地基线。永久 409 标记 rejected 并停止；`STALE_CONTEXT` 留给切换流程处理；网络错误和 5xx 保留原批等待重试。

## 不由这些证据证明的事项

- 没有 Fastify、WebSocket、正式会话或多个 API 实例。账号直接写在请求体里，由探针信任；回执查询接口没有鉴权；广播前的重新授权没有测试。
- 编辑通过页面内的 `app.edit` 生成，不是渲染编辑器里的真实键入；只覆盖 Chromium。草稿界面、提示文字和保存状态展示没有测试。
- 25 笔、4096 字节是探针取值，不是设计参数。单笔超过字节上限时，探针让它单独成批，这只是探针的选择，Q6 仍未决定。
- PG 写入失败只注入了 `select 1/0`，进程崩溃只用了 API 进程的 SIGKILL；没有测试 PG 服务端崩溃、连接池耗尽、锁超时或磁盘故障。重开只更换 generation/epoch 并清理基线，没有新增基线版本。
- 输入、远端正文与光标延迟以及批上限的性能实测仍留给正式集成；Q2、Q3、Q4、Q6、Q7 的技术设计不因本次验证而完成。
